# PR 생성 가이드

## 개요

기능 구현이 완료된 후, 코드를 분석하여 PR 문서를 작성하는 워크플로우입니다.

---

## 핵심 원칙: "PR만 읽으면 코드가 보인다"

PR 문서는 세 가지 레벨을 동시에 달성해야 한다:
1. **왜 이 설계인가** — 주어진 제약 하에서 이 설계가 논리적 귀결임을 증명
2. **어떻게 동작하는가** — 코드를 열지 않아도 요청이 시스템을 관통하는 흐름이 머릿속에 그려지는 것
3. **코드가 어떤 모양인가** — 핵심 메서드 시그니처, 객체 구조, 경계 처리가 실제로 어떻게 짜여 있는지 리뷰어가 예측할 수 있는 것

레벨 1~2는 "설계 설명서", 레벨 3이 추가되어야 "PR 코드 리뷰 가이드"가 된다.

### 좋은 PR의 서사 구조

```
1. 환경 제약 정의 → "우리 시스템의 현실은 이렇다" (수치)
2. 문제 도출      → "그래서 이런 현상이 발생한다" (수치로 위험 정량화)
3. 대안 탐색      → "A, B, C를 고려했다" (각각의 장단점)
4. 검증           → "테스트/계산으로 비교했다" (측정값, 계산식)
5. 결정 + 포기    → "C를 선택하고 ~를 포기한다" (트레이드오프 명시)
```

### 안티패턴

**기능 나열형** (무엇만, 왜 없음):
> "Redis Sorted Set으로 대기열을 구현했다. Lua Script로 원자성을 보장한다."

**결론만 제시** (도출 과정 없음):
> "배치 크기를 30으로 설정했다."

**경중 무시** (모든 결정을 같은 깊이):
> score 설계(코드 1줄)와 Circuit Breaker 전략(시스템 가용성)을 같은 분량으로 서술

## 워크플로우

### 전체 흐름

```
[Step 1] 개발 기록 분석    커밋 히스토리 + 환경 제약 + 변경 파일 구조
[Step 2] PR 문서 작성      volume-{n}-pr.md — 서사 구조 기반 의사결정 문서
```

저장 경로: `.idea/volume-{n}*.md`

---

### Step 1: 개발 기록 분석 (`volume-{n}.md`)

브랜치의 커밋 히스토리와 변경 파일을 분석하여 개발 흐름을 Phase 단위로 정리한다.

#### 수집 정보

1. **커밋 히스토리**: `git log {base}..HEAD` — 해시, 날짜, 메시지 테이블
2. **변경 통계**: `git diff {base}..HEAD --shortstat` — 파일 수, 추가/삭제 라인
3. **커밋별 변경**: `git log {base}..HEAD --stat` — 각 커밋의 영향 파일
4. **환경 제약 조건**: discussion/plan 문서, 코드 설정값, 테스트 결과에서 핵심 수치 추출
5. **대안 비교 기록**: discussion 문서에서 검토했던 대안과 기각 사유 추출

#### 구성

```markdown
# Volume {n} - {도메인} 구현 기록

## 환경 제약 조건
이번 주 발제가 전제하는 환경 제약을 수치로 정리

## 개요
시작 커밋 ~ 종료 커밋 범위, 총 변경 통계

## 커밋 히스토리
| Hash | 날짜 | 커밋 메시지 |

## Phase 1~N
관련 커밋을 기능/레이어 단위로 묶고, 각 Phase가 이전 Phase의 한계를 해결하는 구조

## 의사결정 추적
| 결정 | 선택 | 기각된 대안 | 근거 |
```

---

### Step 2: PR 문서 작성 (`volume-{n}-pr.md`)

Step 1 분석을 바탕으로 PR 문서를 생성한다.

코드에서 설정값이나 설계 선택의 근거를 찾을 수 없는 경우:
- 테스트 클래스, discussion 문서, 커밋 메시지를 우선 탐색한다
- 그래도 근거를 찾을 수 없으면 `(검증 필요)` 표시를 남긴다
- **근거 없는 추론으로 내용을 채우지 않는다**

---

## PR 문서 구조 및 작성 규칙

### 목표 분량: 250~350줄

코드 조각과 객체 단면이 추가되므로 기존 200~300줄보다 약간 넓다. 그래도 400줄을 넘기면 리뷰어가 읽지 않는다. 밀도를 높이되 분량은 줄인다.

---

### Summary — 3초 안에 파악 가능해야 한다

```markdown
## Summary

- **배경**: {현재 시스템 상태와 문제 상황 — 1문장}
- **문제**: {수치로 정량화된 핵심 위험 — 1문장}
- **목표**: {이 PR이 달성하려는 것 — 1문장}
- **결과**: {달성한 것 — 개선 수치, 테스트 수}
```

**규칙:**
- 각 항목 1~2문장. 문단 금지
- 계산식은 Summary에 넣지 않는다 — Context & Decision에서 풀어낸다
- 개선 경로가 있으면 결과에 포함: `31.7% → 48.1% → 90.7% → 92.3%`

**나쁜 예** (Summary에 계산식 우겨넣기):
> **문제**: DB 커넥션 풀이 1초 이내 고갈. 40개 × 44ms/txn = 908 TPS이나, 비주문 30% 고려 시 636 TPS가 한계. 초과 유입 시 커넥션 대기 → 응답 지연 → 연쇄 장애

**좋은 예** (핵심만):
> **문제**: 초당 10,000건 유입 시 안전 한계 636 TPS 초과 → DB 커넥션 풀 고갈 → 시스템 전체 불능

---

### Context & Decision — 경중을 구분한다

**핵심 결정 2~3개**만 깊게 서술하고, **부수 결정**은 간략히 묶는다.

#### 핵심 결정의 경중 판단 기준

| 레벨 | 기준 | 서술 깊이 |
|------|------|-----------|
| **핵심** | 시스템 가용성·성능·정합성에 직접 영향 | 환경→문제→대안표→검증→결정→트레이드오프 전체 |
| **부수** | 구현 편의·코드 1줄 차이·관례 선택 | 1~3줄 요약 (대안표 없이) |

#### 핵심 결정의 밀도 제어

하나의 핵심 결정 안에 **대안 비교표가 2개 이상** 들어가면 과밀하다. 관련된 하위 결정이 여러 개라면:
- 소제목으로 분리하거나
- 핵심 결정을 2개로 나누거나
- 부수적인 하위 결정(score 설계, Master/Replica 등)은 본문에 1줄로 녹인다

#### 인과 없는 결정의 처리

모든 결정이 인과로 연결되지는 않는다. 독립적 관심사(예: 장애 대응 vs 공정성)는 **인과가 없음을 명시**하거나, "1에서 이어지는 문제"를 생략한다. 억지 인과를 만들지 않는다.

#### 핵심 결정 템플릿

```markdown
### {번호}. {결정 주제}

**환경/전제**: {제약 조건, 수치}

**문제**: {위험을 수치로 정량화}

**고려한 대안**:

| 대안 | 방식 | 장점 | 문제점 |
|------|------|------|--------|
| A | ... | ... | ... |
| **B (선택)** | ... | ... | ... |

**검증**: {테스트 결과, 계산식}

**결정**: {선택 + 트레이드오프}
```

#### 부수 결정 템플릿

```markdown
### 부수 결정

- **{주제}**: {A vs B — B 채택. 이유: ...}
- **{주제}**: {A 채택. 이유: ...}
```

#### 결정 간 서사 연결

결정들이 독립적으로 나열되지 않도록, **이전 결정이 다음 결정을 강제하는 인과관계**를 명시한다.

**나쁜 예** (나열형):
> ### 1. 자료구조 선택
> ...
> ### 2. 배치 크기 결정
> ...

**좋은 예** (인과 연결):
> ### 1. 자료구조 선택 — Redis Sorted Set
> ...
> **이 선택이 강제하는 다음 결정**: Sorted Set에서 꺼내는 속도를 제어할 밸브가 필요 → 배치 크기 결정으로 이어진다.
>
> ### 2. 배치 크기 — 100ms × 14명
> **1에서 이어지는 문제**: 대기열 자체는 속도를 제어하지 않는다. DB가 감당 가능한 TPS로만 풀어주는 밸브 설계가 필요하다.

### Implementation Overview — 코드를 열지 않아도 구현이 보여야 한다

이 섹션의 목표: **리뷰어가 이 섹션만 읽고 "어떤 클래스가, 어떤 순서로, 무슨 일을 하는지" 머릿속에 그릴 수 있어야 한다.**

```markdown
## Implementation Overview

### 구현 구조

| 레이어 | 클래스 | 책임 | 협력 대상 |
|--------|--------|------|-----------|
| Interfaces | `OrderV1Controller` | 주문 요청 수신, DTO 변환 | `OrderFacade` |
| Application | `OrderFacade` | 재고 차감 + 주문 생성 조율 | `StockApp`, `OrderApp` |
| Domain | `OrderService` | 주문 유효성 검증, 상태 전이 | `OrderRepository` |
| Infrastructure | `OrderRepositoryImpl` | JPA 영속화 | `OrderJpaRepository` |

### 핵심 흐름: {API 이름} `{METHOD} {PATH}`

요청이 시스템을 관통하는 과정을 자연어로 서술한다:

1. 클라이언트가 `POST /api/v1/orders`를 호출한다
2. `OrderV1Controller`가 DTO를 Command로 변환하여 `OrderFacade`에 전달한다
3. `OrderFacade`가 `StockApp.decrease()`로 재고를 먼저 차감한다
4. 재고 차감 성공 시 `OrderApp.create()`로 주문을 생성한다
5. `OrderService`가 주문 금액 검증 + 상태를 CREATED로 설정한다
6. 트랜잭션 커밋 시 dirty checking으로 flush된다
7. 실패 시 `StockApp.rollback()`으로 재고를 복구한다

### 핵심 수치 도출

| 설정 | 값 | 도출 근거 |
|------|-----|-----------|
| ... | ... | {한 줄 요약 — 상세 과정은 Context & Decision 참조} |
```

**규칙:**
- **구현 구조 테이블**: 이 PR에서 핵심적인 클래스 5~8개. 전부 나열하지 않는다
  - "책임" 열: 그 클래스가 **무엇을 하는지** 한 문장 (코드를 열지 않아도 알 수 있게)
  - "협력 대상" 열: 그 클래스가 **누구에게 위임하는지** — 의존 방향이 보여야 한다
- **핵심 흐름**: 가장 중요한 API 1~2개만 자연어로 서술
  - 번호 매긴 단계로 작성 — 각 단계에 **클래스명 + 메서드 역할**을 명시
  - "무슨 클래스의 무슨 행위"가 빠진 추상적 서술 금지 (예: "주문을 처리한다" → "OrderService가 금액을 검증하고 상태를 CREATED로 전이한다")
  - 분기(성공/실패, 조건별)가 있으면 분기도 서술한다
  - 5~10단계. 15단계 이상은 요약이 부족한 것
- **수치 도출**: 테이블로 압축. Context & Decision에서 풀어 설명한 계산을 반복하지 않는다

### Flow Diagram — 핵심만

핵심 흐름 서술을 **시각적으로 보강**하는 용도. 텍스트 흐름과 중복되더라도 다이어그램이 있으면 전체 구조가 한눈에 들어온다.

```markdown
### {핵심 API 이름} `{METHOD} {PATH}`

```mermaid
sequenceDiagram
  autonumber
  participant Client
  ...
```
```

**규칙:**
- participant는 **최대 6~7개**
- 핵심 흐름 1개 + 장애/예외 흐름 1개 = **최대 2~3개**
- 모든 API에 다이어그램을 만들지 않는다 — 복잡하거나 비직관적인 흐름만
- 단순 CRUD는 텍스트 흐름만으로 충분. 다이어그램 생략 가능

#### Mermaid 규칙

1. **autonumber** 사용
2. **alt/else** 블록으로 성공/실패 분기
3. **에러 응답에 ErrorType 명시**: `CoreException(CONFLICT)`
4. **self-call**: `Model->>Model: validate()`
5. **JPA dirty checking**: `TX commit (dirty checking flush)`

### Code Guide — 리뷰어를 위한 코드 탐색 가이드

이 섹션의 목표: **리뷰어가 코드를 열었을 때, 어디부터 읽고 무엇을 기대해야 하는지 알려주는 것.** Implementation Overview가 "구조와 흐름"이라면, Code Guide는 "코드의 질감"이다.

```markdown
## Code Guide

### 리뷰 시작점

이 PR은 {N}파일 변경이지만, 아래 {3~5}개 파일만 먼저 보면 전체가 파악됩니다:

1. `{파일 경로}` — {왜 이 파일이 진입점인지 한 문장}
2. `{파일 경로}` — ...
3. `{파일 경로}` — ...

추천 읽기 순서: 1 → 3 → 2 (Consumer 흐름 먼저 → Repository → API)

### 핵심 코드

**{코드 조각 제목}** (`{파일명}:{라인 범위}`)
```java
// 실제 코드 10~20줄
```
{이 코드가 왜 중요한지, 무엇을 보여주는지 — 1~2문장}

**{코드 조각 제목}** (`{파일명}:{라인 범위}`)
```lua
-- 실제 코드
```
{설명}

### 경계 명세

| 경계 | 위치 | 처리 방식 |
|------|------|-----------|
| 멱등성 | `{클래스명}.{메서드}()` | {EventHandledRepository로 eventId 중복 체크} |
| 트랜잭션 | `{클래스명}.{메서드}()` | {`@Transactional` — DB 적재와 이벤트 기록이 원자적} |
| 예외 전파 | `{클래스명}.{메서드}()` | {`BatchListenerFailedException` → Kafka 재시도 → DLQ} |
| 실패 격리 | `{클래스명}.{메서드}()` | {try-catch로 랭킹 실패가 상품 조회를 막지 않음} |

### 객체 설계 단면

**{Payload/DTO 이름}** — {용도 한 문장}
```java
// record 정의 또는 핵심 필드
public record XxxPayload(
    String eventId,
    String eventType,
    Long productDbId,
    ...
) {}
```

**{Repository Interface}** — {포트 역할 한 문장}
```java
public interface XxxRepository {
    void incrementScore(LocalDate date, Long productDbId, double score);
    List<XxxEntry> findTopN(LocalDate date, long offset, long size);
}
```
```

**규칙:**
- **리뷰 시작점**: 3~5개 파일. "N파일 변경이지만 이것만 보면 됩니다" 형태. 추천 읽기 순서까지
- **핵심 코드**: 실제 코드 스니펫 **2~3개**. 각 10~20줄. PR에서 가장 중요한 로직을 보여준다
  - 코드 스니펫은 **실제 코드에서 복사**한다 — 의사 코드나 요약 금지
  - 스니펫 아래에 **왜 이 코드가 중요한지** 1~2문장 설명
  - 선정 기준: 핵심 비즈니스 로직, 원자성/동시성 처리, 비직관적 분기
  - **코드가 20줄 이상이거나 분기/흐름이 복잡하면 Mermaid로 대체**:
    - 분기 로직 → `flowchart` (if/else 분기가 한눈에 보임)
    - 객체 관계/인터페이스 구조 → `classDiagram` (record 필드, interface 시그니처)
    - 상태 전이 → `stateDiagram-v2`
    - 코드 10줄 이하의 핵심 로직(Lua Script, 단일 메서드)은 코드 스니펫이 더 효과적
- **경계 명세**: 멱등성·트랜잭션·예외 전파·실패 격리가 **어느 클래스, 어느 메서드**에서 처리되는지 테이블로 명시
  - "멱등성 체크를 한다"가 아니라 "`CatalogEventConsumer.processViewIfNotHandled()`에서 `EventHandledRepository.existsByEventId()`로 중복 검사"처럼 구체적으로
- **객체 설계 단면**: 핵심 record/interface의 실제 정의 **2~3개**. payload JSON 예시나 interface 시그니처
  - 리뷰어가 "이 객체가 어떤 모양인지" 코드를 열지 않고 알 수 있게

### Review Questions — 진짜 딜레마만

```markdown
## Review Questions

1. {양쪽 모두 일리 있는 기술적 딜레마 — 2~3문장}

```

**규칙:**
- **2~3개**. 5개 이상은 산만
- "이게 맞나요?" 금지 → "~와 ~의 트레이드오프를 어떻게 판단하시나요?"
- 각 질문은 **맥락(왜 딜레마인지) + 질문** 구조. 장황한 배경 설명 금지

**나쁜 예** (배경이 본문보다 긴 Review Question):
> 단일 회원이 매크로/새로고침으로 과도하게 폴링하는 시나리오를 방어하기 위해... (이하 30줄)

**좋은 예** (맥락 + 질문):
> **로컬 Rate Limit의 스케일아웃 한계**: ConcurrentHashMap 기반이므로 인스턴스별 카운트가 분리된다. Redis 글로벌 Rate Limit은 폴링 자체의 Redis 부하를 2배로 늘린다. 폴링이 p99=48ms로 가벼운 경우에도 Rate Limit이 필요한가?

### 패턴 1: 경중 구분

핵심 결정 2~3개에 분량의 70%를 집중하고, 나머지는 "부수 결정"으로 묶어 3줄씩 처리.

"Step 1을 했다. Step 2를 했다."가 아니라, "Step 1의 한계(~) 때문에 Step 2가 필요했다."

### 패턴 3: 밀도

한 줄에 하나의 정보. 설명 없이 표만으로 전달 가능한 것은 표로.

### 패턴 4: 정직한 한계

"완벽하다"는 PR은 신뢰를 잃는다. "이것은 아직 못 풀었다"가 있어야 한다.
