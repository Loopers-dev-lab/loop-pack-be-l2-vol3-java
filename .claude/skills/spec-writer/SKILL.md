# Spec Writer

요구사항 정의서를 기반으로 **모호함 없는 기능 명세서**를 작성합니다.
명세서 템플릿은 [templates/spec-template.md](templates/spec-template.md) 참고.

## 핵심 원칙

- 기능 명세서는 **뭘 만들지**만 정의한다 (**어떻게 만들지**는 rules와 기존 코드가 담당)
- 구현 세부사항(클래스명, 메서드명, 구현 위치)을 명세서에 넣지 않는다
- 모든 AC는 테스트 코드로 1:1 변환 가능해야 한다
- 모호한 표현("적절한", "안전하게", "빠르게")은 반드시 구체화한다

## 워크플로우

```
1. CAPTURE  — 기능 목록 추출
2. CLARIFY  — 모호함 제거 (핵심)
3. WRITE    — 명세서 작성 + 검증
```

### 1. CAPTURE

요구사항 정의서에서 기능 단위를 추출합니다.

**입력**: 요구사항 정의서(`docs/requirements/`), 원시 텍스트, 기획 문서, 구두 설명 등 어떤 형식이든 가능
**산출물**: 기능 목록 + 각 기능의 한 줄 설명

```
시작하기:
"요구사항을 공유해주세요. 요구사항 정의서, 원시 텍스트, 구두 설명 어떤 형식이든 괜찮습니다."
```

추출한 기능 목록을 사용자에게 확인:
```
다음 기능들을 도출했습니다:
1. 회원가입 — 사용자가 계정을 생성할 수 있다
2. 로그인 — 사용자가 인증할 수 있다

이대로 진행할까요? 추가/수정할 기능이 있나요?
```

### 2. CLARIFY

**이 단계가 명세서 품질을 결정합니다.** 모호한 부분을 질문으로 명확하게 만듭니다.

#### 모호함 탐지 체크리스트

각 기능에 대해 아래 관점으로 모호함을 탐지:

**데이터 관점**
- 어떤 필드가 필요한가?
- 각 필드의 타입, 필수 여부, 검증 규칙(최소/최대 길이, 허용 문자, 형식)은?

**행위 관점**
- 정상 동작의 결과는?
- 실패할 수 있는 모든 경우는? 각각의 HTTP 상태코드와 메시지는?

**상태 관점**
- 이 작업의 선행 조건은? (인증 필요? 특정 상태 필요?)
- 이 작업이 다른 기능에 영향을 주는가?

**보안 관점**
- 인증/인가가 필요한가?
- 민감 정보(비밀번호, 개인정보)가 있는가? 어떻게 처리하는가?

#### 질문 방식

모호한 부분은 선택지를 제시하며 질문:
```
loginId 검증 규칙을 확인해야 합니다:
A) 영문소문자+숫자, 4~20자
B) 영문+숫자, 4~20자 (대소문자 허용)
C) 다른 규칙
```

한 번에 3개 이하로 질문. 많으면 나눠서 진행.

#### 모호한 표현 변환

| 모호한 표현 | 질문 | 구체화 예시 |
|---|---|---|
| "적절한 길이" | 최소/최대 몇 자? | 4~20자 |
| "안전하게 저장" | 어떤 암호화? | BCrypt |
| "빠르게 응답" | 몇 ms 이내? | 200ms |
| "적절한 에러" | 어떤 상태코드, 메시지? | 409, "이미 존재하는 ID" |
| "유효한 이메일" | 형식만? 실존 확인? | RFC 5322 형식 검증만 |

### 3. WRITE

명확해진 요구사항을 [templates/spec-template.md](templates/spec-template.md) 형식으로 작성합니다.

#### AC 작성 규칙

**정상 케이스를 먼저**, 실패 케이스를 나중에:
```markdown
## 인수 조건
- [ ] 유효한 정보로 가입하면 200 응답
- [ ] 로그인ID 중복이면 409 응답
- [ ] 비밀번호는 BCrypt로 암호화하여 저장
- [ ] 요청 필드 규칙 위반 시 400 응답
```

**요청 테이블과 중복하지 않는다:**
- 요청 테이블의 필드별 규칙(필수, 타입, 길이, 형식)을 AC로 반복하지 않는다
- `요청 필드 규칙 위반 시 400 응답` 한 줄로 대체
- AC에는 요청 테이블만으로 표현 안 되는 규칙만 작성 (필드 간 조합 검증, 비즈니스 규칙)

**나쁜 AC:**
- "비밀번호는 안전해야 한다" → 테스트 불가
- "에러를 적절히 처리한다" → 모호함

**좋은 AC:**
- "비밀번호는 BCrypt로 암호화하여 저장한다" → 테스트 가능
- "로그인ID 중복 시 409 응답, 메시지: '이미 사용 중인 로그인 ID입니다'" → 테스트 가능

#### 명세서에 넣지 않는 것

- 클래스명, 메서드명 (예: `UserService.register()`)
- 구현 위치 (예: "Entity에서 검증")
- 트랜잭션 격리수준, 캐싱 전략 등 구현 세부사항
- 이것들은 구현 후 리뷰 단계에서 다룸

#### 저장 위치

docs/specs/{epic-name}/{NNN-feature-name}.md
- 디렉토리명, 파일명 모두 영어 케밥케이스
- 번호는 001부터 순차 부여

#### 완료 전 검증

작성 완료 후 3가지만 확인:
1. 모든 필드에 타입과 검증 규칙이 있는가?
2. 모든 AC가 테스트 코드로 변환 가능한가?
3. 실패 케이스가 빠진 게 없는가?

누락 탐지 질문:
- "이 API를 E2E 테스트한다면 어떤 시나리오가 필요한가?"
- "이 기능이 실패할 수 있는 모든 경우는?"

```
마무리:
"{기능명} 명세서가 완성되었습니다.
- API: {엔드포인트}
- AC: {N}개 (정상 {X}개, 실패 {Y}개)

다음 기능으로 넘어갈까요, 수정할 부분이 있나요?"
```

## 예시

사용자: "회원가입 기능 명세서 만들어줘"

CAPTURE:
```
기능을 도출했습니다:
1. 회원가입 — 사용자가 계정을 생성할 수 있다
```

CLARIFY:
```
회원가입에 대해 확인이 필요합니다:
1. 필요한 필드: loginId, password, name, birthDate, email — 맞나요?
2. loginId 규칙: A) 영문소문자+숫자 4~20자  B) 다른 규칙?
3. loginId 중복 시 대응: A) 409 응답  B) 다른 처리?
```

WRITE:
```markdown
# 회원가입

## 배경
시스템에 회원 가입 기능이 없다. 사용자가 직접 계정을 생성할 수 있어야 한다.

## API
POST /api/v1/users

## 요청
| 필드 | 타입 | 필수 | 규칙 |
|------|------|------|------|
| loginId | String | O | 영문소문자+숫자, 4~20자 |
| password | String | O | 영문+숫자+특수문자, 8~20자 |
| name | String | O | 2~20자 |
| birthDate | LocalDate | O | 미래 날짜 불가 |
| email | String | O | 이메일 형식 |

## 인수 조건
- [ ] 유효한 정보로 가입하면 200 응답
- [ ] 로그인ID 중복이면 409 응답
- [ ] 비밀번호는 BCrypt로 암호화하여 저장
- [ ] 요청 필드 규칙 위반 시 400 응답

## 제약
- 이메일 인증은 이번 스코프 아님
```

## 트러블슈팅

### 요구사항이 너무 모호한 경우
- 핵심 기능 하나만 먼저 CLARIFY
- 하나가 완성되면 나머지 기능은 패턴이 잡힘

### 기능 간 의존성이 복잡한 경우
- 의존성이 없는 기능부터 시작
- 의존 관계는 제약 섹션에 명시: "선행: 회원가입 API 구현 필요"

### 사용자가 구현 세부사항을 명세서에 넣으려는 경우
- "구현 방식은 기존 코드 패턴을 따르므로 명세서에는 '무엇을' 하는지만 명시합니다"
- "트랜잭션 격리수준 같은 세부사항은 구현 후 시퀀스다이어그램을 보면서 결정하면 더 정확합니다"
