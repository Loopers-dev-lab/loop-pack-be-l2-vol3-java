# Design Writer

설계 문서를 Mermaid로 작성하고 **이력으로 관리**합니다.

Mermaid 문법:
- [references/sequence-syntax.md](references/sequence-syntax.md)
- [references/class-diagram-syntax.md](references/class-diagram-syntax.md)
- [references/erd-syntax.md](references/erd-syntax.md)

## 핵심 원칙

- 설계 문서는 **사람과 AI의 핸드오프 지점**이다
- 사람이 설계 의도를 확정하고, AI가 그대로 구현한다
- 구현 후 달라진 부분은 설계 문서를 갱신하여 이력을 유지한다
- 사람이 코드를 읽지 않고 문서만으로 맥락을 파악할 수 있어야 한다

## 문서 종류

| 문서 | 단위 | 역할 |
|------|------|------|
| 도메인맵 | 전체 | 도메인 간 의존 방향 |
| ERD | 전체 | 테이블 전체 관계 |
| 클래스다이어그램 | Epic | 이 도메인의 객체 구조 |
| 시퀀스다이어그램 | Feature | 이 기능의 서비스 흐름 |

## 저장 위치

```
docs/design/
├── domain-map.md                   # 전체: 도메인 간 의존 방향
├── erd.md                          # 전체: 테이블 전체 관계
└── {epic-name}/
    ├── class-diagram.md
    └── sequences/
        ├── 001-order-create.md
        └── 002-order-cancel.md
```

도메인맵과 ERD는 전체에 하나. 클래스다이어그램은 Epic 단위로 누적 갱신, 시퀀스는 Feature별로 쌓임.

## 워크플로우

### 신규 작성 (구현 전)

```
1. specs 읽기 → 어떤 문서가 필요한지 판단
2. 사용자에게 작성 대상 확인
3. 문서 작성 → 사용자 리뷰
4. 확정 후 저장
```

### 갱신 (구현 후)

```
1. 기존 설계 문서 읽기
2. 코드 읽기 → 달라진 부분 파악
3. 설계 문서 갱신 + 변경 사유 기록
```

## 작성 대상 판단

### 도메인맵

다음 중 하나 이상이면 작성/갱신:
- 새 도메인(Epic) 추가
- 도메인 간 의존 관계 변경

### 시퀀스다이어그램

다음 중 하나 이상이면 작성:
- 2개+ Service 협력
- 트랜잭션 경계가 중요
- 조건 분기(alt/opt) 존재
- 연쇄 동작 (브랜드 삭제 → 상품 연쇄 삭제)

단순 CRUD(단건 조회, 목록 조회, 단순 등록)는 제외.

### ERD

다음 중 하나 이상이면 작성/갱신:
- 새 테이블 생성
- 테이블 관계 변경
- 컬럼 추가/변경

### 클래스다이어그램

다음 중 하나 이상이면 작성/갱신:
- 새 엔티티 생성
- 엔티티 간 관계 변경
- VO 도입/변경

판단이 애매하면 사용자에게 확인.

## 문서 구조

### 도메인맵

```markdown
# 도메인맵

## 개요
{프로젝트 전체 도메인 간 의존 방향을 정의한다. 도메인 나열하지 않는다.}

## 도메인 의존 관계
(Mermaid graph 코드블록)

## 도메인 설명
| 도메인 | 설명 |
|--------|------|
| {도메인명} | {한마디 정의. 기능 나열 금지.} |
```

### 시퀀스다이어그램

```markdown
# {기능명} 시퀀스다이어그램

## 개요
{이 흐름이 무엇인지 1-2문장}

## 시퀀스
(Mermaid 코드블록)

## 핵심 포인트
- {트랜잭션 경계, 주의사항 등}
```

### ERD

```markdown
# ERD

## 개요
{프로젝트의 데이터 구조 1-2문장}

## ERD
(Mermaid 코드블록)

## 테이블 설명
| 테이블 | 도메인 | 설명 | 삭제 정책 |
|--------|--------|------|----------|
| {테이블명} | {소속 도메인} | {설명} | Soft/Hard/불가 |
```

### 클래스다이어그램

```markdown
# {Epic명} 클래스다이어그램

## 개요
{이 도메인의 객체 구조 1-2문장}

## 클래스다이어그램
(Mermaid 코드블록)

## 설계 결정
- {VO 분리 이유, 관계 선택 이유 등}
```

## 예시

사용자: "주문 도메인 설계 문서 만들어줘"

```
specs를 확인했습니다. 주문 도메인에 다음 설계 문서를 작성하겠습니다:

1. ERD 갱신 — Order, OrderItem 테이블 추가
2. 클래스다이어그램 — Order, OrderItem 엔티티 + 관계
3. 시퀀스다이어그램 — 주문 생성 (재고 차감 + 스냅샷 + 트랜잭션)

주문 목록/상세 조회는 단순 CRUD라 시퀀스 제외합니다.
진행할까요?
```

## 트러블슈팅

### 코드와 기존 설계 문서가 다른 경우
- 코드 기반으로 갱신하고 핵심 포인트에 변경 사유 기록

### 어떤 다이어그램을 그려야 할지 모를 때
- 작성 대상 판단 기준을 적용하고 사용자에게 확인

### Epic 간 관계가 있는 경우 (예: 주문 → 상품)
- domain-map.md에서 의존 방향 확인
- 각 Epic의 ERD/클래스다이어그램에서는 의존하는 도메인의 ID만 참조로 표시
