Redis 기반 대기열 코드를 리뷰할 때 반드시 다음 흐름을 따른다.

### 분석 준비

#### Step 1: 설계 문서 우선 확인

코드를 보기 전에 설계 의도와 기결정 사항을 먼저 파악한다.
- `.docs/subject/` 에서 해당 주차 요구사항 문서를 읽어 구현 범위를 확인한다
- `.docs/week*/qna.md` 에서 이미 논의된 설계 결정과 trade-off를 파악한다
- 이미 검토·결정된 항목은 리뷰에서 제외한다. 단, 결정과 구현이 불일치할 때만 지적한다.

#### Step 2: 코드 탐색

프로젝트 전체에서 대기열 관련 코드를 자동 탐색한다.
- Redis 설정 클래스 (RedisConfig, RedisTemplate 등)
- Sorted Set 연산 사용 코드 (ZADD, ZRANK, ZCARD, ZPOPMIN)
- 입장 토큰 발급/검증/삭제 코드
- 스케줄러 (@Scheduled, TaskScheduler 등)
- 순번 조회 API (Controller, Service)
- 대기열 진입 API
- 주문 API의 토큰 검증 로직

> 특정 파일만 떼어내어 판단하지 않는다. 대기열 진입 → 순번 조회 → 스케줄러 토큰 발급 → 토큰 검증 → 주문 → 토큰 삭제 전체 파이프라인을 기준으로 분석한다.

#### Step 3: 해당 여부 필터링

각 점검 항목에 대해, 먼저 현재 구현에 해당 기능/패턴이 존재하는지 확인한다.
- 코드에 구현되지 않은 기능에 대해서는 리스크를 지적하지 않는다.
- 요구사항 문서에 명시된 범위 밖의 기능 부재는 리스크가 아니다.
- 설계 문서에서 구현 예정으로 명시되었으나 코드에 누락된 경우에만 "미구현" 지적을 한다.

### 1. Redis Sorted Set 기반 대기열 점검

다음을 순서대로 확인한다.
- `ZADD` 사용 시 score 설계
  - score = timestamp 기반인지, 순서 보장이 되는지
  - 동일 시각 진입 시 score 충돌 가능성과 해소 전략
- `ZRANK` 기반 순번 조회
  - 0-based 인덱스를 사용자 향 순번으로 변환하는지
  - 대기열에 없는 userId 조회 시 처리 (null 반환 vs 예외)
- `ZCARD` 기반 전체 대기 인원 조회
  - 불필요하게 빈번한 호출이 아닌지
- `ZPOPMIN` 기반 스케줄러 꺼내기
  - 원자적으로 꺼내는지, 꺼낸 후 토큰 발급 실패 시 복구 전략
- 중복 진입 방지
  - Sorted Set의 Set 특성(동일 member 자동 덮어쓰기)에만 의존하는지
  - 이미 대기열에 있는 유저가 재진입하면 score가 갱신되어 순서가 뒤로 밀리는 문제는 없는지
  - `ZADD NX` 옵션 사용 여부

### 2. 입장 토큰 설계 점검

다음을 확인한다.
- `SET entry-token:{userId} {token} EX {ttl}` 구조인지
  - TTL 값의 적정성 (너무 짧으면 정상 유저 만료, 너무 길면 자리 점유)
  - TTL 설정 근거가 문서화되어 있는지
- 토큰 검증 로직
  - `GET entry-token:{userId}` → 존재 여부 + 값 일치 확인
  - 토큰 값 자체를 검증하는지, 존재 여부만 확인하는지
  - 토큰이 없거나 불일치할 때의 에러 응답
- 토큰 삭제
  - 주문 완료 후 `DEL entry-token:{userId}` 호출 여부
  - 주문 실패 시 토큰은 어떻게 되는지 (삭제? 유지? 재사용 가능?)
- 토큰 만료 후 추가 발급
  - TTL 만료된 토큰 수만큼 다음 유저에게 추가 발급하는 메커니즘이 있는지
  - 만료 감지 방식 (Redis Keyspace Notification vs 스케줄러 주기적 체크)
- 토큰 발급과 대기열 제거의 원자성
  - ZPOPMIN으로 꺼낸 후 토큰 발급이 실패하면 유저가 대기열에서도 사라지고 토큰도 없는 상태가 되는지

---

### 3. 스케줄러 점검

다음을 확인한다.
- 실행 주기의 적절성
  - 주기가 너무 길면 유저 대기 시간 증가
  - 주기가 너무 짧으면 Redis 부하 + 스케줄러 오버헤드
- 배치 크기 산정 근거
  - DB 커넥션 풀, 평균 주문 처리 시간 기반으로 TPS를 산출했는지
  - 안전 마진을 적용했는지
  - 배치 크기와 실행 주기의 조합이 목표 TPS에 부합하는지
- `ZPOPMIN` 호출 후 처리
  - 꺼낸 userId 목록에 대해 토큰을 일괄 발급하는지
  - 일부 발급 실패 시 나머지는 어떻게 되는지
- 스케줄러 장애 시 대기열 정체
  - 스케줄러가 단일 인스턴스인지, 다중 인스턴스에서 중복 실행 방지가 되어 있는지
  - 분산 환경에서 스케줄러 Lock (e.g. ShedLock, Redis Lock) 사용 여부
  - 스케줄러 미실행 감지 및 알림 메커니즘
- 현재 활성 토큰 수 고려
  - 이미 발급된(미사용) 토큰 수를 고려하여 추가 발급량을 조절하는지
  - 토큰 발급 상한(동시 접속 가능 인원)이 있는지

---

### 4. Thundering Herd 완화 점검

다음을 확인한다.
- 토큰 발급 분산
  - 1초에 N명을 한 번에 발급하는지, 분할하여 발급하는지
  - e.g. 100ms마다 소량씩 발급하여 부하 평탄화
- Jitter 적용 여부
  - 토큰 활성화 시점에 랜덤 딜레이를 포함하는지
  - Jitter 없이 모든 유저가 동시에 주문 API를 호출하면 순간 스파이크 발생
- 주문 API Rate Limit
  - 토큰이 있어도 초당 N건까지만 처리하는 최종 안전장치가 있는지
  - Rate Limit 초과 시 유저에게 어떤 응답을 주는지 (재시도 안내? 거부?)
- 토큰 발급 직후 동시 요청 시나리오
  - 스케줄러가 배치로 발급한 유저들이 동시에 주문 API를 호출할 때 DB 커넥션 풀이 감당 가능한지

---

### 5. 순번 조회 & 실시간 피드백 점검

다음을 확인한다.
- Polling 기반 순번 조회 API
  - `ZRANK` 기반 순번 + `ZCARD` 기반 전체 대기 인원 응답
  - 응답에 예상 대기 시간이 포함되는지
- 예상 대기 시간 계산
  - `내 순번 / 초당 처리량` 등 합리적인 계산식을 사용하는지
  - 계산에 사용되는 처리량 수치가 하드코딩인지 동적 산출인지
- 토큰 발급 시 응답에 토큰 포함
  - 순번 조회 시 이미 토큰이 발급되었으면 토큰을 함께 응답하는지
  - 대기열에도 없고 토큰도 없는 상태 (만료된 유저)의 응답 처리
- Polling 부하 고려
  - 대기 인원이 많을 때 Polling 자체가 서버 부하가 되지 않는지
  - 순번 구간별 Polling 주기 동적 조절을 고려했는지
  - 클라이언트에 Polling 주기를 응답에 포함하여 안내하는지
- SSE 구현 여부 (Nice-to-Have)
  - SSE 사용 시 연결 관리, 재연결 전략, 서버 리소스 사용량

---

### 6. 주문 API 연동 & R7 파이프라인 연결 점검

다음을 확인한다.
- 주문 API 진입 시 토큰 검증
  - 토큰 검증 위치 (Interceptor/Filter vs Controller vs Service)
  - 토큰 없이 주문 API 직접 호출 시 차단 여부
- 주문 완료 후 토큰 삭제
  - 주문 성공 시 토큰이 즉시 삭제되는지
  - 주문 실패 시 토큰 처리 정책 (재사용 허용? 삭제?)
- R7 이벤트 파이프라인 연결
  - 주문 완료 → ApplicationEvent → Kafka → collector 흐름이 기존대로 동작하는지
  - 대기열 도입으로 인해 기존 주문 흐름에 부작용이 없는지
- 트랜잭션 경계
  - 토큰 검증(Redis) → 주문 처리(DB) → 토큰 삭제(Redis) 의 트랜잭션 경계
  - DB 트랜잭션 커밋 후 Redis 토큰 삭제가 실패하면 토큰이 남는 문제
  - 토큰 삭제 실패 시 TTL에 의한 자연 만료로 보완되는지

---

### 7. Graceful Degradation 점검

다음을 확인한다.
- Redis 장애 시 전략이 정의되어 있는지
  - 전면 차단: 대기열 진입 불가 + 안내 메시지
  - 대기열 우회: 주문 API 직접 접근 허용 (과부하 위험)
  - Fallback 큐: 로컬 메모리 큐 또는 Kafka 임시 전환
- Redis 연결 실패 감지 및 복구
  - RedisTemplate 호출 실패 시 예외 처리 방식
  - Circuit Breaker 적용 여부
  - Redis 복구 후 자동 재연결 및 대기열 상태 복원
- 대기열 최대 인원 제한
  - 무한정 대기열에 쌓이는 것을 방지하는 상한이 있는지
  - 상한 초과 시 유저에게 어떤 응답을 주는지

### 8. 동시성 & 엣지 케이스

다음을 확인한다.
- 대기열 순서 보장
  - 동시 진입 시 score(timestamp) 정밀도로 순서가 보장되는지
  - 나노초 vs 밀리초 정밀도, 동일 시각 처리
- 토큰 만료 후 재진입
  - 토큰이 만료된 유저가 다시 대기열에 진입할 수 있는지
  - 재진입 시 기존 순번이 유지되는지 또는 맨 뒤로 가는지
- 어뷰징 방어
  - 동일 유저의 다중 디바이스/브라우저 중복 진입 방지
  - userId 기반 Sorted Set member로 자연 방지되는 범위와 한계
  - 비로그인 상태 방어 (과제 범위 외일 수 있으나 인지 여부 확인)
- 스케줄러 중복 실행
  - 다중 인스턴스 환경에서 동일 유저에게 토큰이 두 번 발급되는 시나리오
  - ZPOPMIN의 원자성으로 방지되는 범위와 한계
- 대기열 + 토큰 상태 불일치
  - 대기열에는 없는데 토큰은 있는 상태 (정상: 이미 입장)
  - 대기열에도 없고 토큰도 없는 상태 (만료 또는 미진입)
  - 대기열에 있으면서 토큰도 있는 상태 (비정상: 상태 불일치)

### 톤 & 스타일 가이드
- 코드 레벨 수정안을 직접 제시하지 않는다.
- 설계를 비판하지 말고 리스크를 드러내는 리뷰 톤을 유지한다.
- Redis는 항상 다음을 만족한다고 가정한다:
  - 단일 명령은 원자적이지만, 복합 연산은 원자적이지 않다
  - 네트워크 지연이나 장애가 발생할 수 있다
  - TTL 기반 만료는 정확한 시점을 보장하지 않는다 (lazy expiration + active expiration)
  - 메모리 제한에 도달할 수 있다 (eviction policy)
- 구현보다 파이프라인 전체의 신뢰성, 순서 보장, 공정성, 유저 경험을 중심으로 분석한다.
- 설정값에 대해서는 "왜 이 값을 선택했는가?"를 질문하는 방식으로 접근한다.
- 대기열은 부하를 없애는 것이 아니라 **평탄화(smoothing)** 하는 것임을 전제로 리뷰한다.
- 설계 문서(qna.md 등)에서 이미 논의·결정된 trade-off는 존중한다. 결정과 구현이 일치하면 재지적하지 않는다. 결정과 구현이 불일치할 때만 "설계 결정과 다른 점"으로 언급한다.
- "구현하지 않은 것"과 "구현해야 하는데 빠진 것"을 구분한다. 요구사항 문서에 없는 기능의 부재는 리스크가 아니다.
