# Tech Research

기술 의사결정을 위해 **외부 사례 조사 → 트레이드오프 분석 → 되돌림 비용 평가**를 수행합니다.

## 3-Phase 워크플로우

```
SEARCH  → WebSearch/WebFetch로 외부 사례 3-5개 수집
ANALYZE → 트레이드오프 매트릭스 + 되돌림 비용 평가
PRESENT → 이해하기 쉬운 보고서 형태로 출력
```

---

## Phase 1: SEARCH

WebSearch와 WebFetch를 활용하여 외부 사례를 수집한다.

### 절차

1. 사용자의 질문에서 **핵심 기술 키워드**를 추출한다
2. 다음 3가지 축으로 검색한다:
   - **기업 사례**: "{키워드} production case study" — 실제 운영 환경에서의 경험
   - **기술 비교**: "{키워드} vs {대안} tradeoffs" — 대안 간 비교
   - **최신 동향**: "{키워드} 2024 2025 best practice" — 최신 권장 사항
3. 검색 결과 중 **구체적 데이터/수치가 있는** 상위 3-5개 페이지를 WebFetch로 읽는다
4. 각 사례에서 핵심 정보를 추출한다:
   - 어떤 문제를 풀었는가
   - 어떤 접근법을 선택했는가
   - 결과는 어떠했는가 (수치가 있으면 포함)

### 검색 품질 기준

- 개인 블로그 < 기업 엔지니어링 블로그 < 학술 논문/공식 문서
- 2023년 이전 자료는 최신 자료로 보완
- "best practice"만 나열하는 글보다 **구체적 경험담**을 우선

---

## Phase 2: ANALYZE

수집한 사례를 분석하여 트레이드오프와 되돌림 비용을 평가한다.

### 절차

1. **접근법 분류**: 수집된 사례에서 나타나는 접근법을 2-4개로 분류한다
2. **트레이드오프 매트릭스 작성**: 각 접근법의 장점, 단점, 적합한 상황을 정리한다
3. **되돌림 비용 평가**: 각 접근법이 "one-way door"인지 "two-way door"인지 판단한다

### 되돌림 비용 판단 기준

| 되돌림 비용 | 특징 | 예시 |
|------------|------|------|
| **One-way door** | 변경 시 데이터 마이그레이션, API 호환성 파괴, 대규모 리팩토링 필요 | DB 스키마 설계, 외부 API 응답 형식, 인증 방식 |
| **Two-way door** | 변경 시 코드 수정만으로 해결, 기존 데이터/API에 영향 없음 | 내부 구현 패턴, 캐시 전략, 로깅 방식 |

### 우리 프로젝트 맥락 반영

분석 시 현재 프로젝트의 기술 스택과 아키텍처를 고려한다:
- Java 21 + Spring Boot 3.4
- DDD + Hexagonal Architecture
- MySQL + Redis + Kafka

## Phase 3: PRESENT

`references/research-template.md`의 포맷으로 보고서를 출력한다.

### 출력 규칙

1. **한 줄 요약**부터 시작 — 가장 중요한 결론을 먼저
2. **되돌림 비용**을 바로 다음에 표시 — 의사결정의 긴급도를 알려줌
3. **외부 사례**는 표로 — 한눈에 비교 가능
4. **트레이드오프 매트릭스**는 표로 — 장단점 직관적 비교
5. **추천**은 마지막에 — 근거와 함께 한 문장으로
6. 사용자가 이해하기 쉽게 기술 용어를 설명하되, 비유보다 **구체적 예시**를 사용

### 사용자 확인

보고서 출력 후:

```
추가로 궁금한 점이 있으면 질문해주세요.
결정이 되셨으면 다음 단계(설계/구현)로 진행할 수 있습니다.
```

## 에러 처리

| 상황 | 대응 |
|------|------|
| WebSearch 결과가 없거나 부족 | 검색 키워드를 변경하여 재시도. 영어/한국어 양쪽으로 검색 |
| WebFetch로 페이지 접근 불가 | 검색 결과의 스니펫 정보를 활용하고, 다른 소스를 찾는다 |
| 관련 사례가 너무 오래됨 (2020년 이전) | 사용자에게 알리고, 해당 기술의 공식 문서 최신 버전을 참조한다 |
| 주제가 너무 광범위 | 사용자에게 범위를 좁혀달라고 요청 (예: "캐시 전략" → "Redis vs Caffeine 로컬 캐시") |

## 예시

### 예시 1: 기술 선택

사용자: "이벤트 기반 통신에 Kafka 대신 Redis Streams 쓰면 어떨까?"

동작:
1. SEARCH — Kafka vs Redis Streams 비교 사례 5개 수집
2. ANALYZE — 처리량, 내구성, 운영 복잡도 축으로 매트릭스 작성
3. PRESENT — 되돌림 비용(Two-way door) + 트레이드오프 + 추천

### 예시 2: 아키텍처 결정

사용자: "주문 서비스에서 결제 실패 시 Saga vs 보상 트랜잭션 어떤게 나아?"

동작:
1. SEARCH — Saga pattern, compensating transaction 기업 사례 조사
2. ANALYZE — 복잡도, 일관성 보장, 디버깅 난이도 비교
3. PRESENT — 되돌림 비용(One-way door) + 매트릭스 + "현재 규모에서는 보상 트랜잭션 추천"

### 예시 3: 설계 패턴

사용자: "다른 회사는 재고 동시성 어떻게 처리해?"

동작:
1. SEARCH — 쿠팡, 배민, Amazon 재고 시스템 사례 조사
2. ANALYZE — 비관적 락, 낙관적 락, Redis 분산 락, DB atomic operation 비교
3. PRESENT — 사례 + 매트릭스 + 현재 프로젝트 규모에 맞는 추천
