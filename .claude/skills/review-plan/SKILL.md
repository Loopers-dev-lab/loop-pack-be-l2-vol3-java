# review-plan Skill

## 목적

시니어 개발자의 관점에서 주차별 플랜(plan)과 구현을 **다면 리뷰**한다.
플랜 문서, discussion, 코드, 발제 문서를 종합적으로 분석하여 **학습 방향이 올바른지, 실무 수준의 판단을 하고 있는지** 검증한다.

---

## 리뷰 대상 수집

### 1. 대상 주차 파악

사용자가 주차를 명시하지 않으면 현재 브랜치에서 추출한다.

```bash
git rev-parse --abbrev-ref HEAD
```

### 2. 문서 수집

| 문서 | 경로 |
|------|------|
| 발제 문서 | `docs/discussion/{주차}/week{N}-*.md` (발제 원문) |
| 플랜 | `docs/plan/{주차}/` 하위 모든 파일 |
| Discussion | `docs/discussion/{주차}/{브랜치명}-discussion.md` |
| 코드 | `git log main..HEAD --name-only` 또는 플랜에 명시된 파일 |

### 3. 기존 코드베이스 확인

플랜이 참조하는 기존 코드(week9 등)의 실제 상태를 확인한다.

---

## 리뷰 항목 (7개 축)

### 축 1. 발제 의도 분석 (What should be learned?)

발제 문서를 읽고 시니어 관점에서 분석한다:

- **발제자가 이번 주차에서 학습자에게 깨닫길 바라는 핵심 포인트**는 무엇인가?
  - Keywords, Learning 섹션, Must-Have 항목에서 추출
  - 발제의 예시 코드와 설명에서 암시하는 학습 방향
- **발제의 깊이 수준** — 기초 개념 학습인지, 실무 패턴 체득인지, 아키텍처 판단력인지
- **발제가 의도적으로 열어둔 설계 자유도** — 어디까지가 필수이고 어디부터가 탐구 영역인지

출력 형식:
```markdown
#### 발제 의도 분석

**핵심 학습 포인트** (발제자가 기대하는 것)
1. ...
2. ...
3. ...

**깊이 수준**: [기초 개념 / 실무 패턴 / 아키텍처 판단]

**필수 vs 탐구 경계**
- 필수: ...
- 탐구: ...
```

### 축 2. 핵심 캐치 검증 (Did you catch the right things?)

플랜과 discussion에서 학습자가 **발제의 핵심을 제대로 파악했는지** 확인한다:

- 발제의 핵심 학습 포인트를 플랜에서 다루고 있는가?
- 놓친 핵심 포인트가 있는가?
- 발제 의도와 다른 방향으로 해석한 부분이 있는가?

판정 기준:
| 판정 | 의미 |
|------|------|
| **정확히 캐치** | 발제 의도와 일치하는 고민/설계를 하고 있음 |
| **과잉 캐치** | 발제 범위를 넘어서는 고민 (나쁘지 않으나 우선순위 확인 필요) |
| **미캐치** | 발제가 요구하는 핵심을 놓침 |
| **오해** | 발제 의도를 잘못 해석함 |

### 축 3. 고민 포인트 + 선택지 + 추천 검증 (Are you worrying about the right things? Are your choices good?)

플랜의 결정 사항(선택사항/결정)과 discussion의 논의 내용을 **3단계**로 분석한다.

#### 3-a. 고민 포인트 적절성

- 각 고민 포인트가 **이 주차의 발제 주제와 관련**이 있는가?
- **현재 프로젝트 규모와 맥락**에서 의미 있는 고민인가?
  - 예: 상품 10만개 규모에서 파티셔닝 고민은 과잉
  - 예: 계정 보안 수준이 기본인 프로젝트에서 OAuth2 MFA 고민은 동떨어짐
- 고민의 **깊이**가 적절한가? (너무 피상적 / 적절 / 너무 깊음)
- **실무에서 실제로 중요한 고민**을 빠뜨리고 있지 않은가?

판정 기준:
| 판정 | 의미 |
|------|------|
| **적절** | 발제 주제 + 프로젝트 맥락에 맞는 실용적 고민 |
| **과잉** | 현재 규모/맥락에서 불필요한 수준의 고민 |
| **부족** | 실무에서 중요하지만 빠뜨린 고민 |
| **동떨어짐** | 발제 주제나 프로젝트 맥락과 관련 없는 고민 |

#### 3-b. 선택지(대안) 리스트 검증 + 보강

각 결정 사항의 **선택지 자체**가 충분하고 적절한지 검증한다:

- 제시된 선택지가 **해당 고민의 핵심 축**을 커버하는가?
- 실무에서 흔히 고려하는 **빠진 선택지**가 있는가?
- 선택지 간 **차별점이 명확**한가? (비슷한 선택지를 억지로 나눈 건 아닌가?)
- 선택지의 **장단점 분석이 정확**한가? (과장/누락된 장단점은 없는가?)

피드백 시 **취소선 + 보강 방식**으로 표현:

```markdown
> 선택사항: Reader 집계 전략
> A-1: JdbcCursorItemReader — SQL GROUP BY + score + LIMIT 100
> A-2: JdbcCursorItemReader — SQL GROUP BY만, score는 Processor
> ~~A-2를 삭제 제안: A-1과 Reader 기술이 동일하여 차별점이 score 위치뿐. 진짜 축은 "DB 집계 vs Java 집계"~~
> **추가 제안 C: JpaPagingItemReader — Entity 기반 전체 읽기 + Java에서 집계/정렬/TOP N**
>   장점: JPA Entity 활용, 순수 Java 로직 / 단점: 전체 상품 메모리 로드, 정렬 비용
>   이 선택지를 추가하면 "DB에 위임 vs Java에서 처리"라는 진짜 트레이드오프가 드러남
```

보강 규칙:
- 추가 선택지는 **발제 범위 + 프로젝트 맥락 내**에서만 제안한다
- 삭제 제안은 **반드시 이유**와 함께 취소선으로 표시한다
- 기존 선택지의 장단점이 부정확하면 **수정선으로 교정**한다:
  ```
  > A-1 장점: ~~DB 옵티마이저 활용~~ → DB에 집계를 위임하여 네트워크 전송 최소화 (100행만)
  ```

#### 3-c. 추천(Recommendation) 적절성 검증

플랜에서 `> 추천:` 또는 `> **추천:**`으로 표시된 추천 의견을 **두 가지 기준**으로 검증한다:

**기준 1: 발제 맥락에 적절한가?**
- 추천이 발제의 학습 목표에 부합하는가?
- 발제가 경험하길 원하는 패턴을 회피하는 방향으로 추천하고 있진 않은가?
  - 예: 발제가 Chunk Oriented Processing 경험을 원하는데, Tasklet에서 전부 처리하라고 추천
- 학습 효과를 극대화하는 선택인가?

**기준 2: 현재 프로젝트에 적절한가?**
- 프로젝트의 규모(상품 10만, 일 트래픽 수만)에 맞는 추천인가?
- 기존 코드베이스의 패턴과 일관성 있는 추천인가?
- 이미 존재하는 인프라를 무시하고 새로 만드는 방향은 아닌가?
- 운영 복잡도 대비 실익이 있는 추천인가?

추천 판정:
| 판정 | 의미 |
|------|------|
| **적절** | 발제 맥락 + 프로젝트 맥락 모두 적합 |
| **발제 부합, 프로젝트 과잉** | 학습 효과는 있으나 실제 프로젝트엔 과한 선택 (허용 가능) |
| **프로젝트 부합, 발제 미달** | 실용적이나 학습 기회를 놓치는 선택 |
| **부적절** | 양쪽 모두 맞지 않음 — 대안 제시 필요 |

부적절 판정 시 **대안 추천을 반드시 제시**:
```markdown
> 플랜 추천: A-1 (SQL 인라인 score)
> **리뷰어 판정: 프로젝트 부합, 발제 미달**
> 이유: SQL에 score를 인라인하면 가장 실용적이지만, 발제가 Processor의 역할을 경험하길
> 원하는 맥락에서 Processor가 rank 번호만 부여하게 되어 학습 효과가 축소됨.
> **대안 추천**: A-2 또는 -b 플랜의 Java Processor 방식 — Processor에서 score 계산을 수행하면
> ItemProcessor의 변환 책임을 온전히 경험할 수 있음.
```

### 축 4. 코드 품질 리뷰 (Is the code well-written?)

플랜의 코드 스니펫과 실제 커밋된 코드를 검토한다:

- **CLAUDE.md 코딩 규칙 준수**: var 금지, nested class 금지, 주석 규칙, 타입 패턴 등
- **SOLID 원칙**:
  - SRP: 클래스/메서드가 단일 책임을 가지는가?
  - OCP: 확장에 열리고 수정에 닫혀 있는가? (특히 score 계산 같은 변경 가능 지점)
  - LSP: 추상화 계약을 위반하는 곳은 없는가?
  - ISP: 불필요하게 큰 인터페이스를 강제하지 않는가?
  - DIP: 상위 레이어가 하위 구현에 직접 의존하지 않는가?
- **Spring Batch 관용 패턴**: @JobScope/@StepScope 사용, chunk size 설정, Reader/Processor/Writer 분리
- **에러 처리**: 배치 실패 시나리오 대응
- **테스트 가능성**: 코드가 테스트하기 쉬운 구조인가?

### 축 5. 아키텍처 준수 (Does it follow the architecture?)

프로젝트의 아키텍처 규칙을 기준으로 검토한다:

- **레이어 의존성 방향**: Interfaces → Application → Domain ← Infrastructure
- **모듈 의존성**: apps → modules/supports (역방향 금지)
- **네이밍 규칙**: Entity `{Domain}Model`, Service `{Domain}Service`, Repository 패턴 등
- **App/Facade/Service 역할 분리**: 크로스 도메인이면 Facade, 단일이면 App
- **금지 사항**: App→App 의존, Facade→Service 직접 호출 등
- **새 모듈(commerce-batch)이 기존 아키텍처와 일관성 있는가?**

### 축 6. 기술 이해 방향 (Is the technical understanding correct?)

플랜과 discussion에서 드러나는 기술 이해도를 검증한다:

- **Spring Batch 핵심 개념** 이해가 정확한가?
  - Job/Step/Chunk/Tasklet의 역할
  - @JobScope/@StepScope의 의미
  - ItemReader/Processor/Writer의 계약
  - chunk size와 트랜잭션 경계
  - 재시작(restartability), 멱등성
- **MV(Materialized View) 개념** 이해가 정확한가?
  - 사전 집계의 목적과 트레이드오프
  - 갱신 전략 (DELETE+INSERT vs UPSERT)
  - 서빙 경로 설계 (실시간 vs 배치)
- **실시간 vs 배치의 트레이드오프** 이해
- 기술 용어를 **정확하게** 사용하고 있는가?
- 잘못된 가정이나 오개념이 있는가?

### 축 7. 프로젝트 맥락 적합성 (Does it fit the project?)

- 기존 코드베이스(week9 등)와 **자연스럽게 연결**되는가?
- 기존에 만든 인프라(ShedLock, RedisConfig, ScoreAggregator 등)를 **적절히 재사용**하고 있는가?
- 불필요한 중복 구현이 있는가?
- 프로젝트에 **없는 기능/인프라를 전제**로 설계하고 있지 않은가?

## 리뷰 원칙

### 시니어 관점의 기준

1. **"이 주차에서 뭘 배워야 하는가"가 최우선 기준**: 코드 완성도보다 학습 방향이 중요
2. **현재 프로젝트 규모를 기준으로 판단**: 상품 10만개, 일 트래픽 수만 수준의 커머스
3. **과잉 엔지니어링 경계**: "더 좋은 방법"보다 "이 맥락에서 적절한 방법"
4. **정직한 피드백**: 좋은 건 좋다고, 방향이 틀린 건 명확히 지적

### 판단 시 주의사항

- 발제 문서에 없는 요구사항을 임의로 추가하여 평가하지 않는다
- "실무에서는 이렇게 한다"는 참고 정보일 뿐, 학습 맥락에서 반드시 따라야 하는 기준이 아니다
- 프로젝트에 존재하지 않는 기능(예: 고도화된 인증 체계)을 전제로 비판하지 않는다
- 학습자의 성장 단계를 고려하여 피드백 톤을 조절한다

### 코드가 아직 없는 경우

플랜만 있고 코드가 아직 커밋되지 않은 경우:
- 축 4(코드 품질)는 **플랜의 코드 스니펫 기반으로 사전 리뷰**
- "실제 구현 시 주의할 점" 형태로 피드백
- 축 1~3, 5~7은 정상 리뷰

### 복수 플랜이 있는 경우

기본/-a/-b 등 복수 플랜이 존재하면:
- **채택된 플랜을 주 리뷰 대상**으로 삼는다
- 플랜 선택 과정 자체도 리뷰 대상이다 (결정 근거가 합리적인가?)
- 기각된 플랜과의 비교가 적절했는지도 검토한다
- **플랜 선택의 추천이 발제 맥락 + 프로젝트 맥락에 적절한지** 검증한다
  - discussion에서 채택 이유로 제시한 근거가 타당한가?
  - 기각 이유가 공정한가? (한쪽 장점만 보고 다른 쪽을 기각하진 않았는가?)
  - 채택 플랜이 발제의 학습 효과를 극대화하는 선택인가?

## Never Do

- 발제 범위를 넘어서는 고도화를 요구하는 리뷰
- 학습자의 시도 자체를 부정하는 톤
- 코드 스타일 취향(tab vs space 등)에 대한 지적
- 발제 문서를 읽지 않고 리뷰하는 행위
- 플랜에 없는 내용을 추측하여 평가하는 행위
- "이건 틀렸다"만 말하고 "왜 틀렸는지, 어떻게 하면 좋은지"를 안 말하는 행위
