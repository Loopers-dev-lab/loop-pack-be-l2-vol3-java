---
name: analyze-external-integration
description:
  외부 시스템(결제 PG, 재고 시스템, 메시징, 서드파티 API 등)과 연동되는 기능의 설계를 분석한다.
  Timeout, Circuit Breaker, Retry, Fallback 등 Resilience 전략의 적정성을 점검한다.
  비동기 결제(콜백 기반) 흐름에서의 상태 관리와 복구 경로를 검증한다.
  트랜잭션 경계, 상태 일관성, 실패 시나리오, 재시도 및 중복 실행 가능성을 중심으로 리스크를 드러낸다.
  설계를 대신 생성하지 않으며, 이미 작성된 설계를 검증하고 개선 선택지를 제시하는 데 사용한다.
  외부 시스템 호출이 포함된 기능 구현 전/후 설계 리뷰 목적으로 사용한다.
---

외부 시스템 연동 설계를 분석할 때 반드시 다음 흐름을 따른다.

### 1️⃣ 기능이 아니라 "불확실성" 관점으로 재해석한다
- 단순 호출 순서를 요약하지 않는다.
- 외부 시스템은 항상 다음을 만족한다고 가정한다:
  - 지연될 수 있다
  - 실패할 수 있다
  - 중복 실행될 수 있다
  - 성공했지만 응답이 유실될 수 있다
- 현재 설계가 이러한 불확실성을 어떻게 다루는지 설명한다.

---

### 2️⃣ 트랜잭션 경계를 검증한다
- 외부 호출이 트랜잭션 내부에 존재하는지 확인한다.
- 외부 시스템과 내부 DB 상태가 하나의 트랜잭션처럼 다뤄지고 있는지 분석한다.
- 다음 질문을 반드시 포함한다:
  - 외부 호출이 트랜잭션 안에 있다면, DB 커넥션은 외부 호출 동안 점유되는가?
  - 외부 호출 실패 시 내부 상태는 어떻게 되는가?
  - 내부 커밋 이후 외부 호출 실패 시 복구 가능한가?
  - 외부 성공 후 내부 실패 시 상태는 어떻게 정합성을 유지하는가?
- 외부 호출이 트랜잭션 내부에 포함된 경우, 커넥션 풀 고갈을 통한 장애 전파 리스크를 명시한다.

---

### 3️⃣ 상태 기반으로 구조를 다시 본다
- 호출 흐름이 아니라 상태 전이를 중심으로 설명한다.
- 내부 도메인 상태와 외부 시스템 상태를 분리해서 정리한다.
- 두 상태가 어긋날 수 있는 지점을 명시한다.
- 허용되지 않는 상태 전이를 코드로 방어하고 있는지 확인한다.

#### 비동기 흐름(콜백 기반)이 존재하는 경우 추가로 확인한다:
- "요청 성공 = 처리 완료"가 아님을 설계가 구분하고 있는가?
  - 200 응답은 "접수됨"이지 "결제 성공"이 아니다.
- 콜백 미수신 시 상태가 영원히 중간 상태(PENDING)로 남는가?
- 콜백 미수신에 대한 복구 경로가 존재하는가?
  - 폴링(스케줄러) 기반 자동 복구
  - 수동 조회 API를 통한 관리자 트리거
- 콜백 인증/검증이 존재하는가? (위조된 콜백 방어)
- "진실의 원천(Source of Truth)"이 내부 DB인지 외부 시스템인지 명확한가?

---

### 4️⃣ 중복 요청 및 재시도 가능성을 분석한다
- 네트워크 재시도 상황을 가정한다.
- 동일 요청이 두 번 실행될 경우 어떤 문제가 발생하는지 설명한다.
  - Read Timeout 후 자동 재시도 → 외부에서는 두 건 모두 성공 → 이중 처리
- 멱등성(Idempotency) 고려 여부를 확인한다:
  - 요청 측 멱등성: 같은 요청을 N번 보내도 결과가 1번과 같은가?
  - 콜백 수신 측 멱등성: 동일 콜백이 중복 도착해도 안전한가?
- 동시 요청에 대한 방어(비관적 락, UNIQUE 제약 등)가 있는지 확인한다.

---

### 5️⃣ Resilience 전략의 적정성을 검증한다

각 전략이 존재하는지, 설정값의 근거가 설명 가능한지 확인한다.

#### Timeout
- Connection Timeout과 Read Timeout이 분리 설정되어 있는가?
- 타임아웃 값은 외부 시스템의 평소 응답 시간(p99) 대비 적절한가?
- 타임아웃 부재 시 스레드/커넥션 고갈 가능성은 고려되었는가?

#### Circuit Breaker
- Closed → Open → Half-Open 상태 전이 설정이 존재하는가?
- sliding-window-size, failure-rate-threshold 값의 근거는?
  - 외부 시스템의 "평소 실패율"과 threshold가 적절히 분리되어 있는가?
- slow-call 설정으로 "에러 없이 느리기만 한 장애"도 감지하는가?
- Open 상태에서의 동작(CallNotPermittedException → Fallback)이 정의되어 있는가?

#### Retry
- 재시도 대상 예외가 Retryable(일시적 장애)과 Non-retryable(영구적 장애)로 구분되는가?
  - Retryable: SocketTimeoutException, ConnectException, HTTP 503
  - Non-retryable: HTTP 400/401, 비즈니스 에러(잔액 부족 등)
- Backoff 전략이 적용되어 있는가? (Fixed / Exponential / Exponential + Jitter)
  - Jitter 없이 고정 간격 재시도 시 Retry Storm(Thundering Herd) 가능성은?
- Retry + Circuit Breaker의 Aspect 순서는 적절한가?
  - 권장: CircuitBreaker( Retry( 실제호출 ) ) — Retry가 다 끝난 후 최종 결과를 CB가 판단

#### Fallback
- Fallback이 단순 에러 메시지 변경이 아니라 "시스템이 할 수 있는 최선"인가?
- Fallback 수준을 확인한다:
  - Level 1: 안내 메시지 반환
  - Level 2: PENDING 상태 저장 후 나중에 재처리
  - Level 3: 부분적 서비스 유지 (Graceful Degradation)
- Fallback 안에서 하면 안 되는 것을 하고 있지는 않은가?
  - 또 다른 외부 호출 ❌ (장애 전파)
  - 무거운 DB 쿼리 ❌ (커넥션 풀 압박)
  - Fallback 자체가 장애 원인이 될 수 있는 구조 ❌

---

### 6️⃣ 장애 시나리오를 우선순위 기반으로 도출한다
- 정상 흐름보다 실패 흐름을 우선한다.
- 현재 설계에서 발생 가능한 시나리오를 전수 도출하되, 다음 기준으로 우선순위를 매긴다:
  - 데이터 정합성 훼손 여부
  - 복구 가능성 (자동 복구 / 수동 개입 / 복구 불가)
  - 발생 빈도

#### 반드시 포함해야 할 시나리오 후보:
1. 외부 호출 실패 → 내부 커밋 성공 (상태 불일치)
2. 외부 호출 성공 → 내부 커밋 실패 (돈은 빠졌는데 주문 미생성)
3. 외부 호출 성공 → 응답 유실 (우리는 실패, 외부는 성공)
4. 콜백 미수신으로 PENDING 영구 잔류
5. 중복 콜백 수신 시 이중 처리
6. Retry 중 첫 번째 요청이 외부에서 실제로 성공 → 이중 결제
7. Circuit Breaker Open 상태에서 긴급 결제 처리 불가

---

### 7️⃣ 운영 관점: 관찰 가능성(Observability)을 점검한다
- 장애 발생 시 로그/메트릭으로 감지할 수 있는가?
- Circuit Breaker 상태 전이를 실시간으로 확인할 수 있는가?
  - 이벤트 리스너 로그, Actuator 엔드포인트 등
- 중간 상태(PENDING 등)가 장기간 방치되고 있음을 알 수 있는가?
- Retry 횟수, 실패율, 응답 시간 등의 메트릭이 수집되고 있는가?
- 장애 발생 시 원인 추적(어떤 예외, 어떤 시점, 어떤 요청)이 가능한가?

---

### 8️⃣ 해결책은 정답처럼 제시하지 않는다
- 현재 구조의 장점과 리스크를 분리한다.
- 대안 구조가 있다면 선택지 형태로 제시한다.
  예:
  - 동기 호출 유지
  - 상태 기반 단계 분리 (2단계 커밋)
  - 비동기 이벤트 전환
- 각 선택지의 복잡도와 운영 부담을 함께 설명한다.

---

### 9️⃣ 톤 & 스타일 가이드
- 코드 레벨 수정안을 직접 제시하지 않는다.
- 설계를 비판하지 말고 리스크를 드러내는 리뷰 톤을 유지한다.
- 외부 시스템은 항상 신뢰할 수 없다는 전제를 유지한다.
- 구현보다 책임, 경계, 상태 일관성을 중심으로 분석한다.
- 설정값에 대해서는 "왜 이 값을 선택했는가"를 질문하는 방식으로 접근한다.
