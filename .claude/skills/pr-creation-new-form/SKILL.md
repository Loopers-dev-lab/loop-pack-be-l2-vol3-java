# PR 생성 가이드 (기술 보고서 형식)

## 개요

기능 구현 완료 후, **기술 보고서** 형식으로 PR 문서를 작성하는 워크플로우입니다.
"의사결정 나열"이 아니라 **하나의 논문처럼 읽히는 연속된 서사**를 지향합니다.

---

## 핵심 원칙: "PR만 읽으면 코드가 보인다"

두 가지를 동시에 달성한다:
1. **같은 결론에 도달** — 리뷰어가 "나라도 이렇게 했겠다"고 느끼게
2. **코드를 열지 않아도 구현이 보임** — 어떤 클래스가 어떤 순서로 무슨 일을 하는지 머릿속에 그려지게

```
1. 현실 진단      → "측정하면 이런 숫자가 나온다"
2. 설계 원칙 도출  → "따라서 핵심 원칙은 ~이다" (1~3개)
3. 구현 전개      → "원칙을 코드로 풀면 이렇다" (클래스 책임 + 흐름 서사, 인과 연결)
4. 실험 검증      → "실제로 돌려보니 이렇다" (before/after)
5. 한계 인정      → "이것은 아직 못 풀었다"
```

---

## 워크플로우

```
[Step 1] 개발 기록 분석    커밋 히스토리 + 환경 제약 + 변경 파일 구조
[Step 2] PR 문서 작성      volume-{n}-pr.md — 기술 보고서 형식
```

저장 경로: `.idea/volume-{n}*.md`

### Step 1: 개발 기록 분석

기존 pr-creation과 동일한 수집 과정을 따른다.

---

## PR 문서 구조 및 작성 규칙

### 목표 분량: 200~300줄

300줄을 넘기면 밀도를 높이고 중복을 제거한다. 길이가 깊이는 아니다.

---

### 1. 현실 진단 — 수치로 시작한다

```markdown
# {제목} — {핵심 원칙을 한 문장으로}

## 1. 현실 진단

| 리소스 | 설정값 | 의미 |
|--------|--------|------|
| ... | ... | ... |

### 문제 시나리오

{특정 조건에서 시스템이 무너지는 과정을 3~5줄 시나리오로}

> 핵심 위험: {한 문장}
```

**규칙:**
- 추상적 배경 없이 **측정값/설정값**으로 시작
- 문제 시나리오는 "1→2→3→결과" 형태로 연쇄 과정을 보여준다
- 계산식이 있으면 시나리오 아래에 간결하게 (3줄 이내)

---

### 2. 설계 원칙 — 문서를 관통하는 1~3개

```markdown
## 2. 설계 원칙

> **원칙 1**: {원칙 — 한 문장}
> {현실 진단의 어떤 위험에 대응하는지 — 한 문장}

> **원칙 2**: ...
```

**규칙:**
- **최대 3개**. 4개 이상은 원칙이 아니라 나열
- 각 원칙이 이후 구현의 어떤 결정을 지배하는지 명확해야 한다
- 추상적 격언 금지 → "~하라"보다 "~를 제어하라, ~를 늘리지 마라" 형태
- 검증 가능해야 한다: "이 원칙을 어겼는가?"로 구현을 점검할 수 있어야 함

---

### 3. 구현 전개 — 코드를 열지 않아도 구현이 보여야 한다

**두 가지를 동시에 달성한다:**
1. **경중 구분** — 핵심만 깊게, 나머지는 압축
2. **구현 흐름 가시화** — 각 단계에서 "어떤 클래스가 어떤 순서로 무슨 일을 하는지" 서술

#### 하나의 단계에 독립적 관심사를 합치지 않는다

"Redis 장애 대응"과 "어뷰저 방어"는 서로 다른 문제다. 같은 단계에 넣으면 "이전 한계 → 이번 해결"이라는 인과 서사가 흐려진다. 독립적 관심사는 별도 단계로 분리하거나 부수 테이블에 넣는다.

```markdown
## 3. 구현 전개

### 구현 구조

| 레이어 | 클래스 | 책임 | 협력 대상 |
|--------|--------|------|-----------|
| Interfaces | `XxxV1Controller` | 요청 수신, DTO→Command 변환 | `XxxApp` |
| Application | `XxxApp` | 유스케이스 조율, Model→Info 변환 | `XxxService` |
| Domain | `XxxService` | 비즈니스 검증, 상태 전이 | `XxxRepository` |
| Infrastructure | `XxxRepositoryImpl` | JPA 영속화 | `XxxJpaRepository` |

### 3.1 {핵심 단계} ← 깊게

**풀려는 문제**: {원칙 N에 대응}

{기각된 대안을 서술 흐름 안에서 자연스럽게 — 별도 표 없이}
{왜 이 방법을 택했는지, 현재 환경에서 다른 방법이 왜 부적합한지}

**구현 핵심**: (3~5개 bullet)

**동작 흐름**:
1. `XxxController`가 요청을 받아 `Command`로 변환하여 `XxxApp`에 전달한다
2. `XxxApp`이 `XxxService.validate()`로 비즈니스 규칙을 검증한다
3. 검증 통과 시 `XxxService.execute()`가 상태를 전이하고 저장한다
4. 실패 시 `CoreException(INVALID_STATE)`를 던진다

**수치 도출**: (계산 과정 — 해당 시)

**→ 이 단계의 한계**: {다음 단계가 필요한 이유 — 1문장}

### 3.2 {핵심 단계} ← 깊게

(같은 구조. 단, 이전 단계의 한계에서 시작)

### 3.3~3.N {부수 단계} ← 압축

| 단계 | 해결하는 문제 | 핵심 구현 |
|------|---------------|-----------|
| 3.3 | ... | ... |
| 3.4 | ... | ... |
```

**규칙:**
- **핵심 단계 2~3개**만 깊게 (각 15~25줄)
- 나머지는 **테이블 1개로 압축** (각 1~2줄)
- 대안은 서술 흐름 안에서 녹인다 — 별도 비교표를 만들면 pr-creation과 차이가 없어진다
- "이 단계의 한계 → 다음 단계" 인과 연결은 필수
- 같은 패턴(풀려는 문제→대안→구현→한계)을 6번 반복하면 읽는 사람이 지친다. **구조적 반복을 피한다**

#### 구현 흐름 서술 규칙

- **구현 구조 테이블**: Section 3 시작에 1회. 이 PR의 핵심 클래스 5~8개
  - "책임" 열: 그 클래스가 무엇을 하는지 한 문장
  - "협력 대상" 열: 누구에게 위임하는지 — 의존 방향이 보여야 한다
- **동작 흐름**: 핵심 단계(3.1, 3.2)마다 필수. 번호 매긴 단계로 서술
  - 각 단계에 **클래스명 + 메서드 역할** 명시
  - "무슨 클래스의 무슨 행위"가 빠진 추상적 서술 금지 (예: "주문을 처리한다" → "`OrderService`가 금액을 검증하고 상태를 CREATED로 전이한다")
  - 분기(성공/실패, 조건별)가 있으면 분기도 서술
  - 5~10단계. 15단계 이상은 요약이 부족한 것
- **부수 단계 테이블**: "핵심 구현" 열에도 클래스명을 포함 (예: "`ViewBitmapService`가 Bitmap offset으로 중복 체크")

---

### 4. 실험 검증 — 데이터만

```markdown
## 4. 실험 검증

### 성능/개선 결과

| 시나리오 | Before | After | 개선 |
|----------|--------|-------|------|
| ... | ... | ... | ... |

또는 개선 경로: `기준선 → 1차(+N%) → 2차(+N%) → 최종`

### 테스트 커버리지

| 카테고리 | 수량 | 검증 대상 |
|----------|------|-----------|
| ... | ... | ... |
```

**규칙:**
- Section 3에서 이미 사용한 수치를 **반복하지 않는다**
- 성능 검증은 Section 3에서 언급하지 않은 **종합 결과**만
- 테스트는 시나리오 중심 (클래스명 나열 금지)

---

### 5. 설정값 근거 — 한눈에 요약

```markdown
## 5. 설정값 근거

| 설정 | 값 | 도출 근거 |
|------|-----|-----------|
| ... | ... | {한 줄 요약 — 상세 과정은 Section 3 참조} |
```

**규칙:**
- Section 3에서 풀어 설명한 계산의 **결론만** 여기에 요약
- 10~15행 이내. 모든 yml 설정을 나열하지 않는다 — 핵심만

---

### 6. 트레이드오프와 한계

```markdown
## 6. 트레이드오프와 한계

### 의식적으로 포기한 것

| 포기한 것 | 얻은 것 | 판단 근거 |
|-----------|---------|-----------|
| ... | ... | ... |

### 알려진 한계

1. **{한계}**: {상황} — {현재 대응 또는 "대응 없음"}
```

**규칙:**
- 트레이드오프 5~7행 이내
- 한계는 3~5개. **정직하게** — "완벽하다"는 PR은 신뢰를 잃는다
- "향후 개선 방향"은 **비자명한 것만**. "모니터링 추가", "테스트 보강" 같은 뻔한 내용 금지

---

### 7. 리뷰 포인트

```markdown
## 7. 리뷰 포인트

1. {딜레마 — 2~3문장. 맥락 + 질문}
2. ...
```

**규칙:**
- **2~3개**
- 장황한 배경 설명 금지 — 맥락은 1문장, 질문 1문장
- "확인해 주세요"가 아니라 "~와 ~의 트레이드오프를 어떻게 판단하시나요?"

---

### 다이어그램

비직관적 흐름(대기열, 이벤트 파이프라인, 결제 상태 전이 등)이 있으면 **Mermaid 다이어그램 1개는 필수**다. Section 3의 동작 흐름 서술을 **시각적으로 보강**하는 역할. 단순 CRUD는 생략 가능.

```markdown
### 핵심 흐름

```mermaid
sequenceDiagram
  autonumber
  ...
```
```

**규칙:**
- participant **최대 6~7개**
- 전체 구조 다이어그램은 **Mermaid flowchart** 1개로 충분. ASCII art 금지 (환경마다 깨짐)
- 모든 API에 시퀀스 다이어그램을 만들지 않는다
- Section 3 동작 흐름과 다이어그램이 **동일 흐름을 서술**하더라도 OK — 텍스트는 세부 로직, 다이어그램은 전체 구조를 보여주는 역할이 다르다

## 중복 제거 규칙

| 정보 유형 | 한 번만 등장할 곳 |
|-----------|-------------------|
| 수치 도출 과정 | Section 3 (해당 단계) |
| 수치 요약 | Section 5 (설정값 근거) |
| 성능 측정 결과 | Section 3 (검증으로) 또는 Section 4 (종합만) |
| 트레이드오프 | Section 6 (테이블) |
| 클래스 책임·협력 관계 | Section 3 구현 구조 테이블 (1회) |
| 동작 흐름 | Section 3 각 핵심 단계 + 다이어그램 (시각 보강) |

Section 3에서 배치 크기 비교를 서술했으면, Section 4에서 같은 표를 반복하지 않는다.

Section 5 설정값 근거는 Section 3의 **결론 1줄 요약**이다. 도출 과정을 반복하지 않는다. 상세가 필요하면 "→ 3.1 참조" 형태로.

Section 4에 본 서사와 무관한 부수 실험(예: 블로킹 vs WebFlux 비교)을 넣으면 흐름이 끊긴다. 부수 실험은 Section 6 한계나 별도 부록으로.

## pr-creation과의 차이 요약

| pr-creation | 이 스킬 (new-form) |
|-------------|---------------------|
| 결정별 섹션 분리 (D1, D2...) | 연속된 서사 (3.1→3.2→...) |
| 대안 비교표 필수 | 서술 흐름 안에서 자연스럽게 |
| Summary + Context & Decision + Implementation Overview | 현실진단 + 원칙 + 구현전개(구현 구조 + 동작 흐름) + 검증 |
| 결정의 독립성 | 결정 간 인과관계 필수 |
| Implementation Overview에서 흐름 서술 | Section 3 각 단계에 동작 흐름 내장 |

같은 것: 경중 구분, 중복 제거, 분량 제한, 트레이드오프 명시, 수치 근거, **"코드를 열지 않아도 구현이 보인다" 원칙**
