# 리포트 포맷 스펙

## 판정 기준

| 판정 | 의미 | 사용 시점 |
|------|------|----------|
| **PASS** | 기준 충족 | 체크리스트 항목을 완전히 만족 |
| **WARN** | 경미한 위반 또는 의도적일 수 있음 | 위반이지만 맥락상 허용 가능하거나, 확인이 필요한 경우 |
| **FAIL** | 명확한 위반 | 기준을 충족하지 않으며 수정이 필요한 경우 |
| **N/A** | 해당 없음 | 검증 대상이 없는 경우 (예: design 문서 없을 때 D7, D8) |

## 개별 축 리포트 포맷

에이전트는 아래 포맷의 마크다운 텍스트를 반환한다.

```markdown
# {축 이름} 검증 리포트
- 대상: {epic}/{feature}

## 요약
| 판정 | 개수 |
|------|-----|
| PASS | N |
| WARN | N |
| FAIL | N |
| N/A  | N |

## 상세

### [{코드}] {항목명} — {PASS|WARN|FAIL|N/A}

(PASS 또는 N/A인 경우)
(위반 없음) 또는 (해당 없음)

(WARN 또는 FAIL인 경우)
- **위치**: {파일명}:{라인번호}
- **내용**: {무엇이 잘못되었는지 — 한 문장}
- **수정 제안**: {구체적 수정 방법 — 한 문장}
```

### 작성 규칙

1. 항목 코드는 체크리스트의 ID를 사용한다 (D1, D2, ..., T1, T2, ..., R1, R2, ...)
2. FAIL/WARN 항목은 반드시 **위치**, **내용**, **수정 제안** 3개 필드를 포함한다
3. 하나의 항목에서 여러 위반이 발견되면 각각 별도의 bullet으로 나열한다
4. 위치의 파일명은 프로젝트 루트 기준 상대 경로가 아닌 **파일명만** 표기한다 (예: `OrderRequest.java:15`)
5. 수정 제안은 구체적이어야 한다 — "수정 필요" 같은 모호한 표현 금지

## 통합 요약 포맷

오케스트레이터가 3개 리포트를 종합하여 대화에 출력하고 파일로 저장한다.

```markdown
## Parallel Review: {epic}/{feature}

| 축 | FAIL | WARN | PASS | N/A | 상태 |
|----|------|------|------|-----|------|
| 문서 정합성 (D) | N | N | N | N | {상태} |
| 테스트 품질 (T) | N | N | N | N | {상태} |
| 규칙 준수 (R)   | N | N | N | N | {상태} |

### FAIL 항목
| # | 항목 | 위치 | 내용 |
|---|------|------|------|
| {코드} | {항목명} | {파일:라인} | {내용 한 줄} |

### WARN 항목
| # | 항목 | 위치 | 내용 |
|---|------|------|------|
| {코드} | {항목명} | {파일:라인} | {내용 한 줄} |

상세: .claude-work/reviews/{epic}-{feature}/ 참조
```

### 상태 결정 규칙

- FAIL이 1개 이상 → **FAIL**
- FAIL 0개, WARN 1개 이상 → **WARN**
- FAIL 0개, WARN 0개 → **PASS**

### 표시 규칙

- PASS 항목은 통합 요약에 나열하지 않는다 (상세 리포트에만 존재)
- FAIL 항목이 없으면 "### FAIL 항목" 섹션 자체를 생략한다
- WARN 항목이 없으면 "### WARN 항목" 섹션 자체를 생략한다
- 모든 축이 PASS이면 "모든 검증 항목을 통과했습니다." 한 줄만 출력한다
