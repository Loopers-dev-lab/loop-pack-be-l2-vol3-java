# Requirements Writer

원시 아이디어를 **팀 전원이 읽는 요구사항 정의서**로 변환합니다.
템플릿은 [templates/requirements-template.md](templates/requirements-template.md) 참고.

## 핵심 원칙

- 기획자, 디자이너, 프론트, 백엔드 **모두가 읽는 공통 문서**다
- 구현 세부사항(클래스명, DB 컬럼명, HTTP 상태코드)을 넣지 않는다
- 도메인 용어는 유비쿼터스 언어로 통일한다
- 모든 Use Case에 Main/Exception Flow가 있어야 한다

## 워크플로우

```
1. DISCOVER  — 도메인과 사용자 시나리오 도출
2. CLARIFY   — 비즈니스 규칙 명확화 (핵심)
3. WRITE     — 정의서 작성 + 검증
```

### 1. DISCOVER

원시 아이디어에서 도메인 경계와 사용자 시나리오를 도출합니다.

**입력**: 기획 문서, 구두 설명, 와이어프레임, 메모 등 어떤 형식이든 가능

```
시작하기:
"어떤 서비스를 만드려고 하시나요? 기획 문서, 메모, 구두 설명 어떤 형식이든 괜찮습니다."
```

도출할 것:
- Epic 단위 도메인 목록 (예: 브랜드, 상품, 주문)
- 각 도메인의 사용자 시나리오
- 도메인 간 관계

```
다음 도메인들을 도출했습니다:
1. 브랜드 & 상품 — 관리자가 브랜드/상품을 관리하고, 사용자가 탐색한다
2. 좋아요 — 사용자가 관심 상품을 모아본다
3. 주문 — 사용자가 상품을 구매한다

이대로 진행할까요?
```

### 2. CLARIFY

**이 단계가 정의서 품질을 결정합니다.** 비즈니스 규칙의 모호함을 제거합니다.

#### 도메인 관점

각 도메인에 대해:
- 핵심 엔티티는 무엇인가?
- 엔티티 간 관계는? (1:N, N:M)
- 각 엔티티의 생명주기는? (생성 → 수정 → 삭제)
- 삭제 정책은? (soft delete / hard delete / 삭제 불가)

#### 사용자 관점

각 역할(사용자, 관리자)에 대해:
- 어떤 행위를 할 수 있는가?
- 인증/인가가 필요한가?
- 다른 역할과 같은 데이터를 다르게 보는가? (예: 관리자는 삭제된 것도 조회)

#### 비즈니스 규칙 관점

각 기능에 대해:
- 유일성 제약이 있는가? (예: 브랜드명 중복 불가)
- 연쇄 동작이 있는가? (예: 브랜드 삭제 → 상품도 삭제)
- 변경 불가 필드가 있는가? (예: 상품의 소속 브랜드)
- 멱등성이 필요한가? (예: 좋아요 중복 요청)

#### 질문 방식

```
브랜드 삭제 시 하위 상품 처리를 확인해야 합니다:
A) 하위 상품도 함께 삭제 (연쇄 삭제)
B) 하위 상품이 있으면 삭제 불가 (선삭제 요구)
C) 브랜드만 삭제, 상품은 유지
```

한 번에 3개 이하로 질문. 많으면 나눠서 진행.

#### 미결 처리

- 사용자가 즉시 답할 수 없는 질문은 미결 사항 테이블에 등록하고 다음으로 진행한다
- 미결 사항이 있어도 나머지 작성은 계속한다
- 결정되면 결정/결정일 컬럼을 채우고 관련 섹션(Business Rule, Use Case Flow)을 갱신한다

### 3. WRITE

명확해진 요구사항을 [templates/requirements-template.md](templates/requirements-template.md) 형식으로 작성합니다.

#### 공통 섹션 작성 규칙

**유비쿼터스 언어**: 도메인에서 사용하는 모든 용어를 한글/영문/정의로 정리. 이후 문서 전체에서 이 용어만 사용.

**공통 용어정리**: "활성", "삭제", "미존재" 등 여러 도메인에 걸쳐 동일한 의미로 사용하는 용어 정의.

**접근 권한 정의**: 역할별 인증 방식 정리.

#### Feature List 작성 규칙

- ID는 도메인 약어 + 번호 (예: BR-01, PR-01, LK-01, OD-01)
- API 엔드포인트는 RESTful 규칙 준수
- Admin API는 `/api-admin/v1/`, User API는 `/api/v1/`

#### Use Case Flow 작성 규칙

- **Main Flow**: 정상 동작 시나리오. 번호 매기기.
- **Alternate Flow**: 정상이지만 다른 경로 (검색, 필터, 정렬 등)
- **Exception Flow**: 실패 시나리오. 에러 메시지 포함.
- **Precondition**: 선행 조건이 있으면 명시.
- 단순 CRUD도 Flow 생략하지 않는다.

#### 저장 위치

docs/requirements/{epic-name}.md
- 파일명은 영어 케밥케이스

#### 완료 전 검증

작성 완료 후 확인:
1. 모든 Feature에 Use Case Flow가 있는가?
2. 모든 Exception Flow에 에러 메시지가 있는가?
3. 도메인 간 연쇄 동작이 Business Rule에 명시되었는가?
4. 유비쿼터스 언어에 누락된 용어가 없는가?
5. 미결 사항이 있으면 목록을 사용자에게 안내하는가?

```
마무리:
"{Epic명} 요구사항 정의서가 완성되었습니다.
- Feature: {N}개 (Admin {X}개, User {Y}개)
- Business Rule: {M}개
- Use Case Flow: {K}개
- 미결 사항: {L}개

다음 도메인으로 넘어갈까요, 수정할 부분이 있나요?"
```

## 예시

사용자: "상품에 좋아요 기능을 추가하고 싶어"

DISCOVER:
```
도메인을 도출했습니다:
1. 좋아요 — 사용자가 관심 상품에 좋아요를 등록/취소하고 모아볼 수 있다

진행할까요?
```

CLARIFY:
```
좋아요에 대해 확인이 필요합니다:
1. 좋아요 취소 시: A) soft delete  B) hard delete (물리 삭제)?
2. 중복 좋아요 요청 시: A) 에러 응답  B) 멱등 처리 (현재 상태 유지)?
3. 삭제된 상품의 좋아요: A) 자동 정리  B) 조회에서만 제외?
```

WRITE → `docs/requirements/like.md` 생성

## 트러블슈팅

### 도메인 경계가 불명확한 경우
- "이 기능을 다른 팀이 독립적으로 개발할 수 있는가?"로 판단
- 불명확하면 하나의 Epic으로 묶고 나중에 분리

### 기존 요구사항 정의서에 도메인을 추가하는 경우
- 기존 공통 섹션(유비쿼터스 언어 등)에 신규 항목 추가
- 신규 도메인 섹션을 문서 하단에 추가

### Business Rule이 너무 많은 경우
- 도메인별로 테이블 분리
- 여러 도메인에 걸치는 규칙은 "공통" 섹션에 배치
