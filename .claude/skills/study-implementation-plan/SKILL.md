  개념 이해 → 테스트 전후 비교 → 실무 사례 참고 → 깊이 있는 고민 포인트를 포함하는 가이드 문서를 생성한다.
  학습 주제와 구현 목표가 주어졌을 때, 코드 작성 전에 학습 로드맵을 세우는 데 사용한다.
---

학습 + 구현 계획을 수립할 때 반드시 다음 흐름을 따른다.

### 1️⃣ 개발자의 현재 수준을 파악한다
- 해당 기술/패턴에 대한 사전 지식 수준을 확인한다 (초보 / 개념만 있음 / 실무 경험 있음).
- 코드베이스에서 이미 해당 기술을 사용하는 곳이 있는지 탐색한다.
- 기존 코드를 **학습 참조점(anchor)**으로 활용해, 새로운 개념을 익숙한 것에 연결한다.

### 2️⃣ Phase 0: 개념 학습 단계를 설계한다
구현에 앞서 반드시 개념을 먼저 이해하는 단계를 둔다.
각 학습 주제에 대해 다음을 포함한다:
- **학습 목표** — 체크리스트 형태로 구체적으로
- **코드베이스 참조점** — 이미 있는 유사 패턴, 파일 경로와 함께
- **깊이 있는 고민 질문 3~5개** — 코드를 복사해서는 답할 수 없는, 이해를 강제하는 질문
- **실무 사례 검색 키워드** — 한국 IT 기업(우아한형제들, 토스, 카카오, 라인, 컬리, 29CM 등)의 기술 블로그 검색 방향
- 이 단계에서는 **구현 없이 순수 이해**에 집중

### 3️⃣ 구현 Phase를 테스트 중심으로 설계한다
각 구현 Phase에 다음 구조를 적용한다:
- **현재 상태** — 코드가 지금 어떻게 동작하는지 (코드 스니펫/흐름도)
- **목표 상태** — 변경 후 어떻게 동작해야 하는지 (흐름도)
- **구현 태스크** — 체크리스트 형태, 의존 순서대로
- **테스트 계획** — 전후 비교 테스트를 반드시 포함:
  - 동기→비동기 전환 시 흐름/응답 차이 확인
  - 정상 동작 통합 테스트
  - 장애/실패 시나리오 테스트 (메시지 유실, 순서 보장, 크래시 복구 등)

### 4️⃣ "개념 샌드위치" 패턴을 적용한다
```
개념 이해 → 구현 → 고민/회고 → 다음 개념
```
- 각 Phase 끝에 **고민 포인트**를 배치하여, 현재 구현의 한계가 다음 Phase의 동기가 되도록 연결한다.
- 예: "ApplicationEvent만으로는 앱 크래시 시 이벤트 유실이 가능하다 → 그래서 Outbox Pattern이 필요하다"

### 5️⃣ 테스트 코드는 실행 가능한 스펙으로 포함한다
- 테스트 패턴(AAA: Arrange-Act-Assert)에 맞는 **테스트 구조 스니펫**을 제시한다.
- 구현 코드는 구조(클래스명, 패키지, 책임)만 기술하되, 테스트를 통해 "무엇을 만들어야 하는지"를 명확히 한다.
- TDD Red Phase에서 개발자가 직접 구현을 생각하게 유도한다.

### 6️⃣ 실무 사례 참고 방향을 제시한다
각 주제별로 다음을 포함한다:
- 구체적인 블로그/발표 검색 키워드 (한국 IT 기업 중심)
- 해당 기업이 겪은 문제와 해결 방향에 대한 학습 포인트
- 종합 키워드 표를 문서 마지막에 배치

### 7️⃣ 파일 구조 요약으로 마무리한다
- 모든 신규 파일을 모듈/Phase별로 정리한 트리 구조를 제공한다.
- 개발자가 전체 구현 범위를 한눈에 파악할 수 있게 한다.

## 원칙

| 원칙 | 설명 |
|------|------|
| **개념 우선** | 모르는 상태로 구현에 들어가지 않는다. 구현하면서 익힐 것은 구현 단계에서. |
| **테스트 전후 비교** | 적용 전/후의 차이를 테스트로 눈에 보이게 확인한다 |
| **실무 기반** | 이론만이 아닌 실제 기업의 도입/운영 사례를 참고한다 |
| **깊이 있는 고민** | "왜?"를 반복해서 표면적 이해를 넘어서게 한다 |
| **점진적 자신감** | 각 Phase가 이전 Phase 위에 쌓이며, 이전 테스트는 항상 통과해야 한다 |

- 클로드 코드와 함께 단계별로 진행할 수 있는 가이드 역할
