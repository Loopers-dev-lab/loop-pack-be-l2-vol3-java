name: create-pr
description:
  현재 브랜치의 전체 커밋 이력을 분석하고, PR 템플릿에 맞춰 본문을 자동 생성한 뒤,
  remote push와 PR 생성까지 수행합니다. 실행 전 사용자 확인을 거칩니다.
---
PR을 생성할 때 반드시 다음 흐름을 따른다.

### 1️⃣ 브랜치 상태를 확인한다
- 현재 브랜치명을 확인한다.
- base branch를 결정한다 (기본값: `main`).
- `git status`로 미커밋 변경이 있는지 확인한다.
  - 미커밋 변경이 있으면 사용자에게 알리고, 먼저 커밋할지 물어본다.
- remote 추적 여부를 확인한다 (`git branch -vv`).

> **근거**: PR은 커밋된 변경만 포함하므로, 미커밋 변경이 누락되는 상황을 사전에 방지한다. base branch를 명시적으로 확인해야 올바른 diff를 분석할 수 있다.

### 2️⃣ 전체 커밋 이력을 분석한다
- `git log {base}..HEAD --oneline`으로 브랜치의 모든 커밋을 확인한다.
- `git diff {base}...HEAD`로 전체 변경 내용을 확인한다.
- `git diff {base}...HEAD --stat`로 변경된 파일 목록과 규모를 파악한다.
- **최신 커밋만이 아니라, base branch 이후의 모든 커밋을 분석 대상으로 한다.**

> **근거**: PR은 브랜치의 전체 작업 단위를 설명하는 문서다. 최신 커밋만 보면 전체 맥락이 누락되어 리뷰어가 변경의 목적을 파악하기 어렵다.

### 3️⃣ PR 본문을 생성한다
- `.github/pull_request_template.md`의 구조를 그대로 따라 작성한다:

#### 📌 Summary
- 커밋 이력과 변경 내용에서 다음을 도출한다:
  - **배경**: 이 변경이 필요한 이유 (어떤 문제/요구사항이 있었는지)
  - **목표**: 이 PR이 달성하려는 것
  - **결과**: 이 PR이 완료되면 어떻게 달라지는지

#### 🧭 Context & Decision
- **문제 정의**: 변경 전 상태의 제약이나 문제점
- **선택지와 결정**: 코드에서 드러나는 설계 결정과 그 이유
- **트레이드오프**: 선택한 접근법의 장단점

#### 🏗️ Design Overview
- **변경 범위**: 영향받는 모듈/도메인 나열
- **신규 추가**: 새로 생성된 파일/클래스
- **제거/대체**: 삭제되거나 대체된 항목
- **주요 컴포넌트 책임**: 변경된 주요 컴포넌트와 각각의 역할

#### 🔁 Flow Diagram
- 주요 흐름이 있는 경우 Mermaid 시퀀스 다이어그램으로 작성한다.
- 단순 문서 수정이나 설정 변경처럼 흐름이 없는 경우는 생략한다.

> **근거**: 기존 `.github/pull_request_template.md`와 동일한 구조를 사용해야 리뷰어가 익숙한 포맷으로 읽을 수 있다. 템플릿을 무시하고 새 형식을 만들면 팀 내 일관성이 깨진다.

### 4️⃣ PR 제목을 생성한다
- 70자 이내로 핵심 변경을 요약한다.
- 커밋 prefix 패턴을 참고하되, PR 제목은 대괄호 태그 형식을 사용할 수 있다.
  - 예: `[volume-2] 인증 기능 구현`

> **근거**: GitHub PR 목록에서 제목이 잘리지 않는 길이를 유지한다. 상세 내용은 본문에서 다룬다.

### 5️⃣ 사용자에게 확인을 받는다
- 다음 항목을 사용자에게 보여주고 확인을 받는다:
  - PR 제목
  - PR 본문 전체
  - base branch
  - push 대상 remote/branch
- 사용자가 수정을 요청하면 해당 부분을 반영한 뒤 다시 확인을 받는다.

> **근거**: PR은 팀원에게 공개되는 공유 작업이다. 자동 생성된 내용을 사용자가 반드시 검토해야 의도하지 않은 정보 노출이나 부정확한 설명을 방지할 수 있다.

### 6️⃣ Push하고 PR을 생성한다
- remote에 push한다:
  ```bash
  git push -u origin {현재_브랜치}
  ```
- `gh` CLI로 PR을 생성한다:
  ```bash
  gh pr create --base {base_branch} --title "{제목}" --body "$(cat <<'EOF'
  {본문}
  EOF
  )"
  ```
- 생성된 PR URL을 사용자에게 반환한다.

> **근거**: `gh` CLI를 사용하면 브라우저 없이 터미널에서 PR 생성이 완결된다. HEREDOC으로 본문의 멀티라인 포맷팅을 안정적으로 보존한다.

### 톤 & 스타일 가이드
- PR 본문은 리뷰어가 읽는 공식 문서이므로, 정중하고 명확한 톤으로 작성한다
- "왜 이렇게 했는가"를 중심으로 설명하며, 단순 변경 나열을 지양한다
- PR 본문 하단에 자동 생성 표시를 포함한다:
  ```
  🤖 Generated with [Claude Code](https://claude.com/claude-code)
  ```
