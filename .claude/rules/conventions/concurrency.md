# 동시성 제어

## 핵심 원칙

**Lock 시간을 최소화하여 처리량을 최대화한다.**

## 전략 선택 가이드

| 전략 | 언제 사용 | 특징 |
|------|----------|------|
| **Fail-Fast + Atomic Operation** | 단일 필드 변경, 카운터 증감, 상태 플래그 전환 | Lock 없이 DB 원자적 연산으로 해결. 처리량 최대 |
| **비관적 락 (Pessimistic Lock)** | 조회 → 검증 → 수정이 한 트랜잭션 안에서 반드시 순차 실행되어야 할 때 | 확실하지만 처리량 감소 |
| **낙관적 락 (Optimistic Lock)** | 충돌 빈도가 낮고 재시도가 가능한 경우 | 처리량 높지만 충돌 시 재시도 비용 |

### 비관적 락 + 낙관적 락 공존 시

- 같은 Entity에 두 락이 공존하면 낙관적 락이 무력화될 수 있다 (비관적 락이 version을 항상 갱신)
- 한 Entity에는 하나의 전략을 택하되, 유스케이스별로 다른 Entity에 다른 전략 적용은 가능

## Fail-Fast + Atomic Operation

Lock 없이 `@Modifying` 쿼리의 WHERE 조건으로 비즈니스 규칙을 검증하고, 영향받은 행 수(int)로 성공/실패를 판단한다.

### 전제 조건

1. **Entity 불변식 분리**: Entity의 상태 변경 메서드에 있던 도메인 불변식이 `{Domain}.validateXxx()` 형태의 검증 메서드로 분리되어야 한다
2. **쿼리 안에 비즈니스 로직 포함**: Atomic Operation 쿼리의 WHERE 조건에 비즈니스 규칙이 포함되어야 한다

### 가능한 것 vs 불가능한 것

| 쿼리로 가능 | 쿼리로 불가능 |
|-------------|-------------|
| 단순 비교 (`quantity >= :requested`) | 복잡한 비즈니스 규칙 (여러 필드 조합 판단) |
| 상태 전환 (`status = 'REQUESTED'`) | 다른 Entity 참조가 필요한 검증 |
| null 체크 (`used_at IS NULL`) | 외부 호출이 필요한 검증 |

### JPQL flush 시점 주의

`@Modifying` 쿼리 실행 전에 영속성 컨텍스트가 자동 flush된다. 같은 트랜잭션에서 Entity를 변경한 후 `@Modifying` 쿼리를 실행하면 의도치 않은 UPDATE 쿼리가 먼저 발생할 수 있다.

### 에러 메시지 한계

Atomic Operation은 실패 원인을 구체적으로 알 수 없다. 에러 메시지는 다음 형식으로 제공한다:

```
일반적인 메시지 + 어떤 데이터가 실패했는지 + xxxId
```

예: `"재고 차감에 실패했습니다. productId=123"`

## 연산 순서 원칙

여러 자원에 대한 동시성 제어가 필요할 때, **경합이 가장 높은 연산을 가장 마지막에 배치**하여 Lock 점유 시간을 최소화한다.

- 해당 유저의 개인 데이터 (경합 낮음) → **먼저 처리**
- 공유 자원 (경합 높음) → **가장 마지막에 처리**

예: 쿠폰 사용(개인 데이터, 경합 낮음) → 주문 생성 → 재고 차감(공유 자원, 경합 높음)

## 멱등성 보장

동일 요청이 여러 번 실행되어도 결과가 같아야 하는 연산:

- 상태 확인 → 조건부 변경 패턴 사용
- boolean 반환으로 실제 변경 여부를 호출자에게 알린다
- 이미 처리된 경우 예외를 던지지 않고 조용히 종료한다
