# 1. 브랜드 (Brand)

## 1.1 목적 및 범위

### 목적
감성 이커머스 시스템에서 상품을 그룹핑하고 관리하기 위한 브랜드 기능을 제공한다.

### 범위
- 어드민의 브랜드 등록, 조회, 수정, 삭제 기능
- 고객의 브랜드 조회 기능 (비로그인 가능)
- 브랜드와 상품 간의 관계 관리

### API 범위
- 어드민 API: `/api-admin/v1/brands`
- 고객 API: `/api/v1/brands/{brandId}`

### DB 범위
- `brands` 테이블
- Soft Delete 방식 (`deleted_at` 컬럼)

## 1.2 유저 시나리오

### 시나리오 1: 브랜드 등록
**액터:** 어드민  
**목표:** 새로운 브랜드와 계약을 맺었을 때 시스템에 브랜드를 등록한다.

**전제 조건:**
- 어드민 권한이 있어야 함 (`X-Loopers-Ldap: loopers.admin`)

**정상 흐름:**
1. 어드민이 브랜드 등록 화면에 접근한다.
2. 브랜드명, 설명, 로고 URL을 입력한다.
3. "등록" 버튼을 클릭한다.
4. 시스템은 브랜드를 생성하고 성공 메시지를 반환한다.

**예외 흐름:**
- 브랜드명이 중복되면 → "이미 존재하는 브랜드명입니다." 에러 반환
- 브랜드명이 비어있으면 → "브랜드명은 필수입니다." 에러 반환

**도출된 행위:**
- `POST /api-admin/v1/brands` - 브랜드 등록

## 1.3 비즈니스 규칙

### 도메인 모델

**Brand (브랜드)**
- 상품을 제조하거나 판매하는 회사/제조사
- 이커머스 시스템에서 상품을 그룹핑하는 단위
- 예: 샤넬, 구찌, 메종마르지엘라

**생명주기:**
1. Register (등록): 어드민이 새로운 브랜드를 시스템에 추가
2. Active (활성): 고객에게 노출되고 상품을 가질 수 있는 상태
3. Update (수정): 브랜드 정보 변경
4. Delete (삭제): 브랜드와 계약 종료 시 시스템에서 제거 (Soft Delete)

**상태:**
- Active (활성): `deleted_at == null` - 조회 가능, 상품 등록 가능
- Deleted (삭제됨): `deleted_at != null` - 조회 불가, 상품 등록 불가

**책임:**
- 브랜드 정보 관리 (이름, 설명, 로고)
- 소속 상품들의 그룹핑
- 브랜드 삭제 시 소속 상품들도 함께 삭제 (Cascade)

### 제약 조건 (Invariants)

1. **브랜드명 고유성**
   - 브랜드명은 시스템 내에서 고유해야 한다.
   - 대소문자를 구분하지 않는다. (예: "Chanel"과 "chanel"은 중복)
   - 검증 시점: 브랜드 등록, 브랜드 수정

2. **브랜드명 길이 및 형식**
   - 최소 1자, 최대 100자
   - 빈 문자열 불가
   - 입력 시 앞뒤 공백 자동 제거 (trim)
   - 공백만으로 구성된 문자열 불가 (trim 후 빈 문자열 검증)
   - 예: `"   "` → trim → `""` → 에러 반환
   - 예: `" Chanel "` → trim → `"Chanel"` → 정상 처리

3. **설명 길이**
   - 최대 1000자 (선택 사항)
   - null 허용

4. **로고 URL 길이**
   - 최대 500자 (선택 사항)
   - null 허용

5. **삭제된 브랜드 접근 제한**
   - 삭제된 브랜드는 조회, 수정, 삭제 불가
   - `deleted_at IS NULL`인 브랜드만 활성 상태로 간주

6. **생성일시 불변성**
   - 생성일시는 한 번 설정되면 변경할 수 없음

7. **수정일시 자동 갱신**
   - 브랜드 정보 수정 시 자동으로 현재 시각으로 갱신

### 판단 기준 (Business Logic)

1. **브랜드 활성 여부 판단**
   ```
   활성 브랜드 = deleted_at IS NULL
   삭제된 브랜드 = deleted_at IS NOT NULL
   ```

2. **브랜드명 중복 검증**
   ```sql
   중복 여부 = SELECT COUNT(*) FROM brands 
               WHERE LOWER(name) = LOWER(입력된_브랜드명)
               AND deleted_at IS NULL
               AND id != 현재_브랜드_id (수정 시)
   ```

3. **Cascade 삭제 정책**
   ```
   브랜드 삭제 트랜잭션:
   BEGIN TRANSACTION
     1. 브랜드 조회 (활성 브랜드만)
     2. 브랜드의 deleted_at = NOW() 설정
     3. 해당 브랜드의 모든 상품 deleted_at = NOW() 설정
   COMMIT
   ```

4. **부분 수정 (Partial Update) 정책**
   - 제공된 필드만 수정
   - null 값이 전달되면 해당 필드는 수정하지 않음
   - 예: 브랜드명만 수정하고 설명은 그대로 유지

### 검증 순서

**브랜드 등록 시:**
1. 필수 필드 검증 (브랜드명)
2. 길이 검증 (브랜드명, 설명, 로고 URL)
3. 중복 검증 (브랜드명)

**브랜드 수정 시:**
1. 브랜드 존재 여부 확인
2. 브랜드 활성 상태 확인
3. 제공된 필드에 대해 길이 검증
4. 브랜드명 변경 시 중복 검증

**브랜드 삭제 시:**
1. 브랜드 존재 여부 확인
2. 브랜드 활성 상태 확인
3. Cascade 삭제 대상 상품 조회
4. 트랜잭션으로 브랜드 및 상품 삭제

## 1.4 예외 및 정책

### 에러 처리

| 상황 | HTTP Status | Error Code | Error Message |
|------|-------------|------------|---------------|
| 브랜드명 누락 | 400 | BAD_REQUEST | "브랜드명은 필수입니다." |
| 브랜드명 길이 초과 | 400 | BAD_REQUEST | "브랜드명은 100자를 초과할 수 없습니다." |
| 브랜드명 중복 | 409 | CONFLICT | "이미 존재하는 브랜드명입니다." |
| 설명 길이 초과 | 400 | BAD_REQUEST | "설명은 1000자를 초과할 수 없습니다." |
| 로고 URL 길이 초과 | 400 | BAD_REQUEST | "로고 URL은 500자를 초과할 수 없습니다." |
| 브랜드 없음 | 404 | NOT_FOUND | "브랜드를 찾을 수 없습니다." |
| 삭제된 브랜드 접근 | 404 | NOT_FOUND | "브랜드를 찾을 수 없습니다." |
| 페이지 크기 초과 | 400 | BAD_REQUEST | "페이지 크기는 100을 초과할 수 없습니다." |

### 데이터 정책

1. **Soft Delete 정책**
   - 브랜드 삭제 시 물리적 삭제가 아닌 논리적 삭제
   - `deleted_at` 컬럼에 삭제 시각 기록
   - 데이터 복구 가능성 확보
   - 삭제된 데이터는 조회 쿼리에서 자동 제외 (`WHERE deleted_at IS NULL`)

2. **Cascade 정책**
   - 브랜드 삭제 시 연관된 모든 상품도 함께 Soft Delete
   - Application Level에서 처리 (DB Cascade 아님)
   - 트랜잭션으로 원자성 보장
   - 이유: Soft Delete는 UPDATE 쿼리이므로 DB Cascade가 동작하지 않음
   - 상품 삭제 시 연관된 좋아요도 함께 Hard Delete (Application Level)

3. **페이지네이션 정책**
   - 기본 페이지 크기: 20
   - 최대 페이지 크기: 100
   - 정렬: 최신순 (created_at DESC)
   - 페이지 번호는 0부터 시작

4. **인증 및 권한 정책**
   - 어드민 API: `X-Loopers-Ldap: loopers.admin` 헤더 필수
   - 고객 API: 인증 불필요 (브랜드 조회만 가능)

5. **API 응답 형식**
   - 모든 API는 `ApiResponse<T>` 래퍼 사용
   - 성공: `metadata.result = "SUCCESS"`
   - 실패: `metadata.result = "FAIL"`, `metadata.errorCode`, `metadata.message`

### 성능 최적화

1. **인덱스 전략**
   - `name` 컬럼: 중복 검증 및 검색 성능 향상
   - `created_at` 컬럼: 정렬 성능 향상
   - `deleted_at` 컬럼: 활성 브랜드 필터링 성능 향상

2. **쿼리 최적화**
   - 활성 브랜드 조회 시 `deleted_at IS NULL` 조건 필수
   - 브랜드명 중복 검증 시 대소문자 구분 없이 비교 (`LOWER()` 함수 사용)

## 2.2 유저 시나리오

### 시나리오 1: 상품 등록

**전제 조건:**
- 어드민 권한이 있어야 함
- 등록할 브랜드가 활성 상태여야 함

**정상 흐름:**
1. 어드민이 상품 등록 화면에 접근한다.
2. 브랜드를 선택한다.
3. 상품명, 가격, 재고, 설명, 이미지 URL을 입력한다.
4. "등록" 버튼을 클릭한다.
5. 시스템은 상품을 생성하고 성공 메시지를 반환한다.

**예외 흐름:**
- 브랜드가 존재하지 않으면 → "브랜드를 찾을 수 없습니다." 에러 반환
- 브랜드가 삭제되었으면 → "삭제된 브랜드에는 상품을 등록할 수 없습니다." 에러 반환

## 2.3 비즈니스 규칙

### 도메인 모델

**Product (상품)**
- 고객이 구매할 수 있는 판매 아이템
- 반드시 하나의 브랜드에 속함
- 가격, 재고, 좋아요 수 등의 정보를 가짐

**생명주기:**
1. Register (등록): 어드민이 특정 브랜드에 상품을 추가
2. On Sale (판매 중): 재고가 있고 고객에게 노출되는 상태
3. Out of Stock (품절): 재고가 0인 상태 (조회는 가능, 주문 불가)
4. Update (수정): 상품 정보 변경 (가격, 재고, 설명 등)
5. Delete (삭제): 시스템에서 제거 (Soft Delete)

**상태:**
- Active (활성): `deleted_at == null` - 조회 가능, 주문 가능 (재고 있을 때)
- Deleted (삭제됨): `deleted_at != null` - 조회 불가, 주문 불가

**책임:**
- 상품 정보 관리 (이름, 설명, 가격, 재고, 이미지)
- 재고 관리 (재고 확인, 재고 차감)
- 좋아요 수 관리 (좋아요 증가/감소)
- 브랜드 소속 관계 유지

**브랜드와 상품의 관계:**
- 1:N 관계 (하나의 브랜드는 여러 상품을 가질 수 있음)
- 강한 참조 (상품은 반드시 브랜드에 속해야 함)
- 생명주기 공유 (브랜드가 삭제되면 상품도 함께 삭제됨)
- 불변 관계 (상품의 브랜드는 생성 후 변경할 수 없음)

### 제약 조건 (Invariants)

1. **브랜드 필수성**
   - 상품은 반드시 유효한 브랜드에 속해야 함
   - 브랜드가 삭제되면 상품도 함께 삭제됨

2. **브랜드 불변성**
   - 상품의 브랜드는 생성 후 변경할 수 없음
   - 잘못 등록 시 삭제 후 재등록 필요

3. **상품명 길이**
   - 최소 1자, 최대 200자
   - 빈 문자열 불가

4. **가격 제약**
   - 가격은 0보다 커야 함
   - BigDecimal 타입 사용 (정확한 금액 계산)

5. **재고 제약**
   - 재고는 0 이상이어야 함
   - 음수 불가

6. **좋아요 수 제약**
   - 좋아요 수는 0 이상이어야 함
   - 비정규화된 값으로 관리

7. **삭제된 상품 접근 제한**
   - 삭제된 상품은 조회, 수정, 삭제 불가
   - `deleted_at IS NULL`인 상품만 활성 상태로 간주

### 판단 기준 (Business Logic)

1. **상품 활성 여부 판단**
   ```
   활성 상품 = deleted_at IS NULL
   삭제된 상품 = deleted_at IS NOT NULL
   ```

2. **재고 충분 여부 판단**
   ```
   재고 충분 = stock >= 주문_수량
   재고 부족 = stock < 주문_수량
   ```

3. **판매 가능 여부 판단**
   ```
   판매 가능 = deleted_at IS NULL AND stock > 0
   품절 = deleted_at IS NULL AND stock == 0
   판매 불가 = deleted_at IS NOT NULL
   ```

4. **재고 차감 로직**
   ```
   재고 차감:
   1. 현재 재고 확인
   2. 재고 충분 여부 검증
   3. stock = stock - 주문_수량
   4. 트랜잭션으로 원자성 보장
   ```

5. **좋아요 수 증감 로직**
   ```
   좋아요 등록: likesCount = likesCount + 1
   좋아요 취소: likesCount = MAX(0, likesCount - 1)
   
   Note: DB 레벨에서도 CHECK 제약으로 음수 방지
   ```

6. **브랜드 삭제 시 Cascade**
   ```
   브랜드 삭제 시:
   1. 브랜드의 deleted_at 설정
   2. 해당 브랜드의 모든 상품 deleted_at 설정
   3. 하나의 트랜잭션에서 처리
   ```

### 검증 순서

**상품 등록 시:**
1. 브랜드 존재 여부 확인
2. 브랜드 활성 상태 확인
3. 필수 필드 검증 (상품명, 가격, 재고)
4. 길이 검증 (상품명, 설명, 이미지 URL)
5. 가격 범위 검증 (> 0)
6. 재고 범위 검증 (>= 0)

**상품 수정 시:**
1. 상품 존재 여부 확인
2. 상품 활성 상태 확인
3. 제공된 필드에 대해 길이 검증
4. 가격 변경 시 범위 검증
5. 재고 변경 시 범위 검증
6. 브랜드 ID 변경 시도 시 무시

**상품 삭제 시:**
1. 상품 존재 여부 확인
2. 상품 활성 상태 확인

### 데이터 정책

1. **Soft Delete 정책**
   - 상품 삭제 시 물리적 삭제가 아닌 논리적 삭제
   - `deleted_at` 컬럼에 삭제 시각 기록
   - 주문 스냅샷과의 일관성 유지

2. **Cascade 정책**
   - 브랜드 삭제 시 연관된 모든 상품도 함께 Soft Delete
   - Application Level에서 처리
   - 트랜잭션으로 원자성 보장

3. **브랜드 불변 정책**
   - 상품의 브랜드는 생성 후 변경 불가
   - 브랜드 ID 변경 시도 시 에러 반환 (BAD_REQUEST)

4. **가격 정확성 정책**
   - BigDecimal 타입 사용
   - 소수점 이하 2자리까지 지원
   - 반올림 정책: HALF_UP

5. **좋아요 수 비정규화 정책**
   - 성능을 위해 Product 테이블에 저장
   - 좋아요 등록/취소 시 자동 증감
   - 동시성 이슈는 Phase 5에서 해결

6. **페이지네이션 정책**
   - 기본 페이지 크기: 20
   - 최대 페이지 크기: 100
   - 정렬 옵션:
     - `latest`: 최신순 (created_at DESC)
     - `price_asc`: 가격 낮은 순 (price ASC)
     - `likes_desc`: 좋아요 많은 순 (likes_count DESC)

7. **인증 및 권한 정책**
   - 어드민 API: `X-Loopers-Ldap: loopers.admin` 헤더 필수
   - 고객 API: 인증 불필요 (상품 조회만 가능)

### 성능 최적화

1. **인덱스 전략**
   - `brand_id` 컬럼: 브랜드별 상품 필터링
   - `created_at` 컬럼: 최신순 정렬

# 3. 좋아요 (Product Like)

## 3.1 목적 및 범위

### 목적
고객이 마음에 드는 상품을 표시하고 관리할 수 있는 좋아요 기능을 제공한다.

### 범위
- 고객의 좋아요 등록, 취소 기능
- 고객의 좋아요한 상품 목록 조회 기능
- 상품의 좋아요 수 관리

### API 범위
- 고객 API: `/api/v1/products/{productId}/likes`, `/api/v1/users/me/likes`

### DB 범위
- `product_likes` 테이블
- Hard Delete 방식 (물리적 삭제)
- User, Product와 외래 키 관계

## 3.2 유저 시나리오

### 시나리오 1: 좋아요 등록
**액터:** 고객 (인증 필요)  
**목표:** 마음에 드는 상품에 좋아요를 누른다.

**전제 조건:**
- 로그인 상태여야 함 (`X-Loopers-LoginId`, `X-Loopers-LoginPw`)
- 상품이 활성 상태여야 함

**정상 흐름:**
1. 고객이 상품 상세 페이지에서 "좋아요" 버튼을 클릭한다.
2. 시스템은 좋아요를 등록한다.
3. 상품의 좋아요 수를 1 증가시킨다.

## 3.3 비즈니스 규칙

### 도메인 모델

**Product Like (상품 좋아요)**
- 고객이 특정 상품에 대해 관심을 표시하는 행위
- 고객과 상품 간의 다대다(N:M) 관계
- 한 고객은 여러 상품에 좋아요를 누를 수 있음
- 한 상품은 여러 고객으로부터 좋아요를 받을 수 있음

**생명주기:**
1. Register (등록): 고객이 상품에 좋아요를 누름
2. Active (활성): 좋아요가 유지되는 상태
3. Cancel (취소): 고객이 좋아요를 취소함 (Hard Delete)

**책임:**
- 고객-상품 간 좋아요 관계 관리
- 중복 좋아요 방지 (한 고객은 한 상품에 한 번만 좋아요 가능)
- 좋아요 등록 시 상품의 좋아요 수 증가
- 좋아요 취소 시 상품의 좋아요 수 감소

**관계:**
- User ↔ Product (N:M): ProductLike 테이블이 중간 테이블 역할
- ProductLike → Product (N:1): 좋아요는 반드시 하나의 상품에 속함
- ProductLike → User (N:1): 좋아요는 반드시 하나의 고객에 속함
- ProductLike ↔ Likes Count (비정규화): 좋아요 등록/취소 시 상품의 likesCount 증감

### 제약 조건 (Invariants)

1. **좋아요 유일성**
   - 한 고객은 한 상품에 한 번만 좋아요 가능
   - `(user_id, product_id)` 복합 유니크 제약

2. **상품 필수성**
   - 좋아요는 반드시 유효한 상품에 속해야 함
   - 상품이 삭제되면 관련 좋아요도 함께 삭제 (Cascade)

3. **고객 필수성**
   - 좋아요는 반드시 유효한 고객에 속해야 함
   - 고객이 탈퇴하면 관련 좋아요도 함께 삭제 (Cascade)

4. **삭제된 상품 좋아요 불가**
   - 삭제된 상품에는 좋아요를 등록할 수 없음

5. **좋아요 수 동기화**
   - 좋아요 등록 시 상품의 likesCount 증가
   - 좋아요 취소 시 상품의 likesCount 감소

### 판단 기준 (Business Logic)

1. **좋아요 중복 여부 판단**
   ```sql
   중복 여부 = SELECT COUNT(*) FROM product_likes
               WHERE user_id = 고객_ID
               AND product_id = 상품_ID
   ```

2. **좋아요 등록 트랜잭션**
   ```
   BEGIN TRANSACTION
     1. 상품 조회 (활성 상품만)
     2. 좋아요 중복 확인
     3. 좋아요 등록
     4. 상품 likesCount 증가 (likesCount = likesCount + 1)
   COMMIT
   ```

3. **좋아요 취소 트랜잭션**
   ```
   BEGIN TRANSACTION
     1. 상품 조회 (활성 상품만)
     2. 좋아요 존재 확인
     3. 좋아요 삭제 (Hard Delete)
     4. 상품 likesCount 감소 (likesCount = MAX(0, likesCount - 1))
   COMMIT
   
   Note: 삭제된 상품의 좋아요는 취소할 수 없음
   Note: likesCount 음수 방지를 위해 MAX 함수 사용
   ```

4. **Cascade 삭제 정책**
   ```
   상품 삭제 시: 관련 좋아요도 함께 삭제 (DB Cascade)
   고객 탈퇴 시: 관련 좋아요도 함께 삭제 (DB Cascade)
   ```

### 검증 순서

**좋아요 등록 시:**
1. 상품 존재 여부 확인
2. 상품 활성 상태 확인
3. 좋아요 중복 확인

**좋아요 취소 시:**
1. 상품 존재 여부 확인
2. 상품 활성 상태 확인 (삭제된 상품의 좋아요는 취소 불가)
3. 좋아요 존재 확인

**좋아요한 상품 목록 조회 시:**
1. 활성 상품만 필터링 (deleted_at IS NULL)
2. 최신 좋아요 순 정렬 (created_at DESC)

## 3.4 예외 및 정책

### 에러 처리

| 상황 | HTTP Status | Error Code | Error Message |
|------|-------------|------------|---------------|
| 상품 없음 | 404 | NOT_FOUND | "상품을 찾을 수 없습니다." |
| 삭제된 상품에 좋아요 | 400 | BAD_REQUEST | "삭제된 상품에는 좋아요할 수 없습니다." |
| 삭제된 상품 좋아요 취소 | 400 | BAD_REQUEST | "삭제된 상품에는 좋아요를 취소할 수 없습니다." |
| 이미 좋아요한 상품 | 409 | CONFLICT | "이미 좋아요한 상품입니다." |
| 좋아요 없음 | 404 | NOT_FOUND | "좋아요를 찾을 수 없습니다." |
| 페이지 크기 초과 | 400 | BAD_REQUEST | "페이지 크기는 100을 초과할 수 없습니다." |

### 데이터 정책

1. **Hard Delete 정책**
   - 좋아요 취소 시 물리적 삭제
   - 복구 불필요 (재등록 가능)
   - Soft Delete 불필요

2. **Cascade 정책**
   - 상품 삭제 시 관련 좋아요도 함께 삭제 (Application Level Cascade)
   - 이유: Soft Delete는 UPDATE 쿼리이므로 DB Cascade가 동작하지 않음
   - 브랜드 삭제 → 상품 Soft Delete → 좋아요도 Application Level에서 Hard Delete 처리
   - 고객 탈퇴 시 관련 좋아요도 함께 삭제 (DB Cascade)

3. **좋아요 수 비정규화 정책**
   - 성능을 위해 Product 테이블에 likesCount 저장
   - 좋아요 등록/취소 시 자동 증감
   - 트랜잭션으로 일관성 보장
   - likesCount 음수 방지: `likesCount = MAX(0, likesCount - 1)`
   - DB 레벨 체크 제약: `CHECK (likes_count >= 0)`
   - 동시성 이슈는 Phase 5에서 해결

4. **페이지네이션 정책**
   - 기본 페이지 크기: 20
   - 최대 페이지 크기: 100
   - 정렬: 최신 좋아요 순 (created_at DESC)

5. **인증 및 권한 정책**
   - 모든 좋아요 API는 인증 필수
   - 헤더: `X-Loopers-LoginId`, `X-Loopers-LoginPw`
   - 고객은 자신의 좋아요만 관리 가능

### 성능 최적화

1. **인덱스 전략**
   - `(user_id, product_id)` 복합 유니크 인덱스: 중복 방지 및 조회 성능
   - `user_id` 인덱스: 고객별 좋아요 목록 조회
   - `product_id` 인덱스: 상품별 좋아요 수 계산
   - `created_at` 인덱스: 최신순 정렬

2. **쿼리 최적화**
   - 좋아요한 상품 목록 조회 시 JOIN 사용
   - 활성 상품만 필터링 (`deleted_at IS NULL`)

**Order (주문)**
- 고객이 여러 상품을 한 번에 구매하는 행위
- 주문 시점의 상품 정보를 스냅샷으로 저장
- 여러 개의 주문 상품(OrderItem)으로 구성됨

**생명주기:**
1. Create (생성): 고객이 주문을 요청
2. Completed (완료): 주문이 성공적으로 처리됨
3. Failed (실패): 재고 부족 등으로 주문 실패 (현재는 미구현)

**책임:**
- 주문 정보 관리 (주문자, 주문 상품, 총 금액)
- 주문 시점의 상품 정보 스냅샷 저장
- 재고 차감 처리
- 총 주문 금액 계산

**Order Item (주문 상품)**
- 주문에 포함된 개별 상품 정보
- 주문 시점의 상품 정보를 스냅샷으로 저장
- 상품 ID, 상품명, 가격, 수량 등을 포함

**책임:**
- 주문 시점의 상품 정보 보존
- 상품별 주문 수량 관리
- 상품별 금액 계산 (가격 × 수량)

**Snapshot (스냅샷)**
- 주문 시점의 상품 정보를 그대로 저장하는 패턴
- 상품 가격이나 정보가 변경되어도 주문 내역은 변하지 않음

**저장 정보:**
- 상품 ID (참조용)
- 상품명 (스냅샷)
- 가격 (스냅샷)
- 수량

**관계:**
- Order → User (N:1): 주문은 반드시 하나의 고객에 속함
- Order → OrderItem (1:N): 하나의 주문은 여러 주문 상품을 가짐
- OrderItem → Product (참조): 주문 상품은 상품 ID를 참조 (외래 키 아님)

### 제약 조건 (Invariants)

1. **주문 상품 최소 개수**
   - 주문은 최소 1개 이상의 상품을 포함해야 함

2. **주문 상품 중복 불가**
   - 동일한 상품 ID가 주문 상품 목록에 중복으로 포함될 수 없음
   - 같은 상품을 여러 개 주문하려면 수량을 증가시켜야 함
   - 예: `[{productId: 1, quantity: 3}, {productId: 1, quantity: 2}]` → 에러 반환
   - 올바른 예: `[{productId: 1, quantity: 5}]`

3. **고객 필수성**
   - 주문은 반드시 유효한 고객에 속해야 함

3. **수량 제약**
   - 주문 상품의 수량은 1 이상이어야 함

4. **재고 충분성**
   - 주문 시 모든 상품의 재고가 충분해야 함
   - 재고 부족 시 주문 전체가 실패함 (부분 주문 불가)

5. **트랜잭션 원자성**
   - 주문 생성과 재고 차감은 하나의 트랜잭션에서 처리
   - 전체 성공 or 전체 실패

6. **스냅샷 불변성**
   - 주문 시점의 상품 정보는 스냅샷으로 저장됨
   - 주문 후 상품 정보가 변경되어도 주문 내역은 변하지 않음

7. **총 금액 일관성**
   - 총 주문 금액은 자동으로 계산됨
   - 총 금액 = Σ(각 상품의 가격 × 수량)

8. **주문일시 불변성**
   - 주문일시는 변경할 수 없음

9. **주문 수정 불가**
   - 주문 후에는 수정/취소 불가 (현재 스펙)

### 판단 기준 (Business Logic)

1. **재고 충분 여부 판단**
   ```
   재고 충분 = 모든 상품에 대해 (stock >= 주문_수량)
   재고 부족 = 하나라도 (stock < 주문_수량)
   ```

2. **주문 생성 트랜잭션**
   ```
   BEGIN TRANSACTION
     1. 모든 상품 조회 (활성 상품만)
     2. 모든 상품의 재고 확인
     3. 주문 생성
     4. 주문 상품 생성 (스냅샷 저장)
        - productId: 상품 ID (참조용)
        - productName: 상품명 (스냅샷)
        - price: 가격 (스냅샷)
        - quantity: 수량
     5. 모든 상품의 재고 차감
        - stock = stock - 주문_수량
     6. 총 주문 금액 계산 및 저장
        - totalAmount = Σ(price × quantity)
   COMMIT
   ```

3. **재고 차감 로직**
   ```
   상품 A: 재고 10개, 주문 3개 → 재고 7개
   상품 B: 재고 5개, 주문 2개 → 재고 3개
   ```

4. **스냅샷 저장 정책**
   ```
   주문 시점의 상품 정보를 OrderItem에 복사:
   - 상품 ID는 참조용으로만 사용
   - 상품명, 가격은 스냅샷으로 저장
   - 상품이 삭제되어도 주문 내역은 유지
   ```

5. **권한 검증**
   ```
   고객 API: 자신의 주문만 조회 가능
   어드민 API: 모든 주문 조회 가능
   ```

### 검증 순서

**주문 생성 시:**
1. 주문 상품 목록 비어있는지 확인
2. 주문 상품 중복 확인 (동일한 productId가 여러 번 포함되었는지)
3. 모든 상품 존재 여부 확인
4. 모든 상품 활성 상태 확인
5. 모든 수량이 1 이상인지 확인
6. 모든 상품의 재고 충분 여부 확인

**주문 조회 시 (고객):**
1. 주문 존재 여부 확인
2. 자신의 주문인지 권한 확인

**주문 조회 시 (어드민):**
1. 주문 존재 여부 확인

### 데이터 정책

1. **스냅샷 정책**
   - 주문 시점의 상품 정보를 OrderItem에 저장
   - 상품 가격/정보 변경되어도 주문 내역은 불변
   - 상품이 삭제되어도 주문 내역은 유지
   - 상품 ID는 참조용으로만 사용 (외래 키 아님)

2. **재고 차감 정책**
   - 주문 생성 시 즉시 재고 차감
   - 추후 결제 기능 추가 시 재검토 필요
   - 트랜잭션으로 원자성 보장

3. **부분 주문 불가 정책**
   - 재고 부족 시 주문 전체가 실패
   - 일부 상품만 주문 불가
   - 이유: 고객 경험 일관성 유지

4. **트랜잭션 정책**
   - 주문 생성과 재고 차감은 하나의 트랜잭션
   - 재고 부족 시 전체 롤백
   - 원자성 보장 (전체 성공 or 전체 실패)

5. **Cascade 정책**
   - 주문 삭제 시 주문 상품도 함께 삭제 (DB Cascade)
   - 현재는 주문 삭제 기능 없음

6. **페이지네이션 정책**
   - 기본 페이지 크기: 20
   - 최대 페이지 크기: 100
   - 정렬: 최신 주문 순 (ordered_at DESC)

7. **인증 및 권한 정책**
   - 고객 API: 인증 필수, 자신의 주문만 조회 가능
   - 어드민 API: LDAP 인증 필수, 모든 주문 조회 가능

8. **가격 정확성 정책**
   - BigDecimal 타입 사용
   - 소수점 이하 2자리까지 지원
   - 반올림 정책: HALF_UP

### 성능 최적화

1. **인덱스 전략**
   - `user_id` 컬럼: 고객별 주문 조회
   - `ordered_at` 컬럼: 최신순 정렬
   - `order_id` 컬럼 (order_items): 주문 상품 조회

2. **쿼리 최적화**
   - 주문 조회 시 주문 상품도 함께 조회 (JOIN)
   - 기간 필터링 시 인덱스 활용
