## 3. 데이터 파이프라인

### 3.1 subject가 가정하는 기본 그림

```
[commerce-api]
     → 유저 행동 이벤트 발행 (조회, 좋아요, 주문 등)
     → Kafka

[commerce-collector]
     → 이벤트 소비
     → product_metrics upsert (R7 유지)
     → Redis ZSET 점수 갱신 (R9)

[commerce-api]
     → GET /api/v1/rankings?...
     → 상품 상세 응답에 순위 필드
```

### 3.2 쓰기 주체를 바꾸는 선택지

쓰기 주체 선택은 랭킹 시스템의 **실시간성, 복잡도, 복구 용이성**을 결정한다.

**쓰기 부하와 읽기 부하를 분리**하여 시스템 전체의 처리량(Throughput)을 높이기 위해 필요합니다. RDBMS는 가중합산 수식에 대한 인덱스를 제공하지 않으며, 지표가 바뀔 때마다 인덱스를 재정렬하는 부하가 매우 크기 때문입니다.


| 방향                               | 의미                                                                               | 장점                                                 | 단점                                                                              |
| -------------------------------- | -------------------------------------------------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------------------------- |
| **A. Collector만 쓰기 (비동기 파이프라인)** | `commerce-api`는 Kafka에 이벤트만 발행하고, collector가 Redis ZSET을 `ZINCRBY` 또는 `ZADD`로 갱신 | 읽기 API와 쓰기 파이프라인이 분리되어 SRP가 선명하고, API 응답 경로가 가벼워진다 | Kafka 컨슈머 Lag 시 랭킹 반영이 늦어지는 결과적 정합성(Eventual Consistency) 이슈가 생길 수 있다           |
| **B. API도 같이 쓰기 (이중 쓰기/동기 방식)**  | 주문/좋아요 API 처리 시점에 DB·Kafka 처리와 함께 Redis ZSET도 즉시 갱신                              | 유저 행동이 랭킹에 즉시 반영되어 체감 성능이 높다                       | Kafka 컨슈머가 동일 이벤트를 재처리하면 중복 합산 위험이 있고, 이를 막기 위한 멱등성 전략(이벤트 ID 기반 등)으로 복잡도가 증가한다 |
| **C. 배치 재생성 (주기적 동기화)**          | 실시간 증분 대신 주기적으로 RDBMS 원장(SSOT)을 읽어 ZSET 전체를 재생성                                  | 원본 데이터 기반으로 재계산하므로 유실·오류 시 동일 결과로 복구(보정)하기 쉽다      | 배치 주기 사이에는 랭킹 변화가 반영되지 않아 실시간성이 낮다                                              |


**읽기 단일 진실**: quest는 Redis ZSET 조회를 전제로 하므로, **B/C**를 택해도 API 응답 시점에 “어느 스토어를 볼지”를 하나로 정해야 한다(예: 항상 Redis, 또는 Redis miss 시 null/빈 목록).

### 3.3 R7 테이블과 ZSET의 정렬

- **같은 이벤트로 DB upsert + Redis 증분**을 같이 할지, **DB만 맞고 Redis는 비동기 보정**할지는 운영 허용 오차에 따라 갈린다.
- **동일 DB 트랜잭션에 Redis 포함**은 일반적으로 권장되지 않는다(2PC 아님, 롤백 불일치). 보통 **DB 커밋 성공 후 Redis**, 실패 시 **재처리 파이프라인**을 둔다.

### 3.4 SSOT와 Redis의 역할

가장 먼저 기억해야 할 점은 RDBMS가 매트릭의 원본 저장소(SSOT)이고, **Redis는 이를 가공한 파생 데이터의 원장**이라는 점이다. 따라서 Redis에 문제가 생기더라도 **원본 데이터인 DB만 안전하다면** 언제든 복구가 가능하다는 관점에서 접근한다.

### 3.5 Redis 실패 시 최소 정책


| 구분                | 전략 및 지침                                                                                                                                                                                                          |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Offset 커밋 시점**  | Redis 갱신 시도 **후** 커밋하는 것을 기본으로 하되, Redis 실패가 **전체 프로세스 중단**으로 이어지지 않게 설계한다. **DB 매트릭 저장이 성공했다면** 원장은 확보된 것이므로, Redis 갱신 실패 시 해당 이벤트를 **DLQ(Dead Letter Queue)**로 보내거나 **에러 로그**를 남기고 **다음 이벤트로 넘어가는** 방식이 합리적이다. |
| **재시도(Retry) 여부** | 즉각적인 재시도보다는 **DLQ를 통한 비동기 재처리** 혹은 **다음 이벤트에 의한 자가 보정**을 기대하는 것이 효율적이다. 무리한 재시도는 컨슈머 **Lag**을 유발하여 실시간성을 저해할 수 있다.                                                                                               |
| **최소 정책 권고**      | **Redis 갱신 실패를 유연하게 허용하되, 로그를 통해 모니터링한다**는 수준으로 정한다. 랭킹은 100% 정밀함보다 **실시간 조회**가 목표인 경우가 많아, 일부 점수 누락은 치명적이지 않다는 전제를 둘 수 있다(제품·운영 합의 하에).                                                                         |


### 3.6 실패 대응이 가능한 이유: 매트릭 기반 ZADD와 자가 보정

멱등성을 7단계 등에서 더 다듬기 전이라도, **매트릭 기반 `ZADD` 덮어쓰기** 방식 자체가 방어 기제가 된다.

- **자가 보정(Self-correction):** 특정 이벤트 처리 시 Redis 갱신에 실패하더라도, **다음 이벤트**가 들어올 때 DB에서 **최신 매트릭**을 읽어와 `ZADD`로 점수를 덮어쓰면 이전 실패가 상쇄된다.
- **덮어쓰기 전략:** `ZINCRBY`와 달리 `ZADD`는 **계산된 최종 결과값**을 넣는 업서트(Upsert) 방식이므로, 재처리가 발생해도 점수가 **중복 합산**되지 않고 최신 상태를 유지하기 쉽다.
- **과도한 비용 지불 금지:** 조회(View)와 같이 **볼륨이 큰 이벤트**에 대해 Redis 실패를 막으려고 **아웃박스 패턴** 같은 무거운 원자성 비용을 쓰는 것은 비효율적일 수 있다.
- **최후의 수단 보전:** Redis가 완전히 다운되어 데이터가 유실된 경우를 대비해, **DB(SSOT)를 풀스캔하여 Redis를 다시 채우는 복구 스크립트**를 염두에 두는 것이 실무적인 대비책이다.

**DB 저장은 확실히 하되**, Redis 갱신 실패 시 **에러 로깅 후 다음 이벤트로 진행(Skip 또는 DLQ)** 하는 최소 정책을 수립한다. 정밀한 멱등성 로직이 없더라도 **매트릭 기반 재계산 + `ZADD`**가 데이터의 최종적인 일관성을 끌어가는 데 기여한다. 상세 구현 순서는 [09-ranking-implementation-roadmap.md](../Implementation/09-ranking-implementation-roadmap.md) §5.3a와 연결한다.

### 4.1 점수 갱신 방식 선택지

쓰기 주체와 별개로, 점수 갱신 전략은 아래 3가지를 중심으로 결정한다.

가중합산(Weighted Sum)을 통해 계산된 인기도 점수를 Redis에 어떤 명령어로 반영할지는 **오류 복구 능력**과 직결됩니다.


| 방식                                              | 의미                                                   | 장점                                                                         | 단점                                                                             |
| ----------------------------------------------- | ---------------------------------------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| **1. `ZINCRBY` 증분 방식 (Incremental Update)**     | 이벤트(좋아요, 주문 등) 발생 시 기존 점수에 delta를 즉시 더하는 방식          | 처리 경로가 단순하고 빠르다. `ZINCRBY`는 원자적으로 동작해 별도 read-modify-write 없이 실시간 반영이 가능하다 | Kafka at-least-once 특성으로 동일 이벤트 재수신 시 중복 합산 리스크가 있다. 가중치 변경 시 과거 점수 소급 적용이 어렵다 |
| **2. 전량 재작성 방식 (`ZADD` + Swap / Batch Update)** | 주기적으로 RDBMS 원장(SSOT)을 조회해 전체 점수를 재계산하고 ZSET을 교체하는 방식 | 같은 입력이면 같은 결과가 나오는 멱등성이 높고, 유실/중복 이슈에서 복구(보정)가 쉽다                          | 배치 주기만큼 실시간성이 떨어지며, 상품 수가 많을수록 DB 조회·Redis 쓰기 부하가 증가한다                         |
| **3. 혼합 방식 (실시간 증분 + 주기적 보정)**                  | 실시간 이벤트 반영을 기본으로 하되, 주기 배치로 Redis-DB 오차를 보정하는 절충안    | 사용자 체감 실시간성과 데이터 보정 능력을 함께 확보할 수 있다                                        | 실시간 경로와 배치 경로를 모두 운영해야 하므로 운영 복잡도가 커진다                                         |


**-> 매트릭 기반** `ZADD` **보정 제언**: 이벤트 처리 시 단순 `ZINCRBY` 대신 DB 매트릭을 조회해 현재 총점을 재계산하고 `ZADD`로 덮어쓰면, 이전 이벤트 누락이 있어도 다음 이벤트 처리 시점에 자동 보정되는 효과를 기대할 수 있다.

`ZINCRBY`는 이벤트가 중복 수신될 경우 점수가 과대 산정될 위험이 있습니다. 반면, 매트릭 기반으로 다시 계산해서 넣으면 설령 이전 이벤트 처리가 유실되었더라도 다음 이벤트 처리 시점에 점수가 자동으로 보정(Self-correction)되는 효과가 있기 때문입니다.

**1. 가중합산(Weighted Sum) 기반의 스코어링**

인기도를 단순한 합계가 아닌, 서비스의 목적에 맞는 **복합적인 지표의 합**으로 계산합니다.

- **지표 선정 및 가중치 부여:** 조회, 좋아요, 구매 등 다양한 유저 행동 이벤트를 수집하고, 각 요소에 비즈니스 중요도에 따른 가중치를 곱해 합산합니다.
- **정규화(Normalization):** 서로 다른 단위(수량, 금액 등)를 가진 지표들을 **0에서 1 사이의 값으로 변환**하여 비교 가능하게 만듭니다. 이는 특정 아웃라이어(예: 고가의 상품)가 전체 랭킹을 왜곡하는 것을 방지합니다.

**2. 매트릭 기반의 ZADD 덮어쓰기 (핵심 전략)**

단순히 점수를 누적하는 `ZINCRBY` 대신, **DB 매트릭을 조회해 총점을 재계산하고 ZADD로 반영**하는 방식을 권장합니다.

- **ZINCRBY의 한계:** 이벤트가 중복 수신될 경우 점수가 과대 산정될 위험이 있습니다.
- **ZADD를 통한 자가 보정(Self-correction):** 이벤트를 처리할 때마다 DB에서 현재 시점의 총 지표를 읽어와 점수를 다시 계산해 `ZADD`로 넣으면, **이전 이벤트가 누락되었더라도 다음 이벤트 처리 시점에 점수가 자동으로 정상화**됩니다.
- **배치 리스너(Batch Listener) 활용:** 이벤트를 단권으로 처리하지 않고 묶어서 처리함으로써 DB와 Redis 접근 횟수를 줄이고 처리 효율을 극대화합니다.

**3. 타이 브레이크(Tie-break) 및 정밀도 설계**

동점자가 발생했을 때의 순위 결정 로직을 스코어 산정 단계에서 미리 설계합니다.

- **소수점 활용:** 정수보다 정밀도가 높은 소수점을 사용하여 동점 발생 확률을 낮춥니다.
- **정수부와 소수부의 분리:** 0~1 사이의 정규화된 점수를 소수부에 배치하고, **정수부에는 상품 등록일이나 특정 우선순위 값**을 넣어 동점 시 최신 상품이 상단에 오도록 설계할 수 있습니다.

**조회/좋아요/주문 delta 정의**는 quest 예시(가중치·`price*amount`)를 참고하되, **선형 vs log·캡**은 별도 행으로 튜닝한다. 어떤 방식을 택해도 **단위 테스트에 숫자 예시를 박아** 체크리스트(주문 vs 좋아요 역전)를 만족시키면 된다.

### 4.2 읽기 연산 (API·도메인에서 사용)

- **Top-N (높은 점수 우선)**: `ZREVRANGE key start stop WITHSCORES`
- **전체 개수·페이지 계산**: `ZCARD`
- **특정 상품 순위**: `ZREVRANK` (없으면 null 처리 — quest 체크리스트)
- **점수만 필요 시**: `ZSCORE`
- **스냅샷 목록**: 스냅샷 키에 대해 동일하게 `ZCARD` + `ZREVRANGE`(점수 내림차순). 스냅샷 조회 경로에서는 Redis 실패 시 **DB fallback을 쓰지 않음**(스냅샷 의미 유지).

### 4.3 스냅샷과 오프셋 페이징 (§13.7과 연결)

- 라이브 키만 쓰는 `GET .../rankings`는 §4.2.6·§13.7대로 **재요청 사이 ZSET 변경 시 중복·누락**이 생길 수 있다.
- **완화**: `POST .../rankings/snapshots`로 복제본을 만든 뒤, 이후 페이지는 `rankingSnapshotId`를 붙여 **복제본 ZSET**만 읽는다. Lua 단일 틱 스냅샷 대신 **서버 주도 복제 키 + 짧은 TTL** 패턴이다.

## 5. 시간의 양자화·롱테일

양자화: 특정 시간 단위(예: 10ms, 100ms)를 기준으로 작업을 쪼개거나 타임아웃을 설정하여 자원 점유를 제어하는 전략

롱테일: 전체 요청 중 **아주 적은 비중을 차지하지만 응답 시간이 비정상적으로 긴 '지연 시간(Latency)'** 영역

- **일간 키**를 쓰는 이유: 영구 누적이면 **옛날 인기 상품이 계속 상위**를 잡는 **롱테일**이 생기고, “오늘의 인기” 의미가 흐려진다.
- **랭킹의 신선도 유지**: 어제 인기 있었던 상품이 오늘까지 계속 1위로 남아 있으면 랭킹의 의미가 퇴색됩니다. 따라서 날짜별로 Redis 키(ZSET)를 분리하여 "오늘의 트렌드"를 정확히 보여줘야 합니다.
- **자정(00:00) 경계 처리**: 자정이 되는 순간 랭킹 데이터가 사라지는 '콜드 스타트' 문제를 해결하기 위해, 어떤 기준으로 이벤트를 새 날짜의 키에 할당할지 명확한 기준이 필요합니다.
- **TTL**: 오래된 키를 Redis가 정리해 **메모리 상한**을 돕는다.
- **API `date` 쿼리**: quest는 과거 일자 조회를 체크리스트에 넣었으므로, **기본값은 “오늘”**이어도 `**yyyyMMdd`로 과거 키 조회가 가능해야 한다.

### 5.1 `yyyyMMdd`와 이벤트 시각 (QnA와 연결)

- **화면·API의 “오늘/어제”는 `**ZoneId`를 명시하는 편이 안전하다. 한국 서비스면 `**Asia/Seoul` 달력**으로 `yyyyMMdd`를 자르면 유저 기대와 맞추기 쉽고, **UTC만** 쓰면 **한국 자정 전후**에 날짜 경계가 어긋날 수 있다(자세한 경계·테스트는 §13.5).
- **ZSET 키에 넣을 날짜**를 **이벤트 `occurredAt`(서울 변환)** 으로 자를지, **컨슈머 처리 시각**으로 자를지에 따라 의미가 갈린다 — **“행동이 속한 날”** vs **“집계가 돌아간 날”**. 제품 문장으로 먼저 정하면 선택이 수렴한다([09-qna.md](../qna/09-qna.md) Q2).

### 5.2 날짜 귀속 기준 선택지


| 기준                          | 의미                  | 장점                    | 단점                                | 근거                                    |
| --------------------------- | ------------------- | --------------------- | --------------------------------- | ------------------------------------- |
| `occurredAt` + `Asia/Seoul` | 유저가 실제로 행동한 날에 귀속   | 제품 의미와 가장 잘 맞는다       | 지연 도착 이벤트에 대한 별도 처리 정책이 필요하다      | design의 “행동이 속한 날 vs 집계가 돌아간 날” 구분    |
| **처리시각 + `Asia/Seoul`**     | 컨슈머가 처리한 시각 기준으로 귀속 | 구현이 단순하다              | 늦게 처리되면 다른 날짜 키로 들어가 의미가 왜곡될 수 있다 | design의 자정 전후 날짜 경계 이슈 설명             |
| **UTC 기준**                  | UTC 달력 기준으로 귀속      | 글로벌 표준 시간 체계로 일관성이 높다 | 한국 서비스에서는 사용자 체감 자정과 어긋날 수 있다     | design의 UTC-only 사용 시 한국 자정 경계 불일치 지적 |


### 5.3 결정

- **날짜 귀속 기준**: `occurredAt + Asia/Seoul`을 기본으로 채택한다.
- **채택 근거**: “행동이 속한 날” 기준이 제품 의미(오늘의 인기)와 가장 일치한다.
- **지연 도착 이벤트 정책**: 지연 이벤트는 원칙적으로 발생일 키에 반영하되, 운영 정책(허용 지연 시간/무시 기준)을 별도로 정의한다.
- **보완책 1 (콜드 스타트 완화)**: 자정 직전 전일 Top-N을 낮은 가중치(예: `0.01`)로 다음 날 키에 캐리오버한다.
- **보완책 2 (정합성 보정)**: RDBMS 원장을 기준으로 주기적 보정 배치를 수행해 날짜 경계·중복/유실로 인한 오차를 교정한다.

## 6. 가중치 합산 (subject)

문서상 총점 직관:

\text{score}(p) \approx w*{view}\cdot C*{view} + w*{like}\cdot C*{like} + w*{order}\cdot C*{order}

(주문 항은 건수·매출 등 팀이 정한 함수로 둘 수 있다.)


| 반영 전략       | 트레이드오프                                                 | 구현 스케치                                                                                     |
| ----------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| **증분 일치**   | 매 이벤트마다 위 식의 **한 항만** delta로 반영하면, 수학적으로는 선형 항의 합과 동치. | `RankingScoreCalculator`가 타입별 delta만 반환, 저장은 `ZINCRBY`.                                    |
| **주기적 재계산** | 가중치 변경을 **과거 전체에 소급**하기 쉽다. 실시간은 희생.                   | 배치가 DB 카운트·매출 집계를 읽어 score 재작성.                                                            |
| **가중치 외부화** | 운영 중 튜닝 가능. 잘못된 배포 시 **순위 급변**.                        | `ConfigurationProperties`/DB 테이블/Redis 해시 중 하나를 “단일 소스”로 정하고, calculator가 주입받아 delta에 곱한다. |


**체크리스트**: “주문 1건 > 좋아요 3건” 등은 **테스트 픽스처**로 고정해, 위 전략 중 무엇을 택해도 검증 가능하게 한다.

## 7. 콜드 스타트·Carry-Over

**문제**: 자정 직후 ZSET이 비어 있거나 의미 없는 순위만 보일 수 있다.


| 완화책                                              | 트레이드오프                                        | 구현 스케치                                                                                     |
| ------------------------------------------------ | --------------------------------------------- | ------------------------------------------------------------------------------------------ |
| **Score Carry-Over** (`ZUNIONSTORE` + 작은 weight) | 어제 인기가 오늘 **시드**로 남는다. 비율이 크면 신규가 밀린다.        | 스케줄러가 `ranking:all:{next}` 생성, `ZUNIONSTORE` 후 `EXPIRE`. collector는 자정 이후 동일 키에 `ZINCRBY`. |

| **DB 인기 상품으로 시드**                                | 비즈 규칙(카테고리·고정 큐레이션) 반영 가능. **배치·정책** 유지보수 증가. | 배치가 상품 ID 목록을 읽어 초기 `ZADD`로 작은 점수 부여.                                                      |

## 13. 딥다이브 (심화 탐구)

아래는 과제 구현을 넘어, **운영·정합성·성능**까지 파고들 때 유용한 주제다. 전부 구현할 필요는 없고, 리뷰·블로그·장애 대응 시 참고용으로 쓰면 된다.

### 13.1 Redis ZSET 내부와 복잡도 (왜 O(log N)인가)

- ZSET은 **스킵리스트 + 해시 테이블** 조합으로 구현되는 것이 일반적이다(구현체는 Redis 버전에 따름). member → score 매핑과 score 순서를 동시에 잡는다.
- `**ZADD` / `ZINCRBY`**: 대략 **O(log N)** (N = 해당 키의 멤버 수). 랭킹 키에 상품이 수십만 개여도 **단건 갱신은 보통 가볍다.
- `**ZREVRANGE start stop`**: **O(log N + M) (M = 반환 구간 길이). Top 20만 가져오면 M이 작아 유리하다.
- `**ZRANK` / `ZREVRANK`**: **O(log N). “한 상품이 몇 위냐”는 전체 정렬을 돌리지 않고 순위만 구한다.
- `**ZCARD`**: **O(1).
- **시사점**: 쓰기 TPS가 극단적이면 **같은 키에 대한 단일 스레드 처리**가 Redis 인스턴스에서 병목이 될 수 있다. 파이프라인·배치로 **왕복(RTT)만 줄이는 것**과 **서버 CPU**는 별개라는 점을 구분한다.

### 13.2 부동소수점 score: 동점·정렬 안정성

- Redis score는 **IEEE 754 double**이다. 누적 `ZINCRBY` 시 **반올림 오차**가 쌓일 수 있다.
- **동점(score 동일)** 인 member들 사이의 순서는 **lexicographical member 순**으로 정해진다(버전별 문서 확인). “같은 점수면 최근에 활동한 상품이 위” 같은 규칙을 넣으려면 **tie-breaker를 score에 소량 가산**(예: 극소 epsilon + 타임스탬프 기반)하거나 **별도 정렬 단계**를 API에서 둔다.
- **금액·건수를 그대로 score에 넣는 설계**는 큰 수·작은 수가 섞일 때 **표현 한계**를 검토한다. log·캡은 여기서 나온다.

### 13.3 메모리 추정과 “전 상품 vs Top-K만”

- 대략: ZSET 한 멤버는 **member 문자열 + score + 내부 포인터 오버헤드**를 먹는다. 상품 10만 개 × 키 1개면 **수 MB~수십 MB**대로 갈 수 있어, 멤버 문자열 길이(prefix 여부)가 누적에 영향을 준다.
- **전 상품을 매일 키에 넣을지**, **이벤트가 있었던 상품만** 넣을지에 따라 `ZCARD`·메모리·콜드 상품 순위(null) UX가 달라진다.
- **상위 K개만 유지**하는 전략(오래된 하위권 `ZREMRANGEBYRANK` 등)은 메모리는 줄이지만, **“진짜 순위” 정의가 바뀌고** 상세 API의 “몇 위”가 전역 순위가 아닐 수 있다 — 비즈와 맞춰야 한다.

### 13.4 키 만료(TTL)와 lazy/free 메모리

- `EXPIRE`는 **정확한 시각에 즉시 삭제**를 보장하지 않는다. 접근 시 lazy expire, 백그라운드 샘플링 등 **구현 의존**이 있다.
- **만료 직후** 첫 요청이 잠깐 miss처럼 보이거나, **메모리 해제가 지연**될 수 있음을 운영 가이드에 적어 두면 장애 분석이 쉽다.
- Carry-Over + TTL을 같이 쓰면 **“새 키 생성 시점에 EXPIRE를 몇 초로 줄지”** 가 하루 경계와 겹칠 때 레이스가 난다 — 스케줄·컨슈머 순서를 문서화한다(로드맵 §7과 연결).

### 13.5 타임존·자정 경계

- `yyyyMMdd`는 **어느 타임존의 날짜인지**가 곧 버그다. 서버 UTC vs `Asia/Seoul` vs “이벤트 발생 시각 기준”이 다르면 **같은 이벤트가 두 날짜 키에 갈** 수 있다.
- **구현**: `RankingKeyResolver`에 **ZoneId를 명시**하고, 단위 테스트에 **23:59:59.999 ↔ 00:00:00** 경계 케이스를 넣는다.
- **DST(서머타임)** 이 있는 존이면(해외 확장 시) 하루가 23/25시간이 되는 날이 있다 — 글로벌 서비스면 Instant(UTC) 저장 후 변환 패턴을 쓴다.

### 13.6 Kafka 소비와 정합성: offset, 재처리, 순서

- **파티션 내 순서**는 보장되지만, **상품 단위 전역 순서**는 보장되지 않는다. 같은 상품에 대한 이벤트가 여러 파티션으로 가면 **ZSET 반영 순서가 뒤바뀔** 수 있다(대부분의 증분 합산에서는 교환법칙 성립 → 최종 합은 같을 수 있으나, “비가산” 로직이면 위험).
- **at-least-once** 소비 + `ZINCRBY` = **중복 시 점수 과대**. 딥다이브 대응: **dedup store**, **정확히 한 번** 스트림(트랜잭션/아이덤포턴트 프로듀서 등), 또는 비즈니스적으로 **과대 허용**.
- **DB 커밋 성공 후에만 offset commit** 같은 패턴을 쓸 때, Redis만 실패하면 **DB는 반영됐는데 ZSET은 늦는** 상태가 된다 — 모니터링 지표를 분리한다(DB lag vs Redis lag).

### 13.7 읽기 일관성: ZRANK vs ZREVRANGE를 같은 “틱”에

- 클라이언트가 목록에서 “10위인 줄 알았는데 상세는 11위”처럼 보일 수 있다. **두 명령 사이에 쓰기가 끼어들면** 정상이다.
- 완화: **같은 응답 안에서 필요한 값을 한 번에 계산**하거나, “순위는 대략값” UX 문구, 또는 **Lua로 스냅샷**(대기열 R8에서 쓰던 패턴과 유사)을 검토한다. 랭킹은 대기열보다 **약한 일관성**을 허용하는 경우가 많다.
- **구현 반영(목록 다중 페이지)**: `POST /api/v1/rankings/snapshots` + `rankingSnapshotId`로 **복제 ZSET**(§4 표 아래 스냅샷 키)을 읽으면, **페이지를 넘기는 동안** 라이브 키가 바뀌어도 동일 스냅샷 내 순서는 고정된다. 목록·상세 간 시점 차이(I4) 자체는 남는다.

### 13.8 Redis Cluster / 해시 태그

- 키가 `{shard}:ranking:all:20250407`처럼 **해시 태그**(`{...}`)를 쓰면 **같은 슬롯**에 모을 수 있다. **Lua·MULTI**가 여러 키를 묶을 때 필요할 수 있다.
- 반대로 **모든 랭킹 키를 한 슬롯**에 몰면 **핫스팟 샤드**가 될 수 있다 — 트래픽·키 분산과 트레이드오프.

### 13.9 랭킹 조작·어뷰징 (제품 관점)

- 조회수만 크면 **봇·새로고침**으로 순위를 올릴 수 있다. 가중치·캡·유저당 rate limit, **신뢰 구간이 높은 이벤트(주문)** 비중을 높이는 이유가 여기에 있다.
- **내부 직원·테스트 계정** 이벤트를 필터링할지는 정책이다.

### 13.10 관측 가능성: 무엇을 메트릭으로 남길까

- 컨슈머: **lag**, **처리 건수/초**, **실패·DLQ 카운트**, 이벤트 타입별 delta 합(샘플링 가능).
- Redis: **used_memory**, **해당 prefix 키 수**, 대표 키 **ZCARD**, **명령 지연**(latency monitor).
- API: **p95 지연**, 캐시 hit(캐시를 쓴 경우), `ranking:all:*` 조회 실패율.

### 13.11 테스트에서 재현하기 어려운 것

- **동시에 같은 상품에 대량 `ZINCRBY`** — 통합 테스트에서 스레드/가상 스레드로 재현해 **최종 score가 기대 합과 일치**하는지 본다.
- **날짜 경계** — `Clock` 고정 또는 Testcontainers + 시간 고정.
- **Kafka 재전송** — 동일 페이로드를 두 번 보내 **멱등 정책**이 의도대로인지 확인.
