# 01. 유저 시나리오 기반 기능 정의 및 요구사항 명세

---

## 0. 문서 범위

- **현재 구현 범위**: 브랜드(Brand), 상품(Product), 좋아요(Like), 주문(Order) 도메인
- **제외**: 회원(User) - v1에서 완성
- **향후 확장**: 결제(Payment), 장바구니(Cart), 쿠폰(Coupon), 옵션/Variant 시스템은 부록에서 설계 방향만 제시
- 용어는 유비쿼터스 언어 기준을 따른다

---

## 1. 유비쿼터스 언어 (핵심 도메인)

| 한글 | 영문 | 정의 | 비고 |
|------|------|------|------|
| 브랜드 | Brand | 상품을 공급하는 단위. 어드민이 등록/관리 | 삭제 시 소속 상품 연쇄 삭제 |
| 상품 | Product | 판매 단위. 하나의 Brand에 소속 | Brand와 N:1 |
| 좋아요 | Like (ProductLike / BrandLike) | 사용자가 관심 상품/브랜드를 저장하는 행위 | 토글이 아닌 등록/취소 분리 |
| 주문 | Order | 사용자의 구매 거래 단위 | 복수 상품 단건 주문 |
| 주문항목 | OrderItem | 주문 시점의 상품 정보 스냅샷 | Order와 1:N |
| 재고 | Stock (quantity) | 상품의 판매 가능 수량 | Product에 귀속 |
| 어드민 | Admin | 운영자. LDAP 헤더로 식별 | 브랜드/상품 CRUD 권한 |

### 상태 정의

| 도메인 | 상태(Enum) | 값 | 설명 |
|--------|-----------|-----|------|
| Brand | BrandStatus | `ACTIVE`, `INACTIVE` | ACTIVE만 고객 노출 |
| Product | ProductStatus | `ACTIVE`, `SOLD_OUT`, `HIDDEN`, `DISCONTINUED` | ACTIVE: 판매 중, SOLD_OUT: 품절, HIDDEN: 비노출, DISCONTINUED: 판매 중단 |
| Order | OrderStatus | `PLACED`, `PAID`, `CANCELED` | PLACED: 주문 생성(재고 차감 완료), PAID: 결제 완료(향후), CANCELED: 취소 |
| Like | - | 존재하면 좋아요, 없으면 해제 | row 존재 여부로 판단 (soft delete 시 deleted_at) |

## 2. 공통 정책

### 2-1. 인증 체계

| 구분 | prefix | 헤더 | 설명 |
|------|--------|------|------|
| 고객 API | `/api/v1` | `X-Loopers-LoginId`, `X-Loopers-LoginPw` | 로그인 필요 API는 헤더로 사용자 식별 |
| 어드민 API | `/api-admin/v1` | `X-Loopers-Ldap: loopers.admin` | LDAP 기반 어드민 식별 |

- 인증/인가 구현은 스코프 밖 (헤더 기반 식별만 수행)
- 유저는 타 유저의 정보에 직접 접근 불가

### 2-2. 공통 규칙

- **소프트 삭제**: 모든 삭제는 `deleted_at` 컬럼 업데이트 (물리 삭제 금지)
- **페이징**: 목록 조회는 page/size 기반 페이징 필수 (기본값: page=0, size=20)
- **정렬**: 기본 정렬은 최신순(created_at DESC)
- **에러 응답**: 검증 실패는 예외가 아닌 Response return (CLAUDE.md 규칙)

### 2-3. 에러 응답 범주

| HTTP 상태 | 의미 | 사용 예시 |
|-----------|------|----------|
| 400 | 입력값 오류 | 필수값 누락, 형식 오류, 수량 비정상 |
| 401 | 인증 없음 | 로그인 필요 API에 헤더 없음 |
| 403 | 권한 없음 | 타인 리소스 접근, 어드민 권한 없음 |
| 404 | 리소스 없음 | 존재하지 않는 브랜드/상품/주문 |
| 409 | 상태 충돌 | 이미 좋아요함, 재고 부족, 중복 등록 |
| 500 | 서버 내부 오류 | 예상치 못한 시스템 에러 (에러 코드 포함 로깅, 클라이언트에는 일반 메시지 반환) |

## 3. 유저 시나리오 기반 기능 정의

| 시나리오 | 대상 | 핵심 기능 | 기능 번호 |
|---------|------|----------|----------|
| A | 고객 | 탐색 + 좋아요 | F-01 ~ F-06 |
| B | 고객 | 주문 + 조회 | F-07 ~ F-09 |
| C | 어드민 | 브랜드/상품 관리 | F-10 ~ F-19 |
| D | 어드민 | 주문 조회 | F-20 ~ F-21 |

### 시나리오 A. "브랜드/상품 탐색 → 좋아요 → 좋아요 목록 재탐색"

**사용자 목표**: 마음에 드는 상품/브랜드를 저장해두고 다시 쉽게 찾는다.

1. 브랜드 정보를 조회한다
   - 기능: 브랜드 상세 조회
   - 정책: 로그인 불필요, ACTIVE 브랜드만 조회 가능

2. 상품 목록을 조회한다 (필터/정렬)
   - 기능: 상품 목록 조회 (brandId 필터, 정렬, 페이징)
   - 정책: 로그인 불필요, 노출 가능 상품만 조회

3. 상품 상세를 확인한다
   - 기능: 상품 상세 조회 (재고 상태 포함)
   - 정책: 로그인 불필요

4. 좋아요를 등록한다
   - 기능: 상품 좋아요 등록
   - 정책: 로그인 필수, (user_id, product_id) 유일성

5. 좋아요를 취소한다
   - 기능: 상품 좋아요 취소
   - 정책: 로그인 필수, 본인의 좋아요만 취소 가능

6. 좋아요 목록에서 저장된 상품을 다시 본다
   - 기능: 내가 좋아요 한 상품 목록 조회
   - 정책: 로그인 필수, 본인 좋아요만 조회

**예외/제약**
- 401: 로그인 필요 (좋아요 등록/취소/목록)
- 404: 상품/브랜드 없음
- 409: 이미 좋아요한 상품에 재등록

---

### 시나리오 B. "상품 선택 → 주문 → 주문 확인"

**사용자 목표**: 여러 상품을 한 번에 주문하고 주문 내역을 확인한다.

1. 상품을 선택하고 주문을 요청한다
   - 기능: 주문 요청 (복수 상품, 수량 지정)
   - 정책: 로그인 필수, 재고 확인 및 차감 보장

2. 주문 목록을 조회한다
   - 기능: 주문 목록 조회 (날짜 범위 필터)
   - 정책: 로그인 필수, 본인 주문만 조회

3. 주문 상세를 확인한다
   - 기능: 단일 주문 상세 조회 (스냅샷 기반)
   - 정책: 로그인 필수, 본인 주문만 조회, 주문 당시 상품 정보 유지

**예외/제약**
- 401: 로그인 필요
- 403: 타인 주문 접근
- 404: 주문/상품 없음
- 409: 재고 부족, 판매 불가 상품 포함

**핵심 불변 규칙**
- 주문 정보에는 당시의 상품 정보가 **스냅샷으로 저장**되어야 함
- 주문 시 **상품 재고 확인 및 차감**이 보장되어야 함

---

### 시나리오 C. "어드민 - 브랜드/상품 관리"

**운영자 목표**: 브랜드와 상품을 등록/수정/삭제하며 카탈로그를 관리한다.

1. 브랜드를 등록한다
   - 기능: 브랜드 등록
   - 정책: LDAP 인증 필수

2. 브랜드를 수정한다
   - 기능: 브랜드 정보 수정
   - 정책: LDAP 인증 필수, 존재하는 브랜드만

3. 브랜드를 삭제한다
   - 기능: 브랜드 삭제 (소프트 삭제)
   - **핵심 정책: 브랜드 삭제 시, 해당 브랜드의 상품들도 함께 삭제**

4. 상품을 등록한다
   - 기능: 상품 등록
   - **핵심 정책: 상품의 브랜드는 이미 등록된(ACTIVE) 브랜드여야 함**

5. 상품을 수정한다
   - 기능: 상품 정보 수정
   - **핵심 정책: 상품의 브랜드는 수정할 수 없음**

6. 상품을 삭제한다
   - 기능: 상품 삭제 (소프트 삭제)

**예외/제약**
- 403: LDAP 인증 실패
- 404: 브랜드/상품 없음
- 409: 삭제된 브랜드에 상품 등록 시도

---

### 시나리오 D. "어드민 - 주문 조회"

**운영자 목표**: 전체 주문 현황을 파악한다.

1. 주문 목록을 조회한다
   - 기능: 전체 주문 목록 조회 (페이징)
   - 정책: LDAP 인증 필수

2. 주문 상세를 조회한다
   - 기능: 단일 주문 상세 조회
   - 정책: LDAP 인증 필수

## 4. 기능 명세

### 4-1. 탐색/조회 (고객)

#### F-01. 브랜드 정보 조회

| 항목 | 내용 |
|------|------|
| **API** | `GET /api/v1/brands/{brandId}` |
| **인증** | 불필요 |
| **목적** | 특정 브랜드의 상세 정보를 조회한다 |
| **사전조건** | 없음 |
| **정상 흐름** | 1. brandId로 브랜드 조회 2. 존재 및 ACTIVE 확인 3. 브랜드 정보 반환 |
| **정책** | ACTIVE 브랜드만 조회 가능. 삭제/비활성 브랜드는 404 |
| **고객 노출 정보** | 브랜드명, 설명, 로고 등 (내부 관리 정보 제외) |
| **예외** | 404: 브랜드 없음 또는 비활성 |
| **수용 기준** | Given ACTIVE 브랜드, When 조회, Then 브랜드 정보 반환 / Given 삭제된 브랜드, When 조회, Then 404 |

#### F-02. 상품 목록 조회

| 항목 | 내용 |
|------|------|
| **API** | `GET /api/v1/products?brandId={brandId}&sort={sort}&page={page}&size={size}` |
| **인증** | 불필요 |
| **목적** | 상품 목록을 필터/정렬/페이징하여 조회한다 |
| **사전조건** | 없음 |
| **정상 흐름** | 1. 쿼리 파라미터 파싱 2. 조건에 맞는 상품 페이징 조회 3. 목록 반환 |
| **쿼리 파라미터** | `brandId`: 특정 브랜드 필터 (선택), `sort`: 정렬 기준 (기본: latest), `page`: 페이지 번호 (기본: 0), `size`: 페이지 크기 (기본: 20) |
| **정렬 기준** | `latest`: 최신 등록순 (필수), `price_asc`: 가격 낮은순 (선택), `likes_desc`: 좋아요 많은순 (선택) |
| **정책** | 판매 가능 상품만 노출 (ACTIVE, SOLD_OUT은 노출 + 배지 표시), HIDDEN/DISCONTINUED는 제외 |
| **고객 노출 정보** | 상품명, 가격, 브랜드명, 썸네일, 좋아요 수, 재고 상태(품절 여부) |
| **예외** | 400: page/size 비정상 (음수 등) |
| **수용 기준** | Given 상품 30개 + size=10, When 조회, Then 10개 반환 + hasNext=true / Given brandId=1 필터, When 조회, Then 해당 브랜드 상품만 반환 |

#### F-03. 상품 상세 조회

| 항목 | 내용 |
|------|------|
| **API** | `GET /api/v1/products/{productId}` |
| **인증** | 불필요 |
| **목적** | 특정 상품의 상세 정보를 조회한다 |
| **사전조건** | 없음 |
| **정상 흐름** | 1. productId로 상품 조회 2. 존재 및 노출 가능 확인 3. 상세 정보 반환 |
| **정책** | 노출 가능 상품만 조회 (HIDDEN/DISCONTINUED는 404). 재고 상태는 "재고 있음/품절"로만 표시 (정확 수량 비노출) |
| **고객 노출 정보** | 상품명, 가격(정가/판매가), 상세 설명, 브랜드 정보, 재고 상태, 좋아요 수 |
| **예외** | 404: 상품 없음 또는 노출 불가 |
| **수용 기준** | Given ACTIVE 상품, When 조회, Then 상세 정보 반환 / Given HIDDEN 상품, When 조회, Then 404 |

### 4-2. 좋아요 (고객)

#### F-04. 상품 좋아요 등록

| 항목 | 내용 |
|------|------|
| **API** | `POST /api/v1/products/{productId}/likes` |
| **인증** | 필수 (X-Loopers-LoginId, X-Loopers-LoginPw) |
| **목적** | 사용자가 상품에 좋아요를 등록한다 |
| **사전조건** | 로그인 상태, 상품 존재 |
| **정상 흐름** | 1. 사용자 인증 확인 2. 상품 존재 및 노출 가능 확인 3. 기존 좋아요 여부 확인 4. 없으면 좋아요 생성 5. like_count 반영 |
| **정책** | (user_id, product_id) 유일성 보장. 이미 좋아요한 경우 409. 삭제된(deleted_at) 좋아요가 있으면 복구(ACTIVE) |
| **예외** | 401: 로그인 없음, 404: 상품 없음, 409: 이미 좋아요 등록됨 |
| **수용 기준** | Given 좋아요 없음, When 등록, Then 좋아요 생성 + liked=true / Given 이미 좋아요, When 등록, Then 409 |

#### F-05. 상품 좋아요 취소

| 항목 | 내용 |
|------|------|
| **API** | `DELETE /api/v1/products/{productId}/likes` |
| **인증** | 필수 |
| **목적** | 사용자가 상품 좋아요를 취소한다 |
| **사전조건** | 로그인 상태, 해당 상품에 좋아요가 존재 |
| **정상 흐름** | 1. 사용자 인증 확인 2. (user_id, product_id) 좋아요 존재 확인 3. 좋아요 삭제 (soft delete) 4. like_count 반영 |
| **정책** | 본인의 좋아요만 취소 가능. 존재하지 않는 좋아요 취소 시 404 |
| **예외** | 401: 로그인 없음, 404: 좋아요 없음 |
| **수용 기준** | Given 좋아요 존재, When 취소, Then 삭제 + liked=false / Given 좋아요 없음, When 취소, Then 404 |

#### F-06. 내가 좋아요 한 상품 목록 조회

| 항목 | 내용 |
|------|------|
| **API** | `GET /api/v1/users/{userId}/likes` |
| **인증** | 필수 |
| **목적** | 사용자가 좋아요한 상품 목록을 조회한다 |
| **사전조건** | 로그인 상태, userId가 본인과 일치 |
| **정상 흐름** | 1. 인증 확인 2. userId == 로그인 사용자 확인 3. 좋아요 목록 페이징 조회 4. 상품 정보와 함께 반환 |
| **정책** | 본인의 좋아요만 조회 가능 (타인 userId 시 403). 정렬: 최근 좋아요 순. 삭제된 상품은 목록에서 제외 |
| **예외** | 401: 로그인 없음, 403: 타인의 좋아요 목록 접근 |
| **수용 기준** | Given 좋아요 25개 + size=10, When 조회, Then 10개 반환(최신순) / Given 타인 userId, When 조회, Then 403 |

### 4-3. 주문 (고객)

#### F-07. 주문 요청

| 항목 | 내용 |
|------|------|
| **API** | `POST /api/v1/orders` |
| **인증** | 필수 |
| **목적** | 사용자가 복수 상품을 한 번에 주문한다 |
| **요청 형식** | `{ "items": [{ "productId": 1, "quantity": 2 }, { "productId": 3, "quantity": 1 }] }` |
| **사전조건** | 로그인 상태, 모든 상품이 존재하고 판매 가능 |
| **정상 흐름** | 1. 인증 확인 2. items 유효성 검증 (비어있지 않음, 수량 >= 1) 3. 각 상품 존재/판매 가능 확인 4. 각 상품 재고 확인 5. **재고 차감 (원자적)** 6. Order 생성 (PLACED) 7. **OrderItem에 상품 스냅샷 저장** 8. 주문 결과 반환 |
| **스냅샷 저장 필드** | 상품명, 브랜드명, 가격(주문 시점), 수량, 라인 합계 |
| **재고 정책** | 주문 시점에 재고 확인 및 차감을 **원자적으로** 수행. 부분 성공 없음 (전체 성공 or 전체 실패) |
| **예외** | 401: 로그인 없음, 400: items 비어있음/수량 비정상, 404: 상품 없음, 409: 재고 부족/판매 불가 상품 |
| **수용 기준** | Given 재고 충분, When 주문, Then Order(PLACED) + 재고 차감 + 스냅샷 저장 / Given 재고 부족, When 주문, Then 409 + 재고 변경 없음 / Given items 2개 중 1개 품절, When 주문, Then 전체 실패(409) |

**설계 의도 - 재고 차감 원자성**:
- 여러 상품을 주문할 때, 일부만 재고가 차감되고 일부가 실패하는 상황을 방지
- 하나의 트랜잭션 내에서 모든 상품의 재고를 확인하고 차감
- 동시 주문 시 경합 방지를 위해 `UPDATE stock SET quantity = quantity - ? WHERE product_id = ? AND quantity >= ?` 패턴 또는 비관적 락 사용

## 6. 설계 결정 포인트 (구현 시 고려)

| # | 항목 | 결정 | 근거 |
|---|------|------|------|
| 1 | Like 집계 방식 | products 테이블에 like_count 컬럼 유지 | 조회 성능 우선. 등록/취소 시 동기 증감. 동시성은 향후 대응 |
| 2 | 재고 차감 방식 | 원자적 UPDATE (qty >= ? 조건) | 단순하고 경합에 안전. 향후 Reservation 모델로 확장 가능 |
| 3 | 주문 스냅샷 범위 | 상품명, 브랜드명, 가격, 수량 | 주문 이후 원본이 변해도 스냅샷은 유지 |
| 4 | 브랜드 삭제 시 상품 처리 | 연쇄 소프트 삭제 | 요구사항 명시 |
| 5 | Like 중복 방지 | DB 유니크 제약 (user_id, product_id) + deleted_at | 애플리케이션 검증 + DB 제약 이중 방어 |
