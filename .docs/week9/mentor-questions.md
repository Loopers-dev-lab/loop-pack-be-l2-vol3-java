# Round 9 - 멘토 질문 정리

> Redis ZSET 기반 실시간 랭킹 시스템 설계/구현 과정에서의 고민 포인트

## 1. Score 설계 관련

### Q1. Weight 기반 점수 합산의 공정성 문제
조회(0.1), 좋아요(0.2), 주문(0.6 * price * amount)로 점수를 합산하면,
**고가 상품 1건 주문이 저가 상품 100건 주문보다 높은 점수**를 받게 됩니다.
"인기 상품"의 정의가 **거래액 기준**인지 **거래 빈도 기준**인지에 따라 결과가 완전히 달라지는데,
실무에서는 이 기준을 어떻게 정하나요? 두 기준을 혼합하는 사례가 있는지도 궁금합니다.

### Q2. 주문 점수에 log 정규화를 적용할 때의 트레이드오프
quest에서 `log(price * amount)` 정규화를 언급하는데,
log를 적용하면 고가/저가 간 격차는 줄지만 **주문 금액의 차이가 무의미해지는 구간**이 생깁니다.
(e.g. 10만원 vs 12만원 → log 차이 미미)
정규화 전략을 선택할 때 어떤 기준으로 판단하는 게 좋을까요?

### Q3. ZINCRBY의 부동소수점 정밀도 문제
Redis ZSET score는 IEEE 754 double인데, Weight를 곱한 소수점 점수를 ZINCRBY로 누적하면
**부동소수점 오차가 축적**될 수 있습니다.
실무에서 이게 실제로 랭킹 역전을 일으킨 사례가 있나요?
정수 기반 점수(e.g. Weight를 100배 곱해 정수화)로 우회하는 게 일반적인지 궁금합니다.

## 2. 키 전략 및 데이터 수명 관련

### Q4. 일간 키(`ranking:all:{yyyyMMdd}`) vs 시간 단위 키의 운영 복잡도
시간 단위 랭킹(`ranking:all:{yyyyMMddHH}`)을 만들면 하루에 24개 키가 생기고,
"최근 1시간 인기 상품"을 보여주려면 현재 시각 기준 키를 조회해야 합니다.
그런데 **이벤트 발생 시각 vs 컨슈머 처리 시각**이 다를 수 있는데,
어느 시각 기준으로 키를 결정해야 하나요? (이벤트 발생 시각이면 과거 키에 ZINCRBY를 해야 하는 상황 발생)

### Q5. TTL 2일의 의미와 경계 시점 처리
TTL 2일이면 `ranking:all:20260405` 키는 4월 7일에 만료됩니다.
그런데 **자정 직후** 새 키(`ranking:all:20260407`)는 비어 있어서 랭킹이 텅 빈 상태로 노출됩니다.
이 "콜드 스타트" 문제를 해결하기 위해 전날 Score를 Carry-Over하는 스케줄러를 만든다면,
**어느 비율로 carry해야** 하는지(100%? 감쇠 적용?) 어떤 기준으로 결정하나요?

## 3. Kafka Consumer → ZSET 적재 관련

### Q6. 배치 리스너에서의 집계 최적화 전략
단건 처리 시 매 메시지마다 `ZINCRBY`를 호출하면 Redis 연산이 과도해질 수 있어서
배치 리스너로 묶어 처리하라는 가이드가 있습니다.
이때 **애플리케이션에서 Map으로 점수를 합산한 뒤 한 번에 ZINCRBY**하는 방식과,
**Redis Pipeline으로 여러 ZINCRBY를 묶어 보내는 방식** 중 어느 쪽이 더 일반적인가요?
두 방식의 트레이드오프가 궁금합니다.

### Q7. Consumer 장애 시 점수 정합성
Consumer가 메시지를 컨슘하고 ZSET에 반영하기 전에 죽으면,
Kafka offset은 커밋되지 않아 재처리되지만 — **이미 ZINCRBY가 된 상태에서 재처리되면 점수가 중복 반영**됩니다.
랭킹처럼 "정확하지 않아도 되는" 시스템에서는 이 정도 오차를 허용하는 게 일반적인가요?
아니면 멱등성을 보장하는 별도 처리가 필요한가요?

## 4. Ranking API 설계 관련

### Q8. 상품 상세 정보 Aggregation 전략
ZSET에는 productId와 score만 있으므로, 랭킹 조회 시 **상품 상세 정보를 어디서 가져올지** 결정해야 합니다.
- (A) ZSET 조회 후 productId 목록으로 DB 조회 (N+1 or IN query)
- (B) 상품 정보를 Redis Hash에 캐싱해두고 조회
- (C) 랭킹 전용 Denormalized 테이블 유지

실무에서는 랭킹 페이지의 트래픽 특성상 어떤 방식을 주로 사용하나요?

### Q9. 페이지네이션과 실시간 랭킹의 충돌
랭킹이 실시간으로 변하는 상황에서 page=1 → page=2로 넘어가는 사이에
순위가 바뀌면 **같은 상품이 두 페이지에 나오거나, 아예 안 나오는 문제**가 생깁니다.
ZRANGEBYSCORE나 커서 기반으로 해결할 수 있는지,
아니면 "랭킹은 일정 주기로 스냅샷을 찍어 제공"하는 게 더 현실적인지 궁금합니다.

## 5. 아키텍처 관련

### Q10. 랭킹 집계의 책임 위치 — Streamer vs API 모듈
현재 프로젝트에서 Kafka Consumer는 `commerce-streamer` 모듈에 있고, API는 `commerce-api`에 있습니다.
랭킹 ZSET 적재는 streamer가, 조회는 api가 담당하게 되는데,
**랭킹 도메인의 Score 계산 로직(Weight 적용)이 streamer에만 존재하면**
API 모듈에서 랭킹의 비즈니스 규칙을 알 수 없게 됩니다.
이 로직을 공유 모듈로 분리해야 할까요, 아니면 streamer의 책임으로 두는 게 맞을까요?

### Q11. product_metrics 테이블과 Redis ZSET의 역할 분담
이전 주차에서 이미 `product_metrics` 테이블에 조회수/좋아요수/주문수를 집계하고 있습니다.
이번에 Redis ZSET으로 랭킹을 별도로 관리하면 **두 곳에서 비슷한 데이터를 관리**하게 됩니다.
ZSET은 "실시간 랭킹 조회용", DB는 "영구 저장/분석용"으로 역할을 나누는 게 맞을까요?
아니면 하나로 통합할 수 있는 구조가 있나요?

## 6. 운영/확장 관련

### Q12. Weight 실시간 변경 시 기존 점수 재계산 문제
Weight를 운영 중 변경할 수 있게 만든다면 (e.g. 좋아요 비중을 0.2 → 0.5로),
**이미 적재된 ZSET 점수는 이전 Weight로 계산된 값**입니다.
기존 점수를 전부 재계산해야 할까요?
아니면 "변경 시점부터 새 Weight 적용"으로 충분한지, 실무에서의 판단 기준이 궁금합니다.

### Q13. 랭킹 어뷰징 대응
특정 상품을 반복 조회하거나 주문/취소를 반복해서 점수를 인위적으로 올리는 경우,
랭킹 시스템에서 이를 어떻게 감지하고 대응하나요?
"같은 유저의 같은 상품 조회는 하루 1회만 반영" 같은 규칙을 Consumer에서 처리해야 할까요,
아니면 별도의 안티 어뷰징 레이어가 필요한가요?
