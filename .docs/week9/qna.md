## Q1. 왜 DB로 랭킹을 뽑으면 안 되는가?

**[질문]**
오늘의 인기 상품 랭킹을 DB 집계 쿼리(`COUNT(*) + GROUP BY`)로 구현하면 어떤 문제가 생길까요?

**[답변]**
> 음 일단 집계함수(count)가 작업 소요시간이 꽤 걸리는걸로 알고 있어. 그리고 where 절이나 group by같은 명령어를 쓰게 되면 시간이 더 소요될거 같아. 이것의 정확한 이유는 몰라... 그리고 랭킹페이지를 조회할때마다 DB를 조회하게 되면 커넥션 풀 고갈로 이어질거 같아.

**[후속 질문: GROUP BY 내부 동작]**
`created_at` 인덱스가 있어도 `GROUP BY product_id` 처리를 위해 DB가 내부적으로 뭘 해야 할까요?

**[답변]**
> group by가 내부적으로 어떻게 동작하는지 잘 모르겠네... 그치만 그룹바이는 인덱스를 못 타지 않나...? 그래서 created_at 인덱스로 거른 데이터 안에서 풀 스캔을 해야할거 같은데

**[후속 질문: 1,000명 동시 조회의 낭비]**
이 쿼리가 느린 건 어느 정도 감수할 수 있다고 칩시다. 동시에 1,000명이 조회하면 1,000번의 집계 연산이 동시에 DB에서 돌아가는 건데, 근본적으로 이게 왜 낭비인가요?

**[답변]**
> 그렇게 되면 DB 커넥션 풀이 꽉 차게 되고 매 요청마다 DB를 조회해야 되므로 처리 시간도 많이 소요될거야. 그리고 작업이 길어지면 뒷부분에 들어온 요청을 커넥션 타임아웃도 될 수 있을거 같아.

**[후속 질문: 결과가 다른가 같은가]**
1,000번의 집계 연산 결과가 서로 다른가요, 같은가요?

**[답변]**
> 아 집계 결과가 대부분 같을거 같아. 그렇기에 천 번 다 DB를 조회할 필요가 없겠네

**[정리]**
랭킹은 조회 요청마다 바뀌는 게 아니라 주문/좋아요/조회 이벤트가 발생할 때만 바뀐다. 1,000번의 조회가 모두 같은 결과를 위해 같은 비싼 연산(정렬+해시 집계)을 반복하는 건 순수 낭비. 해결책은 **이벤트 발생 시점에 미리 계산해두고, 조회 시에는 그 결과만 읽어오는 것** — Kafka Consumer → Redis ZSET 파이프라인의 핵심 아이디어.

## Q2. Weight/Score 설계 — 어떤 이벤트에 얼마나 가중치를 줄 것인가?

**[질문]**
조회/좋아요/주문 이벤트에 각각 다른 가중치를 줘야 하는 이유와, 적절한 가중치 값 + 근거를 설명해보세요.

**[답변]**
> 음 조회/좋아요/주문 중에서 가장 의미 있는 행위는 주문이라고 생각해. 사용자가 실제로 해당 제품이 필요하기도 하고, 좋기 때문에 주문이라는 행위로 이어진 것일테니까. 그래서 주문의 가중치가 가장 높아야 하고, 두번째는 좋아요라고 생각해. 사용자가 제품에 좋아요를 눌렀다는건 해당 제품을 구매할 의사가 있다는거니까. 그리고 조회는 빈번하게 일어나고, 사용자가 꼭 그 제품을 구매할 의사가 있지 않아도 볼 수 있는거니까 가장 낮아야 한다고 생각해. 조회/좋아요/주문의 가중치는 각각 0.1/0.2/0.7이 적합하다고 생각해, 회사마다 의도가 달라질 수 있겠지만

**[후속 질문: price × amount의 의미]**
과제 예시에서 주문 Score = `price × amount`인데, 1,000원짜리 1,000건 주문 vs 100만원짜리 1건 주문의 점수가 어떻게 되나요? 이게 "인기 상품" 랭킹에서 의도한 동작인가요?

**[답변]**
> 아 그러네... 음...상대적으로 값싼 물건은 소비자들이 값이 싸기 때문에 제품의 퀄리티라던지 실용성을 크게 고려하지 않은채 구매하는 경우가 있어서 이 부분을 고려한걸까? 그에 반해 100만원 짜리는 가격이 비싸기 때문에 사용자가 해당 제품을 사기까지 고민을 많이 할거 같아.

**[후속 질문: 랭킹의 목적]**
이 랭킹은 "가장 많이 팔린 상품", "가장 많은 매출을 만든 상품", "지금 가장 많이 관심 갖는 상품" 중 어느 목적을 위한 설계인가요?

**[답변]**
> 아 가장 많은 매출을 만든 상품에 포커스를 둔거 같아.

**[후속 질문: log 정규화가 필요한 이유]**
과제에 `정규화 시에는 log 적용도 가능`이라는 힌트가 있는데, 왜 그냥 `price × amount` 그대로 쓰지 않을까요?

**[답변]**
> 음 log를 적용하면 어떻게 되는지는 수학적으로 잘 모르겠지만, 가격이 비싼데 1개 팔린 것과, 만원인데 100개 팔린것의 간극을 표현하고 싶어서일까...?

**[정리]**
- 이벤트별 가중치: 구매 의도 강도 순서 (주문 > 좋아요 > 조회)
- `price × amount` = 매출 절대값 → 고가 상품이 압도적으로 유리
- `log(price × amount)` = 점수 정규화(Score Normalization) → 극단값 억제, 100배 매출 차이가 점수로는 훨씬 작은 차이로 압축됨
- 어떤 방식을 택할지는 "이 랭킹이 무엇을 측정하려는가"라는 비즈니스 목적에 따라 결정

[글감] 랭킹 점수 설계에서 log 정규화가 필요한 이유

## Q3. ZSET 키 전략과 TTL

**[질문]**
ZSET 키를 `ranking:all:{yyyyMMdd}`처럼 날짜별로 분리하는 이유는? 그냥 `ranking:all` 하나에 누적하면 안 되나요?

**[답변]**
> 음 이건 일간 랭킹을 구현하는 것이기 때문에 그 해당 날짜에 해당하는 것들만 계산해서 적용해야 하기 때문일거 같아. 그냥 ranking:all에 적재 해버리면 예를 들어 A상품이 4월 1일에는 엄청 인기 있어서 점수를 많이 얻었는데, 하루 뒤, 이틀 뒤에 인기가 없어도 키를 날짜별로 분리하지 않으면 그 이틀뒤에도 점수가 압도적일 수 있잖아?

**[후속 질문: TTL이 1Day가 아닌 2Day인 이유]**
TTL을 하루(1Day)가 아니라 2Day로 설정한 이유는?

**[답변]**
> 음 내일의 랭킹을 집계할 때, 아무 기반없이 그냥 다 제로베이스에서부터 시작하게 되면 자정을 기준으로 먼저 주문을 한 상품이 결국 1위에 오를 수 있기 때문에, 전날의 데이터를 5프로 혹은 10프로 정도 반영해서 랭킹을 만들어놔야 하기 때문에, 다음날에 전날의 랭킹을 참고하기 위해서 필요하지 않을까?

**[정리]**
TTL 2일은 두 가지 목적을 커버:
1. **전날 랭킹 조회 가능** — TTL 1일이면 자정에 생성되어 다음날 자정에 바로 만료, 4월 7일 오전에 "어제(4월 6일) 랭킹" 조회 불가
2. **Score Carry-Over 가능** — 콜드 스타트 완화를 위해 자정 직후 전날 데이터를 참조해 새 키에 일부 점수를 이월하는 패턴. 사용자가 이 개념을 스스로 유도해냄.

[글감] 콜드 스타트 문제와 Score Carry-Over — 자정에 랭킹이 초기화될 때 생기는 문제와 해결 전략

## Q4. Kafka Consumer 단건 처리 vs 배치 처리

**[질문]**
단건 처리가 "너무 많은 ZSET 연산"을 동반하는 이유는? 1초에 이벤트 1,000개가 들어온다면 어떤 일이 벌어지나요?

**[답변]**
> 음 아마 현재 프로젝트는 내가 배치 처리를 해놨을거야. 질문에 답하자면, 들어온 이벤트 개수당 레디스 연산을 해야돼. 건당 처리하는 것이기 때문에. 예를 들어 같은 제품을 다른 고객 2명이 주문했으면, 같은 제품인데도 불구하고 2번 연산을 해야해.

**[후속 질문: 배치 처리 시 연산 횟수 비교]**
같은 상품 A에 대한 주문 이벤트 100건이 배치로 들어오면, 단건 vs 배치의 Redis 연산 횟수는?

**[답변]**
> 배치 처리는 1번 연산이 이루어지고, 단건은 100번 이루어져

**[후속 질문: 배치 크기를 크게 잡을 때의 단점]**
배치 크기를 크게 잡으면 Redis 연산은 줄어들지만, 반대로 생기는 문제는?

**[답변]**
> 음 컨슈머가 소비하는데 시간이 오래 걸릴거 같아... 설정에서 이벤트 건수가 설정한 값만큼 쌓이면 컨슘을 진행하고 그만큼 안 쌓여도 지정한 시간 뒤에는 컨슘하는 설정값이 있었던거 같은데(뭔지 알려줘). 근데 이것도 단점은 아닌거 같아

**[관련 설정]**
- `max.poll.records` — 한 번의 poll에 최대 몇 건 가져올지 (배치 크기 상한)
- `fetch.max.wait.ms` — 그 건수가 안 차도 최대 몇 ms 기다렸다가 가져올지

**[후속 질문: 랭킹 실시간성]**
배치 크기를 1,000건으로 잡으면 1,000건이 쌓일 때까지 Redis에 아무것도 반영이 안 되는데, 그 사이에 랭킹 API를 조회하면?

**[답변]**
> 아~~ max.poll.records를 너무 크게 잡거나, fetch.max.wait.ms를 너무 크게 잡으면 랭킹 반영에 좀 지체가 될거 같아. 랭킹이 빨리 바뀔 수 있음에도 그 시간동안은 전혀 영향을 받지 않을거 같아.

**[정리]**
배치 크기 ↑ → Redis 연산 횟수 ↓, 랭킹 반영 지연 ↑  
배치 크기 ↓ → Redis 연산 횟수 ↑, 랭킹 반영 지연 ↓  
"오늘의 인기 상품"은 수초 지연이 체감되지 않아 배치를 크게 잡아도 OK. 실시간 트렌딩이라면 배치 크기를 줄이거나 `fetch.max.wait.ms`를 짧게.

[글감] 배치 리스너 설정과 랭킹 실시간성 트레이드오프

## Q5. 랭킹 API — 상품 정보 Aggregation & 캐시 무효화

**[질문]**
Redis ZSET에는 `(score, productId)`만 있는데, 랭킹 API 응답에 상품명/가격을 포함하려면? N+1은 어떻게 피하나요?

**[답변]**
> 음 일단 DB를 조회해야할거 같아..N+1이 생긴다면 in절 쿼리로 조회하고, 어플리케이션 레벨에서 랭킹순으로 조합하면 되지 않을까...? 또 다른 방법이 있으려나?

**[후속 질문: Redis 캐시 활용]**
IN 쿼리 외에 Redis를 이미 쓰고 있다는 점에서 다른 방법은?

**[답변]**
> 음 레디스를 통해서 상품 정보를 캐싱해야 할거 같아! 그냥 string으로 캐시하면 되려나...?

**[후속 질문: 캐시 무효화 시점]**
관리자가 상품 가격을 변경하면, 캐시된 정보는 어떻게 처리해야 할까요?

**[답변]**
> 음 일단 첫번째 드는 생각은 랭킹 페이지에서 굳이 가격을 보여줘야하나? 싶기도 하고. 관리자가 상품 가격을 변경하면 캐시도 evict하고 다시 캐싱해야겠지? 아니면 어차피 PDP로 가면 정확한 상품가격을 확인할 수 있으니 랭킹페이지에 가격이 다르게 나오는 트레이드 오프는 감수할 수 있을거 같기도 하고

**[후속 질문: eviction 레이어 위치]**
현재 상품 가격 수정 코드 흐름에서 캐시 eviction을 어느 레이어에 넣어야 하나요?

**[답변]**
> 지금 캐시 evict가 구현되있는 부분은 productAdminFacade에서 관리자가 상품정보를 변경한 후에 하나의 트랜잭션 안에서 evict 이벤트를 발행시키고 있어. 스프링 어플리케이션 이벤트로. 음 이게 레이어 아키텍쳐 원칙상 문제는 없어보이는데 혹시 문제가 있을까?

**[후속 질문: 트랜잭션 내 eviction 타이밍 문제]**
트랜잭션 안에서 캐시 evict를 하면 — 캐시 evict 후 DB 커밋 전에 다른 요청이 들어오면 어떻게 되나요?

**[답변]**
> 음 phase를 After_commit으로 하면 될거 같아. 근데 이렇게 한다고 해도 stale closure 문제가 완전히 사라지나...?

**[정리]**
- 상품 정보 조회: IN 쿼리 or Redis 캐시(`product:{productId}` → JSON String)
- 캐시 무효화: `@TransactionalEventListener(phase = AFTER_COMMIT)` — commit-to-eviction 사이의 window는 잔존하지만 최소화
- Redis eviction 실패 시: TTL로 최종 보호
- 랭킹 페이지의 약간의 staleness는 PDP에서 정확한 정보를 보여주는 트레이드오프로 허용 가능
- 완벽한 일관성이 필요하다면 캐시 포기 → DB 직접 조회

[글감] 캐시 무효화 타이밍 — AFTER_COMMIT으로 줄일 수 있는 것과 줄일 수 없는 것

## Q6. 콜드 스타트 — Score Carry-Over 이월 비율

**[질문]**
23:50 스케줄러가 다음날 키에 오늘 점수를 일부 이월한다면, 이월 비율을 어떻게 결정할 건가요? 너무 많으면/적으면 각각 어떤 문제가 생기나요?

**[답변]**
> 음 근데 이건 사실 개발자가 정한다기 보다는 회사의 비즈니스 정책에 의해서 정하는게 맞는거 같아. 나는 일단은 10프로를 적용할거 같아. 너무 많이 적용하면 롱테일 문제가 생기기 때문에.

**[후속 질문: 이월이 너무 적으면?]**
이월을 너무 적게 하면(~1%) 어떤 문제가 생기나요?

**[답변]**
> 너무 적게 한다면 거의 점수가 없는 수준이므로 랭킹자료가 의미없게 정렬될거 같아. 그리고 만약 새벽에 구매가 더 많이 발생한 제품들이 일시적으로 상위 랭킹을 차지하겠지?

**[정리]**
- 이월 너무 많음 → 기존 인기 상품이 계속 독점 (롱테일 억압, 부상 상품 진입 불가)
- 이월 너무 적음 → 자정 직후 소수 주문으로 랭킹 왜곡 (콜드 스타트 미해결)
- 적정 이월(~10%) → 전날 인기가 시작점이 되되, 당일 데이터가 빠르게 역전 가능
- 이월 비율 자체는 비즈니스 정책으로 결정 (개발자가 임의로 정할 문제 아님)

## 구현 준비도 판정 — 백지 설계

**[백지 설계 결과]**

> 레디스 sortedSet을 써서 점수 기준으로 자동 정렬. 조회/좋아요/주문이 발생하면 카프카 메세지를 발행하고(메인 트랜잭션과 분리), consumer가 소비할 때 product_metrics 테이블에 집계하고, ZINCRBY로 랭킹 ZSET에 점수 누적.
>
> ZINCRBY를 쓰면 DB 조회 없이 이벤트 delta만 계산해서 바로 누적 가능. product_metrics와 Redis ZSET은 별개 관심사.
>
> Redis가 죽으면 product_metrics가 SSOT 역할을 해야 하는데, 현재 누적 집계 구조로는 일간 랭킹 복원 불가. 이벤트별 row + createdAt 컬럼이 필요.

**커버된 포인트:**
- Redis ZSET + ZINCRBY로 DB 조회 없이 랭킹 누적
- Kafka로 메인 트랜잭션과 랭킹 집계 분리
- product_metrics 테이블 구조 변경 필요성 (SSOT 관점)
- Redis 유실 시 복구 경로 필요

**보완이 필요한 포인트:**
- 키 전략(`ranking:all:{yyyyMMdd}`) 및 TTL 2일 언급 없음
- Score Carry-Over 스케줄러 언급 없음
- 배치 리스너 설정 및 실시간성 트레이드오프 언급 없음

**판정:** 핵심 파이프라인 흐름과 SSOT 관점을 잘 잡았으나, 운영 관련 세부 설계(키 전략/TTL/Carry-Over/배치 설정) 보완 필요

## 추가 고민: product_metrics 테이블 구조 & 이원화 저장

**[고민 1: 실시간 weight 변경을 위한 테이블 구조]**
> weight가 실시간 변경될 수 있으므로 pre-computed score가 아닌 원시 데이터 저장 필요. 집계 최소 단위는 1시간. product_metrics를 시간대별 row로 변경.

**[결론: 테이블 구조]**
```
product_metrics (
  productId     BIGINT,
  viewCount     INT,          -- 해당 시간대 조회수
  likeCount     INT,          -- 해당 시간대 좋아요수
  orderRevenue  DECIMAL,      -- 해당 시간대 주문 매출 합계 (price × amount 스냅샷)
  metricsHour   DATETIME      -- '2026-04-07T14:00:00' (1시간 단위)
)
```
- `orderRevenue`가 price × amount 스냅샷 역할 — 가격 변경 영향 차단
- weight 변경 시: 오늘 시간대별 row → `SUM(viewCount) × newWeight + ...` → ZSET 재생성
- 시간 단위 랭킹(Nice-to-Have)도 자연스럽게 지원

**[고민 2: Redis + DB 이원화 저장의 원자성]**
> Redis와 MySQL은 별도 시스템이라 하나의 트랜잭션으로 원자성 보장 불가. Kafka at-least-once 보장을 활용해 재처리로 해결 가능. 단, ZINCRBY 중복 실행 시 멱등성 문제는 구현 시 고려 필요.
> → 이 부분은 구현하면서 구체화하기로 함.

## 핵심 개념 정리

| 개념 | 요약 |
|------|------|
| **왜 Redis ZSET인가** | DB 집계 쿼리는 같은 결과를 반복 계산하는 낭비. 이벤트 발생 시 미리 계산해두고 조회 시 읽기만 |
| **ZINCRBY** | 현재 score를 읽지 않고 delta만 더함 → DB 조회 없이 랭킹 누적 가능 |
| **키 전략 + TTL** | `ranking:all:{yyyyMMdd}` TTL 2일 — 전날 랭킹 조회 + Carry-Over 참조용 |
| **배치 리스너** | 배치 크기 ↑ → Redis 연산 ↓, 랭킹 지연 ↑. 목적에 맞게 조절 |
| **Score Normalization** | `log(price × amount)`로 고가 상품의 점수 독점 억제 |
| **콜드 스타트** | 23:50 Score Carry-Over(~10%)로 자정 직후 랭킹 왜곡 완화 |
| **캐시 무효화** | `@TransactionalEventListener(AFTER_COMMIT)` + 짧은 TTL로 staleness 최소화 |
| **SSOT** | Redis는 휘발성. product_metrics를 이벤트별 row + createdAt 구조로 유지해야 복구 가능 |

## 구현 연결 포인트

- **ranking_metrics 테이블**: 시간대별 row (metrics_date + metrics_hour) + 원시 데이터(view_count, like_count, order_revenue) + dirty 플래그
- **ranking_weight 테이블**: event_type별 weight 저장 (DB 원장 + Redis 캐시)
- **Kafka Consumer**: 배치 리스너 → productId별 합산 → ranking_metrics UPSERT (dirty=true)
- **SyncScheduler (5초 주기)**: dirty 행 조회 → 오늘치 SUM × weight → ZADD 덮어쓰기 → dirty=false
- **랭킹 API**: ZREVRANGE로 상위 N개 productId 조회 → IN 쿼리 or Redis 캐시로 상품 정보 조합
- **VIEW 이벤트**: ApplicationEvent(비동기) → Kafka 발행. 유실 허용.
- **ORDER_CREATED payload**: items 배열 추가 (productId, price, quantity)
- **CarryOver 스케줄러**: 23:50에 오늘 ZSET → 내일 키에 10% 이월
