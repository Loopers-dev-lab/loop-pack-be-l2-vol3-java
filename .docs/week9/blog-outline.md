# 블로그 작성 가이드 — Redis ZSET 기반 실시간 랭킹 파이프라인

> 목표: "나는 이렇게 구현했다" 나열 × → "이런 문제를 만났고, 왜 이 선택을 했는가"를 독자가 따라 사고하게 만드는 글 ○

---

## 글의 핵심 페르소나

**독자가 얻어가길 바라는 것:**
- "랭킹 서비스, 나도 DB 쿼리로 짜면 안 되는 거 알았는데 왜인지 이제 정확히 설명할 수 있겠다"
- "dirty 플래그 패턴 — 이원화 저장의 원자성 문제를 이렇게 피할 수 있구나"
- "부하 테스트 전에는 몰랐던 Cache Stampede를 실측으로 발견했다는 게 인상적"
- "weight 변경 하나로 오늘 랭킹 전체가 재계산되는 구조, 설계가 깔끔하다"

---

## 권장 글 구성 (흐름)

### 1. 도입부 — "인기 상품 랭킹, 왜 어려운가"
**핵심 긴장 관계를 먼저 제시한다.**

- DB `COUNT(*) + GROUP BY` 접근의 문제를 설명하되, "느리다"로 끝내지 않기
- "1,000명이 동시에 조회할 때 모두 같은 결과를 위해 같은 연산을 반복한다" — 이 낭비의 본질을 짚기
- 독자의 공감 포인트: "나도 처음엔 DB 쿼리로 뽑으려 했다"
- 이 글이 다룰 것: 이벤트 발생 시 미리 계산해두고, 조회 시 읽기만 하는 구조

**담을 내용:**
- `GROUP BY`가 인덱스를 타도 왜 비싼가 (정렬 or 해시 집계 단계 필요)
- 1,000번 동시 조회 = 1,000번 동일 연산 → 캐싱 적합성의 근거
- "조회 요청마다 랭킹이 바뀌지 않는다, 이벤트가 발생할 때만 바뀐다" 라는 핵심 통찰

---

### 2. 파이프라인 설계 — "이벤트가 랭킹이 되기까지"
**구조를 먼저 그림으로, 그다음 각 선택의 이유를 설명한다.**

```
VIEW/LIKE/ORDER 이벤트
    → Kafka
        → Consumer (ranking_metrics UPSERT, dirty=true)
            → SyncScheduler 5초 주기 (dirty 행 → SUM × weight → ZADD)
                → Redis ZSET
                    → 랭킹 API
```

**이 흐름에서 독자에게 물음을 던질 포인트들:**

**2-1. "왜 ZINCRBY 대신 DB → ZADD 덮어쓰기인가?"**
- 처음 떠오르는 설계: Consumer에서 바로 `ZINCRBY`로 Redis에 점수 누적
- 문제: weight가 바뀌면 이미 쌓인 점수 수정 불가 / Redis 유실 시 복구 불가
- 선택한 이유: DB가 SSOT(원시 데이터), Redis는 계산된 점수의 서빙 레이어
- **이 결정의 핵심**: "Redis는 휘발성이다. DB만이 신뢰할 수 있는 원천이다"

**2-2. dirty 플래그 패턴 — 이원화 저장의 원자성 딜레마 해결**
- MySQL과 Redis는 하나의 트랜잭션에 참여할 수 없다
- "Consumer가 DB에 저장하고 바로 Redis에도 쓰면?" → 둘 중 하나 실패 시 불일치
- dirty=true로 마킹 → 스케줄러가 성공 시에만 dirty=false → 재처리 보장
- ZADD 덮어쓰기이므로 스케줄러 재실행은 완전 멱등
- 독자 인사이트: "원자성을 보장할 수 없으면, 재처리가 안전한 구조로 설계하라"

---

### 3. 점수 설계 — "무엇이 인기인가를 수치로 정의하기"
**"정답이 없는 결정"을 어떻게 논리적으로 내렸는지 보여준다.**

**3-1. 이벤트별 가중치: 조회/좋아요/주문**
- 구매 의도 강도 순서로 weight 부여하는 이유
- weight를 DB 테이블(`ranking_weight`)에 관리하는 이유: 코드 배포 없이 비즈니스 정책 변경 가능

**3-2. log 정규화 — `log(1 + x)` 적용 이유**
- `price × amount` 그대로 쓰면: 100만원짜리 1건 vs 1,000원짜리 1,000건
- 100배 매출 차이가 점수로도 100배 차이 → 고가 상품 독점
- `log1p`로 극단값 억제: 1,000배 매출 차이가 점수 차이로는 ~3배 수준으로 압축
- 코드 한 줄: `Math.log1p(summary.totalOrderRevenue().doubleValue()) * orderWeight`

**3-3. weight 변경 시 오늘 랭킹 전체 재계산**
- weight 캐시 TTL(300s) 만료 후 새 weight 적용 → 오전/오후 기준이 다른 혼재 문제
- 해결: `UPDATE ranking_metrics SET dirty=true WHERE metrics_date=today` → 스케줄러가 전부 재ZADD
- 부하 테스트 결과: 3,000행 재처리 중 랭킹 API P99 155ms → 159ms (사실상 무변화)
- 이유: Cache-Aside 레이어가 스케줄러 스파이크 흡수 (두 레이어가 독립 동작)

---

### 4. 캐싱 전략 — "두 번의 캐시, 각각의 역할"
**이 섹션이 이 글에서 가장 인사이트가 풍부한 부분이 될 수 있다.**

**4-1. 리팩토링 전 병목 발견 스토리**
- 처음 구현: Redis ZSET에서 productId 목록 → 매 요청마다 DB IN 쿼리
- "Redis 쓰는데 왜 느리지?" → RankingFacade가 ProductFacade(캐시 있음)가 아닌 ProductService 직접 호출
- 부하 테스트 Before: P95 172ms (threshold 50ms ❌ 3.4배 초과)

**4-2. 결과 캐시 도입 (Cache-Aside)**
- 캐시 키: `loopers:ranking:daily:{date}:p{page}:s{size}`
- TTL 30초: 스케줄러 5초 주기보다 길어도 되는 이유 (랭킹은 수초 지연 허용)
- 읽기는 Replica, 쓰기는 Master — `REPLICA_PREFERRED` 설정 효과
- 부하 테스트 After: P95 82ms, RPS 2배 (+97%)

**4-3. Cache Stampede — "캐시를 도입했는데 P99가 여전히 튀는 이유"**
> 이 부분이 블로그의 하이라이트가 될 수 있음. 실측으로 발견한 구조적 한계.

- TTL 30초마다 만료 순간 100개 VU가 동시에 캐시 미스 → DB IN 쿼리 동시 폭발
- P99 374ms → 155ms로 개선됐지만 여전히 threshold(100ms) 초과
- 완전 해결책: Singleflight(동일 키 DB 조회를 정확히 1회만) 또는 Probabilistic Early Expiration
- 현재는 "허용 가능한 트레이드오프"로 수용한 이유 설명

**담을 내용 요약:**
```
레이어 1: Redis ZSET (이벤트 기반 점수 저장, TTL 2일)
레이어 2: Result Cache (조립된 페이지 결과, TTL 30초)
→ 두 레이어가 독립적이기 때문에 스케줄러 스파이크와 API 레이턴시가 분리됨
```

---

### 5. 키 전략과 TTL — "날짜별 키 분리와 2일 TTL의 이유"
짧지만 독자가 "아, 그렇구나" 하는 포인트.

- `ranking:all:{yyyyMMdd}` — 날짜별 분리 이유: 누적 시 어제 인기 상품이 오늘도 1위
- TTL 2일 이유: 전날 랭킹 조회 + (Nice-to-Have) Score Carry-Over 참조용
- "TTL을 1일로 하면 자정에 `어제 랭킹` 조회가 불가능해진다" — 이 케이스를 짚어주면 기억에 남음

---

### 6. 부하 테스트로 검증한 것들 (선택적 섹션)
**숫자가 있으면 설득력이 높아진다. 단, 숫자 나열이 아닌 "무엇을 확인하려 했고, 무엇을 발견했는가"로.**

| 시나리오 | 확인하려 한 것 | 발견한 것 |
|---------|-------------|---------|
| VIEW 폭주 (100VU, 60s, 9상품) | DB deadlock 여부 | `ON DUPLICATE KEY UPDATE` row-level lock 경합 없음 |
| 랭킹 API 조회 (Before/After) | 캐시 효과 | RPS 2배, P95 3.4배 → 1.6배 개선. But Cache Stampede 구조적 잔존 |
| weight 변경 스파이크 | 스케줄러 부하가 API에 전파되는지 | 두 레이어 독립 동작으로 P99 무변화 확인 |
| 토픽 혼재 (VIEW:LIKE = 12:1) | 분리가 필요한가 | 현재 규모에서는 단일 토픽으로 충분. 이벤트 유실 0건 |

---

### 7. 마무리 — "설계를 되돌아보며"
**"이렇게 구현했다" 요약이 아니라, 핵심 판단 3가지를 뽑아 독자에게 남겨준다.**

추천 마무리 3가지 메시지:
1. **DB는 SSOT, Redis는 서빙 레이어** — 역할을 분리하면 장애와 변경 모두 대응 가능
2. **캐시는 문제를 해결하지만, 새로운 문제(Stampede)를 만든다** — 부하 테스트 없이는 보이지 않는다
3. **점수 설계는 기술 문제가 아니라 비즈니스 문제다** — `log1p`를 쓸지, 순수 매출을 쓸지는 "이 랭킹이 무엇을 측정하는가"에서 출발

### 권장 패턴
- 문제 상황 → 첫 번째 떠오른 해결책 → 그것의 한계 → 실제 선택 → 이유
- 반례/대안을 먼저 제시하고 기각하는 흐름 ("~하면 어떨까? → 이런 문제가 생긴다")
- 부하 테스트 결과는 표보다 "Before → After → 아직 남은 것" 흐름으로

### 글감별 분리 vs 단일 글
이 내용은 하나의 긴 글보다 **2개 글로 분리**하는 게 읽기 좋을 수 있음:

**글 A: "실시간 랭킹 파이프라인 설계"**
- 섹션 1~3 (왜 DB가 안 되는가 + 파이프라인 구조 + 점수 설계)
- 메시지: dirty 플래그 패턴과 이원화 저장 원자성 문제

**글 B: "랭킹 API에 캐시를 붙였더니 생긴 일"**
- 섹션 4~6 (캐시 전략 + Cache Stampede 발견 + 부하 테스트)
- 메시지: 캐시는 문제를 해결하고 새 문제를 만든다
