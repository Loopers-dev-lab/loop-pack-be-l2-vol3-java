## Phase 1: 대기열 진입 & 순번 조회

### 재료 1: "ZADD NX vs ZADD — 공정한 대기열을 위한 선택"

**상황**: 대기열에 이미 있는 유저가 진입 요청을 다시 보낼 때 어떻게 처리할 것인가.

**두 가지 선택지와 trade-off**:
- `ZADD NX` (addIfAbsent): 기존 진입자의 score(타임스탬프)를 유지. "재진입해도 순번이 보호된다" → 유저가 무분별하게 재진입 버튼을 눌러도 위험 없음.
- `ZADD` (add): 기존 진입자의 score를 현재 타임스탬프로 갱신 → 맨 뒤로 이동. "진입은 한 번의 행동이다. 다시 진입하면 맨 뒤로" → 단순하고 직관적인 정책.

**선택 근거**: 대기열 진입(`POST /enter`)은 명시적인 사용자 행동이다. 폴링(`GET /position`)은 순번 확인용이므로 재진입과 다르다. `POST /enter`를 다시 호출하면 "다시 줄 서기"로 간주하는 것이 비즈니스적으로 더 명확하다.

**핵심 인사이트**: Redis Sorted Set의 ZADD 플래그(NX/XX/GT/LT) 선택 하나가 "대기열의 공정성 정책"을 결정한다.

### 재료 2: "Redis 호출 순서 최적화 — 조건문 순서가 성능을 결정한다"

**상황**: 순번 조회 API(`GET /position`)에서 Redis를 총 3번 호출해야 한다.
- 토큰 존재 여부 확인 (`EXISTS entry-token:{userId}`)
- 순번 조회 (`ZRANK`)
- 전체 인원 조회 (`ZCARD`)

**나이브한 구현**: 토큰 확인 먼저 → 항상 3회 호출.

**최적화**: ZRANK 먼저 → rank != null이면 토큰 확인 불필요 (대기 중인 유저, 즉 대부분의 경우 2회).

**수치화**:
- 대기자 10,000명, 폴링 주기 1초 → 나이브: 초당 30,000 Redis 명령
- 최적화 후: 대기 중 유저는 20,000 명령 (33% 감소)
- 토큰 발급 직후 유저만 3번 호출

**핵심 인사이트**: "어떤 조건이 더 자주 참인가"를 먼저 체크하는 것이 다중 조건 분기 최적화의 기본이다.

### 재료 3: "tokenIssued 플래그 — 서버 사이드 토큰 + 클라이언트 리다이렉트 패턴"

**상황**: 클라이언트는 토큰 값을 알 필요가 없다. 토큰은 `entry-token:{userId}`로 서버에 저장되고, 주문 API에서 userId로 자동 검증된다.

**폴링 응답에 `tokenIssued: true`를 넣는 이유**:
- 클라이언트 입장에서는 "주문 페이지로 이동할 수 있는가"라는 상태 전이 신호만 필요하다.
- 토큰 값 자체를 응답에 담으면 클라이언트가 그것을 헤더에 넣어야 하고, CSRF/토큰 탈취 리스크가 생긴다.
- userId 기반 토큰 키(`entry-token:{userId}`)이므로, 클라이언트가 토큰을 갖고 있을 필요가 없다.

**연결 포인트**: `entry-token:{userId}` 키 설계가 "클라이언트 토큰 노출 최소화"라는 보안 이점도 자연스럽게 가져온다.

### 재료 4: "@Scheduled 단일 스레드 함정 — OutboxRelayScheduler + EntryTokenScheduler 충돌"

**상황**: Spring Boot 기본 `@Scheduled` 스레드 풀 크기는 1이다. Week 7에서 만든 `OutboxRelayScheduler`가 이미 이 스레드를 점유하고 있다.

**문제**: `EntryTokenScheduler`가 100ms마다 실행되어야 하는데, `OutboxRelayScheduler`가 실행 중인 동안 대기한다. "초당 10회 실행" 전제가 깨진다.

**해결**: `spring.task.scheduling.pool.size: 2` — 스레드 2개짜리 풀로 확장. 스케줄러마다 전용 스레드 확보.

**글감 포인트**: "당신이 `@Scheduled`를 쓸 때 몰랐던 것 — 기본 스레드 풀은 1개다"
