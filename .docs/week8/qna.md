## Q1. 대기열의 필요성

**[질문]**
블랙 프라이데이에 주문 트래픽이 100배 폭증하는 상황을 가정해봅시다. 서버를 10대로 늘리거나(스케일 아웃), 더 좋은 서버로 교체하는(스케일 업) 방식으로는 이 문제를 근본적으로 해결할 수 없습니다. 왜 그렇다고 생각하시나요?

**[답변]**
> 음 서버가 was 서버를 말하는건지 DB 서버를 말하는건지 모르겠지만, 서버를 늘린다 하면 요청 수는 많이 받을 수 있지만 결국 주문을 받으려면 DB에 기록해야 하는데 그게 카프카를 이용했던, 실제 그냥 DB에 바로 저장하면 처리량에 제한이 있기 때문에 스케일 아웃이던 스케일 업이던 어려울거 같아.

**[후속 질문: DB 스케일 아웃의 한계]**
좋은 포인트를 짚었습니다! WAS를 늘려도 결국 DB가 병목이 된다는 핵심을 잘 파악하고 있네요. 그럼 한 가지 더 여쭤볼게요. "DB도 스케일 아웃하면 되지 않냐"는 반론이 나올 수 있잖아요. DB 자체를 여러 대로 늘리는 것은 왜 이 상황에서 현실적인 해결책이 되기 어려울까요?

**[답변]**
> 음 DB를 스케일 아웃하는건...내가 잘 모르지만 DB를 스케일 아웃 하면 예를 들어 master와 replication의 관계로 만든다고 쳤을 때, 결국 쓰기는 master DB에만 하고 나머지 replication에는 내가 어떤 방법인진 잘 모르지만 master DB에 쓰고 난 후에 동기화를 해주는 것으로 알고 있어. 그럼 결국 DB를 여러대 늘려도 결국 쓰기 작업은 똑같기 때문에 그렇지 않을까...?

**[후속 질문: 오토스케일링의 한계]**
정확합니다! Master-Replica 구조에서 쓰기는 결국 Master 한 대에 집중된다는 점을 잘 짚었어요. 그럼 마지막으로 하나만 더 생각해보세요. 비용이나 시간적 측면은 무시하더라도, 트래픽 폭증의 특성 자체가 스케일링을 어렵게 만드는 이유가 있습니다. 블랙 프라이데이 행사 시작 직후의 트래픽 패턴을 떠올려보면 — 오토스케일링이 왜 이 상황에서 무력한지 감이 오시나요?

**[답변]**
> 음 오토스케일링이 들어오는 주문량에 맞춰서 알아서 DB가 스케일 아웃되는 방식인거야? 오토스케일링이 어떤건지 정확히 모르겠어. 근데 어쩄든 질문의 의도는 폭증하는 트래픽을 예측하기 어려울때는 그 트래픽에 맞춰서 자동으로 스케일 아웃을 하는 것이 어려울거 같아. 블랙 프라이데이 직후 패턴을 보면 트래픽이 갑자기 피크를 찍으니까. 근데 반대로 블랙프라이데이라면 미리 트래픽 폭증을 예상하고 스케일 업? 스케일 아웃? 하면 되지 않나...? 근데 내가 아까 말한 제약들 때문에 결국에는 효과가 없나?

**[정리]**
오토스케일링은 클라우드 환경에서 CPU, 메모리 등의 지표를 모니터링하다가 임계치를 넘으면 자동으로 서버 인스턴스를 늘려주는 기능. "이미 터진 다음에 반응"하기 때문에 극단적 피크에는 늦고, 미리 WAS를 늘려놔도 결국 DB 쓰기는 Master 한 대에 집중됨. 결국 하류 시스템(DB)이 감당할 수 있는 속도로 상류(유저 요청)를 조절하는 **Back-pressure** 개념이 필요하고, 대기열이 이를 구현하는 대표적인 방법.

## Q2. Rate Limiting vs Queuing

**[질문]**
트래픽을 조절하는 방법으로 Rate Limiting(초과 요청을 거부)과 Queuing(대기열에 보관) 두 가지가 있습니다. 블랙 프라이데이 주문 시나리오에서 Rate Limiting 대신 대기열을 선택해야 하는 이유는 뭘까요? 그리고 반대로 Rate Limiting이 더 적합한 상황은 어떤 경우일까요?

**[답변]**
> 음 블랙프라이데이에는 많은 고객들이 물건을 사고 싶어하고, 또 많은 요청이 몰릴것을 유저 대부분도 다 어느정도 예측을 하고 있기 때문에, rate limiting으로 아예 요청을 제한시키는 것보다는 대기열을 사용함으로써 아 그래도 내가 대기열에 진입했고, 몇번째에 위치하고 있고 얼마 지나면 주문을 할 수 있겠구나 라는것을 시각적으로 보여주는 좋은 ux같다는 생각이 들어.
> rate limiting이 더 적합한 상황은... 음 선착순 쿠폰 같은 경우...? 아니면 뭔가 애초에 수량이 제한되어 있어서 더 이상 요청을 받을 필요가 없을 경우?

**[후속 질문: Rate Limiting의 적합한 상황]**
Rate Limiting은 "유저의 요청 자체를 거절"하는 방식인데, 이게 오히려 좋은 상황은 어떤 건지 — 유저가 아닌 "요청의 성격" 측면에서 생각해보시겠어요? 예를 들어, 정상적인 유저라면 초당 수십 번씩 같은 API를 호출할까요?

**[답변]**
> 아 악성유저나 아니면 봇,매크로를 사용해서 제품을 싹쓸이 해가기 위해서 비정상적인 요청을 보낼 경우에는, 서버에 부하가 엄청 크고 다른 정상적인 사용자들이 주문을 하는 것을 방해할 수 있으니까, 이런 요청들에는 rate limiting을 적용해야 할거 같아.

**[정리]**
대기열은 "유저가 기다릴 의사가 있는" 상황(블랙 프라이데이 주문)에 적합하고, Rate Limiting은 봇/매크로 같은 비정상 요청 차단에 적합. 실제 서비스에서는 둘을 함께 사용 — Rate Limiting으로 비정상 요청을 먼저 걸러내고, 정상 유저만 대기열에 진입시키는 상호 보완적 구조.

## Q3. Redis Sorted Set을 대기열 자료구조로 선택한 이유

**[질문]**
대기열을 구현할 때 여러 자료구조를 쓸 수 있습니다 — Redis의 List, Set, Sorted Set, 또는 Kafka 같은 메시지 큐도 가능하죠. 이 중에서 Sorted Set을 선택한 이유는 뭘까요? 대기열에 필요한 연산들을 떠올려보면서, Sorted Set이 어떤 점에서 유리한지 생각해보세요.

**[답변]**
> 음 내가 사실 레디스 자료구조를 정확히는 잘 모르지만 sortedSet은 정렬시킬 수 있고, 또 동일한 키로는 덮어쓰기를 할 수 있다고 알 고 있어. 그리고 대기열은 사용자들이 자신이 몇번째에 위치하는지 알 수 있어야 하는데 list는 예를 들어 중간에 위치하는 사용자를 찾으려면 처음이나 끝에서부터 순차적으로 조회가 가능한데 sortedSet은 마치 mysql의 인덱스 비트리 구조같이 되어있다고 알고 있어서, 훨씬 더 빠르게 사용자의 위치를 조회할 수 있는 것으로 알고 있어. 또 대기열에서 일부 유저들을 api에 진입할 수 있게 만드는데도 sortedSet이 적합한 것으로 알고 있어. 내가 말한게 맞을까?

**[후속 질문: 동일 timestamp 충돌]**
아주 잘 알고 계시네요! 핵심을 거의 다 짚었습니다. 정리하면: (1) score 기반 자동 정렬로 선입선출 보장, (2) 같은 member(userId)로 ZADD하면 덮어쓰기 → 중복 진입 자동 방지, (3) Skip List 구조라서 ZRANK O(log N) 순번 조회, (4) ZPOPMIN으로 가장 먼저 들어온 N명을 원자적으로 꺼낼 수 있음. 그럼 여기서 하나 더 — Sorted Set의 score를 timestamp로 사용한다고 했는데, 만약 두 유저가 정확히 같은 밀리초에 진입하면 어떻게 될까요? 순서가 보장될 수 있을까요?

**[답변]**
> 음 사실상 보장하기 어려울거 같아. 일단 score가 같으면 어떻게 되는거지...?그냥 userId의 문자 숫자 크기순으로 정렬되려나...?

**[후속 질문: 동일 score 공정성 완화 방법]**
맞습니다! Redis Sorted Set에서 score가 같으면 member(userId)의 사전순(lexicographical order)으로 정렬됩니다. 그렇다면 이게 "공정한" 대기열이라고 할 수 있을까요? 이 문제를 완화할 수 있는 방법이 있을지 생각해보세요. 힌트: score의 정밀도를 높이는 방법이 있을 수도 있고, 다른 접근도 가능합니다.

**[답변]**
> 음 일단 내 생각에는 정말 완벽히 공정한 대기열이라는 것을 구현하는건 좀 불가능한거 같아. 밀리초가 아니라 마이크로초, 나노초로 해도 이론상 동시에 들어올 수 있으니까 좀 불가능해보여. 아니면 내가 잘 모르지만 score에 timestamp에 뭐 또 숫자를 붙이는것도 가능한가...?

**[정리]**
실무에서는 nanosecond timestamp + 원자적 카운터(INCR) 조합 방식 등을 사용할 수 있으나, 이론상 완벽한 공정성은 불가능. 같은 밀리초에 들어온 유저 간 순서 차이는 체감상 불공정하다고 느끼기 어려우므로, "이론적 완벽함"보다 "실용적으로 충분한 공정성"을 선택하는 것이 좋은 설계 판단.

## Q4. 입장 토큰과 스케줄러 설계

**[질문]**
대기열에서 순서가 된 유저에게 입장 토큰을 발급하고, 이 토큰이 있어야만 주문 API에 진입할 수 있습니다. 토큰의 TTL(만료 시간)을 몇 분으로 설정할 건가요? 그리고 그 기준은 무엇인가요? 너무 짧으면, 너무 길면 각각 어떤 문제가 생길지 생각해보세요.

**[답변]**
> 음 일단 넉넉하게 잡아야 할거 같아.너무 짧으면 유저가 주문하는 와중에 TTL이 만료되서 주문을 완료하지 못하는 상황이 발생할거야.
> 너무 길면, 입장 토큰을 받고도 아무것도 하지 않는 유저도 있을 수 있는데 이런 경우에 긴 TTL이 끝나야 다음 유저가 입장할 수 있으므로 비효율적일거 같아.

**[후속 질문: 구체적인 TTL 산정]**
양쪽 trade-off를 잘 파악하셨어요. 그럼 구체적으로 몇 분이 적절하다고 생각하시나요? 유저가 토큰을 받은 후 주문을 완료하기까지 어떤 행동을 하는지 떠올려보세요. 상품 선택, 배송지 입력, 결제 수단 선택, 결제 처리... 이 과정에 보통 얼마나 걸릴까요?

**[답변]**
> 음 일단 나는 상품을 조회하는 것에는 대기열을 안 걸거 같고, 주문하기를 누른 순간부터 대기열을 걸거 같은데, 그렇다면 대략 5분...?

**[후속 질문: 대기열 진입 시점과 재고 문제]**
5분은 합리적인 선택이에요. 실제로 많은 서비스에서 3~5분 정도로 설정합니다. 그런데 방금 중요한 설계 포인트를 짚으셨어요 — "주문하기를 누른 순간부터 대기열에 진입한다"고 하셨는데, 대기열 진입 시점이 "주문하기 버튼을 누른 순간"이라면, 유저는 이미 상품을 골라놓고 결제 직전인 상태예요. 이 상태에서 대기열에서 10분을 기다리는 동안, 해당 상품의 재고가 다른 유저에 의해 소진될 수도 있지 않을까요? 유저 입장에서 어떤 경험이 될지 생각해보세요.

**[답변]**
> 음 그 부분은 생각 못 했네... 그럼 유저는 10분을 기다렸는데도 결국 결제하지 못하게 되서 기분이 안 좋을거 같아.

**[후속 질문: 대기열 진입 시점 재설계]**
맞아요, 10분 기다렸는데 "품절입니다" 하면 최악의 UX죠. 그렇다면 대기열 진입 시점을 어디로 옮기면 이 문제를 완화할 수 있을까요? 유저가 사이트에 접근하는 전체 흐름을 떠올려보세요 — 상품 목록 조회, 상품 상세 조회, 주문하기, 결제... 어느 시점에 대기열을 두는 게 좋을까요?

**[답변]**
> 음 상품 목록 조회나 상품 조회는 단순히 조회니까 여기에 대기열을 걸진 않을거 같아. 어차피 이건 캐시로 해결되니까 부하도 크지 않을테고...결국 재고가 차감되는 그 시점의 aggregate에 대기열이 걸려야할거 같은데...그럼 결제? 근데 결제가 결국 주문에 포함되는거 아닌가...?

**[후속 질문: 사이트 진입 대기열]**
좋은 고민이에요! 조회는 캐시로 해결되니 대기열이 필요 없다는 판단도 맞고요. 사실 이건 대기열을 어떤 범위에 두느냐의 문제예요. 두 가지 접근이 있습니다: (1) 주문 API 앞에 두기 — 지금 생각하신 방식, (2) 사이트 자체 진입에 두기 — 인터파크, 지마켓처럼 "접속 대기" 화면. 실제로 블랙 프라이데이 때 쇼핑몰에 접속하면 "현재 접속자가 많아 대기 중입니다" 화면을 본 적 있지 않나요? 그건 어떤 시점에 대기열을 건 걸까요? 그리고 그 방식이라면 아까의 "기다렸는데 품절" 문제가 어떻게 달라질까요?

**[답변]**
> 아 그건 그냥 상품 목록 조회 시점에 대기열을 건거 같아.이 방식이라면 함께 대기열에 진입한 사람들끼리 남은 재고를 가지고 경쟁을 할 수 있으니까 결제하는데까지 엄청 오래 기다릴 필요는 없을거 같아.

**[정리]**
대기열 진입 시점에 따라 두 가지 접근이 있음: (1) 사이트 진입 대기열 — 입장 후 여유롭게 주문 가능하지만 조회만 하려는 유저도 대기, (2) 주문 API 대기열 — 조회는 자유롭지만 기다렸는데 품절 가능성. 서비스 특성에 따른 trade-off이며, 이번 과제에서는 주문 API 앞단에 대기열을 두는 방식으로 구현.

## Q5. 스케줄러 배치 크기 산정

**[질문]**
스케줄러가 대기열에서 N명씩 꺼내 토큰을 발급합니다. 이 N(배치 크기)을 어떻게 산정할 건가요? 어떤 수치를 기준으로 계산할 수 있을지 생각해보세요.

**[답변]**
> 음 처리량이 중요할거 같아. 초당 처리량을 기준으로 대기열에서 입장시키면 될거 같은데, 이 처리량을 어떻게 계산하는게 좋을지는 아직 잘 모르겠어.....

**[후속 질문: TPS 계산 힌트]**
처리량이 핵심이라는 방향은 정확해요! 힌트를 드릴게요. 주문 1건을 처리하려면 DB 커넥션 1개를 점유하잖아요. 그렇다면 아래 두 가지 수치를 알면 계산할 수 있어요: (1) DB 커넥션 풀 크기 (예: HikariCP의 maximumPoolSize), (2) 주문 1건의 평균 처리 시간. 이 두 수치로 초당 최대 처리량(TPS)을 어떻게 계산할 수 있을까요?

**[답변]**
> 음 풀 크기 곱하기 주문 1건의 평균 처리 시간 아닐까?

**[후속 질문: TPS 계산 단위 검증]**
거의 다 왔어요! 방향은 맞는데, 단위를 한번 생각해볼게요. 예를 들어 커넥션 풀 50개, 주문 1건 처리 시간 200ms(0.2초)라면: 50 × 0.2 = 10 → 이 단위가 뭘까요? "초당 처리 건수"가 맞나요? 커넥션 1개가 1초에 몇 건을 처리할 수 있는지부터 생각해보면 답이 보일 거예요.

**[답변]**
> 음 0.2초에 1건을 처리할 수 있으니까 초당 처리건수는 1/0.2 해서 5건이네. 그럼 5 곱하기 커넥션 풀 크기 50을 하면 250이네. 초당 처리량은 250이야

**[후속 질문: 안전 마진]**
정확합니다! TPS = 커넥션 풀 크기 / 평균 처리 시간 = 50 / 0.2 = 250 TPS. 그런데 이 250은 이론적 최대치예요. 실제로는 이 수치 그대로 토큰을 발급하면 위험할 수 있는데, 왜 그럴까요? 시스템에 주문 외에 다른 요청도 DB 커넥션을 사용한다는 점을 생각해보세요.

**[답변]**
> 토큰을 250개만큼 받아버리면, 다른 요청이 없다는 전제하에 1초에 다 처리가 되겠지만, 다른 요청도 존재할테니 결국 커넥션 풀을 다 차지하게 되서 too many connection 에러가 발생할거 같아.

**[정리]**
이론적 최대치(250 TPS)의 60~70% 안전 마진을 적용하여 약 175 TPS로 산정. 공식: TPS = 커넥션 풀 크기 / 평균 처리 시간 × 안전 마진(0.7).

## Q6. Thundering Herd 문제

**[질문]**
스케줄러가 1초마다 175명에게 토큰을 발급한다고 해봅시다. 175명이 토큰을 받자마자 동시에 주문 API를 호출하면 어떤 일이 벌어질까요? 그리고 이걸 어떻게 완화할 수 있을지 생각해보세요.

**[답변]**
> 주문을 처리하는데 시간이 걸릴거 같아. 주문에 필요한 재고차감에도 좀 시간이 걸릴테고, 제일 사실상 제일 마지막에 주문 요청이 서버에 온 유저가 주문을 완료하는데 제일 오래 걸릴거 같아.

**[후속 질문: Thundering Herd 완화 방법]**
처리 시간이 늘어나는 건 맞는데, 핵심은 175명에게 "동시에" 토큰을 발급하면 175명이 거의 같은 순간에 주문 API를 호출하게 된다는 점이에요. 이건 대기열로 막으려 했던 순간 부하 스파이크가 그대로 재현되는 거죠. 이 "동시 몰림" 현상을 Thundering Herd(떼몰이)라고 합니다. 이걸 완화하려면 어떻게 하면 좋을까요? "한 번에 175명"이 문제라면, 발급 방식을 어떻게 바꿀 수 있을지 생각해보세요.

**[답변]**
> 아하 175명이 동시에 주문을 하면 DB에 부하가 몰릴 수 있으니까, 입장 토큰을 발급하는걸 약간의 시간차를 두고 하는건 어떨까?

**[후속 질문: 발급 간격 분산 구체화]**
좋습니다! 정확한 방향이에요. 구체적으로 어떻게 시간차를 줄 수 있을까요? 예를 들어 1초에 175명을 발급해야 한다는 건 변하지 않는데, 1초를 더 잘게 쪼개서 발급하면 어떻게 될까요? 몇 ms 간격으로, 몇 명씩 발급하면 좋을지 계산해보세요.

**[답변]**
> 음 구체적으로 어떤 수치로 해야할지는 잘 모르겠어...

**[후속 질문: 100ms 분산 계산]**
같이 계산해볼게요. 스케줄러가 1초마다 175명을 발급한다고 할 때, 1초를 10등분 — 즉 100ms마다 실행하도록 바꾸면 몇 명씩 발급하면 될까요?

**[답변]**
> 17.5명?이니까 대략 18명씩 발급하면 되겠네

**[정리]**
100ms마다 ~18명씩 발급하면 동시 부하가 10배 평탄화됨. 총량(175명/초)은 그대로 유지하면서 순간 스파이크를 분산.

## Q7. Polling 설계와 부하

**[질문]**
유저가 대기 중 순번을 조회하는 방식으로 Polling을 사용합니다. 대기 인원이 10,000명이고 모두 2초마다 순번을 조회한다면, 서버 입장에서 초당 몇 건의 순번 조회 요청이 발생할까요? 그리고 이 부하를 줄일 수 있는 방법이 있을까요?

**[답변]**
> 대기열 만명 그대로 유지된 상태에서 2초마다 순번을 조회한다면 초당 만건의 요청이 들어오는것과 마찬가지일거 같아.

**[후속 질문: 계산 재확인]**
10,000명이 2초마다 1번 조회한다면, 1초에는 몇 번 조회할까요?

**[답변]**
> 아아 만명이 2초마다 1번 조회한다면 1초에 5천번 조회하는것과 같아.

**[후속 질문: Polling 부하 완화]**
맞아요! 5,000건/초입니다. 순번 조회는 Redis 기반이라 DB 부하는 없지만, 5,000건/초라는 숫자 자체는 꽤 크죠. 이 부하를 줄일 수 있는 방법이 있을까요? 힌트: 순번 1번인 유저와 순번 9,000번인 유저가 똑같이 2초마다 조회할 필요가 있을까요?

**[답변]**
> 아니, 그래서 입장에 가까운 순번일수록 자주 조회하고, 입장에서 먼 순번일수록 자주 조회할 필요가 없을거 같아.

**[정리]**
Polling 주기 동적 조절 — 순번 구간에 따라 조회 주기를 다르게 가져감. 예: 순번 1~100은 1초마다, 100~1,000은 3초마다, 1,000+는 5초마다. 전체 Polling 부하를 상당히 줄일 수 있음.

## Q8. Redis 장애 시 어떻게 할 것인가

**[질문]**
대기열의 핵심 인프라인 Redis가 장애 상황에 놓였습니다. 대기열도, 입장 토큰도, 순번 조회도 모두 Redis에 의존하고 있어요. 이 상황에서 우리 서비스는 어떻게 동작해야 할까요? 선택지를 몇 가지 생각해보고, 각각의 장단점도 같이 이야기해보세요.

**[답변]**
> 음 요청을 아예 안 받는 방법도 있겠지만 이건 비즈니스 측면에서 좋지 않은거 같아.
> 그럼 대기열 없이 그냥 바로 모든 요청이 들어오게 하는 방법이 있겠지만, 이게 대기열을 만든 근본적인 이유라서 이것도 좀 위험할거 같아...서버가 죽을 수 있으니까
> 음 또 대기열이 없어졌으니 주문이 생성됐다 라는 이벤트만 발생시키고 나머지 로직은 카프카로 해결하는 방법도 있을거 같은데, 근데 현재는 주문로직에 재고 차감이 있고, PG 요청도 지금 주문로직 한 트랜잭션에 있나...? 그렇다면 이것도 어렵겠네.

**[후속 질문: 사전 정의의 중요성]**
세 가지 선택지를 스스로 모두 떠올리셨네요! 사실 이 질문에는 정답이 없어요. 하지만 한 가지 중요한 포인트가 있는데 — "Redis가 죽은 뒤에 어떻게 할지 그때 가서 판단하면" 어떤 문제가 생길까요?

**[답변]**
> 음 그때 가서 판단한다면 레디스도 죽고 서비스도 죽어서 다른 서비스에도 영향이 갈 수 있기 때문에 아주 끔찍할거 같아.

**[정리]**
장애 상황에서 실시간으로 판단하면 개발자는 패닉 상태, 의사결정자는 연락 안 됨, 그 사이 서비스는 계속 죽어감. "Redis 장애 시 우리 서비스는 어떻게 동작해야 하는가"를 사전에 정의해두는 것 자체가 핵심 — 어떤 선택이든 코드와 운영 가이드에 미리 반영하면 장애 순간에 자동으로 동작함.

## Q9. 입장 토큰 검증 흐름

**[질문]**
유저가 주문 API를 호출할 때 토큰을 어떻게 전달하고, 서버는 어떻게 검증하고, 주문 완료 후 토큰은 어떻게 처리할 건가요?

**[답변]**
> 음 1번 문제는 사실 헤더든 바디든 상관없을것처럼 보이긴 하는데, 상관이 있을까...?
> 2. 서버가 토큰을 발급할 때 레디스에도 토큰을 저장했을 테니까, 유저가 주문 요청시에 함께 보내온 토큰값으로 레디스를 조회해서 해당 토큰이 존재하면 된거지 않을까?
> 3. 주문 완료 후 토큰은 삭제해야 되지 않을까?
> 토큰 키의 경우는 TTL로 자동 만료되지만, active_tokens Set에서는 자동으로 안 빠지는 것으로 알고 있습니다. 그러면 토큰은 만료됐는데 active_tokens에는 남아있어서 스케줄러가 자리가 꽉 찬 것으로 판단하고 새 사용자에게 토큰 발급을 못하는 상황이 생길 것 같습니다. 이런 경우 스케줄러가 동작할 때마다 만료된 토큰을 정리하는 방식으로 구현하면 될까요?
> 동료가 위와 같은 질문을 했는데 내가 active_tokens Set이 뭔지 잘 이해 못 했어.

**[후속 질문: active_tokens Set의 필요성]**
1번은 토큰이 "접근 제어 목적"이므로 비즈니스 데이터와 분리해 Header에 담는 것이 관례 (예: X-Entry-Token). Interceptor/Filter에서 비즈니스 로직 진입 전에 검증 가능. 2번, 3번은 정확함.
active_tokens Set은 "현재 활성 토큰이 몇 개인지"를 별도 Set으로 관리하는 설계로, subject 문서의 기본 설계(SET entry-token:{userId} {token} EX 300만 사용)와는 다름. 그 설계가 왜 필요하다고 생각했을까요? 스케줄러가 단순히 "100ms마다 18명씩 발급"하는 것만으로는 부족한 상황이 있을까요?

**[답변]**
> 음 동료는 처리량을 일정하게 유지 하기 위해 그럼 maxActiveToken이라는 개념을 둔건가?

**[후속 질문: active_tokens Set 만료 문제 해결]**
동료의 의도는 현재 활성 토큰 수 < maxActiveTokens일 때만 새 토큰을 발급하는 흐름. 문제는 TTL 만료 시 token 키는 Redis에서 사라지지만 active_tokens Set에서는 자동 제거되지 않아 카운트가 틀어짐. 그럼 이 문제를 해결하는 방법이 "스케줄러가 만료 토큰을 정리"하는 방식밖에 없을까요? Redis에 키가 만료될 때 이벤트를 발생시키는 기능이 있어요.

**[답변]**
> 음 내가 레디스 기능을 잘 몰라서. 근데 그런 기능이 있다면 해당 토큰이 실제 만료될 때, active_tokens Set에 있는 해당 토큰과 같은 값을 제거하면 되지 않을까?

**[후속 질문: 두 방식 비교]**
맞아요! 그게 Redis Keyspace Notification이에요. 키가 만료될 때 이벤트를 발행하고, 애플리케이션이 이를 구독해서 active_tokens Set에서 제거하는 방식이죠. 하지만 동료의 설계(active_tokens Set + maxActiveTokens)와 단순히 100ms마다 18명씩 발급하는 방식을 비교하면 — 어떤 방식이 더 단순하고, 어떤 방식이 더 정교한 제어가 가능한가요? 그리고 이번 과제에서는 어떤 방식이 적합할 것 같나요?

**[답변]**
> 그냥 스케쥴러로 고정된 요청양에게 토큰을 발급하는게 더 단순해 보여. 동료가 말한 부분은 좀 더 정교한 조절이 가능할거 같고. 근데 비즈니스적인 면에서도 고정된 요청수에게 토큰을 발급하는게 개인적으로 좀 더 좋아보이는거 같긴 해.

**[정리]**
고정 배치 발급: 단순하고 예측 가능한 처리량, 단 토큰 미사용 시 슬롯 낭비.
maxActiveTokens 제어: 처리량을 실시간으로 꽉 채우지만 구현 복잡도 증가.
이번 과제에서는 고정 배치 발급이 적합 — 대기열 구조 이해가 핵심이고, maxActiveTokens 방식은 Nice-to-Have 최적화 수준.

## Q10. 운영 지표 — 무엇을 봐야 시스템이 "살아있는지" 알 수 있나

**[질문]**
대기열 시스템이 운영 중입니다. 모니터링 대시보드에 어떤 지표를 달아놔야 "이상이 있다"는 걸 감지할 수 있을까요? 특히 (1) 대기열에 유저가 쌓이기만 하고 빠지지 않는 상황, (2) 토큰을 받아간 유저들이 주문을 거의 완료하지 않는 상황, 각각 어떤 지표가 이상 신호를 보내주는지 이야기해보세요.

**[답변]**
> 음 내가 모니터링 지표를 잘 모르지만 실제 주문을 완료하고 토큰이 제거?되는 비율을 봐야할거 같아. 입장을 하고 실제로 주문안 유저의 비율.

**[후속 질문: 대기열이 쌓이기만 하는 상황]**
토큰 전환 비율은 두 번째 시나리오를 잘 잡았어요. 그럼 첫 번째 — "대기열에 유저가 쌓이기만 하고 빠지지 않는 상황"은 어떤 지표로 감지할 수 있을까요? 이 상황이 생기는 원인부터 생각해보세요. 스케줄러가 멈추면 어떻게 될까요?

**[답변]**
> 음 유저는 계속 진입하는데 빠지지 않는다면 토큰의 TTL을 너무 길게 잡은것 아닐까? 근데 지금 헷갈리는게 입장 토큰을 생성하고 TTL을 걸어놓으면 주문하고 있던 유저가 어떻게 튕기게 돼?

**[TTL 개념 정리]**
TTL과 대기열에서 "빠지는 것"은 전혀 다른 이야기.
- 대기열에서 빠지는 시점: 스케줄러가 ZPOPMIN으로 꺼낼 때 (TTL과 무관)
- TTL: 토큰을 받은 후, 주문 API를 호출하기까지의 시간제한
- 토큰 검증은 POST /orders 진입 시점에 한 번. 검증 통과 후 주문 처리가 시작되면 TTL 만료는 영향 없음.

**[답변]**
> 아 그럼 지금 너가 말한 전제는 예를 들어 주문하기 버튼에 대기열을 생성한다고 치면, 주문하기를 누르면 유저는 대기열에 입장하게 되고 기다려서 스케쥴러를 통해 입장 토큰을 받고, 그리고 프론트 폴링을 통해 해당 토큰을 가지고 주문서 작성하는 페이지에 입장하게 되는건가? 그리고 주문을 하고 결제하기를 누르면 그떄 토큰이 만료되지 않으면 결제까지 완성할 수 있는거고, 아니면 토큰이 만료되서 주문을 완료하지 못 하는건가?

**[흐름 정리]**
토큰은 "주문서 작성 페이지 진입 권한"이 아니라 POST /orders를 실제로 실행하는 권한.
TTL 5분은 (토큰 발급 → 주문서 작성 → 결제하기 클릭)까지 커버해야 하는 시간.
결제하기 클릭 시점에 POST /orders 호출 → 토큰 검증 → 주문 처리 → 토큰 삭제.

**[후속 질문: 대기열 총량]**
스케줄러가 멈추면 ZPOPMIN이 실행되지 않으니 아무도 빠지지 않겠죠. 이걸 감지하려면?

**[답변]**
> 음 스케쥴러가 멈추면 대기열이 많이 쌓일거 같아. 내가 지표가 뭐가 있는지 몰라서 무슨 지표인지는 모르겠지만...대기열의 총량?을 보면 되려나...? 이게 줄어들지 않고 계속 늘어나기만 한다면

**[후속 질문: 더 직접적인 감지]**
Queue Depth(ZCARD)가 늘어나는 건 후행 지표. 스케줄러가 멈춘 걸 더 직접적으로 감지하는 방법은?

**[답변]**
> dk scheduler health가 있구나. 1분전이라면 스케쥴러가 실행되고 있지 않다는 의미겠지...? 근데 Token Expiry Rate라는건 보통 주문 완료되고 토큰을 삭제?소비?하는 로직을 넣을텐데 그게 아니라 자연스레 TTL에 의해 토큰이 사라지면 이건 유저가 아무 행동도 안 했다고 추정하는거야??

**[정리]**
Token Expiry Rate: TTL로 자연 소멸된 토큰 수 / 전체 발급 토큰 수. 명시적 DEL(주문 완료)이 아닌 TTL 만료 = 유저 이탈 추정.
> 30%면 TTL이 짧거나 대기 시간이 너무 길어서 이미 이탈한 유저에게 토큰이 발급되고 있다는 신호.

`[글감]` Token Expiry Rate가 단순 시스템 지표가 아니라 비즈니스 지표인 이유 — 이 수치가 높으면 TTL 설정 문제인지, UX 문제인지, 대기 시간 문제인지를 같이 분석해야 한다.

핵심 지표 요약:
| 지표 | 감지하는 것 |
|------|------------|
| Queue Depth (ZCARD) | 대기열이 줄지 않고 계속 쌓이는 상황 |
| Scheduler Health (마지막 실행 시각) | 스케줄러가 멈춰서 아무도 못 빠져나가는 상황 |
| Token Conversion Rate | 토큰 받고 주문 완료한 비율 (< 50% 이상) |
| Token Expiry Rate | TTL 만료로 이탈한 비율 (> 30% 문제 신호) |

## 구현 준비도 판정

**백지 설계 결과:**
> 일단 발제 내용대로라면 일단 유저가 주문하기 버튼을 누르면 대기열 진입 요청 api로 요청이 오고, 레디스 sortedSet에 zadd nx? 명령어를 통해서 유저id 값을 넣고, 서버에서 주기적으로 돌아가는 스케쥴러가 일정 범위의 대기열에 있는 유저에게 토큰을 발급하고 초기에는 넉넉하게 5분이라는 TTL을 부여할거 같아. 프론트에서는 주기적으로 폴링 요청을 보내서 주문 api에 진입할 수 있는지 요청을 보내고, 토큰이 있다면 진입시키고 토큰이 없다면 현재 상태를 유지한다. TPS 산정: 커넥션 풀 50개 / 평균 처리 시간 0.2s = 250 TPS × 0.7(안전마진) = 175 TPS. 100ms마다 18명씩 발급(Thundering Herd 완화). 주문 완료 후 토큰 삭제.

**커버된 포인트:**
- Redis Sorted Set + ZADD NX (중복 진입 방지)
- 스케줄러 + TTL 5분
- 프론트 폴링 기반 순번 조회
- TPS 산정 근거 (커넥션 풀 / 처리 시간 × 안전 마진)
- 100ms 분산 발급 (Thundering Herd 완화)
- 토큰 삭제 (주문 완료 후)

**보완이 필요한 포인트:**
- ZADD NX 정확한 이유: NX 없이 ZADD 시 기존 userId의 score(진입 시각)가 갱신 → 순번 뒤로 밀림. NX로 이미 존재하면 무시.
- R7 연결점 누락: 주문 완료 후 ApplicationEvent → Kafka → collector(Metrics 집계) 파이프라인이 그대로 동작해야 함.

## 핵심 개념 정리

- **Back-pressure**: 하류 시스템(DB)이 감당할 수 있는 속도만큼만 상류(유저 요청)를 흘려보내는 것
- **대기열 vs Rate Limiting**: 거부가 아닌 보관. 유저가 기다릴 의사가 있는 상황에 적합
- **Redis Sorted Set**: score(timestamp) 기반 순서 보장 + member(userId) 중복 방지 + O(log N) 순번 조회
- **입장 토큰**: 주문 API 진입 권한 (TTL = 주문 API 호출까지의 시간제한, 처리 도중 만료는 무관)
- **TPS 산정**: 커넥션 풀 크기 / 평균 처리 시간 × 안전 마진(0.7)
- **Thundering Herd**: 토큰 발급 간격 분산(100ms마다 N명)으로 완화
- **Graceful Degradation**: Redis 장애 시 전략을 사전에 정의해두는 것이 핵심
- **운영 지표**: Queue Depth, Scheduler Health, Token Conversion Rate, Token Expiry Rate
