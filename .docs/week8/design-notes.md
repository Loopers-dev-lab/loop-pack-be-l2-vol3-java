## 스케줄러 배치 크기 산정 전략

대기열에서 N명씩 꺼내 토큰을 발급할 때, N을 어떻게 결정할 것인가?

**검토한 세 가지 접근:**

**접근 1: 고정 배치 크기**
이론적으로 미리 계산하고 고정한다. 단순하고 예측 가능하지만 실제 처리 속도 변화를 반영하지 못한다.

**접근 2: maxActiveToken 고정**
현재 활성 토큰 수(발급됐지만 아직 사용/만료 안 된 수)를 모니터링해서 부족한 만큼만 발급한다. DB에 동시에 올라가는 요청 수를 실제로 제어할 수 있다.

**접근 3: 동적 피드백 제어**
주문 API 실제 응답 시간을 실시간으로 측정해서 배치 크기를 계속 재계산한다. TCP 혼잡 제어(AIMD)와 동일한 원리. 가장 정교하지만 피드백 지연(lag)과 진동(oscillation) 위험이 있어 공식 설계가 복잡하다. Micrometer가 이미 있으므로 기술적으로는 가능하다.

**현실적인 진화 경로**: 고정 배치로 시작 → maxActiveToken → 충분한 모니터링 데이터 후 동적 피드백 도입.

## 입장 토큰 방식: UUID vs JWT vs HMAC

대기열을 통과한 유저임을 증명하는 토큰을 어떤 방식으로 만들 것인가. 토큰에는 두 가지 조건이 있다: TTL 5분 후 자동 만료, 주문 완료 후 즉시 삭제(단일 사용 보장).

**검토한 접근들:**

**접근 1: JWT**
서버 서명으로 Redis 없이 검증 가능한 stateless 방식. 하지만 단일 사용 보장을 위해 주문 완료 시 "사용됨" 상태를 어딘가에 저장해야 하므로 어차피 Redis가 필요해진다. stateless 장점이 무의미해진다.

**접근 2: HMAC 서명**
서명으로 위변조를 방지할 수 있지만, 단일 사용 보장은 서명만으로 불가능하다. JWT와 동일하게 Redis 의존이 남고, 서명 검증 로직까지 추가되어 복잡도만 늘어난다.

**접근 3: UUID + Redis SET**
랜덤 문자열을 생성하고 Redis에 저장. 주문 API 진입 시 Redis에서 조회 후 삭제(원자적 단일 사용 보장). TTL도 Redis EX로 자연스럽게 처리된다.

**결론**: UUID + Redis SET. "단일 사용 보장을 위해 어차피 Redis가 필요하다면, 가장 단순한 방식을 선택한다"가 핵심 근거.

## 토큰 Redis 키 구조: entry-token:{userId} vs entry-token:{token}

토큰을 Redis에 저장할 때 키를 무엇으로 잡느냐에 따라 조회 방향과 중복 점유 방지 능력이 달라진다.

**검토한 접근들:**

**접근 1: entry-token:{token}**
토큰 문자열 자체를 키로 사용. 주문 API에서 토큰만 알면 바로 Redis 조회 가능. 단, userId 기반 중복 점유 방지가 불가능해 한 유저가 여러 슬롯을 점유할 수 있다.

**접근 2: entry-token:{userId}**
userId를 키로 사용. userId당 키가 하나이므로 유저가 동시에 두 개의 슬롯을 점유하는 게 구조적으로 불가능하다. 주문 API 진입 시 userId를 먼저 알아야 조회할 수 있지만, 우리 시스템은 AuthInterceptor가 X-Loopers-LoginId 헤더로 userId를 이미 확인하므로 자연스럽게 맞아떨어진다.

**결론**: entry-token:{userId}. 인증 구조와 맞아떨어지고 중복 슬롯 점유를 구조적으로 차단한다.

## 입장 토큰 TTL 초기값 설정 기준

입장 토큰(entry-token:{userId})의 TTL 초기값을 어떻게 결정할 것인가. TTL의 핵심 기준은 "유저가 토큰을 받은 후 주문 정보를 입력하는 데 걸리는 평균 시간"인데, 서비스 초기에는 이 데이터가 없다.

API 처리 속도(밀리초)는 기준이 될 수 없다 — TTL은 서버 처리 시간이 아니라 유저가 화면 앞에서 폼을 채우는 시간이다. 개발자 직접 테스트는 합리적인 출발점이나, 실제 유저는 카드를 찾거나 주소를 검색하므로 2~3배 더 걸릴 수 있다.

**결론**: 보수적 초기값(5분)으로 시작해 모니터링으로 조정한다. Token Expiry Rate > 30%이면 TTL이 너무 짧은 것, Token Conversion Rate < 50%이면 이탈 유저가 슬롯을 점유 중인 것. 적응형 TTL을 도입하더라도 이미 발급된 토큰은 발급 시점의 TTL을 유지한다 — 약속을 소급 변경하는 건 불공평하고 구현도 복잡하다.

## 활성 유저와 이탈 유저의 토큰 만료를 구분할 수 없는 문제

서버는 유저가 폼을 채우는 중에 TTL이 만료된 것인지, 그냥 이탈한 것인지 구분할 수 없다. Redis 입장에서 두 케이스가 동일하게 보인다.

**검토한 접근들:**

**접근 1: Heartbeat 패턴**
클라이언트가 주기적으로 "아직 활성" 신호를 보내면 TTL을 연장한다. 활성/이탈을 구분할 수 있지만, Heartbeat API로 인한 폴링성 부하 재발, 네트워크 오류 시 활성 유저 토큰도 만료되는 문제가 생긴다.

**접근 2: 구분하지 않고 TTL로 정책화**
TTL을 충분히 넉넉하게 잡아 활성 유저가 피해를 받지 않게 하고, "N분 안에 결제 미완료 시 이탈로 간주"를 정책 결정으로 처리한다.

**결론**: 구분하지 않는다. Heartbeat 복잡도를 감수할 만큼 TTL 정밀도가 비즈니스에 중요한지가 판단 기준이 되어야 한다.

## 대기열이 보호하는 범위

대기열은 DB를 보호하는 첫 번째 관문이지만, 토큰을 받은 유저의 재시도까지는 통제하지 않는다. 스케줄러가 DB 실제 처리 속도보다 빠르게 토큰을 발급하면, 대기열이 있어도 소용없다. 배치 크기를 여유 있게 잡아야 하는 이유이자, 주문 API 자체에도 멱등성 키와 토큰 1회 사용 후 삭제가 필요한 이유다.

## 스케줄러 실행 방식: fixedDelay vs fixedRate

스케줄러 배치 실행 방식 선택. Spring TaskScheduler는 단일 스레드이므로, 실행 방식에 따라 배치 크기 통제 가능 여부가 달라진다.

**검토한 접근들:**

**접근 1: fixedRate**
100ms마다 실행을 시도한다. 이전 실행이 100ms를 초과하면 실행이 큐에 쌓이고, 이전 실행 완료 직후 밀린 실행들이 연속으로 터진다 → 배치 크기 통제 불가.

**접근 2: fixedDelay**
이전 실행 완료 후 100ms를 대기한다. 누적이 없어 배치 크기가 항상 예측 가능하다.

**결론**: fixedDelay 사용. 추가로, `@Scheduled` 메서드에서 uncaught exception 발생 시 스케줄러 스레드가 죽고 이후 모든 실행이 영구 정지된다 — 서버와 API는 정상이라 발견하기 어렵다. 최외곽 try/catch 필수.

## 대기열이 비었을 때 스케줄러 동작

트래픽 없는 시간대에도 매 100ms마다 빈 큐에 ZPOPMIN을 호출하는 게 합리적인가.

"ZCARD로 확인 후 ZPOPMIN 꺼내기" 방식은 Redis 호출이 2배가 되므로 역효과다. ZPOPMIN은 빈 큐에서 빈 결과를 반환하므로 별도 확인 없이 결과로 판단하는 게 낫다.

**검토한 접근들:**

**접근 1: 빈 결과 시 간격 늘리기**
빈 큐 감지 시 다음 실행 간격을 늘린다. 계속 실행되는 구조라 근본 해결이 아니다.

**접근 2: 대기열 진입 시 스케줄러 깨우기**
유저가 대기열에 진입할 때 스케줄러를 트리거한다. 직관적이고 단순하지만, 유저 1명 진입에도 배치 18개 단위 스케줄러가 실행되는 불균형이 있다.

**접근 3: Pull 모델 (토큰 소비 시 다음 유저 입장)**
주문 완료로 토큰이 삭제되는 시점에 대기열에서 다음 유저를 꺼내 토큰을 발급한다. 가장 정교하지만, 주문 완료 흐름에 토큰 발급 로직이 결합된다. ApplicationEvent로 분리해도 유실 위험이 있고, Kafka로 가면 Outbox 패턴까지 엮여 Week 7 파이프라인 전체가 결합된다.

**결론**: fixedDelay 스케줄러로 시작, 빈 큐 감지 시 간격을 약간 늘리는 정도로 최적화. Pull 모델은 복잡도 대비 효과를 충분히 검토한 후 도입.

## 다중 인스턴스 환경에서 스케줄러 중복 실행 방지

commerce-api를 2대 이상 운영하면 두 서버에서 스케줄러가 동시에 ZPOPMIN을 호출해 배치 크기 설계가 무의미해진다. ZPOPMIN 자체는 원자적이라 같은 유저가 중복으로 꺼내지지는 않지만, 총 처리량이 인스턴스 수배가 된다.

**검토한 접근들:**

**접근 1: 분산 락 (SETNX)**
commerce-api 인스턴스들이 Redis 락을 경쟁해 획득한 1대만 스케줄러를 실행한다. 락 보유 인스턴스가 죽으면 다음 주기에 다른 인스턴스가 락을 획득해 이어받는다. 단, 분산 락도 Redis로 구현하므로 Redis SPOF에 동일하게 종속된다.

**접근 2: commerce-batch 분리**
스케줄러를 단일 프로세스로 분리해 동시 실행 문제를 원천 차단한다. 코드 책임이 명확하다. 단, commerce-batch가 죽으면 스케줄러가 완전히 멈추는 SPOF가 된다.

**핵심 논의**: "commerce-batch SPOF가 위험하다"는 주장에 대해 — 대기열(Sorted Set), 토큰(Redis SET) 모두 이미 Redis에 의존하므로 Redis SPOF는 전제로 수용된 상태다. 분산 락으로 스케줄러 HA를 맞춰봤자 Redis가 죽으면 락 자체도 동작 불가 → 스케줄러 HA가 무의미해진다. commerce-batch SPOF도 동일한 수준의 트레이드오프다.

**결론**: 정답 없는 설계 결정. 선택 기준은 "코드 구조의 명확성을 위해 별도 프로세스 운영 비용을 감수할 것인가". Redis SPOF 트레이드오프를 수용한다면 두 접근 모두 정당하다.

## 큐 제거(ZREM)와 토큰 발급 사이의 원자성 보장

스케줄러가 대기열에서 N명을 꺼내고 토큰을 발급하는 두 단계 사이에 크래시가 발생하면, 유저는 큐에서 제거됐지만 토큰도 없는 상태가 된다. 에러가 반환되는 게 아니라 조용히 소실 — 순번 조회 시 "대기열에 없음"을 보고, 다시 진입하면 맨 뒤로 밀린다.

**검토한 접근들:**

**접근 1: Lua 스크립트 (ZPOPMIN + SET)**
ZPOPMIN + N개 SET을 하나의 Lua 스크립트로 묶는다. Redis 단일 스레드 특성상 Lua 실행 중 중간 상태가 존재하지 않는다. `coupon_issue_request.lua`에서 이미 검증된 패턴. 단, 배치 크기가 클수록 다른 Redis 클라이언트에 영향. 비즈니스 로직이 Lua 스크립트에 분산된다.

**접근 2: ZRANGE → SET → ZREM (역순 Two-phase)**
ZPOPMIN 대신 ZRANGE로 N명을 먼저 조회(큐에서 제거 안 함)하고, 토큰을 발급한 뒤, 성공하면 ZREM으로 제거한다. SET 실패 시 유저가 큐에 남아 있어 소실되지 않는다는 장점이 있다. 단, ZREM이 실패하면 토큰을 받은 유저가 큐에 그대로 남아 다음 스케줄러가 동일 유저를 다시 조회 → SET NX 실패(이미 존재) → 문제없음. 아키텍처적으로 "토큰이 있으면 ZREM" 불변식이 성립하면 크래시 복구가 자동이다.

**접근 3: 스케줄러 멱등성 + 폴링 API에서 큐 제거**
스케줄러: ZRANGE로 조회 후 SET NX로 토큰 발급(멱등성 보장). 폴링 API: `tokenIssued=true` 확인 시 ZREM. 크래시 시 유저가 큐에 남아있고 스케줄러가 재실행 시 SET NX NOP → 안전하다. Lua 스크립트 없이 애플리케이션 코드로만 구현 가능하다는 장점. 단, **폴링 주기(1초)가 실질 처리량을 제한하는 병목**이 된다(아래 섹션 참고).

**접근 4: 리스크 수용**
최대 배치 크기(N명) 유실을 허용하고 모니터링 알림으로 대응한다.

**결론**: 접근 3(ZRANGE + SET NX + 폴링 시 ZREM)을 1차 채택. Lua 없이 애플리케이션 계층에서 멱등성으로 동등한 안전성을 달성한다. 단, 폴링 주기 병목 문제를 발견해 최종적으로 ZREM 시점을 스케줄러로 이동(아래 섹션 참고).

## 폴링 주기 병목 문제와 스케줄러 즉시 ZREM으로의 진화

접근 3(폴링 시 ZREM)을 실제 k6 부하 테스트에서 검증했을 때 예상치 못한 병목이 발견됐다.

**문제 발견 과정**

k6로 500→1000→2000명 단계적 부하 테스트(staged load) 실행 결과:
- `token_issued_rate: 15.92%` — 3216명 중 512명만 토큰 발급
- `token_wait_time_ms p(95): 2m43s` — 임계 120초 초과
- wave_2000에서 대다수 타임아웃 발생

**병목의 근본 원인**

스케줄러는 100ms마다 실행되지만 이미 토큰이 있는 유저가 폴링(1초)하기 전까지 큐에서 제거되지 않는다. 결과:

```
t=0ms   : ZRANGE → 1~14번 토큰 발급 (큐에 잔류)
t=100ms : ZRANGE → 1~14번 다시 조회 → SET NX NOP (낭비)
  ... 9회 반복 ...
t=1000ms: 1~14번 폴링 → ZREM → 15~28번이 처리 가능해짐
```

- 이론 처리량: 14명/100ms = **140명/초**
- 실질 처리량: 14명/1초(폴링 주기) = **14명/초** (10배 저하)
- wave_2000 예상 처리 시간: 2000 ÷ 14명/초 ≈ 143초 → maxWaitMs(180초)에 근접해 타임아웃 급증

**해결: ZREM 시점을 스케줄러로 이동**

스케줄러에서 SET NX 직후 ZREM을 호출하면 다음 스케줄러 실행(100ms 후)이 곧바로 다음 배치를 처리할 수 있다.

```
t=0ms  : ZRANGE → 1~14번 SET NX + 즉시 ZREM
t=100ms: ZRANGE → 15~28번 SET NX + 즉시 ZREM  ← 폴링 대기 없음
t=200ms: ZRANGE → 29~42번 ...
```

실질 처리량이 140명/초로 회복된다.

**원자성 트레이드오프 재검토**

ZREM을 스케줄러로 이동해도 SET NX와 ZREM은 여전히 두 개의 Redis 명령이다. 단, 크래시 복구 경로가 유지된다:
- SET NX 성공 → ZREM 전 크래시: 다음 스케줄러 실행 시 SET NX returns false(이미 존재) → ZREM 재실행 → 복구
- 데이터 손실 케이스(토큰 없음 + 큐에서 제거)는 불가능: ZREM은 항상 SET NX 이후에만 실행되며, SET NX 성공이면 토큰은 Redis에 존재

진정한 원자성(하나의 트랜잭션)이 필요하다면 Lua 스크립트가 유일한 선택지다. 현재 구현은 "최선 노력 + 자동 복구" 방식이며, 실무 수준에서는 이 수준으로 충분하다고 판단했다.

**폴링 API(getPosition)의 역할 변화**

ZREM이 스케줄러로 이동하면서 폴링 시점에는 유저가 이미 큐에 없다. `getPosition`이 `rank == null`이면서 토큰이 존재하는 경로(`QueueFacade.java:48~50`)가 이제 정상 경로가 된다. 폴링 시 ZREM은 스케줄러 ZREM이 크래시로 실패했을 때의 복구 경로(`rank != null`이면서 토큰 존재, `QueueFacade.java:37~40`)로 역할이 바뀐다.
