# Week 8 멘토링 질문

> 이번 주차 설계 고민 과정에서 나온 질문들.
> 쉽게 검색할 수 있는 개념 질문보다, "내 판단이 합리적인가", "실무에서는 어떻게 하는가" 중심.

---

## 1. 배치 크기 산정: 이론값 vs 실측값

DB 커넥션 풀과 평균 처리 시간으로 이론적 배치 크기를 계산했습니다.
`(커넥션 50개 / 처리 200ms) × 70% 안전 마진 / 초당 10회 = 18명`

실무에서는 이런 이론값을 실제로 초기값으로 쓰는지, 아니면 다른 방식으로 접근하는지 궁금합니다. 특히 "안전 마진 70%"처럼 근거가 애매한 값을 어떻게 결정하는지, 그리고 이 값을 이후에 어떻게 튜닝하는지 실무 경험이 궁금합니다.

---

## 2. 다중 인스턴스 환경의 스케줄러 중복 실행과 SPOF 트레이드오프

다중 인스턴스 환경에서 스케줄러 중복 실행을 방지하는 방법으로 **Redis 분산 락**과 **배치 서버 분리(commerce-batch)** 두 가지를 검토했습니다. 분산 락은 Redis에 의존하고, 배치 서버 분리는 배치 서버 자체가 SPOF가 됩니다. 대기열 자체도 Redis에 의존하므로 어느 방법을 선택해도 SPOF를 완전히 피할 수 없다는 결론을 내렸습니다.

실무에서는 이 두 방법 중 어떤 것을 더 선호하는지 궁금합니다. 또, SPOF를 피할 수 없는 상황에서 이를 보완하기 위한 추가 장치(Redis HA, 배치 서버 이중화 등)를 마련하는 것이 합리적인지, 아니면 그 복잡도가 오버엔지니어링이고 차라리 "죽지 않게 잘 운영하는 것"에 집중하는 게 맞는지 멘토님의 관점이 궁금합니다.

---

## 3. Pull 모델 vs fixedDelay 스케줄러: 실무 선호도

"주문 완료 시 다음 유저 토큰 발급(Pull 모델)"이 처리량을 더 정밀하게 제어할 수 있지만, 주문 완료 흐름에 토큰 발급 로직이 결합되는 문제가 있습니다. ApplicationEvent로 분리해도 유실 위험이 있고, Kafka + Outbox까지 가면 Week 7 파이프라인 전체가 엮입니다.

단순한 fixedDelay 스케줄러로 시작하기로 했는데, 실무에서 대기열 시스템을 설계할 때 이 두 방식 중 어떤 쪽을 더 선호하는지, 그리고 Pull 모델로 전환하는 시점의 기준이 있는지 궁금합니다.

---

## 4. TTL 고정 vs Heartbeat: 언제 복잡도를 감수할 만한가

유저가 폼을 채우는 중인지, 이탈했는지 서버에서 구분할 수 없어서 TTL을 넉넉하게 잡고 "N분 안에 미완료 시 이탈 간주"를 정책으로 처리했습니다. Heartbeat 패턴은 구분이 가능하지만 폴링성 부하와 네트워크 오류 시 활성 유저 토큰 만료 위험이 있습니다.

실무에서 Heartbeat를 실제로 쓰는 케이스가 있는지, 있다면 어떤 조건에서 그 복잡도를 감수하는지 궁금합니다.

---

## 5. 대기열 활성화/비활성화 시점을 어떻게 결정하는가

트래픽이 적을 때는 대기열 없이 바로 주문 API로 진입하게 하고, 폭증 시에만 활성화하는 게 이상적입니다. 하지만 "언제 켜고 끌지"의 기준을 어떻게 잡아야 할지 감이 오지 않습니다.

실무에서 대기열을 동적으로 켜고 끄는 방식을 쓰는지, 아니면 항상 켜두고 트래픽이 없을 때는 스케줄러가 즉시 통과시키는 방식을 쓰는지 궁금합니다. 전자라면 어떤 지표를 트리거로 사용하는지도 여쭤보고 싶습니다.

---

## 6. Graceful Degradation: Redis 장애 시 어떻게 동작해야 하는가

Redis가 죽으면 대기열 전체가 마비됩니다. 이때 선택지가 두 가지입니다. 전면 차단(503 반환)은 안전하지만 서비스가 멈추고, 대기열 우회(bypass)는 서비스를 살리지만 트래픽 폭증 시 DB가 노출됩니다.

스터디 플랜에서 "트래픽이 낮은 시간대면 bypass 허용 가능, 폭증 시에는 전면 차단이 안전"이라고 나와있는데, 이 판단을 실시간으로 자동화하려면 현재 TPS를 모니터링해야 합니다. 실무에서 이런 자동 전환을 실제로 구현하는지, 아니면 수동으로 운영 판단을 내리는지 궁금합니다. 또한 Redis가 복구됐을 때, bypass로 이미 진입한 유저와 큐에서 기다리던 유저 사이의 공정성 문제를 어떻게 다루는지도 여쭤보고 싶습니다.

## 7. Thundering Herd: 배치 발급이 만드는 동시 주문 스파이크

스케줄러가 100ms마다 18명에게 동시에 토큰을 발급하면, 18명이 거의 동시에 주문 API를 호출합니다. 이 순간적인 스파이크가 DB 커넥션 경합을 높일 수 있습니다. 완화 방법으로 발급 간격 분산(100ms → 10ms × 2명), 토큰 활성화 Jitter, 주문 API Rate Limit을 검토했는데, 실무에서 이 문제를 실제로 겪는지, 겪는다면 어떤 방식으로 완화하는지 궁금합니다.
