
`@OneToMany`, `@ManyToOne` 을 사용하지 않는다고 하였으나, Order/OrderItem/Cart/CartItem에는 사용함.
- Aggregate 내부(Order-OrderItem, Cart-CartItem)는 @OneToMany/@ManyToOne 물리 연관을 써도 DDD 위반이 아니라고 생각. 오히려 라이프사이클 통제에 유리하다고 생각.
- Aggregate 간(Order-User/Product/Brand, Cart-User/Product)은 지금처럼 ID만 들고 가는 논리 연관이 맞다고 생각.


Application Layer에서 도메인 리턴하는이유 설명
- 현재 Commerce API는 쓰기 모델(도메인 엔티티/애그리거트)을 중심으로 애플리케이션 계층을 구성하며, 웹 어댑터(Controller)에서 응답 조합을 담당한다. 이는 의존 방향(외부 -> 내부)을 유지하고 프레젠테이션 관심사가 애플리케이션 계층으로 침투
하는 것을 방지하기 위한 의도적 설계다. 다만 목록/검색/리포트처럼 다중 애그리거트 조합이 필요한 조회 유스케이스는 컨트롤러 복잡도가 증가할 수 있으므로, 해당 영역부터 조회 전용 모델(Query DTO/Projection)과 Query 서비스를 단계적으로 도
입한다. 즉, Command는 도메인 중심, Query는 읽기 최적화 모델 중심의 하이브리드 전략을 채택한다.

도메인 엔티티랑 JPA엔티티 나누지 않은 이유 설명


1. Interface 계층: appApi (Controller)
   • 역할: 외부의 요청을 해석하고, 시스템의 처리 결과를 사용자(또는 클라이언트)가 이해할 수 있는 형식으로 변환하여 응답하는 관문입니다.
   • 책임:
   ◦ HTTP 요청(또는 CLI 입력)을 애플리케이션 계층이 요구하는 형식(Command 객체 등)으로 변환합니다.
   ◦ 사용자가 전송한 데이터 형식의 올바름(단순 파라미터 검증)을 확인합니다.
   ◦ 응용 서비스(appService)에 처리를 위임하고, 반환받은 결과(DTO)를 JSON 등으로 변환해 응답합니다.
   • 경계: 절대 비즈니스 로직이나 유스케이스의 흐름 제어(오케스트레이션)를 담당해서는 안 됩니다. 도메인 객체를 직접 다루거나 상태를 변경하는 로직이 포함되면 '스마트 UI(Smart UI) 안티 패턴'에 빠지게 됩니다.
2. Application 계층: appService
   • 역할: 사용자의 목적(유스케이스)을 달성하기 위해 도메인 객체들을 조합하고 작업의 흐름을 제어하는 오케스트레이터이자 파사드(Facade)입니다.
   • 책임:
   ◦ 트랜잭션 관리: 하나의 유스케이스가 완전히 성공하거나 실패하도록 트랜잭션의 경계를 설정합니다.
   ◦ 흐름 제어: domainRepository를 통해 도메인 객체를 가져오고(Find), 도메인 객체에 비즈니스 로직 실행을 위임하며, 그 결과를 다시 리포지터리에 저장(Save)합니다.
   ◦ 접근 제어(보안) 및 외부 시스템과의 연동(이메일 발송 등)을 조율합니다.
   • 경계: 도메인의 상태를 변경하는 핵심 비즈니스 규칙을 직접 구현해서는 안 됩니다. 만약 이 계층에 if문을 통한 핵심 규칙 검사가 들어간다면 '도메인 규칙의 유출'이 발생한 것입니다.
3. Domain 계층: 도메인의 핵심 규칙과 상태
   이 계층은 시스템이 제공할 도메인 지식과 비즈니스 규칙을 온전히 캡슐화하는 곳입니다.
   ① domain (Entity / Aggregate Root)
   • 역할: 고유한 식별자(ID)와 연속적인 생명주기를 가지며, 도메인의 고유한 개념을 표현하는 객체입니다.
   • 책임:
   ◦ 데이터와 함께 그 데이터를 조작하는 도메인 기능(행위)을 제공합니다.
   ◦ **애그리거트 루트(Aggregate Root)**로서, 자신에게 속한 하위 엔티티와 VO들의 일관성(비즈니스 불변성)이 깨지지 않도록 통제하고 보호합니다.
   • 경계: 무분별한 setter를 피하고, 의미 있는 메서드명(예: changeShippingInfo())을 통해 외부에서 상태를 변경하도록 제어해야 합니다.
   ② VO (Value Object)
   • 역할: 식별자 없이 사물의 어떤 특징이나 속성(값)을 묘사하는 객체입니다 (예: Money, Address).
   • 책임:
   ◦ 개념적으로 완전한 하나를 표현하며, 도메인의 서술적 측면을 담당합니다.
   ◦ **불변성(Immutability)**을 가지며, 값을 변경해야 할 때는 기존 객체를 수정하는 대신 새로운 VO를 생성하여 교체합니다.
   ◦ 데이터뿐만 아니라 값과 관련된 계산(예: 금액 더하기) 같은 행위를 자체적으로 가집니다.
   ③ domainService
   • 역할: 특정 엔티티나 VO에 속하기 어색하거나, 여러 애그리거트를 가로질러 이루어지는 비즈니스 행위를 담당하는 객체입니다.
   • 책임:
   ◦ 상태를 갖지 않는 무상태(Stateless) 객체로서 연산(Operation)만을 수행합니다.
   ◦ 대표적으로 '아이디 중복 검사'처럼 데이터베이스 조회가 수반되는 도메인 규칙을 검증하거나, 복잡한 '할인 금액 계산' 등을 처리합니다.
   • 경계: 모든 로직을 도메인 서비스로 빼앗아 오면 엔티티가 데이터만 남는 '빈약한 도메인 모델(Anemic Domain Model)'이 되므로 남용하지 않아야 합니다.
   ④ domainRepository (Interface)
   • 역할: 도메인 객체(애그리거트)를 데이터베이스에 저장하고 복원하는 기능을 추상화한 '인터페이스'입니다.
   • 책임: 마치 메모리에 존재하는 컬렉션(List, Set)처럼 작동하여, 식별자로 애그리거트를 조회(findById)하거나 저장(save)하는 계약(Contract)을 정의합니다.
   • 경계: 특정 데이터베이스 기술(JPA, MyBatis)에 종속되지 않은 순수한 자바 인터페이스여야 하며, 의존 역전 원칙(DIP)에 의해 도메인 계층에 위치합니다.
4. Infrastructure 계층: domainRepositoryImpl
   • 역할: 상위 계층(도메인, 응용)을 지원하는 일반화된 기술적 기능을 제공합니다.
   • 책임:
   ◦ 도메인 계층에 정의된 domainRepository 인터페이스를 **실제로 구현(Implementation)**하여 RDBMS, NoSQL, 메모리 등에 데이터를 읽고 쓰는 퍼시스턴시 로직(JPA, SQL 등)을 담당합니다.
   • 경계: DIP(의존 역전 원칙)를 통해 도메인 계층이 인프라스트럭처를 의존하는 것이 아니라, 인프라스트럭처가 도메인 계층(의 인터페이스)을 의존하게 됩니다. 이로써 기술이 변경되어도 핵심 도메인 로직은 보호받습니다.

1. [Interface] appApi: 클라이언트의 HTTP POST 요청을 받아 CreateOrderCommand 객체로 변환한 뒤, appService.createOrder(command)를 호출합니다.
2. [Application] appService: 트랜잭션을 시작합니다. command에 담긴 데이터를 바탕으로 유스케이스를 진행합니다.
3. [Domain] domainService: (필요시) appService는 도메인 규칙 검사(예: 재고 확인이나 회원 검증)를 위해 domainService를 호출할 수 있습니다.
4. [Domain] domain & VO: appService는 유효성이 검증되면 새로운 Order(엔티티)를 생성합니다. 이때 Order 내부는 Money나 Address 같은 VO들로 구성되며, 생성 규칙은 철저히 Order 내부의 비즈니스 로직에 의해 통제됩니다.
5. [Application ➡ Domain] appService: 생성이 완료된 Order 객체를 영속화하기 위해 도메인 계층의 인터페이스인 domainRepository.save(order)를 호출합니다
