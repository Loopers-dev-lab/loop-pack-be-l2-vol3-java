## Rate Limiting vs Queuing

### 개념
Back-pressure로 한계 TPS를 정했을 때, 초과 요청을 어떻게 처리할지에 대한 두 가지 전략.

| 전략 | 방식 | 유저 경험 |
|---|---|---|
| **Rate Limiting** | 초과 요청을 즉시 거부 (429) | "지금은 안 됩니다" |
| **Queuing** | 초과 요청을 대기열에 보관 후 순서대로 처리 | "기다려 주세요" |

---

### 전략 선택 기준

"유저가 기다릴 의사가 있는가?"는 다음 세 가지를 종합한 판단이다.

**1. 요청이 재시도 가능한가?**
- Rate Limiting 적합: 실패해도 클라이언트가 자동 재시도하면 되는 경우
- Queuing 적합: 실패하면 유저가 직접 다시 행동해야 하는 경우

**2. 요청 하나의 비즈니스 가치가 높은가?**
- Rate Limiting 적합: 요청이 가볍고 언제든 재시도 가능
- Queuing 적합: 요청 하나가 구매 의도를 담고 있어 429 시 매출 손실 발생

**3. 트래픽 폭증이 일시적인가?**
- Rate Limiting 적합: 상시적으로 한도를 초과하는 경우 (스케일 업이 근본 해결책)
- Queuing 적합: 특정 시점에만 폭증하고 평소엔 여유가 있는 경우

> 대기열은 **일시적 폭증을 흡수하는 버퍼**다.
> 상시 초과라면 대기열이 계속 쌓이기만 해서 의미가 없다.

---

### Rate Limiting vs Queuing은 선택 관계가 아니다

둘은 **보완 관계**다. 실무에서는 계층적으로 같이 쓴다.

```
1차 — Rate Limiting  : 봇, 어뷰징, 비정상 트래픽 차단
2차 — Queuing        : 정상 유저의 초과 요청 보관
3차 — Back-pressure  : 대기열에서 하류로 흘리는 속도 제어
```

- Queuing만 있으면: 봇이 대기열을 점령해 정상 유저가 밀려남
- Rate Limiting만 있으면: 정상 유저도 429 받고 이탈 → 매출 손실

> Rate Limiting이 대기열을 보호하고, Queuing이 정상 유저 경험을 보호한다.

---

### Rate Limiting 심화

**어떤 기준으로 제한할 것인가?**

세 가지 기준은 목적이 다르며, 실무에서는 계층적으로 조합해서 사용한다.

```
1차 — IP 기준       : 네트워크 레벨 (Nginx, API Gateway)
2차 — API Key 기준  : 앱/파트너사 단위 (B2B가 있다면)
3차 — 유저 기준     : 애플리케이션 레벨 (로그인 후 요청)
```

IP는 애플리케이션까지 요청이 오기 전에 막을 수 있어 서버 자원 소모 자체를 줄일 수 있다.
유저 기준은 인증 토큰을 파싱해야 하므로 애플리케이션 안에서만 가능하다. 가장 정확하지만 가장 늦게 판단한다.

| 계층 | 목적 | 한계 |
|---|---|---|
| IP 기준 | 봇, DDoS, 비정상 트래픽 차단 | 공유 IP(회사 NAT)에서 무고한 사용자까지 차단될 수 있음 |
| API Key 기준 | 파트너사별 할당량 관리 | B2B가 없으면 불필요 |
| 유저 기준 | 동일 계정의 반복/중복 요청 차단 | 비로그인 요청은 IP 기준으로 fallback 필요 |

> 유저 기준 Rate Limiting은 "계정 하나가 짧은 시간 내에 반복 요청하는 것"을 막는 것이지,
> "한 사람이 여러 계정을 쓰는 것"은 막지 못한다. 후자는 어뷰징 탐지 영역이다.

**API Key 기준 상세**

B2B 서비스에서 파트너사 서버가 API를 호출할 때 사용한다.
파트너사 서버 한 대가 수천 유저를 대신해서 요청하므로, IP 기준으로는 차단되고 유저 기준으로는 식별이 안 된다.
API Key로 파트너사를 식별해 계약별로 할당량을 다르게 부여할 수 있다.

```
파트너사 A (계약: 1000 req/min) → Key: abc123
파트너사 B (계약:  500 req/min) → Key: xyz789

# Redis에 Key별 카운터를 따로 관리
rate:apikey:abc123 → 437
rate:apikey:xyz789 → 12
```

**이 프로젝트(주문 대기열)에서의 적용**

대기열/주문은 B2C 서비스이므로 API Key 기준은 해당 없다. IP + 유저 두 계층으로 충분하다.

- IP 기준: 동일 IP에서 봇이 대기열을 점령하는 것 차단
- 유저 기준: 동일 계정이 대기열 진입을 반복 요청하는 것 차단

**알고리즘 종류**

Rate Limiting의 핵심은 "이 요청을 허용할지 거부할지 판별"하는 것이다.
알고리즘은 그 판별 기준을 어떻게 계산하느냐의 차이다.

```
요청 도착
  → 알고리즘으로 현재 상태 계산
  → 허용 범위 안이면 통과
  → 초과면 429 반환
```

*Fixed Window*

시간을 고정된 창(window)으로 자르고, 각 창 안에서 카운터를 센다.
판별 기준: **이번 창에서 몇 개 왔나?**

```
[00:00 ~ 01:00] 요청 100개까지 허용
[01:00 ~ 02:00] 카운터 리셋, 다시 100개까지 허용
```

문제: 창의 경계 시점에 의도치 않은 버스트가 발생한다.

```
00:59에 100개 → 허용 (1분 창 안)
01:00에 100개 → 허용 (새 창이므로 리셋)
→ 1초 사이에 200개 통과
```

*Sliding Window*

고정 창이 아니라 "지금으로부터 N분 전"을 기준으로 매 요청마다 창을 밀어가며 센다.
판별 기준: **지금으로부터 N분 전까지 몇 개 왔나?**

두 가지 구현 방식이 있다.
- **Log 방식**: 요청마다 타임스탬프를 저장, 1분 이전 것을 제거한 후 남은 개수를 셈. 정확하지만 요청 수만큼 메모리 사용
- **Counter 방식**: 창을 잘게 쪼개(예: 1초 단위) 카운터를 여러 개 유지. 메모리는 줄지만 완벽하게 정확하지는 않음

*Token Bucket*

버킷에 토큰이 일정 속도로 채워지고, 요청이 올 때 토큰을 하나 소비한다.
판별 기준: **지금 토큰이 남아있나?**

```
초당 10개 토큰 충전, 최대 50개 보관

평소에 요청이 적으면 → 토큰이 쌓임
폭증 시 → 쌓인 토큰 소진하며 버스트 처리 가능
```

버스트를 허용하되 평균 속도는 제한하는 게 핵심이다.

*Leaky Bucket*

요청을 버킷(큐)에 넣고, 버킷에서는 일정한 속도로만 흘려보낸다.
판별 기준: **지금 큐에 자리가 있나?**

```
요청이 쏟아져도 → 처리는 항상 일정 속도
버킷 초과 → 거부
```

Token Bucket과 반대다. Token Bucket은 쌓인 토큰으로 버스트를 허용하고, Leaky Bucket은 버스트를 흡수해서 일정하게 내보낸다.

| 알고리즘 | 판별 기준 | 버스트 | 적합한 상황 |
|---|---|---|---|
| Fixed Window | 이번 창에서 몇 개 왔나? | 경계에서 2배 허용 (의도치 않음) | 구현 단순함이 중요할 때 |
| Sliding Window | N분 전부터 지금까지 몇 개 왔나? | 불허 | 정확한 제한이 필요할 때 |
| Token Bucket | 토큰이 남아있나? | 허용 | 평균 속도 제한 + 순간 허용 |
| Leaky Bucket | 큐에 자리가 있나? | 불허 | 처리 속도를 일정하게 유지할 때 |

**분산 환경에서의 문제**

서버가 여러 대면 각 서버가 카운터를 따로 들고 있을 경우 동기화 문제가 생긴다.

```
서버 A: 요청 80개 카운트 (한도 100)
서버 B: 요청 80개 카운트 (한도 100)
→ 실제로는 160개 통과했는데 둘 다 "아직 괜찮다"고 판단
```

Redis로 카운터를 중앙화하면 동기화 문제는 해결되지만, Redis가 단일 장애점(SPOF)이 된다.

**Failure-Ready System: Redis 장애 시 전략**

Redis 장애는 언제든 일어날 수 있는 일로 전제하고, 그때 시스템이 어떻게 동작할지를 미리 설계해야 한다. 이것이 **Graceful Degradation**이다.

| 전략 | 동작 | 적합한 상황 |
|---|---|---|
| Redis 이중화 (Sentinel / Cluster) | 자동 페일오버로 장애 자체를 최소화 | 운영 복잡도를 감수할 수 있을 때 |
| Fail Open | Redis 장애 시 Rate Limiting 우회, 모든 요청 허용 | 가용성이 중요한 서비스 |
| Fail Closed | Redis 장애 시 모든 요청 거부 | 보안이 중요한 서비스 |

핵심은 **한 컴포넌트가 죽어도 전체가 멈추지 않도록 역할을 분산**하는 것이다.

이 프로젝트(주문 대기열)에서는 Fail Open이 합리적이다.
Rate Limiting이 뚫려도 대기열 자체가 처리량을 제어하기 때문에 대기열이 2차 방어선 역할을 한다.

```
정상:      Rate Limiting → 대기열 → 주문 처리
Redis 장애: Rate Limiting 우회 → 대기열이 처리량 제어 → 주문 처리
```

### Queuing 심화

#### 1. 대기열이 무한정 쌓이면?
대기열은 일시적 폭증을 흡수하는 버퍼지만, 한계가 없으면 역효과가 난다.

```
대기열에 100만 명 쌓임
→ 175 TPS로 처리 시 약 95분 대기
→ 유저는 이미 다 이탈
→ 대기열만 쌓이고 처리는 공회전
```

최대 대기 인원을 제한하고, 초과 시 Rate Limiting으로 전환해야 한다.

---

#### 2. 대기 중 유저가 이탈하면?

HTTP는 **비연결성** 프로토콜이라 유저가 브라우저를 닫아도 서버는 알 수 없다.
이탈한 유저의 슬롯이 낭비되는 문제가 발생한다.

**해결 방법 비교**

| 방법 | 방식 | 단점 |
|---|---|---|
| TTL 기반 | 대기열 진입 시 TTL 설정, 갱신 없으면 자동 만료 | TTL 동안은 이탈을 모름 → 슬롯 낭비 |
| Heartbeat | 클라이언트가 주기적으로 생존 신호 전송, 없으면 제거 | 클라이언트가 주기적으로 요청 → Polling 부하 |
| SSE / WebSocket | 연결이 끊기는 순간 서버가 바로 감지 | 연결 유지로 서버 리소스 사용 |

**실무에서는 Heartbeat + 동적 TTL을 함께 사용**

```
Heartbeat  → 이탈 유저 빠르게 감지
동적 TTL   → Heartbeat 누락 시 백업, 예상 대기 시간 반영
```

**동적 TTL 계산 방법**

TTL을 고정값으로 잡으면 문제가 생긴다.
- TTL이 너무 짧으면 → 이탈하지 않은 유저가 순서 전에 만료
- TTL이 너무 길면 → 이탈한 유저의 슬롯이 오래 낭비

현재 대기 예상 시간 기반으로 동적으로 계산한다.

```
현재 대기열 인원: 500명
처리 속도: 175 TPS
예상 대기 시간: 500 / 175 ≈ 3분

TTL = 예상 대기 시간 + 여유 시간(예: 1분) = 4분
```

단, 처리 속도가 갑자기 느려지면 예상보다 대기 시간이 길어져 정상 유저가 제거될 수 있으므로
Heartbeat를 함께 사용하는 것이 안전하다.

---

#### 3. 순서 보장을 어떻게 할 것인가?

동시에 수천 명이 진입할 때 순서를 어떻게 보장할 것인가가 핵심 문제다.
단순 자료구조로는 동시성 문제로 인해 순서가 보장되지 않는다.
→ **원자적(atomic)으로 순서를 결정할 수 있는 자료구조가 필요하다.**
