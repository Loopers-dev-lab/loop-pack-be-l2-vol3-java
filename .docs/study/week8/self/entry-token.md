## 입장 토큰 (Entry Token)

### 왜 필요한가

대기열을 통과한 사람에게 주문 API 진입 권한을 보장하기 위한 장치다.

토큰 없이 대기열 통과 즉시 주문 API를 호출하게 하면, 주문 처리 중 실패(PG 오류 등)했을 때 대기열 맨 뒤에 다시 줄을 서야 한다. 대기해서 얻은 권리를 일정 시간 보장해주는 것이 토큰의 역할이다.

```
대기열 통과 → 토큰 발급 (TTL 5분)
→ TTL 안에 주문 API 호출 → 토큰 검증 → 통과
→ 주문 실패해도 토큰이 살아있으면 재시도 가능
→ TTL 만료 시 토큰 소멸 → 다시 대기열부터
```

---

### 토큰 구조

Redis key로 저장한다. 값 자체는 의미 없고, **키의 존재 여부**가 곧 권한이다.

```
SET entry-token:{userId} "granted" EX 300
```

주문 API 진입 시:
```
EXISTS entry-token:userA
→ 1 (키 있음) → 통과
→ 0 (키 없음, 만료되었거나 발급 안 됨) → 거부
```

Redis는 TTL 만료 시 키를 자동 삭제한다. 별도 만료 처리 로직이 필요 없다.

---

### TTL 설정 기준

TTL은 **주문 한 건을 완료하는 데 걸리는 시간**을 기준으로 설정한다.

```
TTL이 너무 길면 → 주문 안 하는 사람이 슬롯을 점유 → 처리량 낭비
TTL이 너무 짧으면 → 주문 중인 사람이 만료 → 사용자 경험 손상
```

실무에서는 경험적으로 설정하고, 운영 후 실제 주문 완료 로그의 P95 소요 시간을 측정해 조정한다.

```
주문 완료 소요 시간 P95 = 2분
→ TTL = 2분 + 여유 1분 = 3분
```

P95 기준을 쓰는 이유는 100%를 커버하려면 TTL이 너무 길어져 슬롯 낭비가 커지기 때문이다. 상위 5%의 느린 유저는 만료될 수 있음을 감수하는 트레이드오프다.

화면에 타이머를 노출해 사용자가 남은 시간을 인지하게 하면, 시간 안에 완료하려는 행동을 유도해 P95 소요 시간 자체를 줄이는 효과도 있다.

```
"주문 완료까지 남은 시간: 04:32"
```

---

### 토큰 소멸 시점

주문 완료 시 즉시 삭제한다.

```
DEL entry-token:userA
```

TTL이 남아있어도 삭제하는 이유는 재사용 방지다.

```
주문 실패 → 토큰 유지 → 재시도 가능
주문 완료 → 토큰 즉시 삭제 → 재사용 불가
```

---

### 주문 API와 결제 API가 분리된 경우

입장 토큰의 책임은 **주문 생성 권한 보장**으로 한정한다.

```
입장 토큰: 주문 생성 권한 보장
→ 주문 API 진입 시 검증
→ 주문 생성 완료 시 소멸

미결제 주문 TTL: 결제 기한 관리 (별도 관심사)
→ 주문 생성 시 TTL 설정
→ TTL 초과 시 주문 취소 + 재고 반환
```

입장 토큰을 결제 API까지 확장하면 "주문 생성 권한"에서 "전체 플로우 제어"로 책임이 커진다. 미결제 주문 TTL을 별도로 두는 것이 책임이 명확하다.

결제 API는 대기열 없이 Rate Limiting으로 충분하다. 주문 생성은 오픈 순간 동시 폭증이 명확하지만, 결제는 각자 다른 시점에 자연스럽게 분산되기 때문이다.
