## Polling vs SSE

### 왜 필요한가

대기열에 진입한 유저는 다음 정보가 필요하다.
- 내가 몇 번째인지
- 언제 내 차례가 오는지
- 내 차례가 되면 알림

이걸 어떻게 전달할 것인가의 문제다.

---

### Polling

클라이언트가 주기적으로 서버에 "나 몇 번째야?" 요청을 보내는 방식.

```
클라이언트 → GET /queue/position → 서버
클라이언트 ← { rank: 250, estimatedWaitSeconds: 85 } ← 서버
(N초 후 반복)
```

**문제: 불필요한 요청 발생**

순번이 바뀌지 않았어도 계속 요청이 들어온다. 대기열을 도입한 이유가 요청을 줄이기 위해서인데, 대기 중인 모두가 주기적으로 요청하면 부하가 발생한다.

**완화: Polling 주기 동적 조절**

예상 대기 시간 기반으로 Polling 주기를 동적으로 조절한다. 내 차례가 멀수록 자주 물어볼 필요가 없다.

```
예상 대기 시간 10분 이상 → 30초마다
예상 대기 시간 3분 이상  → 10초마다
예상 대기 시간 1분 이상  → 3초마다
예상 대기 시간 1분 이하  → 1초마다
```

서버가 응답에 다음 Polling 주기를 함께 내려주면 서버가 부하를 직접 제어할 수 있다.

```json
{
  "rank": 250,
  "estimatedWaitSeconds": 85,
  "nextPollAfter": 20
}
```

클라이언트가 `rank`나 `estimatedWaitSeconds`를 보고 스스로 주기를 결정할 수도 있다. 단, 서버 보호가 목적이라면 서버가 주기를 내려주는 게 일관성 있다. 클라이언트(앱, 웹)가 여러 종류면 각자 다르게 구현할 위험이 있기 때문이다.

---

### SSE (Server-Sent Events)

서버가 순번이 바뀔 때마다 클라이언트에게 Push하는 방식.

```
클라이언트 → GET /queue/sse (연결 수립)
서버 → { rank: 250 } → 클라이언트 (순번 변경 시마다 Push)
```

불필요한 요청이 없다. 순번이 바뀔 때만 서버가 Push한다.

**부담: 메모리**

커넥션을 서버 메모리에 보관해야 한다. 스레드를 점유하는 게 아니라 Map에 SseEmitter를 들고 있는 구조다.

```
Map<userId, SseEmitter>

userA → SseEmitter
userB → SseEmitter
userC → SseEmitter
```

스케줄러가 순번을 업데이트할 때 Map을 순회하며 각 커넥션에 Push한다. 커넥션 수만큼 메모리를 사용한다.

**연결 끊김 감지**

클라이언트가 브라우저를 닫거나 네트워크가 끊기면 서버는 즉시 알 수 없다. 두 가지 방법으로 감지한다.

- **Push 실패 시 감지**: `SseEmitter.send()` 실패 시 Map에서 제거 + 대기열에서 제거
- **Heartbeat**: 서버가 주기적으로 빈 이벤트를 전송, 실패하면 끊긴 것으로 판단

Push 실패 감지만 있으면 스케줄러가 돌기 전까지 끊김을 모른다. Heartbeat를 함께 쓰면 더 빠르게 감지할 수 있다.

Polling 기반 대기열에서 TTL + Heartbeat로 이탈을 감지하는 것과 달리, SSE는 연결 끊김으로 즉시 감지할 수 있다.

**재연결**

브라우저는 SSE 연결이 끊기면 자동으로 재연결을 시도한다. 재연결 시 userId를 함께 보내면 Map에 SseEmitter를 다시 등록하고 Redis에서 현재 순번을 조회해서 응답하면 된다. 대기 정보는 Redis Sorted Set에 그대로 있으므로 순번은 유지된다.

```
대기 정보: Redis Sorted Set (커넥션 끊겨도 유지)
커넥션:    서버 메모리 Map (끊기면 제거, 재연결 시 다시 등록)
```

Polling은 요청마다 userId를 보내니까 재연결 문제가 없다.

---

### 비교

| | Polling | SSE |
|---|---|---|
| 방식 | 클라이언트가 주기적으로 요청 | 서버가 변경 시 Push |
| 부하 | 불필요한 요청 발생 | 커넥션 수만큼 메모리 사용 |
| 이탈 감지 | TTL + Heartbeat 필요 | 연결 끊김으로 즉시 감지 |
| 재연결 | 자연스럽게 처리 | 재연결 시 Map 재등록 필요 |
| 구현 복잡도 | 단순 | 연결 관리 복잡도 있음 |
