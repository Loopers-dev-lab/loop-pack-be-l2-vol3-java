## Back-pressure

### 개념
하류(downstream) 시스템이 감당할 수 있는 속도만큼만 요청을 흘려보내는 원리.
"거부"가 아니라 **"흐름 조절"** 이다.

### 배경
- 상류(사용자 요청)는 제어할 수 없고, 무한히 빨라질 수 있다.
- 하류(DB, PG 등)는 물리적 처리 한계가 존재한다.
- 그 한계를 초과하는 순간을 미리 대비하는 것이 Back-pressure의 목적.

### 한계 TPS 산정 공식

```
최대 TPS = 동시 처리 슬롯 수 / 평균 슬롯 점유 시간(초)
```

- **슬롯**이란 하류 시스템을 처리하기 위해 점유하는 자원 단위다.
- 하류 시스템마다 슬롯의 정의가 달라진다.

| 하류 시스템 | 슬롯 |
|---|---|
| DB | 커넥션 풀 |
| Redis | 커넥션 풀 |
| 외부 HTTP API | HTTP 커넥션 풀 or 스레드 |
| Kafka | 프로듀서 스레드 |

- 여기서 "처리 시간"은 전체 응답 시간이 아니라 **슬롯을 점유하고 있는 시간**이다.
- TPS 산정 시 **가장 큰 병목이 되는 하류 시스템의 슬롯**을 기준으로 잡는다.

**예시) DB가 병목인 경우**
```
DB 커넥션 풀: 50개
평균 커넥션 점유 시간: 200ms = 0.2초
→ 최대 TPS = 50 / 0.2 = 250 TPS
→ 안전 마진 70% 적용 → 175 TPS
```

주문 API처럼 하나의 요청이 여러 쿼리를 실행하면, 트랜잭션 전체 동안 커넥션을 점유하므로 그 시간을 기준으로 산정한다.

### 안전 마진을 적용하는 이유
한계 TPS는 이론적 최대치다. 공식은 모든 요청의 처리 시간이 일정하다고 가정하지만 현실은 다르다.

| 이유 | 설명 |
|------|------|
| 처리 시간은 평균일 뿐 | 느린 쿼리가 섞이면 실제로는 더 걸림 |
| GC, CPU 등 오버헤드 | 애플리케이션 자체 부하가 존재 |
| 순간 스파이크 대응 | 여유가 없으면 조금만 튀어도 다운 |

> 한계 TPS는 "여기까지 버틸 수 있다"가 아니라 "여기서 무너진다"에 가까운 숫자다.
> 안전 마진은 **이론과 현실의 차이를 흡수하는 버퍼**다.

#### 안전 마진 트레이드오프
```
마진 낮게  → 처리량 높음, 장애 위험 높음
마진 높게  → 처리량 낮음, 장애 위험 낮음
```

#### 안전 마진 결정 기준
| 서비스 특성 | 안전 마진 |
|---|---|
| 트래픽이 예측 가능하고 안정적 | 80~90% |
| 트래픽 변동이 크고 스파이크가 잦음 | 60~70% |
| 결제처럼 장애 시 임팩트가 큰 경우 | 50~60% |

#### 설계 단계에서의 안전 마진 설정 전략
실측 데이터가 없는 설계 단계에서는 **보수적으로 시작해서 점진적으로 올린다**.

1. **보수적으로 시작 (60~70%)** — 장애 임팩트를 고려해 여유를 많이 둔다.
2. **스테이징 환경 부하 테스트** — 위험 신호 구간을 확인하고 마진을 조정한다.
3. **운영 후 APM 실측, 점진적 상향** — 실제 트래픽 패턴 기반으로 마진을 올린다.

```
설계:             70% (보수적)
스테이징 테스트 후: 80%로 상향
운영 1개월 후 실측: 85%로 상향
```

> 낮게 시작해서 데이터로 올리는 게, 높게 잡았다가 장애 나는 것보다 낫다.

### 한계 TPS 측정 방법 (부하 테스트)
TPS를 점진적으로 올리면서 응답시간이 급격히 튀는 지점을 찾는다.
**튀기 직전 TPS 값 자체가 한계 TPS**다. 공식으로 역산할 필요 없이 실험으로 직접 찾는다.

```
10 TPS  → 안정적
100 TPS → 안정적
200 TPS → 슬슬 늘어남
250 TPS → 급격히 튐  ← 한계점
300 TPS → 타임아웃
```

응답시간이 튀는 이유: 하류 슬롯이 포화되면 새 요청이 슬롯을 기다리는 시간이 추가되기 때문.
→ **응답시간이 튀는 지점 = 하류 슬롯이 포화되는 지점**

#### 공식과 부하 테스트의 관계
- **공식** = 테스트 범위를 좁히는 추정치 ("대략 250 TPS쯤이겠다")
- **부하 테스트** = 실제 한계 TPS를 찾는 실험 (집중 구간을 정해 실측)

### 테스트 시나리오 설계
- 초기에는 완벽한 시나리오를 만들 수 없다.
- 대기열 목적이 주문 API 보호라면, **주문 API 기준**으로 TPS를 산정한다.
- 운영 데이터가 쌓이면 실제 API 호출 비율을 반영해 시나리오를 정교하게 다듬는다.

### 처리 시간 측정 방법
| 방법 | 설명 |
|------|------|
| APM 도구 (Datadog, Pinpoint 등) | 트랜잭션 구간별 시간 추적 |
| EXPLAIN ANALYZE (DB 레벨) | 쿼리 실행 시간 직접 확인 |
| 부하 테스트 (k6, nGrinder) | TPS를 올려가며 한계점 측정 |
