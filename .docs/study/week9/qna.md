## Q1. 랭킹 조회에 왜 RDB가 아닌 Redis ZSET을 선택했나요?

**[질문]**
상품 랭킹을 제공하는 방법은 여러 가지가 있어요. RDB에서 `GROUP BY + ORDER BY`로 조회하는 방식도 있고, Redis ZSET을 쓰는 방법도 있죠.
왜 RDB 기반으로 랭킹을 제공하면 안 될까요? 본인이 생각하는 이유를 설명해보세요.

**[답변]**
> RDB 기반으로 랭킹을 제공하면 매번 조회 시마다 집계 비용과 정렬 비용이 발생하기 때문?

**[후속 질문: 데이터 증가에 따른 비용 변화 & 고트래픽 상황에서의 문제]**
"집계 비용과 정렬 비용이 발생한다"는 건 이해했는데, 데이터가 많아질수록 이 비용이 어떻게 변할까요?
그리고 랭킹은 "조회가 굉장히 많은" 기능이에요. 홈 메인, 인기순 정렬, 개별 상품 순위 등 여러 지면에서 동시에 요청이 들어오는 상황을 생각해보면, RDB 조회 비용 문제가 단순히 "느리다"를 넘어서 어떤 문제로 이어질 수 있을까요?

**[답변]**
> 데이터가 많아 질 수록 집계 비용과 정렬 비용이 커지게 됩니다.(서로 비례)
> 조회가 많은 기능의 성능이 느리다면 이는 Connection 점유로 이어지고 서비스 전체 Connection Pool의 고갈을 유발할 수 있습니다.

## Q2. 일별 키 분리, 왜 필요할까요?

**[질문]**
이번 과제에서 ZSET 키를 `ranking:all:{yyyyMMdd}` 형태로 날짜별로 분리하도록 설계되어 있어요.
단순하게 `ranking:all` 하나의 키에 모든 점수를 누적하면 어떤 문제가 생길까요?

**[답변]**
> 잘 모르겠어요

**[힌트: 오래된 점수가 쌓이면 어떻게 될까?]**
시나리오를 생각해봐요.
상품 A가 1월에 엄청난 마케팅으로 주문을 10,000건 받았어요. 그 이후로는 평범한 상품이에요.
반면 상품 B는 신상품으로 오늘 막 출시돼서 주문이 100건이에요.
단일 키에 누적만 한다면, 이 두 상품의 랭킹 순서는 어떻게 될까요? 그리고 그게 사용자에게 의미 있는 정보일까요?

**[답변]**
> 단일 키인 경우 오늘 랭킹만 따로 떼어내서 초기화 할 수 없어요. 날짜별로 분리되어 있다면 날짜별 랭킹을 별도로 관리할 수 있겟죠

## Q3. TTL을 2일로 잡은 이유는 뭘까요?

**[질문]**
이번 과제 스펙에서 ZSET의 TTL을 2일(2 Day)로 지정하고 있어요.
일간 키 전략을 쓰고 있는데, TTL을 딱 1일로 잡으면 어떤 문제가 생길 수 있을까요?

**[답변]**
> 오늘 랭킹이 집계되고 사용자에게 노출되다가 정확히 하루가 지난 시점에 그 날(다음날)의 랭킹이 집계되지 않은 상태라면 랭킹 정보가 아무것도 없이 텅 비어 보일 수 있어요

**[후속 질문: TTL을 30일로 길게 잡으면?]**
그렇다면 TTL을 아예 길게, 예를 들어 30일로 잡으면 어떨까요?

**[답변]**
> 이미 날짜가 지난 데이터를 사용자가 재조회할 일이 거의 없을텐데 그렇게 길게 잡는 건 불필요하게 메모리만 차지하는 거라고 생각해요.

**[추가 논의 1: 1.5일도 과하지 않나?]**
1.5일에서 2일로 TTL을 잡아서 키 만료 시점과 새로운 키가 추가되는 시점 사이의 공백을 없애는 컨셉은 이해했는데, 그 관점에서 볼 때 1.5일도 좀 과하지 않나?

→ API 스펙이 `GET /api/v1/rankings?date=yyyyMMdd` 처럼 날짜 파라미터를 받는 구조임을 감안하면, April 6 키가 April 7 오후 12시(1.5일 TTL 기준)에 만료되면, April 7 오후 3시에 어제 랭킹을 조회하는 사용자는 데이터가 없는 상황을 마주하게 됨.
결국 TTL은 "공백 방지"뿐 아니라 **이전 날짜 랭킹을 언제까지 조회 가능해야 하는가**라는 서비스 정책에 따라 결정되는 설계 결정.

**[추가 논의 2: 콜드 스타트 & Score Carry-Over]**
4월 8일 자정에 7일 키는 이벤트가 없어 존재하지 않고, 6일 키도 TTL이 거의 다 됐을 때 → 8일 랭킹을 어떻게 보여줄 수 있나?

- "이전 날짜 랭킹을 fallback으로 보여주자" → 7일 키가 없고 6일 키도 만료되면 동작 불가
- 해결책: **Score Carry-Over** — 매일 23:50에 오늘 키의 점수를 작은 비율(예: 10%)로 곱해 내일 키를 미리 생성
- 그대로 복사하면 안 되는 이유: 7일 점수가 8일 랭킹을 지배해 실제 8일 이벤트가 반영되지 않는 문제 발생
- 10% 정도의 작은 비율로만 복사하면 내일 첫 이벤트들이 금방 앞질러갈 수 있음

**[추가 논의 3: Score Carry-Over가 있으면 TTL 1.5~2일이 필요 없지 않나?]**
> Score Carry-Over 방식을 취할 거면 TTL이 1.5 ~ 2일일 필요가 없지 않아?

→ Score Carry-Over는 콜드 스타트를 해결하지만, TTL 길이는 별개의 관심사.
- 이전 날짜 조회(`?date=20250407`)를 허용할 것인지는 비즈니스 결정
- 이전 날짜 조회를 지원하지 않는다면 TTL을 짧게 가져가도 무방
- 결국 **콜드 스타트 → Score Carry-Over**, **TTL 길이 → 히스토리 조회 정책**으로 관심사를 분리해서 설계해야 함

**[추가 논의 4: TTL 1.5~2배의 본질적 이유]**
> subject 문서에서 "메모리 관리를 위해 시간 윈도우의 1.5~2배 정도로 잡으면 안정적"이라고 나온 거 보면 이전 날짜 조회 때문이 아닌 것 같은데

→ 맞음. 1.5~2배의 핵심은 키가 자정에 생성되지 않는다는 점.
- 키는 첫 이벤트 발생 시 생성되고 그때 TTL이 시작됨
- 1배(1일)만 잡으면 키 생성 시각에 따라 다음날 중간에 만료될 수 있음
- 1.5~2배는 **키 생성 타이밍의 불확실성을 커버하는 안전 마진**
- 이전 날짜 조회 지원은 부가적 이유
- 단, Score Carry-Over가 있고 이전 날짜 조회도 비즈니스 결정이라면, 다음날 중간에 만료되는 것은 시스템 결함이 아님
- 1.5~2배는 여러 상황을 커버하는 보수적인 기본값이며, 설계에 따라 더 짧게 가져가도 무방

## Q4. 이벤트별 가중치 설계

**[질문]**
조회, 좋아요, 주문 세 가지 이벤트가 있어요. 각각 가중치를 다르게 줘야 하는데, 어떤 순서로 가중치를 높게 주는 게 맞을까요? 그리고 그렇게 생각하는 이유는 뭔가요?

**[답변]**
> 사용자 입장에서 랭킹이 높다는 건 많이 팔린 상품이기 때문에 주문이 가중치가 젤 높아야 해.
> 사실 주문만 반영되어도 괜찮다고 봐. 다만 실제 판매가 되지 않는 경우가 있을 수 있으므로 조회, 좋아요 같은 다른 유저 행동도 반영이 되는 거고 더 Active한 행동인 좋아요에 가중치가 높아야 하지.
> 주문 > 좋아요 > 조회 순으로 가중치를 설정하면 될 거 같아(ex: 0.5, 0.3, 0.2)

**[후속 질문: 주문 이벤트의 점수 설계]**
주문 이벤트의 점수를 어떻게 잡을 건가요?
1,000원짜리 상품 주문 1건과 100,000원짜리 상품 주문 1건을 동일하게 1점으로 처리하면 어떤 문제가 생길까요?

**[답변]**
> 상품 A 를 주문한 수량으로 점수를 책정해야하지 않을까?

**[후속 질문: 수량 기준 vs 매출액 기준]**
수량만 보면 1,000원짜리 100개 vs 100,000원짜리 5개에서 수량 기준으로는 전자가 압도적으로 높은 랭킹이 됨. 비즈니스 관점에서 맞는 랭킹인가?

→ "많이 팔린다"를 두 가지로 해석 가능:
- **판매 건수** (몇 명이 샀나) → 수량 기준
- **매출액** (얼마나 벌었나) → price × quantity 기준

어느 쪽도 틀리지 않으며, 서비스 목표에 따라 결정:
- C커머스 스타일: 매출액(price × amount) 기반
- 소셜 커머스 스타일: 판매 건수 기반
- Quest 문서는 `price * amount`를 예시로 제시 (매출 기여도 반영)
- **중요한 건 설계 당시 그 이유를 명확히 하는 것**

## Q5. 랭킹 API 페이지네이션 설계

**[질문]**
`GET /api/v1/rankings?date=yyyyMMdd&size=20&page=1` 스펙에서 페이지네이션을 지원해요.
Redis ZSET에서 페이지네이션을 구현하려면 `ZREVRANGE`의 범위를 어떻게 계산할 건가요?

**[답변]**
> page * size ~ (page + 1) * size 로 하면 되지 않아?

**[후속 질문: page=1일 때 검증]**
page=1, size=20으로 적용하면 start=20, end=40 → 1페이지인데 21번째 항목부터 조회하게 됨. 의도한 결과인가?

**[답변]**
> 그럼 page를 하나씩 줄이면 되지

**[후속 질문: inclusive 범위로 인한 off-by-one]**
page=1, size=20이면 start=0, end=20 → ZREVRANGE는 양 끝 포함(inclusive)이므로 21개 반환됨. 의도한 건 20개 아닌가?

**[답변]**
> start = (page - 1) * size
> end = page * size - 1

→ page=1, size=20이면 `ZREVRANGE key 0 19` → 20개 정확히 반환

## Q7. 상품 상세 조회 시 순위 정보 반환

**[질문]**
`ZREVRANK`로 순위를 조회할 때, 랭킹에 없는 상품이면 어떤 값이 반환될까요? 그리고 이걸 어떻게 처리할 건가요?

**[답변]**
> 잘 모르겠어

**[힌트: ZREVRANK 결과가 없을 때]**
`ZREVRANK key member`를 실행했을 때 해당 member가 존재하지 않으면 Redis는 어떤 값을 반환할까요?

**[답변]**
> 결과가 없으면 null 아닌가?

**[후속 질문: 0-based 순위 처리]**
Redis는 nil(Java에서 null)을 반환하므로 스펙대로 null 응답 처리 가능.
단, `ZREVRANK`는 0-based 순위를 반환 (1등 = 0). 사용자에게 보여줄 때 어떻게 처리해야 할까요?

**[답변]**
> +1 처리 해줘야 해. 지금 score 기반 오름차순으로 ZSET에 정렬되니까 ZREVRANK를 보여주는 거지?

→ ZSET은 score 오름차순 저장, `ZREVRANK`는 역순(높은 score = 낮은 인덱스)으로 순위 매김
→ 0이 1등이므로 응답 시 +1 처리 필요

## Q8. ZSET에 점수를 어떻게 누적할 건가요?

**[질문]**
이벤트가 발생할 때마다 ZSET에 점수를 반영해야 해요.
Redis ZSET 명령어 중에는 `ZADD`와 `ZINCRBY`가 있는데, 실시간 랭킹 점수 **누적**에는 어떤 명령어를 써야 할까요? 그리고 그 이유는 뭔가요?

**[답변]**
> ZINCRBY 가 적합해. 새로운 이벤트가 발생됐을 때 기존 점수에 누적하는 방식이기 때문이야.
> ZADD 로 하게 되면 기존 점수를 조회해서 직접 더하고 그 결과값을 ZADD 해야 하기 때문에 READ-MODIFY-WRITE 패턴이라 동시성 문제가 발생할 우려도 있어.

**[후속 질문: ZINCRBY increment 값 설계]**
그럼 실제로 ZINCRBY를 호출할 때, 어떤 값을 increment로 넘길 건가요?
`ZINCRBY ranking:all:20250406 ??? productId` 에서 `???` 자리에 어떤 값이 들어가야 할까요?

**[답변]**
> 발생한 이벤트 유형에 따라 score * weight 값을 넣으면 돼!

**[후속 질문: 어떤 Redis 명령어로 하위 항목을 제거할까?]**

**[답변]**
> Redis ZPOPMIN

**[후속 질문: Top 100만 유지하려면?]**

**[답변]**
> 모르겠어
