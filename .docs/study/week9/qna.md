## Q1. 랭킹 Key 설계

**[질문]**
랭킹 데이터를 Redis ZSET에 저장할 때, Key를 하나만 쓴다면(`ranking:all`) 어떤 문제가 생길까요?

**[답변]**
> 하나의 키에 상품 점수를 누적하는 경우 과거에 지표가 훌륭해 높은 랭킹을 차지한 상품이 최근에는 성적이 미진해도 높은 랭킹을 차지하는 문제가 있을 수 있습니다.
> 사용자가 랭킹 시스템에 기대하는 것은 최근 트렌드이기 때문에 키는 최소한 일간 단위로 설계하는 것이 좋다고 생각합니다.

**[후속 질문: 일간 키 전환 시점의 콜드 스타트]**
일간 키로 설계할 때, 자정이 지나 새로운 날짜의 키가 막 생성된 직후 사용자가 "오늘의 인기 상품 Top 10"을 요청하면 어떤 일이 벌어질까요?

**[답변]**
> 콜드스타트 문제가 발생하면 사용자는 텅 비어있는 랭킹보드를 보게됩니다. 이를 방지하기 위해서 Score Carry Over 를 적용해서 23:50분에 ranking:all:20250906 데이터에 매우 작은 값 (ex: 0.0000001) 을 곱해 ranking:all:20250907 에 옮겨놓는 작업이 필요합니다.

**[후속 질문: Carry-Over 가중치 크기의 트레이드오프]**
Carry-Over 가중치가 너무 작으면 어떤 문제가, 너무 크면 어떤 문제가 생길까요?

**[답변]**
> 가중치가 크면 오늘 새로운 지표가 발생했음에도 이것이 랭킹에 미치는 실질적 영향이 미미할 수 있게 됩니다. 가중치가 너무 작은 경우에는 당일 이벤트가 충분히 축적되기 전까지 랭킹이 지속적으로 변화해 유의미하지 않은 정보가 될 수 있는 우려가 있습니다.
>
> 다만 후자의 경우 오늘 1개라도 팔린 상품이 어제 잘 팔린 상품보다 오늘 랭킹이 높은 게 맞다고 비즈니스적으로 판단한다면 감수할 수 있는 부분이라고 봅니다.

**[멘토 보충: 적절한 가중치 기준]**
가중치 선택의 핵심 질문: "오늘의 활발한 상품이 carry-over 점수를 역전하는 데 얼마나 걸려야 적절한가?"

| 가중치 | 현상 |
|---|---|
| 너무 작음 (≈0) | carry-over 자체가 무의미 — 사실상 Cold Start 미해결 |
| 적당 (예: 0.1) | 초기 의미 있는 랭킹 제공 + 당일 이벤트로 자연 역전 가능 |
| 너무 큼 (≈1) | 어제 랭킹이 하루 종일 지배, 오늘 이벤트 영향 미미 |

가중치는 정해진 정답이 없고, 서비스가 추구하는 랭킹 성격(최신 트렌드 vs 검증된 인기)과 실제 이벤트 발생 빈도를 보고 튜닝하는 값.

## Q2. 이벤트별 Score 설계

**[질문]**
조회/좋아요/주문 이벤트에서 주문만 `Score = price * amount`로 설계한 이유는 뭘까요?

**[답변]**
> 상품 A에 대한 주문이 발생하면 Score = 1과 같이 처리해버리면 해당 주문이 갖는 실질적 가치를 랭킹에 반영하기 어렵습니다. 기본적으로 주문수량이 Score에 반영되는 것이 합리적이라고 생각합니다. 여기에 가격이 결합되는 이유는 비싼 상품을 사람들이 기꺼이 주문한다라는 정보 자체가 랭킹에 유의미할 수 있기 때문입니다.

**[후속 질문: price * amount의 스케일 문제]**
상품 A(1,000원, 100건)와 상품 B(500,000원, 1건)를 비교하면 B의 Score가 훨씬 높아지는데, 이게 "인기 상품"을 제대로 반영한다고 볼 수 있을까요?

**[답변]**
> 맞습니다. 가격 단위가 크게 차이나면 가격의 차이가 Score를 지배하는 현상이 발생할 수 있습니다. 그래서 적절한 스케일링이 필요할 것 같습니다.

**[후속 질문: log 정규화]**
왜 log를 적용하면 스케일 문제가 완화될까요?

**[답변]**
> log는 X가 커질 수록 logX의 단위증가량은 줄어드는 방식이기 때문에 수치가 완만하게 나타나게 됩니다. 그래서 기존에 price 로 비교할 때보다 수치 차이를 줄일 수 있습니다.

**[참고: 다른 스케일링 방식]**

| 방식 | 수식 | 특징 | 실시간 적합도 |
|---|---|---|---|
| Log 스케일링 | `log(1 + x)` | 큰 값 차이 압축, 전체 분포 불필요 | ✅ 적합 |
| Square Root | `sqrt(x)` | log보다 완만한 압축, 분포 불필요 | ✅ 적합 |
| Capping | `min(x, MAX)` | 상한 클리핑, 구현 단순 | ✅ 적합 |
| Min-Max | `(x - min) / (max - min)` | [0,1] 범위 압축, min/max 필요 | ⚠️ 복잡 |
| Z-score | `(x - mean) / std_dev` | 평균/표준편차 필요 | ⚠️ 복잡 |

실시간 이벤트 단건 처리 환경에서는 전체 분포 통계가 필요 없는 **log, sqrt, capping** 이 실용적. Min-Max/Z-score는 배치 집계 후 정규화 시 적합.

## Q3. TTL 설계

**[질문]**
ZSET 스펙에 `TTL = 2Day`로 명시되어 있는데, 왜 1일이 아닌 2일일까요?

**[답변]**
> 잘 모르겠습니다. 날짜가 지나면 어제 랭킹을 볼 일이 없어지는데 왜 2일인지 모르겠고, 필요하다면 차라리 DB에 저장해두는 게 낫지 않나요?

**[후속 질문: date 파라미터와 TTL의 관계]**
랭킹 API에 `?date=yyyyMMdd` 파라미터가 있어서 어제 랭킹도 조회 가능한데, TTL이 정확히 1일이면 어떤 문제가 생길까요?

**[답변]**
> TTL이 1일이더라도 DB에 저장이 되어있다면 Redis에서 날아간 건 아무런 문제가 되지 않죠. 오히려 저렇게 해서 과거 날짜 랭킹을 조회하도록 해줘야한다면 TTL 이 2일이든 3일이든 상관없이 영속화된 랭킹 정보가 있어야 맞는 것 아닌가요?

**[멘토 보충]**
DB 영속화는 장기 보관에 맞는 올바른 방향. 단, 이 과제는 Redis-only 설계를 전제로 함.
이 전제에서 TTL = 1일의 문제:
- `date=어제` 쿼리 시 이미 키 만료되어 있을 수 있음 (자정 생성 → 24시간 후 만료)
- Score Carry-Over 스케줄러(23:50)가 실패 후 자정 이후 재시도 시 키가 없을 수 있음

2일 TTL은 이러한 **운영상의 안전 버퍼**를 제공. subject 문서 기준: "시간 윈도우의 1.5배~2배로 안정적".

## Q6. ZADD vs ZINCRBY

**[질문]**
랭킹 점수를 누적할 때 `ZADD`와 `ZINCRBY` 중 어떤 명령어를 써야 할까요?

**[답변]**
> ZADD 방식은 DB에서 product_metrics를 조회해 이벤트를 합산해 SCORE를 재계산 후 덮어씁니다. ZINCRBY는 이벤트 점수값을 바로 SCORE에 더하는 방식입니다.
> Redis 반영 실패 시 ZADD는 다음 이벤트에서 원장 기반으로 재보정되지만, ZINCRBY는 유실된 이벤트가 영구히 반영되지 못하는 문제가 있습니다.
> product_metrics 조회/반영 비용이 크지 않다면 ZADD가 합리적일 것 같습니다.

**[후속 질문: ZADD의 동시성 문제]**
같은 상품 이벤트 두 개가 동시에 처리될 때 ZADD 방식의 문제는?

```
Consumer A: DB atomic update → view_count=11 읽음
Consumer B: DB atomic update → view_count=12 읽음
Consumer B: ZADD score=1.2
Consumer A: ZADD score=1.1  ← 오래된 값으로 덮어씀
```

**[답변]**
> READ-MODIFY-WRITE 패턴에서 동시성 문제로 인한 갱신손실이 발생할 수 있습니다. 다만 DB 반영을 Atomic Update로 먼저 하고 이걸 READ해서 Redis에 쓰는 방식이라면 문제가 발생 안 하지 않을까요?

**[후속 질문: Redis ZADD 쓰기 순서 문제]**
DB 업데이트가 atomic해도, Redis에 ZADD를 쓰는 순서가 보장되지 않으면 어떻게 될까요?

**[답변]**
> 아 그러면 오래된 값으로 덮어써지는 문제가 있겠네요. 어떻게 이 문제를 해결할 수 있을까요?

**[후속 질문: ZINCRBY의 유실 문제와 랭킹 특성]**
ZINCRBY는 atomic이지만 Redis 쓰기 실패 시 유실 문제가 있는데, 랭킹 시스템에서 이벤트 1건 유실이 허용 가능한 수준일까요?

**[답변]**
> 아니요 랭킹 시스템에서 이벤트 1개가 유실되는 건 허용할 수 있는 정도라고 봅니다. 유실되더라도 스케줄러로 재보정하면 되겠죠. 다만 ZADD 방식도 동시성 문제로 잠시 틀어진 점수가 다음 이벤트에 의해 보정될 거잖아요?

**[멘토 보충]**

| | ZINCRBY | ZADD (from DB) |
|---|---|---|
| 동시성 | ✅ atomic | ❌ 일시적 갱신 손실 가능 |
| Redis 장애 복구 | ❌ 해당 증분 유실 | ✅ 다음 이벤트에서 재보정 |
| DB 읽기 비용 | ✅ 없음 | ❌ 이벤트마다 발생 |
| 랭킹 정합성 | 충분히 정확 | 충분히 정확 |

랭킹은 완벽한 정확성보다 빠른 처리와 근사 정확성이 중요한 도메인 → 실무에서는 ZINCRBY가 자연스러운 선택.

## Q7. 상품 상세 조회 시 순위 정보

**[질문]**
`GET /products/{id}` 응답에 현재 상품의 순위를 포함해야 할 때, ZSET에 해당 상품이 없는 경우 어떻게 처리해야 할까요?

**[답변]**
> 상품 상세 조회 시에 랭킹 정보가 없다는 것은 아무런 이벤트가 발생하지 않았음을 의미합니다. 조회 이벤트가 반영되면 꼴등일 것이므로 ZCARD + 1 값을 내보내주면 되지 않을까요?

**[후속 질문: 오늘 이벤트 없는 상품이 여러 개라면?]**
오늘 ZSET에 진입한 상품이 1,000개이고 전체 상품이 10만 개라면, 나머지 9만 9천 개가 모두 ZCARD+1 순위를 갖게 되는데 이 값이 의미 있을까요?

**[답변]**
> 조회 시점에 이벤트가 발행되니까 그거에 의해서 다음에 조회될 상품의 등수는 달라지지 않나요? null로 내보내면 된다는 것은 알겠습니다만..

**[후속 질문: 이벤트 반영 시점]**
API 응답과 ZSET 업데이트 중 어느 쪽이 먼저인가요?

**[답변]**
> 응답을 내보내는 게 먼저죠.

**[멘토 보충]**
응답은 동기, ZSET 업데이트는 비동기(Kafka → collector → ZINCRBY). 응답 시점에 이번 이벤트는 아직 미반영 → ZCARD+1 가정 자체가 성립 안 함.
`null`이 정답인 이유:
- 응답 시점엔 이번 이벤트 미반영
- 오늘 이벤트 없는 상품 수만 개가 동일 순위를 공유 → 의미 없음
- `null`은 "오늘 아직 랭킹 없음"이라는 명확한 정보 전달

## Q9. ZREVRANK 0-based 처리

**[질문]**
`ZREVRANK`는 0-based 순위를 반환하는데, API 응답에 그대로 내보내야 할까요? 변환이 필요하다면 어느 레이어에서 처리해야 할까요?

**[답변]**
> 당연히 변환을 해야 하고 그건 application layer에서 처리하면 될 것 같아요.

**[후속 질문: Redis 지식의 레이어 경계]**
"Redis가 0-based다"는 지식이 application layer에 퍼져도 될까요?

**[답변]**
> 음.. 잘 모르겠네요. 랭킹이 0부터 시작하는 건 Redis라서인데, 그 지식이 애플리케이션 레이어에 퍼져도 되는 건지 모르겠네요.
> Redis 구현 세부사항을 아는 건 infrastructure 레이어예요.

**[멘토 보충]**
Repository 인터페이스는 1-based 순위를 반환하도록 선언, 구현체에서 `ZREVRANK + 1` 처리 → application layer는 Redis 내부 구조를 알 필요 없음.

```java
// domain layer
interface RankingRepository {
    Long findRank(Long productId, LocalDate date); // 1-based or null
}

// infrastructure layer
class RedisRankingRepository implements RankingRepository {
    public Long findRank(Long productId, LocalDate date) {
        Long rank = zSetOps.reverseRank(key, productId); // 0-based
        return rank != null ? rank + 1 : null;           // 1-based로 변환
    }
}
```

## Q10. Carry-Over 스케줄러 위치

**[질문]**
Score Carry-Over 스케줄러를 `commerce-collector`에 둘지, 별도 서비스로 분리할지 어떻게 결정하나요?

**[답변]**
> commerce-collector가 랭킹을 만드는 역할을 하니까 거기서 같이 하는 게 나을 것 같아요.

**[멘토 보충]**
역할 응집도 관점에서 올바른 판단. Carry-Over는 "이벤트 소비 → ZSET 관리"의 연장선이므로 collector의 책임 범위. 별도 서비스 분리는 배포/운영 복잡도만 증가.

---

## 구현 보충 사항

### 이벤트 타입별 ZINCRBY increment 계산식

| 이벤트 | increment |
|---|---|
| view | `0.1` |
| like | `0.2` |
| order | `0.7 * log(1 + price * amount)` |

### TTL 적용 전략

ZINCRBY는 key를 자동 생성하지만 TTL을 설정하지 않으므로 별도 처리 필요.

- **Redis 7.0 이상**: `EXPIREAT key timestamp NX` — TTL 없을 때만 설정, 멱등성 보장
- **Redis 7.0 미만**: 매번 `EXPIREAT key timestamp` 호출 — O(1)으로 부담 없음

만료 시각은 key 날짜 + 2일의 고정 timestamp 사용 (EXPIRE 대비 호출 시각과 무관하게 동일한 만료 시각 보장).

```java
redisTemplate.opsForZSet().incrementScore(key, productId, increment);
redisTemplate.expire(key, Duration.ofDays(2), NX); // Redis 7.0+
```

Carry-Over 스케줄러에서 ZUNIONSTORE로 새 key 생성 후에도 동일하게 TTL 설정 필요.

```java
// 23:50 스케줄러
zunionstore("ranking:all:20250907", "ranking:all:20250906", weight=0.1);
expireat("ranking:all:20250907", timestamp); // 새 key에도 TTL 설정
```

### date 파라미터 기본값

`GET /api/v1/rankings` 에서 `date` 생략 시 오늘 날짜(`LocalDate.now()`)를 기본값으로 사용.
