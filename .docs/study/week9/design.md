# Round 9 — 랭킹 시스템 설계 정리

> QnA 세션을 통해 확정된 설계 결정을 기록한다.

---

## 1. 기술 선택: Redis ZSET

**RDB를 쓰지 않는 이유**

- `GROUP BY + ORDER BY` 기반 집계는 데이터가 늘어날수록 비용이 선형 이상으로 증가
- 랭킹은 홈 메인, 인기순 정렬, 개별 순위 등 다양한 지면에서 동시에 요청되는 고빈도 조회
- 커넥션 점유 시간이 길어지면 커넥션 풀 고갈로 서비스 전체에 영향

**Redis ZSET 선택 이유**

- 삽입/수정 O(logN), Top-N 조회 O(N) — 정렬이 내장되어 별도 처리 불필요
- `ZINCRBY`로 원자적 누적 가능 — READ-MODIFY-WRITE 없이 동시성 안전

---

## 2. ZSET Key 설계

### 일간 키

```
ranking:all:{yyyyMMdd}
예: ranking:all:20250406
```

**날짜별로 분리하는 이유**

- 단일 누적 키는 과거에 점수를 많이 쌓은 상품이 계속 상위를 독식 (롱테일 문제)
- 날짜 키 분리 시 특정 날짜 랭킹만 독립적으로 초기화/보정 가능

### (Nice-to-Have) 시간 단위 키

```
ranking:all:{yyyyMMdd}:{HHmm}
예: ranking:all:20250406:0000
```

- 일간 키와 형태 일관성 유지
- 종료시간은 키에 포함하지 않음 — 1시간 고정 윈도우이므로 시작시간만으로 충분

---

## 3. TTL 설계

| 상황 | TTL | 이유 |
|---|---|---|
| Score Carry-Over **없을 때** | 2일 | 키는 첫 이벤트 시 생성되므로 자정 이후 생성될 수 있음. 1일 TTL은 다음날 중간에 만료될 수 있어 안전 마진으로 1.5~2배 |
| Score Carry-Over **있을 때** | 25시간 | 23:50에 생성, 다음날 23:50 스케줄러가 실행될 때까지만 살아있으면 충분 |
| 시간 단위 키 | 70분 | 50분에 Carry-Over 실행, 다음 시간 키가 생성될 때까지 안전 마진 확보 |

**TTL의 두 가지 관심사**

1. **키 생성 타이밍 안전 마진** — 키가 자정에 생성되지 않으므로 다음날 중간에 만료되는 문제 방지
2. **히스토리 조회 정책** — `?date=yyyyMMdd` 파라미터로 이전 날짜 조회를 얼마나 허용할지는 비즈니스 결정

## 4. 점수 설계 (Weighted Sum)

### 가중치

```
주문(order)  : 0.5
좋아요(like) : 0.3
조회(view)   : 0.2
```

- 주문 > 좋아요 > 조회 순 — 구매 결정과의 직접적 연관도 반영

### 이벤트별 기본 점수

| 이벤트 | Score | ZINCRBY increment |
|---|---|---|
| 조회 | 1 | `1 × 0.2 = 0.2` |
| 좋아요 | 1 | `1 × 0.3 = 0.3` |
| 주문 | `price × amount` | `price × amount × 0.5` |

**주문 점수에 log 적용 고려 시**

- 고가 상품 1건과 저가 상품 100건의 매출 차이가 ZSET 점수를 지배하는 문제 완화
- log 적용은 조회/좋아요 점수도 랭킹에 의미있게 반영되게 함
- 단, "매출 기여도가 높은 상품 노출"이 목표라면 log를 씌우면 안 됨 — 비즈니스 의도가 결정

**ZINCRBY 사용 이유**

- `ZADD`는 READ-MODIFY-WRITE 패턴 필요 → 동시성 문제
- `ZINCRBY`는 원자적으로 누적 — 별도 조회 없이 안전

## 5. 콜드 스타트 해결: Score Carry-Over

**문제**: 날짜가 바뀌는 시점에 새 키에 점수가 없어 랭킹이 비어 있음

**해결**: 매일 23:50 스케줄러가 오늘 키 점수의 10%를 내일 키에 미리 복사

```redis
ZUNIONSTORE ranking:all:20250407 1 ranking:all:20250406 WEIGHTS 0.1 AGGREGATE SUM
EXPIRE ranking:all:20250407 90000  -- 25시간(초 단위)
```

**10%만 복사하는 이유**: 전날 점수를 그대로 복사하면 오늘 이벤트가 어제 점수를 이기기 어려움. 작은 비율로 복사해 오늘 첫 이벤트가 금방 앞질러갈 수 있도록 함.

## 6. 랭킹 API 설계

### 6-1. 랭킹 페이지 조회

```
GET /api/v1/rankings?date=yyyyMMdd&size=20&page=1
```

**ZREVRANGE 범위 계산**

```
start = (page - 1) * size
end   = page * size - 1

예) page=1, size=20 → ZREVRANGE key 0 19 → 20개 반환
예) page=2, size=20 → ZREVRANGE key 20 39 → 20개 반환
```

ZREVRANGE는 양 끝 포함(inclusive)이므로 end를 `page * size - 1`로 설정해야 정확히 size개 반환.

**상품 정보 Aggregation**

1. ZREVRANGE로 `(productId, score)` 목록 조회 (순서 보장됨)
2. productId 목록으로 `IN` 절 단일 DB 조회 — N+1 방지
3. 애플리케이션에서 ZREVRANGE 순서 기준으로 정렬해 바인딩

### 6-2. 상품 상세 조회 시 순위 추가

```redis
ZREVRANK ranking:all:20250406 {productId}
```

- 결과 없으면 nil → null 응답
- ZSET은 0-based이므로 응답 시 `+1` 처리해 1-based 순위 반환

---

## 7. Top-N 메모리 관리

상품 수가 많아지면 ZSET 크기 무한 증가 → ZINCRBY 직후 하위 항목 정리

```redis
ZREMRANGEBYRANK ranking:all:20250406 0 -(N+1)
-- Top N개만 유지, 나머지 삭제
-- 예) Top 100 유지: ZREMRANGEBYRANK key 0 -101
```

## 8. Kafka 배치 리스너

**단건 처리 vs 배치 처리**

| 항목 | 단건 | 배치 |
|---|---|---|
| ZINCRBY 호출 | 이벤트 수만큼 | 배치 내 고유 productId 수만큼 |
| 실시간성 | 높음 | 배치 사이즈에 따라 지연 발생 |
| 처리량(Throughput) | 낮음 | 높음 |

**배치 사이즈 트레이드오프**

- 크게 → Redis 호출 감소, 처리량 향상 / 실시간 랭킹 반영 지연
- 작게 → 실시간성 향상 / 처리량 감소
- "얼마나 실시간에 가깝게 랭킹을 반영할 것인가"는 비즈니스 요구사항에 따라 결정

---

## 9. Top-N 캐싱

매 요청마다 ZREVRANGE를 호출하는 것도 연산 비용이 발생하므로, 응답 결과를 캐싱.

**실제 랭킹 반영 지연 계산**

```
최대 지연 = 배치 처리 지연 + 캐시 TTL
예) 배치 지연 10초 + 캐시 TTL 60초 = 최대 70초 지연
```

캐시 TTL은 "얼마나 실시간 랭킹을 보여줄 것인가"라는 비즈니스 의사결정.

## 10. 실시간 가중치 조절

**현재**: 코드에 하드코딩 → 변경 시 재배포 필요

**개선 방향**: 가중치를 RDB에 저장, 수정 API 제공

**RDB 선택 이유**: 영속성 필요. Redis는 재시작 시 소실 우려. yml은 런타임 수정 불가.

**가중치 조회 전략**

| 처리 방식 | 가중치 조회 |
|---|---|
| 단건 처리 | 이벤트 처리 시 매번 DB에서 조회 (어차피 DB 커넥션이 잡혀있어 추가 비용 낮음) |
| 배치 처리 | 배치 시작 시점에 한 번만 조회해 배치 전체에서 재사용 |

---

## 11. 책임 분리 원칙

**키 결정 책임 위치**: 랭킹 도메인/서비스

- Consumer가 키 포맷을 직접 알면 키 변경 시 Consumer도 수정해야 하는 결합 발생
- Consumer는 이벤트 발생 사실만 전달, "어느 키에 쓸지"는 랭킹 도메인의 관심사

**일간 + 시간 단위 동시 운영 시**

- Redis는 패턴 기반 쓰기 미지원
- 이벤트 하나에 ZINCRBY를 각 키(일간, 시간 단위)에 개별 호출
