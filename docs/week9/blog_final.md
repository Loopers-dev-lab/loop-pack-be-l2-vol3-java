## TL;DR

- "ZINCRBY 한 줄이면 되겠지"라고 생각했다. Kafka 재전달이 발생하자 점수가 3배로 불었다. 설계를 두 번 갈아엎었다.
- 결론: **"DB를 원장으로, Redis는 그 복사본."** 이 원칙 하나가 이후 모든 결정을 단순하게 만들었다.
- Kafka Batch Listener로 N건의 이벤트를 1회 DB 호출로 압축했다. 처리량과 정합성을 동시에 잡을 수 있었다.
- k6로 측정하니 읽기(p95 4.8ms)와 쓰기(p95 3.8s)는 약 800배 차이났다. "왜 읽기 캐시가 필요한가"를 숫자로 확인했다.
- 테스트 100개를 작성하면서 코드만으로는 드러나지 않는 버그 2건을 잡았다.

---

## 들어가며

대기열 시스템을 만들 때 Redis Sorted Set을 처음 써봤었다. 점수를 매기면 정렬이 자동으로 유지되는 구조라 순위를 뽑는 데 꽤 잘 맞는다고 생각했다.

> *"이벤트 들어올 때마다 ZINCRBY로 점수 누적하고, ZREVRANGE로 상위 N개 뽑으면 끝 아닌가?"*

처음에는 이렇게 생각했는데, 실제로 해보니 생각보다 단순하지 않았다.

Kafka 재전달이 발생하면 동일 이벤트가 다시 들어오면서 점수가 계속 누적되고, 결제 이벤트는 파티션 키가 달라서 동시에 같은 DB 행을 건드리는 문제가 있었다. 성능을 올리려고 만든 Redis 병합 로직도 계산 결과가 기대와 다르게 나왔다. 결국 설계를 두 번 갈아엎게 됐다.

최종적으로는 **Kafka Batch Listener**로 메모리에서 먼저 합산하고, DB를 기준으로 집계한 값을 Redis에 반영하는 구조로 바꿨다.  
부분 실패가 발생하더라도 이후 재처리 과정에서 Redis가 DB 기준으로 다시 맞춰지도록 설계했다.

## Part1. 랭킹 시스템, 무엇을 먼저 결정해야 하는가

구현에 들어가기 전에 먼저 정해야 할 것들이 있다. 이걸 먼저 정하지 않으면 기술 선택이 엉뚱한 방향으로 흘러간다.

### 1. "인기 상품"은 어떻게 계산하는가

조회수, 좋아요, 구매 건수, 구매 금액 — 어떤 지표를 쓰느냐에 따라 랭킹의 성격이 달라진다. 조회 위주면 화제성 상품이 올라오고, 구매 위주면 실제 매출 기여 상품이 올라온다.

지표를 정했으면 가중치도 같이 정해야 한다. 조회 1회와 주문 1건을 같은 값으로 볼 수는 없다. 주문은 빈도는 낮지만 실제 구매로 이어지는 강한 신호이기 때문이다.


```
Score = 조회 × 0.1 + 좋아요 × 0.2 + log1p(주문금액) × 0.7
```


여기서 `log1p()`를 쓴 이유는 고액 상품이 점수를 과도하게 가져가는 걸 막기 위해서다.  
단순 금액 기준으로 계산하면 만 원짜리 상품과 백만 원짜리 상품이 같은 횟수로 팔려도 점수 차이가 너무 크게 벌어진다.

`log1p`는 값이 커질수록 증가 폭을 완만하게 만들어서, 금액이 커질수록 영향력은 유지하되 점수가 한쪽으로 쏠리는 걸 완화해준다.



--- 
### 2. 시간 경계를 어떻게 다룰 것인가

랭킹을 계속 누적하기만 하면 오래 팔린 상품이 상위를 계속 차지하게 된다. 신상품은 올라올 기회조차 없어진다.

그래서 시간을 일정 단위로 끊어서 관리하는 방식이 필요했다. (보통은 일간, 시간 단위로 나눈다)


```
ranking:all:20260409   // 4월 9일 랭킹 키
ranking:all:20260410   // 4월 10일 랭킹 키
```

이렇게 날짜별로 키를 분리해두면, 자연스럽게 랭킹이 리셋되고 과거 데이터 조회도 같이 해결된다.


--- 
### 3. 자정이 넘으면 어떻게 할 것인가

일간 랭킹에서는 자정이 되면 새 키가 만들어지는데, 이 시점에는 점수가 전부 0이다. 어제까지 1위였던 상품도 0시가 되면 데이터가 사라진다. 사용자 입장에서는 버그처럼 보일 수 있다.

그래서 자정 직후의 공백을 완화하기 위한 방법이 필요했다.

내가 선택한 방식은 **Score Carry-Over**였다. 새 키를 만들 때 전날 점수의 일부(예: 1%)를 미리 복사해두는 방식이다. 자정 직후에도 어제 인기 있던 상품들이 낮은 초기값을 갖고 시작하고, 이후 오늘 이벤트가 쌓이면서 자연스럽게 순위가 바뀌게 된다.

이 세 가지(지표, 시간 경계, 콜드 스타트)를 먼저 정해두면 이후 기술 선택도 훨씬 명확해진다.  
이번 구현에서는 **다중 지표(조회/좋아요/주문금액) + 일간 단위 + 1시간 버킷 집계 + 전날 점수 일부 이월**로 방향을 잡았다.

---

### 4. 실전에선 어떻게 쓰일까 — 이커머스 3사 분석

이론을 머릿속에 넣었으니, 실제 서비스들이 이 문제를 어떻게 풀고 있는지 살펴봤다. 화면에서 보이는 필터와 구조를 기준으로 정리해봤다.

**무신사**는 URL만 봐도 복잡도가 드러난다.

```
?gf=F&storeCode=musinsa&sectionId=200&categoryCode=000&ageBand=AGE_BAND_ALL
```


`성별 × 스토어 × 카테고리 × 연령대` 조합으로 세그먼트별 랭킹을 나눠서 보여주고 있었다. 이 조합의 수가 많기 때문에, 모든 경우를 실시간으로 계산하기보다는 일부는 미리 준비하거나 요청 시점에 조합해서 처리하는 방식일 가능성이 있어 보였다.

**29CM**는 시간 윈도우와 랭킹 기준을 함께 노출한다.


```
?period=HOURLY&ranking=POPULARITY&gender=F&age=30
```


`HOURLY`, `DAILY`, `WEEKLY`처럼 기간을 나누고, `POPULARITY`, `SALES`처럼 기준도 따로 존재했다.  
여러 기준의 랭킹을 동시에 제공하고 있다는 점에서, 내부적으로도 서로 다른 기준의 집계 로직이 분리되어 있을 것으로 보였다.

**네이버**는 접근이 조금 달랐다. "많이 본 상품", "많이 구매한 상품"처럼 랭킹 종류 자체를 나눠서 보여준다. 하나의 점수로 모든 랭킹을 표현하기보다는, 목적에 따라 랭킹을 분리해서 제공하는 구조에 가까워 보였다.

세 서비스를 보면 한 가지가 분명해진다. "인기 랭킹"이라고 해도 실제로는 **시간 윈도우 × 필터 축 × 점수 기준이 각각 다른 랭킹들의 집합**에 가깝다.

이번 구현에서는 이걸 전부 따라가기보다는, 가장 기본적인 뼈대 — **일간 단위 + 가중치 합산** — 부터 만들어보는 데 집중했다.

---

### 5. 왜 RDB만으로는 안 되는가

랭킹 구현에서 가장 먼저 떠올릴 방법은 `GROUP BY + ORDER BY`다. 소규모 초기 서비스라면 이것으로 충분할 수 있다.

문제는 랭킹이 대부분 홈 화면에 노출되는 영역이라 읽기 트래픽이 집중된다는 것이다. 데이터가 쌓일수록 집계 쿼리는 무거워지고, 이 쿼리가 홈 화면 로드마다 실행된다면 DB에 큰 부담이 간다.

실제 k6 결과를 보면 차이가 명확하다.

| 시나리오 | p95 |
|---|---|
| Redis ZREVRANGE (랭킹 읽기) | **4.8ms** |
| 쓰기 파이프라인 전체 (DB + Kafka 포함) | **3,839ms** |

읽기와 쓰기를 단순 비교하기는 어렵지만, 실제 서비스에서는 읽기 요청이 훨씬 많이 발생하기 때문에 이 차이는 체감 성능에 크게 영향을 준다.

Redis Sorted Set은 정렬을 자료구조 레벨에서 지원한다. 삽입/수정은 O(log N), Top-N 조회는 필요한 범위만 가져오기 때문에 매우 빠르게 동작한다(O(log N + M)).

정렬된 상태를 항상 유지하기 때문에 조회 시 별도의 집계 연산이 필요 없다.

**읽기는 Redis, 쓰기는 DB.** 이 역할 분리가 이 시스템의 기본 전제다.

## Part2. 고민한 것 들

### 1. ZINCRBY의 유혹과 ZADD의 안전함

> *처음 생각: ZINCRBY면 충분하다.*  
> *현실: Kafka 재전달이 발생하면 점수가 멋대로 불어난다.*

ZINCRBY는 단순하다. 이벤트가 들어올 때마다 점수를 더한다. DB 조회가 없으니 빠르다.

그런데 Kafka는 at-least-once 전달을 보장한다. 네트워크 지연이나 Consumer 재시작으로 같은 메시지가 두 번 이상 들어올 수 있다. ZINCRBY를 쓰면 동일 이벤트가 그대로 중복 누적된다.

Redis가 뻗어서 데이터가 날아가면 복구도 쉽지 않다. ZINCRBY로 누적된 값은 별도의 원본이 없기 때문에, 어디서부터 다시 계산해야 하는지도 애매해진다.

그래서 ZADD로 방향을 바꿨다. DB에 집계값을 먼저 쌓고, 그 값을 기준으로 Redis를 덮어쓰는 방식이다.

| 방식 | 장점 | 단점 |
|---|---|---|
| **ZINCRBY** | 구현 단순, DB 호출 없음 | Kafka 재전달 시 중복 누적, 복구 어려움 |
| **ZADD** | DB 기준으로 다시 계산해 반영 가능 | 매 이벤트마다 DB 호출 필요 |

**ZADD를 선택했다.** "DB를 원장으로"라는 원칙을 처음 적용한 부분이다.

DB 호출 부담은 Kafka `@KafkaListener(batch = true)`로 완화했다. 폴링한 이벤트들을 메모리에서 먼저 합산한 뒤, 배치 단위로 DB에 1회 반영한다. N건의 이벤트 → 1회 DB 호출이다.

실제로 49,974건의 view/like/unlike 이벤트를 최대 1,000 VU로 쏘았을 때 **HTTP 에러율 0%**, 초당 385 req/s를 처리했다.

다만 p95 응답시간은 3,839ms로 높게 나왔다. 에러는 없었지만, 처리 속도가 입력 속도를 따라가지 못하면서 지연이 누적되고 있는 상태였다.  
"에러가 없다고 해서 문제가 없는 건 아니다"라는 걸 숫자로 확인한 셈이다. 이 부분은 별도 개선 과제로 남겨뒀다.

---

### 2. 결제 이벤트의 배신 — 파티션 키가 달랐다

> *처음 가정: 파티션 키가 productId라면 같은 상품은 항상 같은 스레드에서 처리된다.*  
> *현실: 결제 이벤트의 파티션 키는 orderId였다.*

조회/좋아요 이벤트는 `productId` 기반으로 파티셔닝된다. 같은 상품 이벤트는 동일 파티션으로 들어오기 때문에, 기본적으로는 순차적으로 처리되는 구조였다.

결제는 달랐다. 장바구니 결제는 여러 상품을 묶어서 처리하기 때문에 `orderId`로 파티셔닝된다. 같은 상품을 두 사람이 동시에 결제하면?
![](https://velog.velcdn.com/images/jsj1215/post/2403d8b1-0312-4f79-b4fb-8dfecd110717/image.png)

애플리케이션 레벨에서 read → 가공 → write로 처리하면 두 스레드가 같은 값을 읽은 뒤 각자 +1해서 덮어쓰는 Lost Update가 발생할 수 있다.

그래서 해결을 DB 레벨 원자성에 맡겼다.

```sql
INSERT INTO product_metrics_hourly (product_id, bucket_hour, view_count, like_count, order_count, order_amount)
VALUES (:pid, :bh, GREATEST(:vd, 0), GREATEST(:ld, 0), GREATEST(:od, 0), GREATEST(:oa, 0))
ON DUPLICATE KEY UPDATE
  view_count   = GREATEST(view_count + :vd, 0),
  like_count   = GREATEST(like_count + :ld, 0),
  order_count  = GREATEST(order_count + :od, 0),
  order_amount = GREATEST(order_amount + :oa, 0)
```

ON DUPLICATE KEY UPDATE는 read와 write를 하나의 쿼리 안에서 처리하기 때문에, 애플리케이션 레벨에서 발생하던 Lost Update 문제를 줄일 수 있다. DB 엔진이 내부적으로 락을 관리하며 동시성을 제어한다.

JPA 엔티티 중심에서 벗어나 Native Query를 쓰는 건 아쉬웠지만, 경합 상황을 직접적으로 처리할 수 있는 방법이었다.

다만 k6 Hot Product 시나리오(상품 1개에 70% 트래픽 집중)에서 p95가 585ms로 상승했다. 특정 row에 트래픽이 몰리면 DB 레벨에서 락 대기가 발생한다는 걸 확인했다. 정확도는 유지됐다(view 드리프트 +1.05%).

### 3. ZUNIONSTORE의 수학적 함정

> *처음 아이디어: 1시간 단위로 ZSET을 캐시해두고, 조회 시 ZUNIONSTORE로 합치면 DB를 거치지 않아도 된다.*  
> *현실: log1p를 쓰는 순간 이 방식은 기대한 결과와 달라진다.*

시간대별로 캐시를 쌓아두고 ZUNIONSTORE로 합산하는 아이디어는 꽤 괜찮아 보였다. DB를 거치지 않고도 일간 랭킹을 만들 수 있으니 성능 면에서도 이점이 있었다.

문제는 `log1p()` 정규화였다.

> 같은 200만원 판매된 상품 A, B를 비교해보자.
>
> - **상품 A** (오전 100만원 + 오후 100만원): 시간대별로 계산 후 합산  
    >   `log1p(1_000_000) + log1p(1_000_000)` ≈ **27.6점**
> - **상품 B** (하루 200만원 한 번에):  
    >   `log1p(2_000_000)` ≈ **14.5점**
>
> 판매액이 같은데 A가 B보다 더 높은 점수를 받는다.

이렇게 시간 단위로 나눠서 계산한 값을 단순 합산하면, 비선형 함수(log1p)의 특성 때문에 결과가 왜곡된다.

정확한 계산은 원본 카운트를 전부 합산한 뒤, 한 번만 log1p를 적용하는 방식이어야 한다.  
![](https://velog.velcdn.com/images/jsj1215/post/42801296-6a92-45a0-bde0-23bc5f49ad74/image.png)

그래서 ZUNIONSTORE 기반으로 시간대별 ZSET을 합치는 방식은 포기했다.  
대신 **DB에서 하루치 데이터를 GROUP BY로 집계한 뒤, 애플리케이션에서 한 번만 log1p를 적용하는 방식**으로 바꿨다.

성능보다 계산의 일관성을 우선한 선택이었다.

---

### 4. '좋아요 취소', 어디까지 쫓아갈 것인가

> *처음 고민: 과거에 누른 좋아요를 오늘 취소하면 그 시간대로 돌아가서 마이너스 처리해야 하는가?*  
> *결론: 랭킹은 완전한 장부처럼 다룰 필요는 없었다.*

완전한 정합성을 유지하려면 과거 시간 버킷을 찾아서 마이너스 처리하고, 이후 점수를 전부 다시 계산해야 한다. 구현 복잡도와 리소스 비용이 크게 올라간다.

반면 현재 시점에 단순 차감하면, 오늘 좋아요가 없는 상품의 카운터가 음수가 될 수 있다.

> *"랭킹은 지금 사람들의 관심 흐름을 보여주는 지표에 가깝고, 모든 과거 상태를 완벽하게 복원하는 시스템은 아니다."*

그래서 현재 버킷에 음수 취소를 반영하되, 0 아래로 내려가지 않도록 막았다.

```sql
ON DUPLICATE KEY UPDATE
  like_count = GREATEST(like_count + :ld, 0)
-- view_count, order_count, order_amount에도 동일 가드 적용
```

추가로 예상하지 못했던 부분도 있었다. Kafka Batch Listener가 짧은 시간 내 좋아요 → 취소를 +1과 -1이 배치 내에서 만나 서로 지워진다
+1과 -1이 배치 내에서 만나 0이 되면서, 일부 케이스에서는 음수로 내려가는 상황 자체가 DB까지 전달되지 않기도 했다.

### 5. 숨김 상품 필터링 — 누가 책임지는가

> *처음 설계: 집계 서버(Streamer)가 상품 상태를 확인하고 살아있는 상품만 ZSET에 올린다.*  
> *문제: Streamer가 상품 도메인 지식에 강하게 결합된다.*

관리자가 상품을 숨김 처리하면 랭킹에서도 빠져야 한다. 처음에는 집계 과정에서 상품 DB를 JOIN해 살아있는 상품만 Redis에 올리는 방식을 생각했다.

그런데 이 방식은 Streamer가 상품 테이블 스키마에 의존하게 만든다. 상품 노출 기준이 바뀌면 집계 쿼리도 함께 수정해야 한다.

그래서 필터링 책임을 API 레이어로 옮겼다.  
![](https://velog.velcdn.com/images/jsj1215/post/c8933eb8-3b49-455a-a5a2-6fb74467b112/image.png)

Streamer는 점수 집계만 담당하고, 숨김 처리나 삭제 여부 같은 비즈니스 로직은 API가 마지막 단계에서 걸러내도록 했다.

이 방식에서는 응답이 항상 20개가 아닐 수도 있다. 하지만 대신 서비스 간 책임이 명확해졌고, 집계 로직도 훨씬 단순하게 유지할 수 있었다.

### 6. 부분 실패 시 Redis는 어떻게 복구하는가

DB에 쓰기는 성공하고, Redis에 쓰는 과정에서 실패하면 어떻게 될까?  
![](https://velog.velcdn.com/images/jsj1215/post/91914a67-2aab-4376-86a7-3c04067cb0a2/image.png)

Kafka가 재전달되더라도 멱등 키 때문에 DB 쓰기는 스킵된다. 반면 Redis는 동일한 방식으로 자동 보정되지 않기 때문에, DB에는 100점이 있는데 Redis에는 99점인 불일치 상태가 생길 수 있다.

해결 방법은 **멱등 적용 범위를 분리**하는 것이었다.

```java
// DB 쓰기: 멱등 필터 적용 (중복 방지)
List<ConsumerRecord<...>> fresh = filterAlreadyHandled(records);
if (!fresh.isEmpty()) {
    persistDeltas(batchAggregator.aggregateCatalog(fresh));
}

// Redis 쓰기: 멱등 필터와 무관하게 — DB 스냅샷 기준으로 덮어쓰기
publishScores(recalculateFromSnapshot(productIdsToSync));
//                                    ↑ 재전달 상황에서도 DB 기준으로 다시 동기화 시도
```

DB는 멱등 필터로 중복 처리를 막고, Redis는 DB 스냅샷을 기준으로 다시 반영하는 방식으로 역할을 나눴다.

이렇게 하면 재전달 상황에서도 Redis가 DB 기준으로 다시 맞춰지게 된다. 별도의 수동 복구 없이도 일관성을 회복할 수 있는 구조였다.

이것도 "DB가 원장"이라는 원칙의 연장선이다. Redis 값이 어긋나더라도, DB를 기준으로 다시 계산해서 맞출 수 있도록 설계했다.

### 7. 최종 아키텍처

위의 고민이 쌓인 결과 아래 구조의 아키텍처로 정리됐다.  
![](https://velog.velcdn.com/images/jsj1215/post/fe94959f-4870-448c-9fc2-5532e3cc6c8e/image.png)

핵심은 DB를 원장으로 두고, Redis를 그 결과를 반영하는 저장소로 사용하는 구조다.

이 역할이 분리되어 있기 때문에:
- Redis 데이터가 유실되더라도 DB를 기준으로 다시 계산해 복구할 수 있고
- Kafka 재전달 상황에서도 DB가 멱등성의 기준이 된다
- 점수 계산 방식이 바뀌더라도 DB를 기준으로 재계산이 가능하다

위에서 내린 결정들은 테스트로 검증하기 전까지는 확신하기 어려운 상태였다.

그리고 코드만으로는 드러나지 않던 버그 2건을 테스트에서 먼저 발견할 수 있었다.

**버그 1. 보이지 않았던 `@Transactional` 누락**

`ProductMetricsHourlyRepositoryImpl` 내부의 UPSERT 메서드에 `@Transactional`이 누락되어 있었다. 이미 상위 레이어인 `RankingAggregationService`에서 트랜잭션이 감싸지고 있어서 겉으로는 정상 동작하는 것처럼 보였다.

하지만 이 상태로 배포된 뒤 다른 서비스에서 해당 Repository를 직접 호출하게 된다면, 런타임에서 `TransactionRequiredException`이 발생할 수 있는 상태였다. 코드만으로는 쉽게 드러나지 않는 문제였는데, 통합 테스트를 통해 확인할 수 있었다.

---

**버그 2. 인증 경로 누락**

`RankingV1ApiE2ETest` 6케이스가 처음 실행되었을 때 전부 **401 UNAUTHORIZED**로 실패했다. `WebMvcConfig.excludePathPatterns`에 `/api/v1/rankings`가 빠져 있어 `MemberAuthInterceptor`가 인증 헤더를 요구하고 있었던 것이다.

이 문제는 단위 테스트에서는 드러나지 않고, 실제 HTTP 요청 흐름을 타는 E2E 테스트에서만 확인할 수 있었다. 인증, 라우팅 같은 계약 수준의 문제는 E2E 레이어에서 검증이 필요하다는 걸 이번 테스트를 통해 느꼈다.

### k6 — 읽기와 쓰기의 차이

테스트가 "설계대로 동작하는가"를 검증했다면, k6는 "실제 트래픽에서 얼마나 버틸 수 있는가"를 확인하는 과정이었다.

4개 시나리오, 총 333,525 req를 쏘아봤다.

| 시나리오 | p50 | p95 | 에러율 | 임계값 |
|---|---|---|---|---|
| A-1. 랭킹 Top-N 읽기 | 2.2ms | **4.8ms** | 0.00% | PASS |
| A-2. 상품 상세 + dailyRank | 10.3ms | **21.3ms** | 0.00% | PASS |
| A-3. 쓰기 파이프라인 (1,000 VU) | 2,008ms | **3,839ms** | 0.00% | FAIL (임계 80ms) |
| A-4. Hot Product 경합 (70% 집중) | 32.3ms | **585.5ms** | 0.01% | FAIL (임계 200ms) |

**읽기(p95 4.8ms)와 쓰기(p95 3,839ms) — 약 800배 차이.**
(단순 수치로 보면 약 800배 차이가 나지만,
Redis 단일 조회와 Kafka + DB를 거치는 쓰기 파이프라인 전체를 비교한 값이라
같은 성격의 성능 비교로 보기는 어렵다.)

**읽기는 충분히 빠르다.** 랭킹 조회(A-1) p95 4.8ms는 Redis ZREVRANGE가 대부분의 조회를 처리하고 있기 때문이다. 상품 상세에 추가한 `ZREVRANK` 오버헤드(A-2)는 p95 기준 약 5~10ms 수준으로, 전체 응답에 큰 영향을 주지 않았다.

**쓰기는 병목이 있다.** A-3에서 p95가 3,839ms로 임계값(80ms)을 크게 초과했다. 에러율은 0%였지만 120,025건(74%)의 이터레이션이 드롭된 것을 보면, 설정된 부하를 안정적으로 소화하지 못하고 있는 상태였다. MySQL 커넥션 풀 대기나 Kafka `send()` 지연이 원인일 가능성이 있다.

**Hot Product 경합도 확인됐다.** A-4에서 특정 row에 70% 트래픽이 몰리자 p95가 585ms로 상승했다. Native UPSERT는 DB 레벨 락을 사용하기 때문에, 극단적인 집중 상황에서는 대기 시간이 증가할 수밖에 없다. 집계 정확도는 유지됐다(view 드리프트 +1.05%).

초기에 Redis ZSET을 선택한 이유가 "읽기 트래픽이 압도적으로 많을 것"이라는 가정이었는데, k6 결과를 통해 이 구조가 실제로도 타당하다는 것을 확인할 수 있었다.

## 마치며

"점수에 1 더하면 끝 아닌 건가?"라는 생각으로 시작했지만, 실제로는 고민해야 할 문제가 훨씬 많았다.

처음에는 단순한 숫자 증감이라고 생각했는데, 랭킹은 쇼핑몰 홈 화면에서 가장 먼저 보이는 영역이었다. 유저 입장에서는 "지금 제일 잘 팔리는 게 뭔지"를 판단하는 기준이고, 판매자 입장에서는 노출 여부가 매출에 직접적인 영향을 준다.

그래서 점수 계산이 틀리거나 캐시가 꼬이면 단순히 화면이 이상해지는 문제가 아니라, 실제 비즈니스에도 영향을 줄 수 있다는 걸 뒤늦게 깨달았다.

이걸 인식하고 나니 설계 선택지들이 다르게 보이기 시작했다. `ZINCRBY`가 구현은 간단하더라도 멱등성이 보장되지 않으면 사용할 수 없다는 판단도 자연스럽게 이어졌고, 테스트 역시 번거롭더라도 반드시 필요한 과정이라는 걸 알게 됐다.

실제 서비스에서는 회사의 비즈니스 목표나 팀의 정책에 따라 전혀 다른 선택을 할 수도 있을 것 같다. 이번 구현은 그중 하나의 방향을 직접 경험해본 과정이었다.

"어디까지 정확해야 할까?"라는 질문도 계속 고민하게 됐다.

좋아요 취소로 인해 발생하는 작은 오차는 감수할 수 있지만, 집계 자체가 누락되는 상황은 막아야 했다. 숨김 상품 때문에 결과가 19개가 되는 건 괜찮지만, 순위 자체가 틀리는 건 허용할 수 없었다.

이처럼 기능마다 허용할 수 있는 오차의 종류와 범위가 다르고, 그 기준을 정하는 과정이 생각보다 어렵다는 걸 느꼈다. 직접 구현해보지 않았다면 몰랐을 부분이었다.

요구사항에 따라 설계가 달라지고, 그 설계는 결국 비즈니스에 영향을 준다.

이번 경험을 통해, 내가 만드는 기능 하나하나가 생각보다 훨씬 더 중요한 의미를 가진다는 걸 느끼게 됐다.
