# 실시간 인기 상품 랭킹 구축기: 단순한 ZSET이 실무에서 복잡해지는 과정

## 들어가며

> "우리가 흔히 보는 쇼핑몰 인기 랭킹, 도대체 어떻게 만들어질까?"

이번 과제의 목표는 유저 행동 데이터(조회, 좋아요, 주문)를 수집하는 기존 Kafka 흐름에 Redis Sorted Set(ZSET)을 엮어 하나의 실시간 실무 랭킹 시스템을 구축하는 것이었다.

처음엔 대기열 구현할 때 한 번 써봤던 기능이라 순위를 정렬하는 건 편하니까 금방 끝날 것 같았다.
그저 점수에 1씩 더하면 완성될 줄 알았던 인기 랭킹 시스템은, 막상 코드를 짜고 아키텍처를 고민해 보니 분산 환경의 멱등성 문제, 쓰기 경합 패턴, 심지어 정규화 함수의 수학적인 함정들까지 사방에서 튀어나오기 시작했다.

결국 시스템을 두 번이나 갈아엎으면서 뼈저리게 배운 **가장 핵심적인 기술적 의사결정과 트레이드오프 5가지**를 깊이 있게 기록해 둔다.

## 랭킹 시스템, 뭘 알아야 만들 수 있을까?

본격적인 삽질기에 들어가기 전에, 랭킹 시스템을 설계할 때 반드시 머릿속에 깔아두어야 할 기본 개념들을 먼저 짚고 넘어간다. 이 배경이 없으면 뒤에 나오는 의사결정들이 왜 그렇게까지 복잡해졌는지 와닿지 않을 수 있다.

### 랭킹 시스템의 특성

쇼핑몰에서 랭킹 정보는 생각보다 훨씬 많이 요청된다. 홈 화면의 "인기 상품", "오늘의 Top 10", 카테고리별 인기순 정렬 등 — 유저에게 가장 먼저 보이는 지면이 대부분 랭킹 기반이다. 개별 상품 상세에서도 "현재 N위" 같은 순위 표기를 제공해야 한다. 즉, **읽기 트래픽이 압도적으로 많다**.

그리고 랭킹은 시간에 따라 **주기적으로 갱신**되어야 한다. 일간, 주간, 월간 단위로 새롭게 리셋되고 다시 쌓이는 구조가 필요하다. 그런데 갱신 주기가 있다는 건 곧 **콜드 스타트 문제**가 뒤따른다는 의미이기도 하다 — 자정이 되면 모든 상품의 점수가 0에서 다시 출발해야 하니까.

### 왜 RDB만으로는 안 되는가?

가장 단순한 접근은 `GROUP BY + ORDER BY`로 DB에서 직접 순위를 뽑는 것이다. 소규모 초기 서비스라면 이것으로 충분할 수 있다. 하지만 데이터가 쌓일수록 집계 쿼리는 점점 무거워지고, 앞서 말했듯 랭킹 조회 빈도는 매우 높다. 결국 DB에 과부하가 쏟아지는 건 시간문제다.

### Redis ZSET이 답인 이유

Redis의 Sorted Set(ZSET)은 `(member, score)` 쌍을 **score 기준으로 항상 정렬된 상태**로 유지한다. 삽입과 수정은 `O(log N)`, Top-N 조회는 `O(N)`으로 끝난다. 정렬 기능이 자료구조에 내장되어 있으니 별도의 인덱스 설정 같은 건 필요 없고, 점수가 바뀔 때마다 실시간으로 순위에 반영된다.

| 방법 | 장점 | 단점 | 적합도 |
|------|------|------|--------|
| DB `ORDER BY` | 정합성 높음 | 느림, DB 부하 큼 | 초기/소규모 |
| 캐시(Map) + 정렬 | 구현 간단 | 매 요청마다 정렬 필요 | 중간 |
| **Redis ZSET** | **빠른 정렬 내장, 다양한 조회** | 메모리 사용 증가 | **대규모 트래픽** |

### Key 설계 — 시간의 양자화

랭킹에서 Key 설계가 중요한 이유는, **언제부터 언제까지의 집계인지**가 명확해야 랭킹에 의미가 생기기 때문이다. 만약 점수를 단순히 누적만 하면 오래전 잔뜩 팔렸던 상품이 영원히 상위에 박혀있게 되고, 신상품은 기회조차 얻지 못한다(Long Tail 현상). 그래서 시간을 일정 단위(시간, 일, 주 등)로 잘라서 관리하는 **시간의 양자화**가 필수다.

```
ranking:all:20260409   // 4월 9일 랭킹
ranking:all:20260410   // 4월 10일 랭킹
```

이렇게 날짜별로 키를 분리하면, 각 키에 적절한 TTL을 설정해 메모리를 관리할 수 있고, 랭킹 리셋이나 과거 조회도 자연스럽게 해결된다.

### 가중치 합산 — 단순 카운팅을 넘어서

조회 1회와 주문 1건은 같은 무게가 아니다. 조회는 가볍지만 숫자가 압도적으로 많고, 주문은 드물지만 구매 결정이라는 강한 시그널이다. 단순히 모든 행동을 1점으로 더해버리면 조회 수가 전체 점수를 지배해버린다.

```
Score = W(view) × Count(view) + W(like) × Count(like) + W(order) × Count(order)

// 예시 가중치 (합계 = 1.0)
view = 0.1 / like = 0.2 / order = 0.7
```

이렇게 서비스 전략에 맞는 가중치를 곱해 합산하면, 주문이라는 핵심 지표가 순위에 의미 있게 반영된다.

### 콜드 스타트 문제

일간 랭킹에서 자정이 넘는 순간 새로운 키가 만들어지는데, 이 시점에는 아무 점수도 쌓이지 않아 랭킹이 텅 비어버린다. 어제까지 인기 폭발이었던 상품도, 자정 이후에는 그냥 0점이다. 사용자 입장에서 새벽에 접속했더니 "인기 상품 없음"이라고 뜨면 그건 버그처럼 보인다.

해결책은 **Score Carry-Over** — 새 키를 만들 때 전날 점수의 아주 작은 비율(예: 1%)을 미리 복사해 두는 것이다. 이렇게 하면 자정 직후에도 어제 인기 있었던 상품들이 초기 순위를 형성하면서, 오늘 실제 이벤트가 들어오면 금방 역전될 수 있는 수준의 낮은 초기값이 된다.

### 실전에선 어떻게 쓰일까? — 국내 이커머스 3사 랭킹 분석

이론을 머릿속에 넣었으니, 실제로 우리가 매일 접하는 쇼핑 앱들이 랭킹을 어떻게 구현하고 있는지 살펴보자. 직접 페이지를 뜯어보면 "아, 아까 배운 그 개념이 여기 쓰인 거구나" 하는 순간이 온다.

**🔹 무신사 — 다차원 필터링의 정석**

무신사의 랭킹 페이지(`/main/musinsa/ranking`)는 URL 쿼리 파라미터만 봐도 랭킹 시스템의 복잡도가 드러난다.

```
?gf=F&storeCode=musinsa&sectionId=200&categoryCode=000&ageBand=AGE_BAND_ALL
```

- **성별 필터(`gf`)**: `M`(남성), `F`(여성), `A`(전체). 같은 상품이라도 성별에 따라 완전히 다른 랭킹이 산출된다.
- **스토어 분리(`storeCode`)**: 무신사/뷰티/부티크/킥스/아울렛/스포츠 등 스토어별로 독립된 랭킹을 운영한다. 각 스토어 설정에 랭킹 전용 API 엔드포인트(`/api2/hm/v5/pans/ranking?storeCode=...`)가 별도로 존재하는 것을 보면, 스토어마다 ZSET 키 체계가 분리되어 있을 것으로 추측된다.
- **섹션/카테고리 필터(`sectionId`, `categoryCode`)**: 전체 카테고리(`000`)부터 세부 카테고리까지 계층적으로 랭킹을 조회할 수 있다.
- **연령대 필터(`ageBand`)**: `AGE_BAND_ALL`, 개별 연령대 등. 즉 **"20대 여성이 가장 많이 산 아우터"** 같은 세그먼트별 랭킹이 가능하다.

기술적으로 흥미로운 점은, 이 조합의 수가 `성별 × 스토어 × 카테고리 × 연령대`로 폭발적이라는 것이다. 모든 조합에 대해 사전에 ZSET을 만들어두는 것은 현실적이지 않으므로, 요청 시점에 필터링하거나 주요 조합만 사전 계산하는 전략이 필요해진다.

**🔹 29CM — 시간 윈도우 × 랭킹 기준의 매트릭스**

29CM의 베스트 상품 페이지(`/best-products`)는 쿼리 파라미터가 더욱 직관적이다.

```
?period=HOURLY&ranking=POPULARITY&gender=F&age=30
```

- **시간 윈도우(`period`)**: `HOURLY`(시간별), `DAILY`(일간), `WEEKLY`(주간). 앞서 설명한 **"시간의 양자화"** 를 정확하게 구현한 케이스다. 시간별 랭킹은 우리 과제의 Nice-To-Have 였는데, 29CM에서는 이미 기본 기능으로 제공하고 있다.
- **랭킹 기준(`ranking`)**: `POPULARITY`(인기순), `SALES`(판매순) 등. "인기"와 "판매"를 나눈다는 건, 내부적으로 **가중치 공식이 다른 여러 벌의 ZSET** 을 운영하거나 동일 데이터에 대해 서로 다른 score 함수를 적용한다는 의미다.
- **인구통계 필터(`gender`, `age`)**: 성별과 연령대(30대 등)를 조합해 타겟 세그먼트별 랭킹을 보여준다.

29CM의 `HOURLY` 옵션은 우리 과제에서 검토했던 "1시간 단위 버킷 → ZUNIONSTORE"의 현실 구현체라 할 수 있다. 시간별 키를 별도로 관리하되, 일간/주간은 이를 합산하는 구조일 가능성이 높다.

**🔹 네이버 쇼핑 — 상품이 아닌 "스토어" 랭킹**

네이버 플러스 스토어의 "스토어의 발견"(`/store_discovery`)은 앞의 두 서비스와 접근이 다르다. **상품 단위가 아니라 스토어(판매자) 단위의 랭킹**이다.

- **공간 카테고리별 Top 10**: 침실 / 욕실 / 거실 / 주방 등 생활 공간별로 스토어 Top 10을 보여준다.
- **랭킹 산정 기준**: 페이지 하단 고지에 따르면 "구매·관심 데이터를 기반으로 집계"되며, "특정 시점의 데이터 기준이며 실시간으로 변동될 수 있다"고 명시한다.
- **부가 정보**: 각 스토어에 "관심 64,927" 같은 관심 수치를 노출하고, 대표 리뷰 문구를 함께 보여준다. 단순 순위 숫자만이 아니라, "왜 이 스토어가 인기인지"를 사회적 증거로 보강하는 셈이다.
- **큐레이션 병행**: 순수 데이터 기반 랭킹 외에도 "오늘의 발견" 같은 에디터 큐레이션 섹션이 공존한다. 랭킹 시스템과 큐레이션이 함께 돌아가는 하이브리드 구조다.

**📊 3사 비교 요약**

| 구분 | 무신사 | 29CM | 네이버 쇼핑 |
|------|--------|------|-------------|
| **랭킹 대상** | 상품 | 상품 | 스토어(판매자) |
| **시간 윈도우** | 일간 (추정) | 시간/일간/주간 | 비공개 (실시간 변동 언급) |
| **필터 축** | 성별 × 스토어 × 카테고리 × 연령대 | 시간 × 기준 × 성별 × 연령대 | 공간 카테고리 |
| **랭킹 기준** | 단일 (인기) | 복수 (인기/판매) | 구매 + 관심 데이터 |
| **순위 변동 표시** | 순위 변동 화살표 | - | - |
| **부가 신뢰 요소** | 리뷰 수, 할인율 | 리뷰 수 | 관심 수, 대표 리뷰 |

이 세 서비스를 보면 한 가지가 분명해진다. "인기 랭킹"이라고 뭉뚱그려 부르지만, **실제로는 시간 윈도우 · 필터 축 · 점수 산정 기준 · 노출 전략이 모두 다른 독립된 시스템의 집합**이라는 것이다. 우리 과제에서 다루는 일간 단일 키 + 가중치 합산 구조는 이 세 서비스 중 가장 기본적인 뼈대에 해당하며, 이 위에 필터 · 세그먼트 · 시간 확장을 얹어가는 것이 실무의 여정이 된다.

이제 이 기본 개념들을 깔고, 실제 구현 과정에서 부딪혔던 핵심 의사결정 5가지를 하나씩 풀어본다.

## 1. ZINCRBY의 실시간성 vs ZADD의 복원력

첫 번째 고민은 랭킹 캐시에 점수를 반영하는 기본 설계부터 시작되었다. Kafka Consumer 가 받은 이벤트를 어떻게 Redis 에 넣을 것인가?

**[Option A] ZINCRBY — 이벤트마다 누적 점수 더하기**
- **장점:** 제일 구현이 쉽다. DB 조회가 전혀 없어서 시스템 부하가 없고 극강의 실시간성을 보장한다.
- **단점:** 만약 Redis 서버가 뻗어서 데이터가 날아가면 아예 복구할 길이 없다. 더욱이 Kafka 가 네트워크 지연 등으로 메시지를 두 번 전송(At-least-once)해 버리면 점수가 억울하게 뻥튀기될 수밖에 없는 치명적인 멱등성 문제가 존재했다.

**[Option B] DB 원장 업데이트 후 재계산 — ZADD 엎어치기**
- **장점:** RDBMS 에 `product_metrics`(집계 테이블)를 원장으로 두고 이벤트를 먼저 집계한 후, 그 통계값으로 새 점수를 계산해서 기존 ZSET의 값을 덮어써버린다(ZADD). 계산 공식이 바뀌든 서버가 날아가든 DB만 읽어오면 언제든 똑같이 복구할 수 있었다.
- **단점:** 이벤트가 들어올 때마다 매번 DB를 찌르고 Redis를 덮어써야 하니까 시스템 부하가 이벤트 수와 정비례하여 커진다.

**[트레이드오프와 결정]**
결과적으로 데이터 유실의 위험을 감수할 수 없어 **[Option B]의 안전성을 선택**했다. 하지만 매번 생기는 부하의 단점은 그대로 두지 않았다.
Kafka Consumer 의 옵션인 **`@KafkaListener(batch = true)`** 를 도입하여, 이벤트를 낱단위가 아니라 짧은 시간 동안 폴링 한 리스트(수백 건)로 통째로 가져오도록 했다. 메모리 안에서 같은 상품의 데이터를 미리 합산한(압축한) 뒤에 DB와 Redis 에 트랜잭션 한 번으로 넘겨버림으로써(N건 → 1회), 부하라는 단점을 극복하고 극강의 정합성을 얻어낼 수 있었다.

## 2. 결제 이벤트의 배신과 Native UPSERT 방어막

"어차피 Kafka 의 동일한 파티션에 들어가니까 여러 스레드가 동시에 경합을 벌일 일은 없겠지?"
라고 느긋하게 생각했는데, 이벤트를 밀어 넣는 Producer 쪽을 확인하고 등골이 서늘해졌다. 

- `catalog-events` (조회, 좋아요): 상품 ID(`productId`)를 기준으로 묶여 있어서 동시성 문제가 없다.
- `order-events` (결제): 장바구니 결제처럼 여러 상품이 함께 묶일 수 있어서 **주문 ID(`orderId`) 기반**으로 아무 파티션이나 무작위로 흩어지고 있었다!

**[트레이드오프 고민지점]**
이 말은 똑같은 아이폰 15를 A유저와 B유저가 동시에 결제하면, 서로 다른 스레드가 동시에 내 랭킹 시스템을 뚫고 들어와 DB의 같은 아이폰 레코드를 수정하려 든다는 뜻이다.
- **(A) 비관적 락(Pessimistic Lock)** 을 잡고 DB 를 수정하자니 전체 스트리머 파이프라인의 처리 속도(Throughput) 가 수직 낙하할 게 뻔했다.
- **(B) 이벤트 시스템 재설계** 를 통해 파티션을 상품 단위로 다 쪼개서 다시 쏘게 만들자니, 이번 프로젝트의 스코프를 완전히 넘어서는 대공사였다.

**[최종 타협]**
결국 Application 레벨의 제어나 인프라 구조 변경을 포기하고, **DB 레벨 네이티브 쿼리 성능에 기대는 방식**을 선택했다. `INSERT ... ON DUPLICATE KEY UPDATE` 네이티브 쿼리를 던져 데이터베이스 엔진 자체에서 원자성(Atomicity)을 보장하도록 만들었다. 코드가 JPA 엔티티 중심에서 조금 벗어나 투박해지는 단점(Trade-off)이 있었지만, 트래픽 병목의 원인을 완벽히 차단하는 가장 깔끔한 비즈니스 해결책이었다.

## 3. ZUNIONSTORE의 수학적 함정 — 로직의 편의성 vs 정규화 정확도

성능을 높이기 위해 구상했던 구조가 한 순간에 박살이 난 결정적 순간이다.
'일간 랭킹'을 만들려면 24시간 치 데이터의 합산이 필요하다. 

- **캐시 합치기 옵션:** 애초 나의 천재적인 최적화 구조는, DB에 무리가 가지 않게 1시간 단위 별로 점수를 `ranking:1h:날짜시간` ZSET으로 저장해 두고, 유저가 요청할 때 `ZUNIONSTORE` 커맨드를 써서 가장 가볍게 24개의 캐시를 합쳐서 반환하는 방식이었다. 가볍고 우아하고 빨랐다.

- **수학적 함정의 발견:** 문제는 랭킹 점수의 절대적인 격차를 줄이기 위해 사용한 **`log1p()` 로그함수 기반 정규화**였다.
시간별로 로그 함수를 씌워둔 캐시들을 나중에 단순히 더해버리면(ZUNIONSTORE), **`log1p(a) + log1p(b)` 가 되어버려 전혀 다른 값**이 도출된다. 정확한 점수는 원래의 카운트를 모두 다 더해둔 총합 전체를 한 번만 로그 씌운 **`log1p(a + b)`** 여야 했다.
시뮬레이션을 돌려보니, 1시간씩 꾸준하게 1번씩 팔린 상품이 한 시간에 20개 물량이 몰아서 터진 상품보다 두 배 이상 점수가 높게 찍히는 심각한 왜곡이 발생했다.

**[트레이드오프와 뼈아픈 재설계]**
성능 향상을 위한 Redis의 우아한 집합 병합 로직(`ZUNIONSTORE`)을 뼈물을 머금고 **전면 폐기**했다. 
수학적 맹점을 안은 채 서비스를 배포할 수는 없었기에, 성능을 조금 내어주고라도 **데이터는 오직 DB 에서 단 한 번만 그룹을 지어서 합치고**, 딱 한 번만 Java 로직에서 `log1p` 계산을 태워서 랭킹을 엎어치도록 아키텍처를 뒤집어버렸다. 어설픈 성능 최적화가 요구사항(정규화)과 만났을 때 시스템이 어떻게 망가지는지 제대로 배웠다.

## 4. '좋아요 취소'의 집착 버리기 — 완벽한 회계장부 vs 살아있는 트렌드

과거에 누른 좋아요를 오늘 취소하면, 이미 산정된 점수들을 어디까지 쫓아가서 지워내야 할까?

- **(A) 완벽한 정합성 루트:** 어제 저장된 좋아요 시간대의 버킷 데이터를 찾아서 마이너스를 친 뒤 랭킹을 끝까지 다시 산정한다. 이렇게 하면 정확하지만 시스템 리소스 낭비가 어마어마하다.
- **(B) 단순 차감 루트:** 오늘 시간에 단순히 마이너스를 때린다. 하지만 오늘 받은 좋아요가 없다면 카운터가 마이너스가 되어 시스템 에러를 일으킬 수 있다.

**[선택: 트렌드의 의미를 깨닫다]**
멘토링에서 이어진 피드백은 머리를 쾅 쳤다. "랭킹은 **지금 진짜 사람들의 관심이 쏠리는 트렌드**를 반영하는 전광판이지, 단 돈 1원의 오차도 내선 안 되는 장부가 아니다."

결국 시스템 전체를 얼어붙게 만드는 무거운 과거 추적 로직을 과감히 포기하고, (B) 루트 기반의 유연한 타협을 택했다.
로직 복잡도를 다 덜어내고, 무조건 현재 시간의 버킷에 음수 취소를 때리되 **`GREATEST(like_count - 1, 0)`** 이라는 단순한 방어 쿼리 하나만 쳐두어 음수로 내려가는 오류만 잘라냈다.

그런데 여기서 소름 돋게도 아까 1번에서 도입한 **Kafka Batch Listener** 가 예상치 못한 든든한 방패가 되어주었다. 한 유저가 충동적으로 밀리초 단위로 '좋아요 → 취소' 를 다발로 눌러대더라도, 데이터베이스에 가기도 전에 컨슈머가 모아둔 메모리 뭉치 안에서 `+1` 과 `-1` 이 서로 만나 `0` 으로 말끔하게 소멸해 버리는 것이다. 
골치 아플 뻔한 마이너스 무결성 오류가 아예 로직을 타기도 전에 사라졌다.

## 5. 도메인 경계 지키기 — 상품의 상태(삭제/숨김) 필터링은 어디서 할 것인가?

랭킹 통계가 예쁘게 ZSET 에 쌓여있어도, 만약 관리자가 그 상품에 심각한 문제가 생겨서 노출을 차단(숨김, 삭제)해 버린다면 랭킹 리스트에서도 실시간으로 안 보이게 만들어야 한다.

- **(A) 집계 시점 완전 필터링:** 랭킹 집계 통계 서버가 쿼리를 날릴 때 Main 상품 테이블과 `JOIN` (조인) 을 걸어버려, 아예 살아있는 상품만 가져와서 ZSET 캐시에 올리는 법. ZSET은 완벽하게 깨끗한 리스트만 갖게 된다.
- **(B) 조회 시점 캐시 우회:** ZSET 에는 일단 잡다한 게 다 올라가더라도, 랭킹을 조회하는 마지막 관문(API 레이어)에서 Top 20개 리스트를 가져온 뒤 응답을 주기 직방에 상품 노출 기준을 따져서 필터링하는 법.

**[트레이드오프의 결론: 느슨한 결합이 이겼다]**
(A) 방법대로 하려면 랭킹 파이프라인(`commerce-streamer`) 이 "무엇이 노출될 수 있는 상품인지(`deletedAt, displayYn`)" 의 핵심 비즈니스 도메인 지식을 강제로 욱여넣어야 한다. 이건 심각한 강한 결합(Tight Coupling) 이었다. 노출 기준이 바뀌면 관련 없는 랭킹 집계 쿼리를 싹 바꿔야 한다.

결과적으로 DB 에 한 번 더 조회를 해야 하는 오버헤드 부하를 감수하고라도 **(B) 의 캐시 우회 방식을 선택**했다. 
랭킹 ZSET 에서는 아무 생각 없이 무식하게 ID 리스트만 뽑아내 위로 던지고, 조립 단계(Facade)에서 `size=20` 정도의 작은 묶음에 대해 상품 Main DB를 찔러 살아남은 녀석만 통과시켰다.
응답 목록이 꽉 찬 20개가 아니라 필터링에 잘려나가 18개가 되더라도(Over-fetch 방어 포기), 서비스 간의 확실히 책임 경계를 긋고 복잡도를 제한하는 쪽에 가중치를 두어 더 나은 유지보수성을 얻어냈다.

## 마치며

이번 과제는 처음부터 끝까지 "이거 당연히 이렇게 캐시 찌르면 되겠지?" 라는 가벼운 판단을 전부 부수는 훈련의 시간이었다.

- 이벤트의 단건 처리 속도 대 배치를 더한 복구력을 시험한 1번
- 파티션 분산과 네이티브 원자성을 교환한 2번
- 인메모리 병합의 속도와 정규화 함수의 수학 모순이 맞붙은 3번
- 정확한 시스템 무결성과 트렌드의 비즈니스 의미가 부딪힌 4번
- 캐시 리스트 단일 호출과 결합도를 포기하지 않은 설계 원칙 5번

어느 하나 답이 뚝 떨어진 게 없었고, 득을 얻으려면 어떤 실을 확실히 내어줄지 밸런스를 측정하는 일이 전부였다. 
계속해서 **"비즈니스적으로 어디까지 오프셋(오차)을 허용하고 넘어갈 것인가?"** 를 질문하는 과정 그 자체가 엔지니어링임을 배운 귀중한 한 주였다.
