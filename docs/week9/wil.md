# WIL - 9주차 (이커머스 랭킹 시스템 및 Kafka 분산 파이프라인 결함 대응)

## 이번 주에 새로 배운 것
- Redis ZSET 기반으로 다중 지표(조회수, 좋아요, 결제 내역)를 단일 스코어로 합산해 인기순을 산출하는 이커머스 랭킹 구조의 핵심 원리를 경험했다.
- 점수 계산 시 수학적으로 발생하는 Σ log1p(x) ≠ log1p(Σx) 오류를 방지하기 위해, 통계를 정규화할 때는 이벤트 증분이 아닌 "최신 스냅샷(총합)"을 기준으로 계산해야 함을 배웠다.
- DB I/O 작업(UPSERT)은 트랜잭션 내부에 묶고, Redis ZADD와 같은 외부 네트워크 호출은 트랜잭션 바깥(commit 이후)에 배치하여 DB 커넥션 풀 고갈을 방지하는 실무적 트랜잭션 분리 패턴을 체득했다.
- Kafka 환경에서 부분 실패(Partial Failure)가 발생했을 때, 장애 난 지점을 스스로 복구(Self-Healing)하는 메커니즘을 설계하며 시스템의 내결함성(Fault Tolerance)에 대해 더 깊이 이해하게 되었다.

## 이런 고민이 있었어요
- Kafka 배치 컨슈머가 다수의 동일 상품 업데이트를 동시다발적으로 가져올 때 발생하는 트랜잭션 경합(Race Condition)을 어떻게 해결할 것인가? → 비관적 락이나 낙관적 락 대신, DB 레벨의 단일 원자 연산인 `Native UPSERT (ON DUPLICATE KEY UPDATE)`를 채택하여 성능과 안전함을 모두 확보했다.
- 좋아요가 취소되어 0 미만으로 내려가는 등 통계 정보 불변성이 깨지는 엣지 케이스 방어를 두고 고민했다. → DB UPSERT 로직 내 `GREATEST(like_count + delta, 0)` 구문을 추가해 데이터베이스 레벨에서 방벽을 치는 방법으로 해결했다.
- **가장 큰 기술적 고민:** 데이터 영속성과 Redis 동기화의 책임 분리. Kafka Consumer가 DB 수정까진 성공하고 Redis 업데이트에 실패했을 때(Redelivery), "이미 처리된 메시지"로 간주되어 영영 Redis 업데이트가 누락되는 사각지대를 어떻게 해결할 지 고민했다. → 최종적으로 멱등성을 띠는 Redis 갱신 로직을 DB 저장 여부와 무관하게 완전히 분리 실행하도록 재설계하여 아키텍처적 약점을 보완했다.

## 앞으로 실무에 써먹을 수 있을 것 같은 포인트
- **최종적 일관성(Eventual Consistency) 회복 전략:** 이벤트를 단순히 소비하는 것을 넘어, 예상치 못한 서버 다운 지연에서도 시스템을 정상으로 되돌리는 "자가 복구"를 위한 책임 분리 패턴은 어떤 분산 시스템을 구축할 때도 강력하게 써먹을 기법이다.
- 무거운 Redis Multi-ZSET 조합(ZUNIONSTORE)의 함정에 빠지지 않고, RDB에 기초 통계를 쌓은 뒤 스냅샷을 찍어 단일 ZSET으로 엎어치는 구조는 비용 효율적이며 확장에 유리하다.
- 이커머스 실무(무신사, 29CM 등 반영)처럼 실시간성 랭킹과 안정성 높은 큐레이션 하이브리드를 위해 "자정 직후 점수 이월(Carry-Over) 스케줄러"와 "백그라운드 스코어 계산 파이프라인"을 혼합한 설계 기법.

## 아쉬웠던 점 & 다음에 해보고 싶은 것
- 실무 쇼핑몰들처럼 성별/연령/카테고리별로 ZSET을 다차원 분리하여 개인화 랭킹을 설계 및 필터링해보는 기능까지는 이번 과제 시간 내에 확장해보지 못한 것이 아쉽다. 
- 추후에는 트래픽이 커졌을 때 ZSET 메모리를 실시간으로 추적하는 Spring Actuator 모니터링 기능 구축과, Redis 장애 시 DB 스냅샷을 직접 퍼올리는 Fallback 서킷 브레이커 전략을 꼭 도입해보고 싶다.
