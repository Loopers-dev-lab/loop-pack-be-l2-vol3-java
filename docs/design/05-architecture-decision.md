# 05. 아키텍처 결정 기록 (Architecture Decision Record)

---

## ADR-001: 순수 도메인 모델 분리 (Domain ↔ JpaEntity)

| 항목 | 내용 |
|------|------|
| **상태** | 채택 |
| **맥락** | JPA 의존성이 도메인 로직을 오염시키는 문제 |
| **결정** | `domain` 패키지의 Entity는 JPA 어노테이션 없는 순수 POJO |
| **근거** | 도메인 로직 단위 테스트 시 Spring Context 불필요<br/>인프라 변경(JPA→다른 ORM)에 도메인 영향 없음 |
| **결과** | `infrastructure`에서 `toDomain()` / `toEntity()` 매핑 필요 |

## ADR-002: Rich Domain Model 채택

| 항목 | 내용 |
|------|------|
| **상태** | 채택 |
| **맥락** | Anemic Domain Model의 문제 (도메인 객체가 데이터만 보유) |
| **결정** | Entity가 스스로 상태를 변경하는 메서드 보유 |
| **근거** | `Order.pay()` - 주문이 스스로 결제 상태로 전이<br/>`Option.decreaseStock()` - 옵션이 스스로 재고 차감<br/>도메인 로직 캡슐화로 응집도 향상 |
| **결과** | DomainService 최소화, Entity 메서드로 충분 |

## ADR-003: 계층별 책임 분리 (AppService + Facade)

| 항목 | 내용 |
|------|------|
| **상태** | 채택 |
| **맥락** | 복잡한 유스케이스에서 서비스 계층 비대화 |
| **결정** | AppService: 단일 도메인 트랜잭션 + Repository 호출<br/>Facade: 여러 AppService 조율 (Orchestration) |
| **근거** | 주문 생성 시: 재고 차감 + 장바구니 삭제 + 주문 저장<br/>각 책임을 분리하여 단일 책임 원칙 준수 |
| **결과** | Facade는 Repository 직접 호출 금지 |

## ADR-004: 물리적 FK 미적용

| 항목 | 내용 |
|------|------|
| **상태** | 채택 |
| **맥락** | Soft Delete 사용 시 참조 무결성 충돌 |
| **결정** | 모든 테이블 간 물리적 FK 제약조건 미적용 |
| **근거** | Brand Soft Delete 시 Product FK 검증 실패 방지<br/>삭제된 옵션도 장바구니/주문에서 참조 가능해야 함 |
| **결과** | 애플리케이션 레벨에서 무결성 검증 |

## ADR-005: Like Hard Delete

| 항목 | 내용 |
|------|------|
| **상태** | 채택 |
| **맥락** | 좋아요 토글 기능에서 Soft Delete 시 3가지 상태 관리 필요 |
| **결정** | Like 테이블에 Hard Delete 적용 |
| **근거** | 좋아요 이력 보존 비즈니스 가치 낮음<br/>토글 로직 단순화 (있으면 삭제, 없으면 생성) |
| **트레이드오프** | 이력 분석 불가 → 필요 시 별도 이벤트 로깅으로 대응 |

## ADR-006: OrderItem 스냅샷 전략

| 항목 | 내용 |
|------|------|
| **상태** | 채택 |
| **맥락** | 상품 정보 변경/삭제 후에도 주문 내역 조회 필요 |
| **결정** | OrderItem에 주문 시점의 상품명, 옵션명, 가격을 값으로 복사 저장 |
| **근거** | 원본 데이터 변경이 과거 주문에 영향 미치면 안 됨<br/>JOIN 없이 주문 내역 조회 가능 (성능)<br/>법적 거래 기록 보존 요건 충족 |
| **트레이드오프** | 데이터 중복 저장 → 주문 내역 데이터 크기 증가 (수용 가능) |
