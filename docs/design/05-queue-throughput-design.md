# 주문 대기열 처리량 설계 근거

## 1. 인프라 조건

| 항목 | 값 | 출처 |
|------|---|------|
| DB 커넥션 풀 (maximum-pool-size) | 50 | `modules/jpa/src/main/resources/jpa.yml` |
| HikariCP 디폴트 | 10 | HikariCP 공식 문서 |

- 커넥션 풀 사이즈는 DB 스펙, 서버 대수, 트래픽 패턴에 따라 팀이 결정한다.
- 프로젝트 초기 세팅은 40이었으나, 블랙프라이데이 대비 **50으로 상향 조정**했다.

## 2. 주문 1건 처리 시간 추정

### 2-1. 트랜잭션 내 DB 왕복 횟수 (OrderPlacementTxService.placeOrder)

상품 2개 주문 기준:

| 단계 | 쿼리 | 횟수 |
|------|------|------|
| 쿠폰 발급 내역 조회 | SELECT coupon_issues | 1회 |
| 쿠폰 템플릿 조회 | SELECT coupons | 1회 |
| 상품 목록 조회 | SELECT products (IN) | 1회 |
| 주문 저장 | INSERT orders | 1회 |
| 주문 아이템 저장 | INSERT order_items | 2회 |
| 상품 재고 차감 | UPDATE products (Optimistic Lock) | 2회 |
| 쿠폰 상태 변경 | UPDATE coupon_issues | 1회 |
| 트랜잭션 커밋 | COMMIT | 1회 |
| **합계** | | **~10회** |

### 2-2. DB 왕복 1회 소요 시간

| 환경 | 1회 왕복 | 비고 |
|------|---------|------|
| 로컬 (localhost) | 0.5~2ms | 네트워크 없음 |
| 같은 VPC 내 RDS | 1~5ms | 일반적인 AWS 환경 |
| Optimistic Lock 경합 시 | +10~50ms | @Retryable에 의한 재시도 포함 |

### 2-3. 종합 추정

```
쿼리 왕복: 10회 x 3ms = ~30ms (실서버 기준)
커밋 오버헤드:             ~10ms
JPA 영속성 컨텍스트 처리:   ~5ms
동시 접속 시 Lock 대기:     ~50~100ms
──────────────────────────
실서버 추정: 100~200ms
```

**200ms를 보수적 추정치로 채택한다.**

이 값은 실측 없는 추정이며, 운영 환경 배포 후 k6 등 부하 테스트 도구로 검증이 필요하다.

## 3. TPS 계산

```
이론적 최대 TPS = 커넥션 풀 / 처리 시간
               = 50 / 0.2
               = 250 TPS
```

### 안전 마진 적용

커넥션 풀 50개 전부를 주문에 사용할 수 없다. 동시에 처리되는 다른 요청들이 있기 때문이다:
- 주문 목록 조회 (GET /orders)
- 주문 취소 (DELETE /orders/{id})
- 상품 조회, 쿠폰 조회 등 기타 API

주문에 할당 가능한 비율을 **70%**로 가정한다.

```
실효 TPS = 250 x 0.7 = 175 TPS
```

## 4. 스케줄러 배치 크기

### Thundering Herd 완화

175명에게 1초에 한 번 토큰을 발급하면, 175명이 동시에 POST /orders를 호출한다.
이를 방지하기 위해 발급 간격을 분산한다.

```
스케줄러 주기: 100ms (1초를 10구간으로 분할)
1회 발급 인원: 175 / 10 ≈ 18명
```

### 토큰 TTL

```
토큰 유효 시간: 300초 (5분)
```

- 유저가 토큰 수신 후 상품 확인 → 결제까지 충분한 시간
- 너무 짧으면: 유저가 주문 전에 만료 → 불만
- 너무 길면: 미사용 토큰이 자리를 차지 → 뒤 유저 대기 시간 증가

## 6. Polling 부하 분석

### 6-1. Polling 1회당 Redis 명령 수

`GET /queue/position` 호출 시 (대기 중인 유저 기준):

| 단계 | Redis 명령 | 시간 복잡도 |
|------|-----------|-----------|
| 토큰 확인 | `GET queue:token:{userId}` | O(1) |
| 순번 조회 | `ZRANK queue:wait userId` | O(log N) |
| 대기 인원 | `ZCARD queue:wait` | O(1) |

**1회 Polling = Redis 3건**

### 6-2. Adaptive Polling 구간별 주기

모든 대기자가 동일 주기로 Polling하면 뒷순번 유저가 불필요한 요청을 반복한다.
서버가 `nextPollAfterSeconds`를 응답에 포함해 클라이언트의 Polling 주기를 제어한다.

| 순번 구간 | Polling 주기 | 이유 |
|----------|-------------|------|
| 1~100 | 2초 | 곧 입장, 빠른 피드백 필요 |
| 101~1,000 | 5초 | 수 분 대기, 빈번한 갱신 불필요 |
| 1,001~10,000 | 10초 | 수십 분 대기 |
| 10,001+ | 30초 | 1시간+ 대기, 순번 변동 체감 없음 |

### 6-3. 대기 인원별 Redis 부하 비교

**고정 주기 (2초)**

| 대기 인원 | 초당 Polling | Redis 명령/초 |
|----------|-------------|--------------|
| 100명 | 50 | 150 |
| 1,000명 | 500 | 1,500 |
| 10,000명 | 5,000 | 15,000 |
| 100,000명 | 50,000 | 150,000 |

**Adaptive Polling 적용 후 (100,000명 기준)**

```
100 / 2 + 900 / 5 + 9,000 / 10 + 90,000 / 30
= 50 + 180 + 900 + 3,000
= 4,130 req/s × 3 = ~12,400 Redis 명령/초
```

고정 주기 대비 **92% 부하 감소** (150,000 → 12,400).

### 6-4. Redis 처리 한계와 판단

싱글 스레드 Redis의 단순 명령 처리 능력은 초당 10만~30만 건이다.

- Adaptive Polling 적용 시 **10만 명에서도 12,400건/초** — 단일 인스턴스로 충분
- Adaptive Polling 없이 10만 명이면 150,000건/초로 한계 근접

현재 설계는 Adaptive Polling을 적용해 **대기자 10만 명 규모까지를 기준**으로 한다.

## 7. 토큰 보충 발급

### 7-1. 문제

토큰을 받고 주문하지 않는 유저(이탈)가 생기면 슬롯이 낭비된다.

```
이탈률 10% 가정:
175 TPS × 0.1 = 초당 17.5 슬롯 낭비
100,000명 처리: 571초 → 실제 635초+ (11% 지연)
```

### 7-2. 해결

스케줄러가 매 주기마다 활성 토큰 수를 확인하고, 배치 크기(18)에 모자란 만큼만 보충 발급한다.

```
활성 토큰 수 = Redis INCR 카운터 (queue:active-token-count)
부족분 = BATCH_SIZE - 활성 토큰 수
부족분 > 0일 때만 ZPOPMIN(부족분) → 토큰 발급
```

- 토큰 발급 시: 카운터 증가
- 주문 완료 시: 카운터 감소 (Interceptor afterCompletion)
- 토큰 TTL 만료 시: 카운터가 실제 토큰 수보다 클 수 있으나, 다음 주기에 자연 보정됨

## 8. 멀티 인스턴스 스케줄러 중복 방지

서버 2대 이상 배포 시 `@Scheduled`가 모든 인스턴스에서 실행되어 설계한 TPS를 초과한다.

ShedLock (Redis 기반)으로 스케줄러를 단일 인스턴스에서만 실행하도록 제어한다.

```java
@SchedulerLock(name = "queue-activate", lockAtMostFor = "PT1S", lockAtLeastFor = "PT0.09S")
```

- `lockAtMostFor = 1초`: 비정상 종료 시 락 자동 해제
- `lockAtLeastFor = 90ms`: 100ms 주기에서 같은 인스턴스가 연속 실행하는 것을 방지

## 9. 미검증 사항

- 200ms는 실측 없는 추정치다. 실서버에서 부하 테스트로 검증해야 한다.
- Optimistic Lock 재시도 빈도에 따라 실제 처리 시간은 더 길 수 있다.
- 안전 마진 70%도 가정이다. 실제 트래픽 비율(주문 vs 조회)에 따라 조정이 필요하다.
- 토큰 보충 발급의 활성 카운터는 근사치이다. TTL 만료 시 카운터 감소가 지연될 수 있어 실제보다 보수적으로 발급할 수 있다.
- ShedLock의 lockAtMostFor(1초)가 실제 처리 시간보다 짧으면 중복 실행 가능성이 있다. 현재 배치 18명 기준 처리 시간은 수 ms 이내로 충분하다.
