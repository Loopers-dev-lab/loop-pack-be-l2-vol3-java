# Step 3 Polling Test TODO (2026-04-03)

## 목적
- 실시간 순번 조회 API의 기능 정확성과 polling 부하 정책의 타당성을 함께 검증한다.
- polling 간격은 고정값이 아니라 `순번 구간 + 서버 수 + 서버별 주문 처리 가능 TPS`를 기준으로 계산하는 정책으로 본다.

## 개념 정리
- `rank`는 Redis Sorted Set의 0-based 위치다.
- 사용자에게 보여주는 `순번`은 보통 `rank + 1`이다.
- API/문서/테스트에서는 혼동을 줄이기 위해 `rank`와 `displayWaitingOrder`를 구분한다.

## 기능 테스트 TODO

### 1. 순번 계산
- 대기열 미진입 사용자가 조회하면 적절한 실패 응답을 반환한다.
- 첫 번째 대기 사용자는 `rank=0`, 표시 순번은 `1`로 계산된다.
- 재진입으로 timestamp가 갱신된 사용자는 뒤 순번으로 밀린다.
- claim 상태인 사용자는 polling 응답에서 대기 중인지 입장 처리 중인지 정책대로 일관되게 표현된다.
- token 발급 완료 사용자는 대기 순번 대신 입장 가능 상태로 전이된다.

### 2. 예상 대기 시간 계산
- `estimatedWaitSeconds`가 `현재 순번 / 시스템 처리량` 기준으로 계산된다.
- 서버 수가 증가하면 동일 순번에서 예상 대기 시간이 감소한다.
- 서버별 주문 TPS가 감소하면 동일 순번에서 예상 대기 시간이 증가한다.
- active admission cap이 꽉 찬 경우 예상 대기 시간 정책이 왜곡되지 않는지 확인한다.

### 3. polling 권장 간격 계산
- 낮은 순번 구간일수록 더 짧은 polling 간격을 제안한다.
- 높은 순번 구간일수록 더 긴 polling 간격을 제안한다.
- 서버 수와 서버별 TPS가 커지면 같은 순번에서도 polling 간격이 짧아질 수 있는지 확인한다.
- polling 간격에 최소/최대 상한이 있다면 그 경계를 검증한다.
- 경계값(예: 구간 전환 직전/직후 순번)에서 interval 계산이 튀지 않는지 확인한다.

### 4. Step 2 상태와 연동
- queue only 상태 사용자는 순번/예상 대기 시간/권장 polling을 반환한다.
- claim 상태 사용자는 중복 발급 없이 일관된 상태 응답을 받는다.
- token 상태 사용자는 더 이상 polling 대상이 아니라는 응답을 받는다.
- 주문 완료 후 token 삭제/queue 정리 이후 polling 응답이 대기 사용자로 돌아가지 않는지 확인한다.
