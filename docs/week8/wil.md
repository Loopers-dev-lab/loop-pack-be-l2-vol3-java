# WIL - 8주차 (Redis 기반 대기열 시스템)

## 이번 주에 새로 배운 것
- 트래픽이 폭증할 때 단순히 거부(Rate Limiting)하는 것과 기다리게(Queuing) 하는 것의 차이를 이해하게 됐다. Rate Limiting은 시스템은 보호하지만 유저를 이탈시키고, 대기열은 시스템도 보호하면서 유저도 붙잡아둘 수 있다는 점이 인상적이었다.
- Back-pressure라는 개념을 처음 제대로 이해했다. 하류 시스템(DB, PG)이 감당할 수 있는 속도만큼만 상류(유저 요청)를 흘려보내는 것이고, 대기열이 바로 이 Back-pressure를 구현하는 대표적인 방법이라는 걸 배웠다.
- Redis Sorted Set(ZADD NX, ZRANK, ZPOPMIN)을 활용한 대기열 구현을 직접 해보면서, 순서 보장 + 중복 방지 + 원자적 연산이 동시에 가능하다는 걸 체감했다.
- `@Scheduled`의 fixedRate와 fixedDelay의 차이, 단일 스레드 문제, 멀티 인스턴스 환경에서의 분산 락 필요성까지 스케줄러에 대해 깊이 있게 학습했다.
- Interceptor를 활용하면 기존 주문 도메인 코드를 한 줄도 건드리지 않고 대기열 검증을 끼워 넣을 수 있다는 점이 좋았다.

## 이런 고민이 있었어요
- 대기열 설계 방식을 고를 때, "은행 창구식(빈자리 채우기)"과 "놀이공원식(유량 제어)" 중 어떤 걸 선택할지 고민이 있었다. 은행 창구식은 활성 유저 수를 정확히 추적해야 해서 복잡하고, 놀이공원식은 주기적으로 일정 인원만 들여보내는 방식이라 구현이 단순하면서도 실용적이었다. 결국 놀이공원식 + TTL 조합을 선택했다.
- 스케줄러 배치 크기를 어떻게 산정할지가 가장 어려웠다. DB 커넥션 풀 50개에서 안전 마진 70%를 적용해 TPS를 도출하고, 거기서 BATCH_SIZE=18 / INTERVAL=100ms 조합을 결정하는 과정이 단순한 감이 아니라 수치 기반의 판단이어서 의미 있었다.
- Feature Flag를 어디에 둘지(yml vs Redis vs DB) 고민했다. yml은 재배포가 필요하고, Redis는 영속성이 불안하고, DB는 조회 비용이 있지만 운영 중 즉시 변경 가능하다는 점에서 DB를 선택했다.
- 순번 응답에 전체 대기 인원을 포함할지 말지도 고민이었다. "앞에 512명 있습니다"는 괜찮은데 "전체 10,000명 중 512번째"는 오히려 이탈을 유발할 수 있다는 UX 관점의 판단이 기술적 결정만큼이나 중요하다는 걸 느꼈다.

## 앞으로 실무에 써먹을 수 있을 것 같은 포인트
- Redis Sorted Set 기반 대기열 패턴은 범용적으로 사용할 수 있을 것 같다. 선착순 이벤트, 예약 시스템 등 순서가 중요한 곳이면 어디든 적용 가능하다.
- Interceptor로 횡단 관심사를 처리하는 패턴. 토큰 검증처럼 기존 비즈니스 로직을 건드리지 않고 전처리/후처리를 끼워 넣는 방식은 Feature Flag 체크, 인증/인가 등에도 활용할 수 있다.
- 처리량 산정 공식(DB 커넥션 풀 기반 TPS 도출 -> 배치 크기 결정)은 실무에서 스케줄러나 배치 시스템을 설계할 때 바로 써먹을 수 있는 프레임워크다.
- k6 부하 테스트로 이론값과 실측값을 비교 검증하는 과정. 이론 TPS 180 vs 실측 p50=966ms가 근사하다는 것을 데이터로 증명하는 습관은 운영 환경에서도 중요하다.
- Graceful Degradation 전략 — Redis가 죽었을 때 대기열을 우회할 수 있도록 Feature Flag로 제어하는 구조는 장애 대응의 기본이 된다.

## 아쉬웠던 점 & 다음에 해보고 싶은 것
- BATCH_SIZE=9, 36에 대한 비교 테스트를 추가로 돌려보지 못한 게 아쉽다. 18이 최적이라는 주장을 더 강하게 뒷받침하려면 다른 값과의 비교 데이터가 있으면 좋겠다.
- k6 테스트에서 BCrypt 인증이 병목으로 나타났는데, 세션/JWT 기반 인증으로 전환했을 때 실제로 얼마나 개선되는지 확인해보고 싶다.
- Polling 방식의 순번 조회를 SSE(Server-Sent Events)로 바꿔보는 것도 해보고 싶다. 순번이 가까워지면 실시간으로 push 해주는 방식이 UX적으로 더 좋을 것 같다.
- 1000명 이상 규모의 대기열에서 스케줄러 소화 시간이 선형적으로 증가하는지 대규모 테스트도 돌려보면 좋겠다.
