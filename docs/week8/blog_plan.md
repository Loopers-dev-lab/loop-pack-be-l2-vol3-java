# 한 명도 놓치지 않을거에요. Redis Sorted set을 사용한 대기열 시스템으로 우리 서비스도 지키고 고객 만족도 잡고

## TL;DR

트래픽 폭증 시 Rate Limiting은 유저를 거부하지만, 대기열은 순서대로 보관하여 한 명도 놓치지 않는다.
Redis Sorted Set 기반의 놀이공원식(스케줄러 + TTL) 대기열을 설계하고, 100ms마다 18명씩 입장 토큰을 발급하는 구조로 175 TPS 안전 마진을 확보했다.
fixedRate 대신 fixedDelay를 선택하여 Redis 지연 시 자연스러운 back-pressure를 만들고, 동적 polling 주기(1/3/5초)로 순번 조회 부하를 5배 줄였다.
k6 부하 테스트 결과 대기열 진입 후 토큰 수령률 100%, 주문 성공률 100%를 달성했고, 실제 병목은 대기열이 아닌 BCrypt 인증에 있음을 확인했다.
설계부터 구현, 코드 리뷰, 부하 테스트까지 — **"왜 그렇게 판단했는가"**를 중심으로 정리한 기록이다.

## 들어가며
블랙 프라이데이 행사를 앞두고 있다고 가정해보자. 평소 초당 100건이던 주문 요청이 행사 시작과 동시에 **초당 10,000건**으로 폭증한다.

```
[10,000명 동시 접속]
     └── POST /orders
           ├── 재고 확인 & 차감
           ├── 결제 처리
           └── 주문 저장
           → DB 커넥션 풀 고갈
           → 응답 지연 → 타임아웃
           → 전체 시스템 장애
```

DB 커넥션 풀이 고갈되고, 스레드가 전부 대기 상태에 빠진다. 응답은 끝없이 느려지고, 유저는 "왜 안 되지?" 하며 새로고침을 누른다. 그 새로고침이 또 다른 요청이 되어 상황은 더 악화된다. 결국 주문뿐 아니라 상품 조회, 장바구니까지 전체 서비스가 멈춘다.

서버를 10배로 늘리면 해결될까? 서버는 늘릴 수 있지만, **DB와 PG(결제 대행사)는 스케일이 제한적**이다. 트래픽의 피크가 극단적으로 짧고 높은 경우(행사 시작 직후 10초), 오토스케일링이 반응하기 전에 이미 터져버린다.

그렇다면 이 폭증하는 트래픽으로부터 우리 서비스를 어떻게 지켜야 할까?

## 1. 문제 정의 — 트래픽 폭증으로부터 서비스를 지키는 방법들

현업에서 트래픽이 몰릴 때 시스템을 보호하기 위해 흔히 사용하는 방법들이 있다.

**Rate Limiting** — IP나 유저 단위로 초당 요청 수를 제한한다. 한도를 초과하면 429(Too Many Requests)를 반환한다. 거의 모든 서비스에 기본으로 깔려 있는 방어 장치다.

**비정상 요청 차단** — 봇이나 매크로를 탐지해 차단하고, 상품 페이지를 거치지 않은 직접 API 호출처럼 정상 플로우가 아닌 요청을 필터링한다.

**캐싱** — 상품 정보, 재고 여부 같은 읽기 요청을 Redis나 로컬 캐시로 흡수한다. DB까지 가지 않아도 되니 부하가 크게 줄어든다.

**Circuit Breaker** — PG나 외부 API에 장애가 발생하면 빠르게 실패를 반환해서 연쇄 장애를 막는다. 느린 응답을 기다리느라 스레드가 묶이는 것을 방지한다.

이 방법들은 모두 시스템을 보호하는 데 효과적이다. 하지만 공통적인 한계가 있다.

**유저가 서비스를 이용하지 못하게 된다.**

Rate Limiting은 "나중에 다시 시도하세요"를 반환하고, 비정상 요청 차단은 아예 진입을 막는다. 캐싱과 서킷브레이커는 읽기나 외부 연동에는 효과적이지만, 주문 요청 자체의 폭증은 해결하지 못한다. 결국 유저 입장에서는 "이 서비스 지금 안 되네"라고 생각하고 주문을 포기한다. 이탈로 이어지는 것이다.

그런데 생각해보면, 블랙 프라이데이에 몰려든 유저들은 **기다릴 의사가 있는 사람들**이다. 이 상품을 사고 싶어서 일부러 시간 맞춰 들어온 사람들이다. 이들에게 "다시 오세요"를 던지는 건 서비스와 유저 모두에게 손해다.

만약 "지금 512번째입니다. 약 3분만 기다려주세요"라고 알려줄 수 있다면?
유저는 이탈하지 않고, 시스템은 감당할 수 있는 속도로 주문을 처리할 수 있다.
유저도, 서비스도 만족스러운 결과다.

**이것이 대기열이다.**

시스템이 처리할 수 있는 속도만큼만 요청을 흘려보내면서, 유저에게는 공정한 순서와 실시간 피드백을 제공하는 구조. 거부를 하는게 아니라 요청한 순서대로 보관하는 것이다. 차단이 아니라 대기다.

이번 글에서는 이 대기열 시스템을 직접 설계하고 구현하면서 내린 결정들을 정리해본다.

## 2. 대기열의 원리 — Back-pressure

### Back-pressure란

Back-pressure는 직역하면 **"역압"**으로, 원래 배관 용어로 파이프에 물이 너무 빠르게 들어오면, 출구 쪽에서 처리가 안 되니까 압력이 역류해서 입구 쪽으로 "그만 보내"라는 신호가 전달되는 현상이다. 소프트웨어에서도 같은 개념으로, 하류 시스템이 감당할 수 있는 속도를 초과하면 상류에게 "속도 좀 줄여"라고 압력을 거슬러 올려보내는 것을 말한다.

대기열은 이 Back-pressure를 구현하는 대표적인 방법이다. 하류 시스템(DB, PG)이 감당할 수 있는 속도만큼만 상류(유저 요청)를 흘려보내는 것이다.

### 대기열을 구현하는 두 가지 방식

멘토님이 대기열을 구현할 수 있는 방법에 대해 이해하기 쉽게 두 가지 비유로 설명해주셨다.

**1. 은행 창구식 — 빈자리가 나면 밀어 넣기**

은행 창구를 떠올리면 된다. 창구가 5개이면, 동시에 5명만 업무를 볼 수 있다. 한 명이 끝나고 자리를 비우면, 대기 번호표 순서대로 다음 사람이 **그 자리에** 앉는다.

```
[창구 5개]

  창구1: 고객A (업무 중)
  창구2: 고객B (업무 중)
  창구3: (비어있음) ← 대기 1번 고객C 입장!
  창구4: 고객D (업무 중)
  창구5: 고객E (업무 중)

[대기열]
  1번: 고객C → 창구3으로 이동
  2번: 고객F
  3번: 고객G
```

핵심은 **"앞사람이 나가야 다음 사람이 들어간다"**는 것이다. 시스템은 현재 누가 활성화되어 있는지, 언제 끝나는지를 모두 추적해야 한다.

직관적이고 이해하기 쉽지만, 현실에서는 유저마다 결제 시간이 다르고 사용하는 리소스도 제각각이라 "정확히 몇 명까지 동시에 수용할 수 있는가"를 계산하기 까다롭다. 활성 인원을 너무 보수적으로 잡으면 시스템이 놀게 되고, 너무 공격적으로 잡으면 과부하가 발생한다.

**2. 놀이공원식 — 주기적으로 일정 인원만 입장시키기**

놀이공원 게이트의 안내원을 떠올리면 된다. 안내원은 내부에 사람이 정확히 몇 명 있는지, 누가 언제 나가는지 알 수 없다. 대신 경험적으로 "5분마다 20명씩 들여보내면 안이 터지지 않는다"는 걸 안다.

```
[놀이공원 게이트]

  매 5분마다 → 대기열에서 20명 입장 허가
  
  T=0분   [대기열 1~20번] → 입장! (토큰 발급)
  T=5분   [대기열 21~40번] → 입장!
  T=10분  [대기열 41~60번] → 입장!
  
  * 안에 몇 명 있는지는 신경 쓰지 않는다
  * 대신 토큰에 유효시간(TTL)을 둔다
    → 30분 내에 안 타면 토큰 만료
```

핵심은 **"앞사람의 종료를 추적하지 않는다"**는 것이다. 시스템은 대기열에서 누가 기다리고 있는지, 순서가 어떻게 되는지만 알면 된다.

다만 들어간 사람이 아무것도 안 하고 무한정 머무르면, 계속 새로운 사람을 밀어 넣는 만큼 시스템이 넘칠 수 있다. 무한 리필 고깃집에 "이용 시간 2시간" 제한이 있는 것처럼, 입장 토큰에 **TTL(만료 시간)**을 부여해서 일정 시간이 지나면 자격을 회수하는 장치가 반드시 필요하다.

**두 방식 비교**

| 구분 | 은행 창구식 | 놀이공원식 |
|------|------------|-----------|
| 입장 기준 | 앞사람이 나가면 다음 사람 입장 | 주기적으로 N명씩 입장 |
| 상태 추적 | 활성 유저 수, 종료 시점 모두 추적 | 대기열 순서만 추적 |
| 구현 복잡도 | 높음 (활성/종료 상태 관리) | 낮음 (스케줄러 + TTL) |
| 처리량 제어 | 정확함 (빈자리만큼만 채움) | 경험적 (주기와 인원 수로 조절) |
| 리스크 | 활성 인원 산정이 어려움 | TTL 없으면 시스템 과부하 가능 |
| 적합한 상황 | 동시 사용자 수가 정확히 제한되는 경우 | 유저별 체류 시간이 불규칙한 경우 |

이번 프로젝트에서는 **놀이공원식**을 선택했다. 주문 과정에서 유저마다 결제 시간이 다르고, PG 응답 시간도 들쭉날쭉하다. 앞사람의 종료를 일일이 추적하는 것보다, 스케줄러가 주기적으로 일정 인원을 입장시키고 TTL로 체류 시간을 제한하는 방식이 우리 상황에 더 맞았다.

### 대기열의 구성 요소

놀이공원식을 기반으로, 대기열 시스템은 네 가지 구성 요소로 이루어진다.

```
[유저] → 대기열 진입 (POST /queue/enter)
      → 대기열에서 순번 부여
      → 순번 조회 (GET /queue/position)  ← 주기적으로 반복 조회
      → 내 차례가 오면 입장 토큰 발급
      → 토큰으로 주문 API 호출 (POST /orders)
      → 토큰 검증 → 주문 처리
```

| 구성 요소 | 역할 | 놀이공원 비유 |
|-----------|------|-------------|
| **대기열 (Queue)** | 유저 요청을 순서대로 보관한다 | 줄 자체 |
| **스케줄러 (Scheduler)** | 일정 주기로 대기열에서 N명씩 꺼내 입장 토큰을 발급한다 | "다음 20명 입장하세요"를 외치는 직원 |
| **입장 토큰 (Entry Token)** | 주문 API에 진입할 수 있는 권한이다. TTL이 있어 일정 시간 내에 사용해야 한다 | 손목에 찍어주는 입장 도장 |
| **순번 조회 (Position)** | 유저가 현재 몇 번째인지 실시간으로 확인할 수 있다 | "현재 대기 약 15분" 안내판 |

### Rate Limiting과 대기열은 양자택일이 아니다

앞에서 Rate Limiting은 유저를 거부하는 방식이라고 했다. 그렇다고 대기열만 쓰면 될까?

그건 아니다. 봇이나 매크로가 대기열에 수만 건의 요청을 넣으면 정상 유저의 순번이 끝없이 밀려난다. Rate Limiting으로 비정상 요청을 먼저 걸러내고, 정상 유저만 대기열에 진입시키는 것이 올바른 조합이다.

```
[유저 요청] → Rate Limiting (봇/매크로 차단)
           → 대기열 진입 (정상 유저만)
           → 스케줄러가 순서대로 토큰 발급
           → 주문 API 처리
```

Rate Limiting은 **문 앞의 경비원**이고, 대기열은 **문 안의 줄서기**다. 둘은 서로 다른 층위에서 시스템을 보호한다.

## 3. 대기열 시스템 설계 — 전체 흐름 잡기

### 진입부터 주문까지

대기열 시스템의 전체 흐름은 네 단계로 나뉜다.

```
[유저] → POST /queue/enter
      → Redis Sorted Set에 userId + timestamp 저장
      → 순번 응답 (e.g. 512번째)

[유저] → GET /queue/position (주기적으로 polling)
      → 현재 순번 + 예상 대기 시간 응답

[스케줄러] → 100ms마다 실행
         → ZPOPMIN으로 18명씩 꺼내기
         → 입장 토큰 발급 (Redis SET + TTL 5분)

[유저] → 순번 0 도달, 토큰 수신
      → POST /orders
      → Interceptor가 토큰 검증 → 주문 처리
      → 주문 성공 시 토큰 삭제
```

| 구성 요소 | 역할 | 놀이공원 비유 |
|-----------|------|-------------|
| **대기열 (Queue)** | 유저 요청을 순서대로 보관 | 줄 자체 |
| **스케줄러 (Scheduler)** | 주기적으로 N명씩 꺼내 입장 토큰 발급 | "다음 18명 입장하세요"를 외치는 직원 |
| **입장 토큰 (Entry Token)** | 주문 API 진입 권한. TTL이 있어 일정 시간 내 사용해야 함 | 손목에 찍어주는 입장 도장 |
| **순번 조회 (Position)** | 현재 몇 번째인지 실시간 확인 | "현재 대기 약 15분" 안내판 |

### 왜 Redis Sorted Set인가

대기열의 저장소로 Redis Sorted Set을 선택한 이유는 간단하다. 대기열에 필요한 네 가지 연산이 모두 원자적이고, O(log N) 이내에 동작하기 때문이다.

```
ZADD  waiting-queue  {timestamp}  {userId}    // 대기열 진입
ZRANK waiting-queue  {userId}                  // 내 순번 조회 (0-based)
ZCARD waiting-queue                            // 전체 대기 인원
ZPOPMIN waiting-queue {N}                      // 앞에서 N명 꺼내기 (스케줄러)
```

- **score = 진입 시각(ms)** → 먼저 들어온 사람이 앞 순번
- **member = userId** → Set 특성으로 중복 진입 자동 방지 (ZADD NX)
- **입장 토큰**: `SET entry-token:{userId} {uuid} EX 300` → 5분 TTL로 자동 만료

### R7 Kafka 버퍼링과 뭐가 다른가

지난 주(R7)에 선착순 쿠폰을 Kafka로 처리했다. 둘 다 "요청을 버퍼링해서 순차 처리"라는 점은 같지만, 유저 경험이 완전히 다르다.

| 구분 | Kafka 버퍼링 (R7 쿠폰) | 대기열 시스템 (R8 주문) |
|------|----------------------|---------------------|
| 유저 경험 | 요청 후 나중에 결과 확인 (fire & forget) | 화면에서 순번을 보며 대기 |
| 결과 전달 | 비동기 (polling으로 결과 조회) | 입장 토큰 발급 → 즉시 주문 가능 |
| 실시간 피드백 | 없음 (결과를 나중에 확인) | 순번 + 예상 대기 시간을 실시간 제공 |
| 핵심 관심사 | 메시지 유실 방지, 멱등 처리 | 공정한 순서, 실시간 피드백, 토큰 만료 |

쿠폰은 "신청 완료, 결과는 나중에"로 충분하다. 하지만 주문은 "지금 몇 번째인지, 언제쯤 될 건지"를 유저가 알아야 한다. 이 차이가 대기열 시스템이 필요한 이유다.

## 4. 설계하면서 내린 7가지 결정

대기열의 구조를 잡고 나서, 세부 설계에서 선택지를 하나씩 좁혀 나갔다. 각 결정의 맥락과 이유를 정리한다.

### 결정 1. 독립 도메인으로 분리 — `domain/queue/`

대기열을 주문 도메인 하위(`domain/order/queue/`)에 넣을지, 독립 도메인으로 뺄지 고민했다.

- 대기열은 주문 전용이 아니다. 향후 한정판 세일, 티켓팅 등 다른 도메인에도 적용할 수 있다.
- 주문 도메인에 넣으면 주문이 대기열을 알아야 하는 역방향 의존이 생긴다.
- feature flag, 스케줄러, 토큰 관리 등 자체 책임이 충분히 크다.

독립 도메인으로 분리했다. API 경로도 `/api/v1/queue/*`로 독립시키고, 주문과의 연결은 Interceptor가 담당하도록 했다. 주문 도메인은 대기열의 존재를 전혀 모른다.

### 결정 2. userId 기반 토큰 검증 — 클라이언트 변경 없이

토큰 검증 방식을 두 가지로 비교했다.

| 방식 | 장점 | 단점 |
|------|------|------|
| 헤더 기반 (`X-Entry-Token`) | 보안 명시적 | 클라이언트가 토큰 저장/전달해야 함 |
| **userId 기반 (서버 조회)** | 클라이언트 변경 없음, 구현 단순 | 로그인 세션 의존 |

**userId 기반**을 선택했다. 서버가 로그인된 userId로 Redis에서 토큰 존재 여부만 확인한다. 클라이언트는 토큰 값 자체를 몰라도 되기 때문에, 기존 주문 플로우를 전혀 수정할 필요가 없었다.

### 결정 3. Interceptor로 검증 — 주문 도메인 코드 0줄 수정

```
요청 → MemberAuthInterceptor → QueueTokenInterceptor → OrderV1Controller
                                   |
                           flag OFF → 통과
                           flag ON  → 토큰 검증
```

`WebMvcConfig`에 등록하여 `POST /api/v1/orders` 경로에만 적용했다. 대기열을 켜든 끄든 주문 컨트롤러와 서비스 코드는 한 줄도 바뀌지 않는다.

### 결정 4. Feature Flag를 DB에 둔 이유

| 방식 | 장점 | 단점 |
|------|------|------|
| application.yml | 단순 | 변경 시 재배포 필요 |
| Redis | 런타임 즉시 변경 | Redis 장애 시 플래그 자체를 못 읽음 |
| **DB (선택)** | 런타임 변경, 이력 추적, Admin API 연동 | DB 장애 시 못 읽음 |

DB가 죽으면 어차피 주문도 못하므로 추가 SPOF가 아니다. Admin API로 운영 중 즉시 ON/OFF 가능하고, 변경 이력도 남길 수 있다.

다만 구현 후 DB 조회 빈도가 문제가 될 수 있다는 걸 깨달았다. 스케줄러(100ms)와 Interceptor(매 요청)에서 호출되면 초당 수십 회 SELECT가 발생한다. 이 부분은 뒤의 고민 포인트에서 별도로 다룬다.

### 결정 5. 순번 응답에서 전체 대기 인원을 뺀 이유

```json
{ "position": 128, "estimatedWaitSeconds": 1, "token": null, "pollIntervalSeconds": 1 }
```

`totalWaiting`(전체 대기 인원)을 응답에 포함하면 "3,420명 대기 중"을 보고 이탈할 수 있다. `ZCARD`의 비용은 O(1)로 거의 없지만, 이건 기술이 아니라 UX 판단이다. "128번째입니다, 약 1초 대기"가 이탈 방지에 훨씬 효과적이다.

### 결정 6. 처리량 산정 — 175 TPS 도출 과정

```
DB 커넥션 풀: 50 (HikariCP)
주문 1건 평균 처리 시간: 200ms (가정 — DB 쿼리 + 트랜잭션, PG 호출 미포함)
→ 이론적 최대 TPS: 50 / 0.2 = 250 TPS
→ 안전 마진 70%: 250 × 0.7 = 175 TPS
→ 100ms당 배치 크기: 175 / (1초 / 100ms) = 175 / 10 = ~18명
```

DB 커넥션 풀이 50개이고 주문 1건 처리에 200ms가 걸린다면, 이론상 초당 250건을 처리할 수 있다. 하지만 커넥션 풀 100% 점유는 다른 API(조회, 장바구니 등)를 죽이므로, 주문 외 API가 평균 30%를 점유한다고 가정하여 70%인 175 TPS를 안전 마진으로 잡았다.

이 200ms는 DB 쿼리 + 트랜잭션 처리 시간만을 고려한 가정값이다. 실제 k6 테스트에서 주문 API의 p50은 520ms, p95는 1,048ms로 나왔는데, 이 차이는 BCrypt 인증 오버헤드가 포함되었기 때문이다. 만약 PG 호출까지 포함되면 처리 시간이 1~3초까지 늘어나고 이론 TPS도 17~50으로 크게 떨어질 수 있다. 운영 환경에서는 실측 기준으로 TPS를 재산정하고 배치 크기를 조정해야 한다.

### 결정 7. 예상 대기 시간 계산 방식

| 방식 | 장점 | 단점 |
|------|------|------|
| A. 고정 TPS 기반 | 단순 | 스케줄러 설정과 괴리 가능 |
| **B. 스케줄러 기반 (선택)** | 설정에 정확히 연동 | 여전히 이론값 |
| C. 실측 기반 | 가장 정확 | 구현 복잡 |

스케줄러 기반으로 계산한다. `(position / batchSize) * (intervalMs / 1000)` 공식을 사용하면 스케줄러 설정을 바꿀 때 예상 시간도 자동으로 바뀐다. 예를 들어 176번째 유저는 `(176/18) * 0.1 ≈ 1초` 대기로 계산된다.

## 5. 구현 Deep Dive — fixedRate vs fixedDelay

### 학습 자료에서는 fixedRate가 적합하다고 했지만

"일정한 처리량 유지"가 목표라면 fixedRate가 맞아 보인다. 이전 실행 시작 시점 기준으로 다음 실행을 예약하니까, 처리 시간과 무관하게 일정한 주기가 보장된다.

그런데 실제로 Redis 지연이 발생하면 어떻게 될까?

```
fixedRate = 100ms일 때, 처리가 150ms 걸리는 경우:

T=0ms    [실행1 시작]
T=100ms  [실행2 시작] ← 실행1이 아직 끝나지 않음
T=150ms  [실행1 종료]
T=200ms  [실행3 시작] ← 실행2가 아직 끝나지 않음
```

Spring의 기본 스케줄러는 단일 스레드이므로 실제로 동시 실행되지는 않지만, 밀린 작업이 대기열처럼 쌓인다. Redis 장애가 복구된 직후 밀린 실행이 한꺼번에 수행되면, **대기열 시스템이 방지하려 했던 Thundering Herd를 스케줄러 자체가 유발**하게 된다.

### fixedDelay를 선택한 이유

fixedDelay는 이전 실행이 완료된 후 100ms를 기다린 뒤 다음 실행을 시작한다.

```
fixedDelay = 100ms일 때, 처리가 150ms 걸리는 경우:

T=0ms    [실행1 시작]
T=150ms  [실행1 종료]
T=250ms  [실행2 시작]  ← 종료 후 100ms 대기
T=400ms  [실행2 종료]
T=500ms  [실행3 시작]
```

- 단일 스레드 내에서 실행 겹침이 방지된다 (분산 환경의 동시성은 별도로 분산 락이 담당한다)
- Redis 지연 시 자연스럽게 처리량이 줄어들어 **back-pressure 효과**가 발생한다
- 장애 복구 후 밀린 작업이 한꺼번에 실행되지 않는다

### 트레이드오프

처리 시간이 길어지면 실제 TPS가 설계값(175)보다 낮아질 수 있다. 하지만 대기열의 본래 목적이 "백엔드를 보호하면서 안정적으로 처리"하는 것이므로, 처리량이 일시적으로 줄어드는 것이 시스템 과부하보다 낫다고 판단했다.

```java
// 구현 코드 — application.yml에서 주기를 주입받는다
@Scheduled(fixedDelayString = "${queue.scheduler.fixed-delay}")
public void processQueue() {
    if (!queueService.isQueueEnabled()) {
        return;
    }
    if (!schedulerLockRepository.tryAcquire(LOCK_KEY, instanceId, LOCK_EXPIRE_SECONDS)) {
        return;
    }
    try {
        processBatch();
    } finally {
        schedulerLockRepository.release(LOCK_KEY);
    }
}
```

`fixedDelay = 100`이라는 매직 넘버를 `application.yml`로 외부화해서, 운영 환경에서 재배포 없이 주기를 조절할 수 있도록 했다.

## 6. 실시간 순번 조회 — Polling vs SSE vs WebSocket

### 세 가지 방식 비교

| 방식 | 장점 | 단점 |
|------|------|------|
| **Polling** | 구현 단순, 인프라 변경 없음 | 대기 인원 많으면 요청 자체가 부하 |
| SSE | 변경 시에만 전송, 효율적 | 유저당 1커넥션 유지 필요 |
| WebSocket | 양방향 실시간 | 순번 조회는 단방향이면 충분, 과도 |

### Polling을 선택한 이유

대기열 순번 조회는 "서버 → 클라이언트" 단방향이면 충분하다. WebSocket의 양방향은 과도하고, SSE는 대기 인원 × 1 커넥션을 유지해야 해서 로드밸런서 설정이 필요하다.

Polling이 부하를 유발할 수 있다는 단점은 **polling 주기를 동적으로 조절**해서 완화했다.

### Polling 주기 동적 조절 — 구간별 1초/3초/5초

```java
private static int calculatePollInterval(long position) {
    if (position <= 100) {
        return 1;   // 곧 입장 → 빠르게 확인
    } else if (position <= 1000) {
        return 3;   // 중간 대기 → 적당히
    } else {
        return 5;   // 뒤쪽 대기 → 느리게
    }
}
```

앞쪽 유저는 곧 입장하므로 1초마다 빠르게 확인하고, 뒤쪽 유저는 5초 주기로 느리게 polling한다. 이렇게 하면 불필요한 API 호출을 줄이면서도 앞쪽 유저의 반응성은 유지할 수 있다. 응답에 `pollIntervalSeconds`를 포함해서 클라이언트가 이 값에 따라 polling 주기를 조절하도록 했다.

실제로 10,000명이 대기 중이라면 얼마나 부하가 발생할까? 구간별로 계산해보면:

```
순번 1~100:      100명 × 1 req/s   =   100 req/s
순번 101~1,000:  900명 × 0.33 req/s =   300 req/s
순번 1,001~10,000: 9,000명 × 0.2 req/s = 1,800 req/s
합계: ~2,200 req/s
```

Redis ZRANK는 O(log N)이고 단순 조회이므로 초당 10만+ 처리가 가능하다. 2,200 req/s는 Redis 입장에서 전혀 부담이 아니다. 동적 polling 주기가 없었다면 10,000명 × 1 req/s = 10,000 req/s가 되었을 텐데, 5배 가까이 줄인 셈이다.

## 7. 코드 리뷰에서 잡아낸 것들

구현을 마치고 코드 리뷰를 진행하면서, "동작은 하지만 위험한" 부분들을 하나씩 개선했다.

### peekFront + remove → ZPOPMIN 원자적 처리

초기 구현에서는 `ZRANGE`로 대기열 앞쪽 N명을 조회(peek)한 뒤, 토큰 발급 성공 시 `ZREM`으로 개별 제거하는 방식이었다.

```
[초기 — 2단계 방식]
1. ZRANGE waiting-queue 0 17  → 18명 조회 (제거 안 함)
2. SET entry-token:{userId}   → 토큰 발급
3. ZREM waiting-queue {userId} → 대기열에서 제거
```

문제는 peek과 remove가 별개의 Redis 호출이라는 점이다. 분산 락으로 단일 인스턴스만 실행되도록 보장하고 있지만, 락 만료(30초) 시 두 인스턴스가 동일 유저를 peek하는 극단적 시나리오가 존재했다.

`ZPOPMIN`으로 바꾸면 조회와 제거가 하나의 Redis 명령으로 수행된다.

```
[변경 후 — 원자적 방식]
1. ZPOPMIN waiting-queue 18   → 18명 조회 + 제거 (원자적)
2. SET entry-token:{userId}   → 토큰 발급
3. (실패 시) ZADD waiting-queue {score} {userId}  → 원래 score로 재삽입
```

ZPOPMIN으로 이미 꺼냈으므로 토큰 발급이 실패하면 유저가 유실된다. 이를 방지하기 위해 `QueueEntry(userId, score)` record를 도입하여 실패 시 원래 score(진입 시각)로 재삽입했다.

```java
for (QueueEntry entry : entries) {
    try {
        if (queueTokenService.hasToken(entry.userId())) {
            continue;
        }
        queueTokenService.issueToken(entry.userId());
    } catch (Exception e) {
        // 원래 score로 재삽입 → 다음 배치에서 우선 처리됨
        queueRepository.enter(entry.userId(), entry.score());
        log.warn("토큰 발급 실패, 대기열 재삽입 userId={}", entry.userId(), e);
    }
}
```

여기서 한 가지 주의할 점이 있다. 특정 유저의 토큰 발급이 계속 실패하면, 원래 score(맨 앞)로 재삽입되기 때문에 다음 스케줄러 실행에서 또 맨 앞에서 꺼내지게 된다. **한 명의 실패가 뒤의 모든 유저를 막는 Head-of-Line Blocking**이 발생하는 것이다.

이를 방지하려면 두 가지 전략을 고려할 수 있다.

- **최대 재시도 횟수 제한**: 3회 이상 실패한 유저는 재삽입하지 않고 로그만 남긴 뒤, 운영자가 수동 처리하도록 한다.
- **순번 밀어 넣기**: 실패 시 원래 score가 아닌 현재 시각으로 재삽입하여 대기열 맨 뒤로 보낸다. 공정성은 약간 손해보지만 전체 대기열이 멈추는 건 방지된다.

현재 구현에서는 Redis 자체가 정상이라면 토큰 발급(`SET` 명령)이 실패할 확률이 극히 낮고, Redis가 비정상이면 대기열 전체가 동작하지 않으므로 Head-of-Line Blocking이 실제로 발생할 가능성은 낮다. 하지만 프로덕션 레벨에서는 최대 재시도 횟수를 두는 것이 더 안전한 방어가 될 것이다.

### Feature Flag에 인메모리 캐시 적용

`isQueueEnabled()`가 스케줄러(100ms)와 Interceptor(매 POST 요청)에서 호출되면 초당 수십 회의 DB SELECT가 발생한다. `volatile` 필드 + 5초 TTL 방식의 단순 인메모리 캐시를 적용해서, DB 조회 빈도를 초당 10회+ → 5초당 1회로 줄였다.

대기열 ON/OFF는 운영자가 수동으로 전환하는 것이므로 5초 지연은 허용 가능하다.

### 토큰 삭제의 안전성 검증

`QueueTokenInterceptor.afterCompletion`에서 `ex == null && status 2xx`를 함께 체크하여, `@RestControllerAdvice`가 예외를 삼키더라도 비정상 응답 시 토큰이 삭제되지 않도록 했다.

```
주문 성공: ex=null, status=200 → 토큰 삭제 ✓
주문 실패(서비스 예외): Advice가 처리 → ex=null, status=400 → 토큰 유지 ✓
주문 실패(미처리 예외): ex≠null → 토큰 유지 ✓
토큰 삭제 시 Redis 호출 실패 → 토큰 잔존 → TTL 5분 후 자동 만료
```

한 가지 남는 위험은, 주문은 성공했는데 Redis `DEL` 호출이 실패하는 경우다. 토큰이 남아있으면 같은 유저가 TTL 만료 전에 다시 주문할 수 있다. TTL 5분이 있으므로 최악의 경우에도 5분 후 자동 만료되지만, 그 5분 안에 재사용될 가능성이 있다. 이를 완전히 막으려면 주문 도메인에 멱등성 키(idempotency key)를 두어 중복 주문을 방어해야 한다.

### 상수 중앙화와 매직 넘버 외부화

Redis 키(`"waiting-queue"`, `"entry-token:"`)가 Repository와 테스트에 분산 하드코딩되어 있었다. `QueueConstants`에 모아서 키 변경 시 한 곳만 수정하면 되도록 했다. 스케줄러 실행 주기도 `application.yml`로 외부화하여 재빌드 없이 조절 가능하게 만들었다.

## 8. k6 부하 테스트 — 숫자로 증명하기

설계와 구현이 끝나면 "정말 의도대로 동작하는가?"를 숫자로 확인해야 한다. k6로 5가지 시나리오를 테스트했다.

### 테스트 환경

| 항목 | 값 |
|------|-----|
| 서버 | Spring Boot 3.4.4 (로컬, 단일 인스턴스) |
| Redis | 7.0 (Docker, Master-Replica) |
| 스케줄러 | BATCH_SIZE=18, fixedDelay=100ms |

### 스케줄러 배치 크기 검증 — 이론값과 실측값이 맞는가

200명이 동시에 대기열에 진입한 후, 스케줄러가 전부 소화하는 시간을 측정했다. BATCH_SIZE=18, INTERVAL_MS=100ms 조합의 검증이 핵심이다.

| 메트릭 | 값 |
|--------|-----|
| 대기열 크기 | 200명 |
| **토큰 수령 p50** | **966ms** |
| **토큰 수령 p95** | **1,623ms** |
| 전체 완료 시간 | 3.9초 |

이론상 200명 / (18명 × 10회/초) = 1.1초인데, 실측 p50이 966ms로 근사했다. 스케줄러가 이론적 처리량에 가깝게 동작한다는 걸 확인했다.

### E2E 전체 흐름 — 진입 → 대기 → 토큰 수령 → 주문

50명이 동시에 진입하여 주문까지 완료하는 전체 플로우를 시뮬레이션했다.

| 단계 | p50 | p95 |
|------|-----|-----|
| 진입 (enter) | 407ms | 480ms |
| 대기 (진입→토큰) | 362ms | 432ms |
| 주문 (order) | 520ms | 1,048ms |
| **전체 흐름** | **1,258ms** | **1,725ms** |

| 메트릭 | 값 |
|--------|-----|
| 진입 성공 | 38/50 (76%) |
| 토큰 수령 | **38/38 (100%)** |
| 주문 성공 | **38/38 (100%)** |
| TTL 내 완료 | 100% |
| 평균 polling 횟수 | **1회** |
| 토큰 만료 | 0건 |

50명 중 12명은 **대기열 진입 자체에 실패**했다. 이는 대기열이나 스케줄러의 문제가 아니라, 50명이 동시에 BCrypt 인증을 수행하면서 CPU 경합으로 인증 타임아웃이 발생한 것이다. 진입 성공한 38명은 100% 토큰 수령 → 주문 완료까지 완주했다. 즉, **대기열에 한 번 들어오면 한 명도 놓치지 않는다.** 놓쳐진 12명은 대기열 앞단의 인증 병목이지, 대기열 시스템의 이슈가 아니다.

TTL 300초 대비 전체 흐름 p95가 1.7초(0.6%)밖에 안 되니 TTL이 충분히 여유 있다는 것도 확인됐다.

평균 polling 1회라는 건, 50명 규모에서 38명이 약 200ms(2배치)면 전부 처리되므로, 유저가 진입 후 첫 polling(1초 후)을 하는 시점에는 이미 토큰이 발급되어 있기 때문이다. 10,000명 규모에서는 뒤쪽 유저의 polling 횟수가 훨씬 많아질 것이다.

### 토큰 동시성 & 엣지케이스

토큰 시스템의 보안/안정성을 검증하는 테스트다.

| 시나리오 | 결과 |
|---------|------|
| 토큰 1개로 연속 주문 2건 | 첫 번째 성공, 두 번째 **100% 차단** |
| 둘 다 성공 (버그) | **0건** |
| 토큰 없이 주문 | **100% 차단** (400 Bad Request) |
| Feature flag OFF → 토큰 없이 주문 | **100% 성공** |

토큰 1회 사용 보장, race condition 없음, Interceptor 정상 동작, feature flag 우회 정상 — 모두 통과했다.

### 시스템 병목 식별

| 구간 | 병목 여부 | 근거 |
|------|----------|------|
| Redis ZADD (진입) | 정상 | O(log N), 마이크로초 단위 |
| Redis ZRANK (조회) | 정상 | O(log N), 대기열 크기 무관 |
| 스케줄러 (토큰 발급) | 정상 | 이론값 근사 처리 |
| **BCrypt 인증** | **병목** | 동시 요청 시 CPU 경합으로 응답 지연 |

대기열/스케줄러/토큰 시스템 자체의 병목은 없었고, 응답 시간의 대부분은 BCrypt 인증 처리 시간이 지배했다. 진입 API의 spike 테스트에서 BCrypt가 포함된 p95는 5,126ms였고, 대기열 진입(Redis ZADD) 자체는 마이크로초 단위에서 처리됐다. BCrypt를 제외한 순수 Redis 연산만 보면 응답시간이 수십 ms 이내인 점에서, 병목의 대부분이 인증에 있다고 판단했다. 세션/JWT 기반 인증으로 전환하면 전체 RPS가 크게 개선될 것으로 예상된다.

특히 순번 조회 API(`GET /queue/position`)는 대기 중인 유저가 1~5초 간격으로 반복 호출하는 엔드포인트다. 이 API까지 매번 BCrypt 인증을 거치면 polling 자체가 서버 부하가 된다. 실제 릴리즈에서는 이 API만큼은 **캐싱된 세션이나 가벼운 토큰(JWT 등)**으로 인증 부하를 줄이는 것이 필수적이다.

## 9. 놓치기 쉬운 함정들

### Thundering Herd — 토큰 발급 직후 N명 동시 주문

스케줄러가 1초마다 175명에게 토큰을 발급하면, 175명이 동시에 주문 API를 호출한다. 이건 원래 문제의 축소판이다.

이를 방지하기 위해 **발급 간격을 분산**했다. 1초에 175명을 한 번에 발급하는 대신, 100ms마다 18명씩 나누어 발급하여 부하를 10배 평탄화했다.

### 토큰 미사용 / 어뷰징

- 토큰을 받고 주문하지 않으면 자리만 차지한다. **TTL 5분**으로 자동 만료 처리한다.
- 한 유저가 여러 디바이스로 중복 진입을 시도할 수 있지만, **Sorted Set에 userId를 member로 사용**하므로 자연스럽게 중복이 방지된다.

### 스케줄러 장애

스케줄러가 멈추면 대기열에서 아무도 빠지지 못한다. DB 기반 `scheduler_lock`으로 분산 환경에서 중복 실행을 방지하면서, 인스턴스 장애 시 락 만료(30초)로 자동 해제되도록 했다.

### Redis 장애 — Graceful Degradation

Redis가 죽으면 대기열 자체가 동작하지 않는다. 선택지는 세 가지다.

| 전략 | 설명 |
|------|------|
| **전면 차단 (Safe Mode)** | 대기열 진입 자체를 막고 안내. 안전하지만 서비스 중단 |
| 대기열 우회 | 토큰 없이 주문 API 직접 접근 허용. 서비스 유지하지만 과부하 위험 |
| Fallback 큐 | 로컬 메모리 큐나 Kafka로 임시 전환 |

정답은 없다. **"Redis 장애 시 우리 서비스는 어떻게 동작해야 하는가?"**를 사전에 정의해두는 것 자체가 중요하다. 이번 프로젝트에서는 Feature Flag OFF로 대기열을 우회시키는 방식을 택했고, 테스트에서 flag OFF 시 토큰 없이도 주문이 100% 성공하는 것을 확인했다.

다만, 여기서 하나 짚고 넘어가야 할 게 있다. Redis가 죽은 상황이 **폭풍 트래픽 중**이라면, 대기열을 우회하는 순간 그 트래픽이 DB에 직접 쏟아진다. 대기열을 도입한 이유가 DB를 보호하기 위해서였는데, 우회하면 원래 문제로 되돌아가는 셈이다. 이 경우에는 차라리 **전면 차단(Safe Mode) 후 트래픽이 줄어든 시점에 순차적으로 오픈**하는 것이 시스템 전체 셧다운을 막는 더 안전한 선택일 수 있다.

대기열 우회가 적합한 건 평시에 Redis가 잠깐 죽었을 때처럼, 트래픽 자체가 감당 가능한 수준인 경우에 한정된다.

## 10. 마무리 — 대기열은 부하를 없애는 게 아니다

처음에는 "대기열 붙이면 트래픽 문제 해결되겠지"라고 단순하게 생각했다. 하지만 직접 구현해보니 대기열은 **피크를 평탄화(smoothing)하는 것이지, 부하 자체를 제거하는 건 아니었다.**

10,000명이 몰려와도 결국 10,000명을 모두 처리해야 한다. 다만 한꺼번에 처리하는 대신 100ms마다 18명씩, DB와 PG가 감당할 수 있는 속도로 흘려보내는 것이다.

구현하면서 가장 크게 느낀 건 세 가지다.

**첫째, fixedRate vs fixedDelay 같은 사소해 보이는 선택이 시스템 안정성을 좌우한다.** fixedRate가 이론적으로 맞아 보여도, Redis 지연 시 밀린 작업이 한꺼번에 실행되면 대기열이 방지하려 했던 Thundering Herd를 스케줄러 자체가 유발한다.

**둘째, "동작한다"와 "안전하다"는 다르다.** peek + remove가 동작은 하지만 원자적이지 않아서 극단적 시나리오에서 문제가 된다. ZPOPMIN으로 바꾸고, 실패 시 재삽입 로직까지 추가하고 나서야 "안전하다"고 말할 수 있었다.

**셋째, 구현 전에 "장애 시 어떻게 동작할 것인가"를 정의하는 것 자체에 가치가 있다.** Redis가 죽으면? 스케줄러가 멈추면? 토큰이 만료되면? 이 질문들에 미리 답을 정해두니까, 실제로 장애가 발생해도 당황하지 않을 수 있다.

결국, 대기열 시스템의 핵심은 기술 구현이 아니라 **"하류 시스템의 한계를 인정하고, 그 한계 안에서 최선의 유저 경험을 만드는 것"**이었다. 거부가 아니라 대기. **한 명도 놓치지 않겠다**는 설계 철학이 코드 전체에 녹아든 프로젝트였다.
