# Redis 장애 시나리오

## 장애 범위

Redis가 죽으면 대기열 시스템 전체가 멈춥니다.

| 기능 | Redis 죽으면 |
|------|-------------|
| 대기열 진입 (ZADD) | 불가 |
| 토큰 발급/검증 | 불가 |
| 순번 조회 (ZRANK) | 불가 |

## 대응 전략

### 1. 서비스 중단 (503 반환)
- 대기열 API 전체 503 반환
- 가장 단순, 데이터 정합성 보장
- 매출 손실 발생

### 2. Fallback: 직접 진입 허용
- Redis 없으면 대기열 우회, 주문 API 직접 접근
- 매출은 유지되지만 대기열이 없던 것과 동일 → DB 커넥션 고갈 위험

### 3. Redis 이중화 (Master-Replica)
- Replica가 Master 대신 서빙 → 장애 확률 감소
- 이 프로젝트에서 Redis Master-Replica로 구성됨 (localhost:6379, 6380)

## 트레이드오프

| 선택 | 장점 | 단점 |
|------|------|------|
| 503 반환 | 안전, 정합성 보장 | 매출 손실 |
| 직접 진입 허용 | 매출 유지 | DB 커넥션 고갈 위험 |

**결론**: 정답 없음. 비즈니스 임팩트 vs 시스템 안정성 트레이드오프로 팀이 결정. PR에 근거를 남기는 게 중요.

## 퀴즈 Q&A

**Q. Redis Master/Replica 모두 죽었을 때 503 vs 직접 진입 중 더 안전한 것은?**
A. 503이 더 안전. 직접 진입 허용 시 대기열 없던 것과 같아져 DB 커넥션 고갈 위험. 하지만 비즈니스 관점에서는 직접 진입 허용이 매출을 지킬 수 있음. 팀의 우선순위에 따라 결정.
