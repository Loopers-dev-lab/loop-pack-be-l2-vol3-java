# 대기열 vs Rate Limiting

## 핵심 차이

| | Rate Limiting | 대기열 |
|-|--------------|--------|
| 초과 요청 처리 | 즉시 거절 (429) | 번호표 발급 후 대기 |
| 사용자 경험 | 재시도 반복 → 혼란 | 내 순번 보여줌 → 예측 가능 |
| 서버 부하 | 거절해도 재시도로 부하 지속 | 대기열에서 흡수 |
| 적합한 상황 | API 남용 방지, 봇 차단 | 한정 자원 공정 분배 (선착순) |

## Rate Limiting의 문제

```
사용자 100명이 동시에 요청
→ 10명만 통과, 90명은 429 거절
→ 90명이 즉시 재시도
→ 또 거절 → 또 재시도 → 카오스
```

서버를 보호하려다가 오히려 재시도 폭탄을 맞는 상황.

## 대기열의 강점

```
사용자 100명이 동시에 요청
→ 100명 모두 번호표 발급 (1~100번)
→ 경쟁 끝. 재시도 없음.
→ 스케줄러가 순서대로 처리
```

## 언제 무엇을 쓰는가

- **Rate Limiting**: 악의적 요청 차단, API quota 관리
- **대기열**: Black Friday, 한정판 판매, 공정한 선착순이 필요한 경우

## 퀴즈 Q&A

**Q. Rate Limiting으로 거절하면 서버를 보호할 수 있는데 왜 대기열이 필요한가?**
A. Rate Limiting은 거절 후 재시도를 막지 못함. 재시도가 반복되면 오히려 부하가 지속됨. 대기열은 번호 발급 즉시 경쟁이 끝나므로 재시도가 없음.
