# Polling 부하 완화

## 문제

Polling 주기가 짧을수록 실시간성은 좋아지지만 서버 부하가 증가합니다.

```
사용자 10,000명 × 3초마다 요청
= 초당 3,333 요청
```

## 완화 전략

### 1. Redis만 조회 (DB 없이)
순번 조회는 Redis Sorted Set의 `ZRANK`만 호출합니다.
DB 조회 없이 인메모리에서 처리 → 응답 빠르고 커넥션 소모 없음.

```
GET /queue/position
→ ZRANK queue:waiting userId  (Redis만)
→ 순번 반환
```

### 2. Adaptive Polling (순번에 따라 주기 조정)

```
순번 1~10번   → 3초마다 (곧 들어가므로 빠르게)
순번 11~100번 → 10초마다
순번 100번~   → 30초마다 (한참 기다려야 하므로 느리게)
```

순번이 멀수록 주기를 늘려서 불필요한 요청을 줄입니다.

### 3. 서버에서 주기 가이드

```json
{
  "position": 150,
  "estimatedWait": 300,
  "nextPollAfter": 30
}
```

서버가 응답에 다음 폴링 시간(`nextPollAfter`)을 포함 → 클라이언트가 그에 맞춰 조정.

## 퀴즈 Q&A

**Q. 순번 조회 API에서 DB를 조회하면 안 되는 이유는?**
A. Polling은 모든 대기자가 주기적으로 호출함. DB 커넥션을 소모하면 주문 API와 커넥션을 경쟁하게 됨. Redis만 조회하면 커넥션 소모 없이 인메모리 처리.
