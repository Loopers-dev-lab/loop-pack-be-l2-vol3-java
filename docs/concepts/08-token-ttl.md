# 입장 토큰 & TTL 설계

## 핵심 개념

대기열 통과 후 발급되는 **입장 토큰**이 없으면 주문 API에 접근 불가.
토큰은 Redis String으로 저장하고, TTL로 자동 만료.

## 전체 흐름

```
스케줄러: 대기열 상위 N명 꺼내기
         → Redis에 토큰 저장 (SET token:{userId} 1 EX {TTL})
         → 대기열에서 제거 (ZREM)

사용자: 주문 API 호출 시 X-Queue-Token 헤더에 userId 전달
       → Interceptor: Redis에서 토큰 존재 여부 확인
       → 없으면 403

주문 완료: 토큰 삭제 (DEL token:{userId})
```

## TTL의 역할

| TTL 설정 | 문제 |
|----------|------|
| 없음 | 토큰이 영원히 유효 → 오래된 토큰으로 재사용 가능 |
| 너무 짧음 | 결제 중 만료 → 사용자 이탈 |
| 너무 길음 | 자리 점유 유저 증가 → 실제 대기자 손해 |

## 퀴즈 Q&A

**Q. 토큰을 DB에 저장하면 안 되는가?**
A. 가능하지만 비효율적. 조회 빈도가 높고(모든 주문 API 호출 시), TTL 관리도 직접 해야 함. Redis는 TTL 내장 + 인메모리 조회 → 적합.
