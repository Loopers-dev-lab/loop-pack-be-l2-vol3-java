# 대기열 스케줄러 배치 크기 산정 근거

## 목표

주문 API 앞단의 대기열 스케줄러가 한 번에 몇 명씩 토큰을 발급할지 결정한다.
하류 시스템(DB, PG)이 감당 가능한 속도로만 요청을 흘려보내는 것이 핵심이다.

## 병목 지점: DB 커넥션 풀

주문 처리의 병목은 DB다. 주문 1건에 재고 차감(비관적 락), 포인트 차감, 쿠폰 처리, 주문 저장이 하나의 트랜잭션으로 묶인다.

| 항목 | 값 | 근거 |
|------|-----|------|
| HikariCP `maximum-pool-size` | **40** | `jpa.yml` 설정 |
| 주문 1건 평균 처리 시간 | **200ms** | 재고 락 + 쿠폰 + 포인트 + INSERT |
| 이론적 최대 TPS | **200** | 40 / 0.2 = 200 |
| 안전 마진 | **70%** | 주문 외 조회 트래픽, GC 등 고려 |
| 목표 TPS | **140** | 200 × 0.7 = 140 |

## 스케줄러 설계

Thundering Herd를 완화하기 위해 1초에 한 번 140명을 발급하지 않고, 100ms 주기로 분산한다.

| 항목 | 값 |
|------|-----|
| 스케줄러 주기 | **100ms** (`@Scheduled(fixedRate = 100)`) |
| 초당 실행 횟수 | 10회 |
| 배치 크기 | **14명** (140 / 10) |
| 초당 토큰 발급량 | 14 × 10 = **140명/초** |

## 토큰 TTL

| 항목 | 값 | 근거 |
|------|-----|------|
| TTL | **300초 (5분)** | 주문 폼 작성 + 결제 수단 선택에 충분한 시간 |

5분 내 주문하지 않으면 토큰이 자동 만료되어 다음 유저에게 기회가 넘어간다.

## 설정값 요약

```yaml
# application.yml
queue:
  batch-size: 14              # 스케줄러 1회 토큰 발급 수
  token-ttl-seconds: 300      # 토큰 유효 기간 (5분)
  throughput-per-second: 140  # 예상 대기 시간 계산용 TPS
```

## 민감도 분석 — 추정이 틀리면?

배치 크기 산정의 핵심 변수는 "주문 1건 처리 시간"이다. 이 값이 달라지면 전체 수치가 연쇄적으로 바뀐다.

| 주문 처리 시간 | 이론 TPS | 안전 70% | 배치 크기 | 조치 |
|:-:|:-:|:-:|:-:|:-:|
| 100ms | 400 | 280 | 28명 | 현재 설정(14)이면 여유 충분 |
| **200ms (현재 추정)** | **200** | **140** | **14명** | **현재 설정** |
| 300ms | 133 | 93 | 9명 | batch-size 하향 필요 |
| 500ms | 80 | 56 | 5명 | PG 지연 시 이 수준 가능 |

처리 시간이 2.5배 느려져도(500ms) 시스템은 동작한다. 배치 크기만 줄이면 된다.
모니터링으로 실제 주문 처리 시간을 추적하고, 300ms를 넘으면 batch-size 조정을 검토한다.

## 한계 및 고려사항

- 위 수치는 주문 처리 시간 200ms 기준 추정치다. 실제 부하 테스트로 검증이 필요하다.
- PG 응답 지연, DB slow query 등 외부 요인에 따라 실제 TPS는 낮아질 수 있다.
- 안전 마진 70%는 보수적 기준이다. 모니터링을 통해 조정할 수 있다.
