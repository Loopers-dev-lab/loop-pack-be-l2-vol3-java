# 결제

## User Scenario

- 사용자: 주문에 대해 카드 결제를 요청하고, 결제 진행 상태를 확인하며, 결제가 완료되면 주문이 확정된다
- 시스템: PG(결제대행사) 시스템과 동기로 결제를 승인하고, 타임아웃 시 보정 스케줄러와 수동 확인으로 최종 결정한다

## Feature List

| ID | 기능 명칭 | 대상 | 인증 | API | 설명 |
| --- | --- | --- | --- | --- | --- |
| PM-01 | 결제 요청 | User | 필요 | POST /api/v1/payments | 주문에 대한 PG 카드 결제 요청 |
| PM-03 | 결제 상세 조회 | User | 필요 | GET /api/v1/payments/{paymentId} | 단일 결제 상태 확인 |
| PM-04 | 주문별 결제 조회 | User | 필요 | GET /api/v1/orders/{orderId}/payment | 주문에 연결된 결제 정보 조회 |
| PM-05 | 결제 상태 수동 확인 | User | 필요 | POST /api/v1/payments/{paymentId}/verify | PG 조회 API를 통한 결제 상태 수동 확정 |
| PM-06 | 결제 취소 | System | 내부 호출 | - | 주문 취소 시 PG에 결제 취소를 요청한다 |

## Business Rule

| 규칙 | 설명 |
| --- | --- |
| 1주문 1결제 | 하나의 주문에 성공(SUCCEEDED) 또는 보류(REQUESTED) 상태의 결제가 존재하면 추가 결제를 요청할 수 없다 |
| 재결제 허용 | 결제가 실패(FAILED)한 주문은 다시 결제를 요청할 수 있다 |
| CREATED 주문만 결제 가능 | 결제는 주문 상태가 CREATED인 경우에만 요청할 수 있다 |
| 결제 금액 자동 산정 | 결제 금액은 주문의 최종 결제 금액(finalAmount)을 사용한다 |
| 결제 실패 시 보상 처리 | 결제 실패가 확정되면 주문을 CANCELED로 전이하고, 점유된 재고를 해제하며, 사용된 쿠폰을 복원한다 |
| 결제 성공 시 즉시 확정 | PG 승인 성공 시 결제를 SUCCEEDED로 변경한다 (비즈니스는 PG 호출 전에 이미 확정됨) |
| 동기 결제 승인 | PG confirm 호출로 동기 승인. 타임아웃 시 REQUESTED 유지 후 보정 스케줄러/수동 확인으로 최종 결정 |
| PG 요청 실패 시 즉시 실패 | PG 요청 자체가 실패(서버 에러 등)하면 결제를 FAILED 처리하고 사용자에게 에러를 반환한다 |
| 본인 결제만 조회 | 사용자는 본인의 결제만 조회할 수 있으며, 타인의 결제 접근 시 미존재로 응답한다 |
| 외부 시스템 장애 보호 | 서킷 브레이커를 적용하여 PG 장애가 내부 시스템으로 전파되지 않도록 보호한다 |
| 결제 흐름 | 비즈니스 먼저 확정(재고 확정 + 주문 PAID) → PG 호출 → 실패 시 보상 트랜잭션 |
| 보상 전략 | 인프로세스 보상(즉시 되돌리기) + 보정 스케줄러(N분마다 불일치 탐지 및 보정) |
| 결제 취소 | 결제 성공(SUCCEEDED) 상태의 결제만 취소할 수 있으며, PG에 취소를 요청한다 |

## Use Case Flow

### [PM-01] 결제 요청

- **Precondition**
    - 해당 주문이 존재하고 CREATED 상태여야 한다
    - 해당 주문이 본인의 주문이어야 한다
    - 해당 주문에 성공 또는 보류 상태의 결제가 없어야 한다
- **Main Flow**
    1. 사용자가 주문 ID, PG 종류, 카드 종류, 카드 번호를 입력하고 결제를 요청한다
    2. 주문의 존재 여부와 소유권을 확인한다
    3. 주문 상태가 CREATED인지 확인한다
    4. 해당 주문에 진행 중이거나 성공한 결제가 없는지 확인한다
    5. 결제 정보를 생성(REQUESTED, paymentKey=UUID)하고 저장한다
    6. 재고를 확정하고 주문 상태를 PAID로 전이한다 (비즈니스 먼저 확정)
    7. PG 시스템에 결제 승인을 요청한다
    8. PG가 승인하면 결제 상태를 SUCCEEDED로 변경한다
    9. 결제 정보를 반환한다
- **Alternate Flow**
    - **[PG 타임아웃]**: PG 응답이 타임아웃(3초)되면 결제 상태를 REQUESTED로 유지하고 (비즈니스는 이미 확정 상태), 결제 정보를 정상 반환한다. 프론트가 status: REQUESTED를 보고 polling을 시작하며, 보정 스케줄러 또는 수동 확인(PM-05)으로 최종 결정한다
- **Exception Flow**
    - **[주문 미존재]**: 해당 주문이 존재하지 않거나 본인의 주문이 아닌 경우 "존재하지 않는 주문입니다" 안내를 노출한다
    - **[주문 상태 불가]**: 주문 상태가 CREATED가 아닌 경우 "결제할 수 없는 주문 상태입니다" 안내를 노출한다
    - **[결제 중복]**: 해당 주문에 이미 진행 중이거나 성공한 결제가 있는 경우 "이미 결제가 진행 중이거나 완료된 주문입니다" 안내를 노출한다
    - **[PG 요청 실패]**: PG 시스템 요청 자체가 실패한 경우 결제를 FAILED 처리하고, 보상 트랜잭션으로 재고 확정 복원 + 주문 CANCELED + 쿠폰 복원을 수행한 뒤 "결제 요청에 실패했습니다. 잠시 후 다시 시도해주세요" 안내를 노출한다
    - **[서킷 브레이커 오픈]**: PG 장애로 서킷이 열린 경우 보상 트랜잭션을 수행한 뒤 "현재 결제 서비스를 이용할 수 없습니다. 잠시 후 다시 시도해주세요" 안내를 노출한다

### [PM-03] 결제 상세 조회

- **Main Flow**
    1. 사용자가 결제 ID로 상세 정보 조회를 요청한다
    2. 결제 존재 여부와 소유권을 확인한다
    3. 결제 상태, 카드 정보, 금액 등을 반환한다
- **Exception Flow**
    - **[결제 미존재]**: 해당 결제가 존재하지 않거나 본인의 결제가 아닌 경우 "존재하지 않는 결제입니다" 안내를 노출한다

### [PM-04] 주문별 결제 조회

- **Main Flow**
    1. 사용자가 주문 ID로 연결된 결제 정보 조회를 요청한다
    2. 주문 존재 여부와 소유권을 확인한다
    3. 해당 주문에 연결된 결제 정보를 반환한다
- **Alternate Flow**
    - **[결제 없음]**: 주문에 연결된 결제가 없으면 빈 응답을 반환한다
- **Exception Flow**
    - **[주문 미존재]**: 해당 주문이 존재하지 않거나 본인의 주문이 아닌 경우 "존재하지 않는 주문입니다" 안내를 노출한다

### [PM-05] 결제 상태 수동 확인

- **Precondition**
    - 결제 상태가 REQUESTED여야 한다 (미확정 상태)
- **Main Flow**
    1. 사용자가 결제 ID로 상태 확인을 요청한다
    2. 결제 존재 여부와 소유권을 확인한다
    3. 결제가 미확정 상태인지 확인한다
    4. PG 조회 API를 호출하여 실제 결제 상태를 확인한다
    5. PG 결과가 결제 완료(found && done)이면 결제를 SUCCEEDED로 확정한다 (비즈니스는 이미 확정 상태)
    6. PG 결과가 결제 미완료이면 결제를 FAILED로 확정하고, 보상 트랜잭션으로 재고 확정 복원 + 주문 CANCELED + 쿠폰 복원을 수행한다
    7. 확정된 결제 정보를 반환한다
- **Exception Flow**
    - **[결제 미존재]**: 해당 결제가 존재하지 않거나 본인의 결제가 아닌 경우 "존재하지 않는 결제입니다" 안내를 노출한다
    - **[이미 확정]**: 이미 SUCCEEDED, FAILED 또는 CANCELED 상태인 결제에 대해 "이미 확정된 결제입니다" 안내를 노출한다
    - **[PG 조회 실패]**: PG 조회 API 호출이 실패하면 "결제 상태를 확인할 수 없습니다. 잠시 후 다시 시도해주세요" 안내를 노출한다

### [PM-06] 결제 취소

- **Precondition**
    - 해당 결제가 SUCCEEDED 상태여야 한다
- **Main Flow**
    1. 주문 취소 요청이 들어오면 해당 주문의 결제를 조회한다
    2. 결제 상태가 SUCCEEDED인지 확인한다
    3. PG 시스템에 결제 취소를 요청한다
    4. PG 취소가 성공하면 결제 상태를 CANCELED로 변경한다
- **Exception Flow**
    - **[PG 취소 실패]**: PG 결제 취소 요청이 실패한 경우 취소를 중단하고 "결제 취소에 실패했습니다. 잠시 후 다시 시도해주세요" 안내를 노출한다
