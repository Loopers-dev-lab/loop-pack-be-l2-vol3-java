# BLOG_GUIDE.md (FINAL)

> TroubleShooting & Study 글을 “내 톤”으로 빠르게, 그리고 일관되게 작성하기 위한 범용 템플릿  
> 고정: **짧은 서사 → 증거 기반 전개 → 짧게 정리(시리즈면 다음 계획 포함)**

---

## 0) 전 글 고정 규칙 (무조건 지키기)

1) **도입(서사) 3~6줄**: 왜 이 글을 쓰는지, 어떤 상황인지 짧게라도 넣기
2) **한글 헤딩 고정**: `문제 상황 / 재현(또는 분석) / 전략 수립(선택) / 원인 / 해결 / 검증 / 정리`
3) **길이 B(7~10분 컷)**: 긴 표/전문/코드/로그는 **더보기**로 밀어넣기
4) **정리는 짧게**: 3~5줄(시리즈면 “다음 실험 계획” 1~3개 bullet 추가)
5) 감정표현/구어체(B 범위) 허용: `오잉?`, `그럴 리가 없지`, `ㅋㅋ/ㅎㅎ/ㅠㅠ`, `현타`, `맞이해버렸다..`
    - 단, **훅/전환에서 0~2회만** (본문 설명 파트 남발 금지)
6) **긴 글/비교 글은 TL;DR 권장**: 도입 전에 `blockquote`로 1~2줄 요약 넣기

## 1) 제목 규칙 (거의 매 글 고정)

- 포맷: **`[키워드] 한 줄 요약`**
- 키워드 예시: `[SpringBoot]`, `[JPA]`, `[Docker]`, `[Test Code]`, `[Security]`, `[Git]`, `[Cache]`
- 제목은 “독자가 얻는 것”을 바로 말하기: 해결/원인/비교/실험/정리 중 하나 포함

## 2) 말투(톤) 고정 가이드

### 2.1 문장 호흡

- 문단 짧게(1~3문장), 줄바꿈 자주
- 결론 먼저 던지고 근거를 붙이기
- 과장 금지(“무조건/100%” 남발 X) → 대신 **한계/대안**으로 처리
- 기본 종결은 **설명형 `-다`** 로 간다
- 다만 실험 과정, 당시 판단, 관찰 결과, 전환점처럼 **맥락상 자연스러운 구간은 `-했다 / -였다`를 섞어도 된다**
- 중요한 건 **한 가지 종결만 기계적으로 반복하지 않는 것**이다. 문단의 역할에 맞게 종결을 고른다
- 널리 쓰는 기술 용어는 굳이 어색하게 한글화하지 않기: `cache`, `hit`, `miss`, `TTL`, `write-through` 같은 표현은 유지 가능
- 다만 `write-through`, `cache-aside`처럼 글 흐름상 처음 등장하는 개념은 첫 등장에 짧게 설명 붙이기
- `stale`, `blast radius`처럼 독자가 바로 읽기 어려운 영어 표현은 한국어로 풀어쓰기

### 2.2 자주 쓰는 패턴(톤 고정용)

- “개발하다 보면 {상황}이 은근 자주 나온다.”
- “처음엔 {가설}이라 생각했는데, 결론은 반대였다.”
- “여기서 의문이 들었다. `{질문}`”
- “결론부터 말하면, {한 줄 결론}이다.”
- “이번 글에서는 {목표}를 실험/검증해보고 정리해본다.”

## 3) 공통 골격 템플릿 (전 글 기본 뼈대)

### 3.1 도입(서사) — 고정

- 상황 1~2줄: {왜 이걸 하게 됐는지}
- 문제 1~2줄: {어떤 문제가 터졌는지}
- 목표 1줄: {이번 글에서 해결/검증/비교할 것}
- TL;DR과 도입 첫 2~4줄은 **메타 설명/OG 설명으로 그대로 노출될 수 있다**고 생각하고 쓴다
  - 줄바꿈이 사라져도 읽히게
  - “TL;DR”, “이번 글에서는” 같은 문구 뒤에 바로 핵심 문장이 오게

> 도입 끝나면 바로 본론. (길게 끌지 않기)

### 3.2 본문(한글 헤딩 고정)

- `문제 상황` → `재현(또는 분석)` → `원인` → `해결` → `검증` 순서가 기본
- 선택적으로 `전략 수립`을 `분석` 뒤, `원인` 앞에 둘 수 있다
  - 사용 시점: 대안 비교, 설계 후보 검토, 의사결정 근거 정리 글
- 글 타입에 따라 일부 섹션은 생략 가능(예: Study 글은 재현이 약할 수 있음)

### 3.3 정리 — 고정(짧게)

- 결론 1줄: “결국 {원인/핵심}이었고, {해결/결론}이 먹혔다.”
- 배운 점 2~3개 bullet
- (시리즈면) 다음에 할 것 1~3개 bullet

## 4) 글 타입별 운영(선택)

> 아래 3개 중 하나를 고르고, 선택한 타입에 맞게 “본문 섹션”의 밀도를 조절한다.

### A) TroubleShooting (장애/오류/삽질)

- 핵심: **재현 가능 + 근거 있는 원인 + 해결 후 검증**
- 본문에서 가장 중요한 섹션: `재현/원인/검증`

### B) Study (개념/정리/적용)

- 핵심: **개념을 내 언어로 정리 + 실전 적용 기준**
- 본문에서 가장 중요한 섹션: `문제 상황(왜 필요한지)/원인(개념 구조)/해결(적용법)`

### C) Experiment (비교/실험/검증)

- 핵심: **가설/통제변수/측정지표/결과**
- 본문에서 가장 중요한 섹션: `문제 상황(가설)/재현(절차)/검증(지표)/정리(한계/다음 실험)`

---

## 5) 섹션별 “작성 규칙”(한글 헤딩 기준)

### 5.1 문제 상황

- 증상/현상 1~3개 bullet
- 영향도(왜 중요?) 1줄
- (Experiment면) 가설 1줄 포함

### 5.2 재현

- 재현 절차 Step 1~N (최대 5단계 권장)
- 입력/요청 예시(REST면 curl, 테스트면 Given-When-Then 형태)
- 긴 로그/전문은 더보기로

### 5.3 원인

- 한 문장 결론 먼저: “원인은 {X}였다.”
- 근거(로그/스펙/코드 흐름) 붙이기
- 후보가 있었으면 “후보 → 배제/채택 근거”로 짧게 정리

### 5.4 해결

- 바꾼 것: {설정/코드/구조}를 구체적으로
- 왜 먹히는지 2~4문장
- 긴 diff/전체 코드는 더보기로

### 5.5 검증

- “해결됐다”가 아니라 **어떻게 확인했는지** 적기
- 가능하면 수치/스크린샷/테스트 결과 1개 이상
- 부작용 체크(성능/보안/호환) 1줄이라도
- 검증 서두에서 **비교 축**과 **트래픽 유형**을 먼저 선언한다
  - 예: `AS-IS API / DB 직접 조회 / cache miss-hit`
  - 예: `단건 응답 / 동시 요청 / 지속 부하`
- 검증 소제목은 **무엇을 측정했는지** 바로 보이게 적는다
  - 예: `Read Model + 복합 인덱스 적용 후 DB 직접 조회 성능 (단건 응답)`
- 표 제목에도 **단건 응답 / 동시 요청 / 지속 부하** 중 무엇인지 반드시 적는다
  - 독자가 표만 보고도 측정 종류를 바로 알 수 있어야 한다

### 5.6 정리

- 짧게. 진짜 짧게.
- (시리즈면) 다음 실험/다음 글 계획 1~3개 bullet

## 9) 마크다운 레이아웃 규칙

> 티스토리 **실제 발행 결과 기준**으로 맞춘다.
> 문법적으로 더 화려한 방식보다, **순수 마크다운이 안정적으로 보이는 방식**을 우선한다.

### 9.1 헤딩
- 메인 섹션: `## **헤딩**` 통일 — 문제 상황, 분석/재현, 전략 수립, 원인, 해결, 검증, 정리
- 서브 섹션: `#### **헤딩**` — 해결 내 개념별 분기, 판단 기준 분기 등
- 도입부: 헤딩 없이 바로 서사 시작
- TL;DR이 있으면 아래 형식 고정:

```md
> TL;DR
>
> 한두 줄 요약
```

### 9.2 섹션 구분선
- 메인 섹션(`##`) 사이에 `---` 삽입
- 서브 섹션(`####`) 사이에는 `---` 없음 (같은 부모 섹션 내)
- `---` 위아래로 빈 줄 1개씩
- HTML `hr`, inline style 사용하지 않음

### 9.3 줄바꿈 / 간격
- 문단 사이: 빈 줄 1개
- 헤딩 앞뒤: 빈 줄 1개
- 코드 블록 앞뒤: 빈 줄 1개
- 의미 전환은 **빈 줄 + blockquote/헤딩**으로 처리하고, trailing double space에 기대지 않음

### 9.4 글머리기호
- 기호: `-` 통일 (`*` 미사용)
- 하위 항목: 4칸 들여쓰기 (`    -`)
- 번호 목록: `1.  ` (번호 + 마침표 + 공백 2칸)
- 비교 항목은 bullet list 또는 표 중 더 읽기 쉬운 쪽을 선택한다

### 9.5 강조
- 핵심 결론/질문/판단 기준: `**'강조 문구'**`
- **인라인 백틱은 본문 강조에 사용하지 않는다** — 티스토리 발행본에서는 사실상 평문처럼 보여 강조 효과가 거의 없다
- 값 이름, 필드명, 메서드명, 애너테이션, 짧은 식별자는 본문에서 백틱 대신 `**'likeCount++'**`, `**'brandId'**`, `**'@Version'**` 같은 식으로 처리한다
- 코드/로그/SQL 예시는 fenced code block 사용
- 인용성 질문은 blockquote 사용

### 9.6 표 / 코드 블록
- 마크다운 표를 쓸 때는 **반드시 `| --- |` 구분선을 포함한 표준 문법**으로 작성한다. 구분선이 없으면 표로 렌더링되지 않는다
- 티스토리에서 표 테마가 기대대로 안 먹을 수 있으므로, 발행본에서 디자인이 중요하면 **스킨 CSS에서 일반 `table`, `th`, `td`를 직접 스타일링**하거나 에디터 표를 사용한다
- 비교가 간단하면 표를 쓰고, 셀 내용이 길어지면 bullet list로 전환한다
- 사용자가 **티스토리 기본모드에 그대로 붙여넣을 본문**을 원하면, **표는 유지하되** 붙여넣기 방법도 같이 안내한다
- 기본모드에서는 마크다운 표 텍스트가 자동으로 표로 바뀌지 않을 수 있으므로, 필요하면 **에디터 표 삽입 후 셀에 붙여넣는 방식**이나 **HTML 모드의 `<table>` 붙여넣기 방식**을 함께 제안한다
- 그대로 복붙했을 때 표 변환이 불안정하면, 마지막 대안으로 **`표 제목 / 컬럼 / row` 형식**을 함께 적어 사용자가 수동으로 옮기기 쉽게 만든다
- 기본모드에 붙여넣은 뒤 **불필요한 `span style` 래퍼**가 생기면, 가능하면 **텍스트만 붙여넣기**로 다시 넣거나 서식을 정리한다
- 목차 스킨을 쓰는 블로그라면, 붙여넣기 후 **빈 `h3/h4`가 생기지 않았는지** 꼭 확인한다
- 코드 블록은 triple backtick 사용
- 문법 하이라이팅보다 가독성이 중요하면 언어 지정 없이 plain fenced code block 사용

## 10) 확장 옵션 (필요 시 선택)

> 0)~9) 고정 규칙은 항상 적용.
> 아래 옵션은 **글 성격에 따라 독립적으로 골라 쓴다.** 여러 개 조합 가능.

### 옵션 A: Experiment 전용 헤딩 셋

- 기본 헤딩(`문제 상황/재현/원인/해결/검증/정리`) 대신 사용 가능
- **대체 헤딩**: `배경 / 가설 / 실험 설계 / 결과 / 한계 / 정리`
- 사용 시점: 비교 실험, 정량 검증 글 (4-C Experiment 타입)
- 기본 헤딩과 **혼용 금지** — 한 글에서 하나만 선택

### 옵션 B: 도입부 확장 (배경 서사)

- 기본 도입 3~6줄 대신, 기술 흐름/패러다임 변화를 설명해야 할 때 **~10줄**까지 허용
- 단, 도입 끝에 반드시 **”이번 글에서는 {목표}”** 한 줄로 마무리
- 사용 시점: 기술 트렌드 비교, 버전 마이그레이션, 새 패러다임 도입 배경이 필요한 글

### 옵션 C: 반전/재발견 구조

- 패턴: `초기 결론 → 문제 발견 → 재평가 → 결론 역전`
- Experiment 글에서 서사 장치로 활용
- 검증 섹션을 `1차 결과 / 문제점 발견 / 재검증`으로 분할
- 사용 시점: 가설이 뒤집히거나, 초기 결과가 재평가되는 실험 글

### 옵션 D: 제목 보조 키워드

- 기본: `[키워드] 한 줄 요약`
- 확장: `[키워드] 한 줄 요약(feat.보조키워드)`
- 사용 시점: 주제가 2개 기술에 걸쳐 있을 때 (예: `[JPA] N+1 해결(feat.BatchSize)`)

### 옵션 E: 톤 패턴 추가

- 2.2 기본 톤 패턴에 더해, 아래를 선택적으로 사용:
  - “놀랍게도, {예상과 반대 결과}였다.”
  - “결론은 그렇지 않다.”
  - “{키워드} 시대를 맞이해버렸다..” (시대 훅)
- 감정표현 0~2회 규칙(0번 5항)은 그대로 적용

### 옵션 F: 정량 비교 테이블

- Experiment 글에서 Before/After 또는 A vs B 점수 비교 시 마크다운 테이블 사용
- 본문에 요약 테이블, 상세 데이터는 **더보기**로 분리
- 예시:

| 항목 | Before | After | 변화 |
|------|--------|-------|------|
| 응답 시간 | 320ms | 45ms | -86% |

- 사용 시점: 정량 지표가 있는 성능/비교 실험 글
