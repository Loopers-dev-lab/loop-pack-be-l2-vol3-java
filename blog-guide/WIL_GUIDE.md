# WIL GUIDE

이 가이드는 이후 어떤 라운드에서든 WIL을 빠르게, 일관되게, 그리고 재사용 가능하게 쓰기 위한 기준이다.  
핵심 목표는 세 가지다.

- 프로젝트 내부 사정을 몰라도 읽히는 글
- 회고 수기보다 개념과 판단 기준이 남는 글
- 나중에 다시 펼쳐봤을 때 바로 써먹을 수 있는 글

---

# **1. 기본 원칙**

### **1-1. WIL은 기록이 아니라 재사용 가능한 정리다**

좋은 WIL은 그 주차에 무엇을 했는지 나열하는 문서가 아니다.  
좋은 WIL은 그 주차에 얻은 기술적 판단 기준을 다시 꺼내 쓸 수 있게 만드는 문서다.

따라서 우선순위는 아래와 같다.

1. 무엇을 배웠는가
2. 왜 그런 구조가 필요한가
3. 어떤 상황에서 다시 적용할 수 있는가
4. 구체 구현은 무엇이었는가

즉 사실 나열보다 개념 정리, 개념 정리보다 적용 기준이 더 중요하다.

### **1-2. 프로젝트 특수성을 일반 원리로 변환한다**

특정 프로젝트에서 얻은 내용으로 쓰더라도, 문서 자체는 가능한 한 보편적으로 읽혀야 한다.

예를 들어 아래처럼 바꾼다.

- 특정 테이블 이름 → 조회 전용 모델
- 특정 API 이름 → 목록 조회 API
- 특정 도메인 이벤트 → 정렬에 영향을 주는 변경
- 특정 장애 사례 → 캐시 저장소 장애 시 원본 조회 전환

구체 정보는 출발점으로만 쓰고, 문서 본문에서는 일반화된 개념으로 정리한다.

### **1-3. 독자가 현재 프로젝트 구조를 안다고 가정하지 않는다**

WIL은 작성자가 가진 배경지식을 전제로 쓰면 안 된다.

아래 문장은 피한다.

- 이 구조는 이미 다 알고 있을 것이다
- 원래 우리 서비스는 이런 식이다
- 기존 테이블 구조를 보면 바로 이해된다

아래 문장으로 바꾼다.

- 이 구조는 조회 원본과 조회용 데이터를 분리하는 상황에서 자주 쓰인다
- 목록과 상세가 같은 데이터를 공유할 때는 캐시 단위를 분리하는 편이 낫다
- 정렬 조건이 자주 바뀌면 목록 캐시 갱신 범위를 먼저 봐야 한다

# **2. 작성 전 준비**

### **2-1. 먼저 수집할 것**

WIL을 쓰기 전에 아래를 먼저 모은다.

- 요구사항
- 실제 구현 코드
- 테스트 코드
- 측정 결과
- 실패 사례나 수정 과정

중요한 것은 설명문보다 코드와 테스트다.  
코드와 테스트가 말해주는 사실을 먼저 정리한 뒤, 그 사실을 일반화해서 문장으로 바꾼다.

### **2-2. 먼저 분리할 것**

자료를 모은 뒤에는 아래를 분리한다.

- 사실
- 해석
- 일반화

예를 들어

- 사실: 목록 캐시와 단건 캐시를 나눴다
- 해석: 무효화 범위를 줄이기 위한 선택이었다
- 일반화: 목록과 상세가 같은 데이터를 공유하면 캐시 단위를 분리하는 편이 유리하다

WIL 본문에는 이 셋이 섞이지 않게 들어가야 한다.

### **2-3. 이번 글의 핵심 질문을 먼저 정한다**

글을 쓰기 전에 반드시 아래 질문 중 하나 이상을 정한다.

- 이번 주차에서 가장 중요한 설계 질문은 무엇인가
- 어떤 판단 기준을 남겨야 다음에 재사용할 수 있는가
- 어떤 실수를 반복하지 않기 위해 이 문서를 남기는가

핵심 질문이 없는 WIL은 내용이 길어져도 기억에 남지 않는다.

# **3. 제목 규칙**

제목은 아래 형식을 기본으로 한다.

- [WIL] - Round숫자. 핵심 키워드

좋은 제목의 조건은 아래와 같다.

- 그 라운드의 핵심 기술이 보인다
- 너무 넓지 않다
- 너무 감상적이지 않다
- 나중에 파일 목록에서 봐도 바로 구분된다

예시

- [WIL] - Round4. 동시성 제어와 정합성
- [WIL] - Round5. 캐시 읽기 전략, 갱신 전략, 장애 대응
- [WIL] - Round6. 결제 흐름과 실패 복구

피해야 하는 제목

- 이번 주 회고
- 정말 많이 배운 한 주였다
- 드디어 끝낸 캐시 적용기

# **4. 구조 선택 기준**

WIL은 매번 같은 구조를 기계적으로 쓰기보다, 주제에 맞는 구조를 고르는 편이 좋다.  
다만 구조는 많아도 세 축 정도로 제한하는 편이 읽기 쉽다.

### **4-1. 기본형**

가장 범용적인 구조는 아래다.

- 문제 구조
- 해결 원리
- 점검 포인트

이 구조는 거의 모든 주제에 적용 가능하다.

### **4-2. 인프라 / 성능 / 캐시형**

아래 주제에는 이 구조를 우선 사용한다.

- 캐시
- 성능 최적화
- 조회 구조
- 장애 대응

추천 구조

- 읽기 전략
- 갱신 전략
- 장애 대응

### **4-3. 동시성 / 정합성형**

아래 주제에는 이 구조를 우선 사용한다.

- 락
- 재고
- 쿠폰 발급
- 경쟁 상태
- 정합성 보장

추천 구조

- 경쟁 조건
- 제어 전략
- 검증 포인트

### **4-4. 외부 연동형**

아래 주제에는 이 구조를 우선 사용한다.

- 외부 API
- 메시징
- 결제
- 인증

추천 구조

- 호출 흐름
- 실패 처리
- 재시도와 복구

### **4-5. 설계 / 리팩터링형**

아래 주제에는 이 구조를 우선 사용한다.

- 도메인 분리
- 모듈화
- 포트와 어댑터
- 책임 재배치

추천 구조

- 문제 구조
- 분리 기준
- 적용 원칙

# **5. 문체 규칙**

### **5-1. 문체는 설명형으로 간다**

기본 종결은 설명형으로 간다.

- 한다
- 본다
- 나뉜다
- 필요하다

아래처럼 수기형 문체는 피한다.

- 해봤다
- 느꼈다
- 깨달았다
- 고생했다
- 삽질했다

WIL은 감상문보다 기술 정리문에 가깝다.

### **5-2. 메타 문장을 줄인다**

독자에게 직접적인 가치가 없는 문장은 넣지 않는다.

피해야 하는 문장

- 이 문서는 이런 문서다
- 회고보다는 참고 문서에 가깝다
- 이번 글에서는 무엇을 다뤄보겠다

대신 바로 본론으로 들어간다.

### **5-3. 설명은 일반화해서 쓴다**

아래 방식으로 쓴다.

- 특정 선택을 설명할 때는 그 선택이 먹히는 조건까지 쓴다
- 특정 구현을 설명할 때는 어떤 상황에서 다시 쓸 수 있는지까지 쓴다
- 특정 문제를 설명할 때는 증상과 원인을 분리한다

즉 단순히 무엇을 했는지보다, 왜 그 방식이 유효한지까지 적는다.

---

# **6. 표현 규칙**

### **6-1. 영어는 꼭 필요한 것만 남긴다**

아래 원칙을 따른다.

- 의미가 바로 들어오지 않는 영어는 한국어로 바꾼다
- 실제로 널리 쓰이는 기술 용어만 남긴다
- 영어를 남기더라도 본문 설명은 한국어로 풀어쓴다

남겨도 되는 경우

- Java
- Spring Boot
- Redis
- API
- Lock

가능하면 바꾸는 쪽이 나은 경우

- source of truth → 기준 원본
- projection → 조회용 데이터
- fallback → 원본 조회 전환
- partial miss → 부분 누락
- invalidation → 무효화

### **6-2. 강조는 본문에서만 쓴다**

강조가 필요하면 아래 형식을 사용한다.

- **'핵심 문구'**

단, 제목에서는 작은따옴표를 쓰지 않는다.

좋은 사용 예

- **'이 변경은 어떤 응답을 바꾸는가'**
- **'정답은 어디에 있고, 어떤 시점에 어떤 응답이 달라져야 하는가'**

### **6-3. 불필요한 링크를 넣지 않는다**

아래 정보는 사용자가 명시적으로 원하지 않는 이상 넣지 않는다.

- PR 링크
- 브랜치 이름
- 커밋 해시
- 리뷰 링크
- 내부 파일 경로 나열

이런 정보는 글의 수명을 줄이고, 재사용성을 떨어뜨린다.

---

# **7. 마크다운 규칙**

### **7-1. 제목 단계**

현재 선호 기준은 아래와 같다.

- 문서 제목: 맨 위 한 줄
- 메인 섹션: #
- 하위 섹션: ###
- 세부 항목: ####

메인 섹션은 너무 많지 않게 제한한다.  
가능하면 세 개 안팎이 가장 읽기 좋다.

### **7-2. 금지 요소**

WIL에서는 아래 요소를 쓰지 않는다.

- blockquote 표시
- 인라인 코드 강조
- 코드 펜스

코드가 필요하면 들여쓰기 코드 블록을 쓴다.

### **7-3. 코드 예시 규칙**

코드 예시는 아래 기준으로 작성한다.

- Java + Spring Boot 기준
- 진짜 핵심 흐름만 남긴다
- import는 쓰지 않는다
- class 선언은 쓰지 않는다
- 식별자는 영어로 쓴다
- 코드 블록 앞에는 예시 코드라는 문장을 둔다

좋은 예시

    UserView find(Long id) {
        return cache.get("user:" + id, () -> loadUser(id));
    }

나쁜 예시

- import가 길게 붙어 있는 코드
- 설정 클래스 전체
- 테스트 클래스 전체
- 설명보다 코드가 더 긴 예시

### **7-4. 표보다 글머리표를 우선한다**

비교 항목이 아주 명확할 때만 표를 쓴다.  
조금만 길어져도 글머리표가 더 읽기 쉽다.

특히 WIL은 요약성과 재사용성이 중요하므로, 표가 아니어도 전달되는 내용이면 글머리표를 우선한다.

---

# **8. 일반화 규칙**

프로젝트에서 출발하더라도 최종 문장은 아래처럼 일반화한다.

### **8-1. 이름을 구조로 바꾼다**

- 특정 엔티티 이름 → 기준 원본
- 특정 조회 테이블 이름 → 조회 전용 모델
- 특정 정렬 타입 이름 → 정렬에 영향을 주는 변경
- 특정 이벤트 이름 → 포함 여부를 바꾸는 변경

### **8-2. 구현을 판단 기준으로 바꾼다**

- 우리는 목록 캐시와 단건 캐시를 나눴다
- 목록과 상세가 같은 데이터를 공유하면 캐시 단위를 나누는 편이 낫다

- 우리는 특정 페이지까지만 캐시했다
- 캐시 범위는 자주 반복되는 요청을 기준으로 제한하는 편이 낫다

### **8-3. 테스트를 결론으로 바꾼다**

- 특정 테스트가 있었다
- 어떤 상황을 검증해야 하는지 기준이 남아야 한다

즉 코드와 테스트는 근거이고, WIL에는 근거가 지지하는 일반 원칙이 남아야 한다.

---

# **9. 작성 순서**

실제로는 아래 순서로 쓰면 가장 안정적이다.

1. 주차 핵심 기술 1개에서 3개를 뽑는다
2. 그 기술을 일반 개념으로 바꾼다
3. 가장 잘 맞는 3파트 구조를 고른다
4. 각 파트마다 핵심 문장 3개에서 5개를 먼저 쓴다
5. 필요한 곳에 아주 짧은 코드 예시를 넣는다
6. 프로젝트 내부 정보와 감상문 문장을 삭제한다
7. 마지막에 점검표를 돌린다

처음부터 완성 문장을 쓰기보다, 핵심 문장부터 뼈대를 세우는 편이 훨씬 빠르다.

# **10. 금지 목록**

아래는 이번 세션 기준으로 반복해서 피해야 할 요소다.

- 프로젝트 내부 구조를 안다고 가정하는 서술
- PR 링크, 커밋 링크, 브랜치 이름 노출
- 과도하게 구체적인 변경 내역 나열
- 회고 수기형 문체
- 메타 문장
- 제목에서 작은따옴표 강조
- 본문에서 불필요한 영어 남발
- blockquote
- backtick
- 긴 코드 덩어리

이 금지 목록은 문서의 가독성과 재사용성을 지키기 위한 최소 기준이다.

# **11. 최종 점검표**

- 제목이 [WIL] - Round숫자. 핵심 키워드 형식인가
- 프로젝트를 몰라도 읽히는가
- 주제가 일반 원리로 정리되어 있는가
- 메인 섹션이 세 축 정도로 정리되어 있는가
- 본문이 수기형 문체로 흐르지 않았는가
- 불필요한 링크가 빠졌는가
- 영어 표현이 꼭 필요한 수준으로만 남아 있는가
- 강조는 본문에서만 쓰였는가
- 제목에 작은따옴표가 들어가지 않았는가
- blockquote, 인라인 백틱, 코드 펜스가 없는가
- 예시 코드는 짧고 핵심만 남았는가
- 나중에 다시 읽었을 때 바로 써먹을 기준이 보이는가

# **12. 추천 시작 문장**

도입이 막힐 때는 아래처럼 시작하면 무난하다.

- 성능 문제는 보통 두 층으로 나뉜다.
- 정합성 문제는 저장보다 갱신 범위에서 자주 발생한다.
- 이 구조의 핵심은 무엇을 어디서 읽고, 언제 다시 채우는가에 있다.
- 같은 문제가 반복될수록 판단 기준을 문서로 남기는 편이 낫다.
- 이 주제는 특정 프로젝트보다 더 넓은 상황에서 반복해서 등장한다.

이 문장들은 메타 설명이 아니라 바로 본론으로 연결되기 때문에 재사용성이 높다.

# **13. 추천 마감 문장**

끝맺음은 짧고 분명해야 한다.

- 결국 핵심은 이 기술 자체보다, 어떤 상황에서 이 구조를 선택해야 하는가에 있다.
- 중요한 것은 구현 세부사항보다 판단 기준을 남기는 일이다.
- 다음에 다시 비슷한 문제가 오면, 이 문서에서는 구조부터 먼저 확인하면 된다.
- 이 주제는 한 번 이해하고 끝나는 것이 아니라, 반복해서 꺼내 써야 하는 기준에 가깝다.

---

# **정리**

좋은 WIL은 이번 주에 무엇을 했는지를 길게 적는 문서가 아니다.  
좋은 WIL은 다음 라운드나 다음 프로젝트에서도 다시 꺼내 쓸 수 있는 기술 기준을 남기는 문서다.

그러므로 항상 아래를 기억한다.

- 프로젝트 특수성은 일반 원리로 바꾼다
- 구조는 세 축 안에서 정리한다
- 문체는 설명형으로 간다
- 불필요한 링크와 메타 문장은 뺀다
- 짧은 코드 예시만 남긴다

마지막 질문은 하나다.

**'이 문서가 다음에도 다시 쓰일 수 있는가'**
